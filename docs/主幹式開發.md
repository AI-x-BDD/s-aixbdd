# 主幹式開發

資料來源分三類：

- **主題官方資料**：Trunk Based Development 官方網站，由 Paul Hammant 等人維護。
- **研究／業界資料**：Google DORA 的 DevOps 研究。
- **實務經驗**：用來補「實際工作怎麼判斷」。

兩個來源對 branch 壽命的標準不同：

> TrunkBasedDevelopment.com 認為短期 branch 通常可以活 1～2 天；DORA 的標準更嚴格，觀察高效團隊時常以不到一天為目標。

所以不要把「2 天」理解成硬性國際標準。

官方網站：[Trunk Based Development](https://trunkbaseddevelopment.com/)

---

# 1. 核心目的

主幹式開發（Trunk-Based Development，TBD）的核心目的一句話就講完：

> 不要讓大家的程式碼分開太久。

例如：

```text
傳統長分支

main
 │
 ├──────── feature-A ────────────────┐
 │                                   │
 ├──────── feature-B ────────┐       │
 │                           ↓       ↓
 └────────────────────────── merge ─ merge
```

分開越久，問題越大：

```text
分開 2 小時
→ 差異很小

分開 2 天
→ 差異開始變大

分開 2 週
→ 兩套世界
→ merge conflict
→ 整合測試爆炸
→ code freeze
→ merge hell
```

TBD 的解法：

```text
main ──●──●──●──●──●──●──●──
        ↑  ↑  ↑  ↑  ↑
       小量、小量、小量
```

大家不停把很小的變更整合回同一條主線。

官方把 TBD 定義為：開發者圍繞單一 trunk/main 工作，避免建立長期開發分支。

DORA 也把「每天至少整合一次」視為核心行為。

---

# 2. 一定要懂的關鍵字

先掌握這 8 個就夠。

| 名詞                  | 白話意思                         |
| --------------------- | -------------------------------- |
| `trunk / main`        | 所有人共同整合的主線             |
| Short-lived branch    | 很短命的工作分支                 |
| Long-lived branch     | 活很多天甚至幾週的開發分支       |
| Small batch           | 把大需求切成很多小改動           |
| CI                    | 每次整合後，自動 build + test    |
| Feature Flag          | 程式已進 main，但功能先關起來    |
| Branch by Abstraction | 大改造拆成很多安全的小步驟       |
| Release Branch        | 為「發布」而切，不是拿來繼續開發 |

它們的關係：

```text
                大需求
                  │
              切 Small Batch
                  │
         ┌────────┴────────┐
         │                 │
   小變更直接完成       大功能還沒完成
         │                 │
         │            Feature Flag
         │           / Abstraction
         │                 │
         └────────┬────────┘
                  ↓
                 main
                  ↓
                  CI
                  ↓
             保持可發布
```

# 3. 方法論：資深開發者先想什麼？

看到需求時，資深開發者不會先問「我要開什麼 branch？」，而是依序想：

```text
① 這個需求能不能再切小？

↓ 能

② 能不能今天就 merge？

↓ 不能

③ 為什麼不能？

├─ 功能還不能曝光
│    → Feature Flag
│
├─ 大規模重構
│    → Branch by Abstraction
│
├─ 相容性遷移
│    → 新舊實作並存
│
└─ 真的是發布版本維護
     → Release Branch
```

TBD 的 Mental Model：未完成的工作不靠 branch 藏起來，靠的是這些工具：

```text
小批次
Feature Flag
抽象層
向後相容
CI
自動測試
```

# 4. 實際工作流程

假設你收到：

> 新增會員搜尋功能。

---

## Step 1：先切需求

不要：

```text
feature/member-search

搜尋 UI
API
權限
排序
分頁
追蹤
測試

全部做完再 merge
```

而是：

```text
PR 1：加入 API client
PR 2：加入搜尋輸入框
PR 3：加入基本搜尋
PR 4：加入分頁
PR 5：加入權限
```

每一個都能獨立整合。

---

## Step 2：建立短期 branch

例如：

```text
main
 │
 └─ feature/member-search-input
```

目標不是「這個 feature 做完再 merge」，而是「這個小變更做完就 merge」。

官方也提醒：

> 一張 Story / Ticket 不代表只能有一個 PR。

一張 Story 可以拆成數個短期 branch / PR。

---

## Step 3：同步 main

工作期間保持接近：

```text
main    A ─ B ─ C ─ D
             \
branch        X
```

發現 main 到 D 了：

```text
main    A ─ B ─ C ─ D
                     \
branch                X'
```

要用 `merge` 還是 `rebase` 同步，通常屬於團隊規則或個人工作流。TBD 關心的是 branch 不要離 main 越來越遠。

官方也指出，在 merge 回 trunk 前應先讓 branch 跟 trunk 保持最新；具體 merge/rebase 方法可以由團隊決定。

---

## Step 4：CI 驗證

至少：

```text
build
↓
lint
↓
unit test
↓
必要的 integration test
```

然後才：

```text
PR
↓
review
↓
CI green
↓
merge main
```

DORA 建議每個 commit 都要觸發 build 與自動測試，而且回饋最好在幾分鐘內。

---

## Step 5：merge 後刪 branch

```text
feature/member-search-input
            ↓
          merge
            ↓
           main
            ↓
        delete branch
```

不要讓 `feature/member-search` 活三個星期。

# 5. 規則怎麼分？

## 核心規則

### ① 不要長期開發分支

這就是 TBD 的定義本身。

---

### ② 頻繁整合 main

DORA：

> 至少每天一次，能一天多次更好。

---

### ③ main 要保持可工作

如果 CI 紅了：

```text
繼續開發新功能
❌

先修 main
✅
```

DORA 建議：

```text
CI failed
↓
立即修
或
立即 revert
```

而不是「晚上再看」。

---

## 強烈建議

### Branch 要非常短

TrunkBasedDevelopment.com：

```text
約 1～2 天內
```

DORA：

```text
最好 < 1 天
```

---

## 團隊自行決定

下面這些 TBD 沒有規定，屬於團隊的 Git workflow：

```text
Squash merge
Merge commit
Rebase merge

branch 命名方式

一定幾個 reviewer

一定用 GitHub / GitLab

一定禁止 direct push
```

# 6. Decision Tree

以後你遇到需求，可以直接跑這棵樹。

```text
我要做一個變更
│
├─ 幾小時 / 一天可以完成？
│
│   ├─ Yes
│   │    ↓
│   │  Short-lived branch
│   │    ↓
│   │  CI + Review
│   │    ↓
│   │  merge main
│   │
│   └─ No
│        ↓
│   能不能切更小？
│
├─ Yes
│    ↓
│   切小
│    ↓
│   多個 PR
│
└─ No
     ↓
   為什麼？
     │
     ├─ 功能不能曝光
     │    → Feature Flag
     │
     ├─ 大型程式重構
     │    → Branch by Abstraction
     │
     ├─ 舊系統遷移
     │    → 新舊並存 / Strangler
     │
     └─ 維護已發布版本
          → Release Branch
```

# 7. 什麼專案適合？

非常適合：

```text
SaaS
Web App
Backend API
Frontend App
Microservice
企業內部系統
頻繁發布產品
多人共同維護 Codebase
```

以下三件事同時成立時，TBD 的價值最高：

```text
需求一直變
+
多人同時改
+
需要頻繁 release
```

---

## 使用前最好具備什麼？

TBD 不只是改 Git branch 策略，至少需要：

```text
自動 Build
+
自動 Test
+
快速 CI
+
小批次開發能力
+
快速 Code Review
```

否則容易變成：

```text
大家一直 merge main
+
main 一直壞
```

那不叫成功導入 TBD。

DORA 指出，經驗不足、缺少 gated checks、沒有「broken trunk 優先修復」紀律的團隊，實行 TBD 反而可能增加錯誤與返工。

# 8. 最大的例外：功能真的要做五天怎麼辦？

假設：

> 我要把 Vuex 換成 Pinia。

可能不是一天做完。

錯誤想法：

```text
feature/migrate-pinia

工作 3 週

最後 merge
```

TBD 思維：

```text
Day 1
建立 abstraction

↓ merge

Day 2
舊 Vuex 接 abstraction

↓ merge

Day 3
增加 Pinia implementation

↓ merge

Day 4
逐步切換

↓ merge

Day 5
移除 Vuex
```

這個做法叫 Branch by Abstraction：讓新舊程式碼暫時一起存在 main，不把分支留三週。

官方把這種需要多天的大修改列為 Branch by Abstraction 的主要用途。

---

# 9. Feature Flag 又什麼時候用？

假設功能做一星期：

```text
新的下注介面
```

但：

```text
星期一
只有 UI

星期二
API 完成一半

星期三
測試中

星期五
才正式開放
```

不要：

```text
feature/new-betting-ui
→ 放五天
```

可以：

```text
main

newBettingUI = false
```

每天照樣 merge：

```text
Mon → UI
Tue → API
Wed → validation
Thu → tracking
Fri → flag ON
```

也就是：

```text
Deploy ≠ Release
```

程式碼已經部署，但功能還沒對使用者開放，這就是 Feature Flag 的用途。

Flag 用完也要刪。官方警告：

> Feature Flag 如果永遠不清理，本身也會變成技術債。

---

# 10. Release Branch 是不是違反 TBD？

不是。

TBD 反對的是：

```text
develop
feature/*
team-a
team-b
release-next

長期共同開發
```

不是反對 `release/1.5` 本身。

例如：

```text
main ─────────────────────→

             \
              release/1.5
```

這個 branch 只負責：

```text
1.5 穩定
bug fix
release
```

不能：

```text
release/1.5
↓
繼續開 1.6 功能
```

官方指出 Release Branch 可以存在，但應該很晚才建立，而且不能承載持續的新功能開發。

# 11. 最常犯的錯

## 錯誤 1

```text
我們都是從 main 開 branch
所以我們是 TBD
```

錯。

如果：

```text
feature/a → 3 週
feature/b → 2 週
feature/c → 1 個月
```

仍然不是 TBD。

官方有一整頁專門談這個問題。

---

## 錯誤 2

```text
一張 Jira Story
=
一個 Branch
=
一個 PR
```

不對。

可以：

```text
Story #123

├─ PR 1 refactor
├─ PR 2 API
├─ PR 3 UI
└─ PR 4 cleanup
```

這樣反而更符合 TBD。

---

## 錯誤 3

為了 Merge 小，硬把「不能工作的程式」merge main。

例如：

```text
commit 1
API 被改掉

commit 2
Frontend 才跟上
```

中間：

```text
main = broken
```

不行。

正確：

```text
舊 API
+
新 API

↓

consumer 遷移

↓

刪舊 API
```

每一步都保持可工作。

---

## 錯誤 4

PR 很小，但：

```text
等 Review 3 天
```

實際效果跟三天 branch 差不多。

DORA 把重量級、非同步且耗時的 Review 流程列為 TBD 常見阻礙。

所以 branch 壽命要把等 Review 的時間算進去，不只是你寫 code 的時間。

# 12. 四個實戰案例

## 案例 A：小 Bug

```text
情況
按鈕顏色錯誤

↓
分析
30 分鐘可以完成

↓
判斷
不需要任何特殊技巧

↓
執行
short-lived branch
→ fix
→ test
→ PR
→ merge

↓
結果
branch 活 30 分鐘
```

典型 TBD。

---

## 案例 B：三天功能

```text
新增會員搜尋
```

不要：

```text
feature/member-search
→ 三天後一次 merge
```

改成：

```text
PR1 API client
↓
PR2 search box
↓
PR3 basic search
↓
PR4 pagination
```

每個都進 main。

如果前面功能不能被使用者看到，就用 Feature Flag 關起來。

---

## 案例 C：大型重構

```text
Axios
↓
Fetch wrapper
```

需要一星期。

判斷：

```text
不能一天完成
↓
也不能讓 main 壞掉
↓
Branch by Abstraction
```

做：

```text
建立 HTTP abstraction
↓
Axios 接 abstraction
↓
加入 Fetch implementation
↓
逐步切換
↓
刪 Axios
```

這比讓 `refactor/http-client` 活兩星期更符合 TBD。

---

## 案例 D：舊版本 Hotfix

目前：

```text
Production = 1.5

main 已經開始 1.6
```

現在 1.5 有 bug。

不要：

```text
release/1.5 修 bug
↓
再往 main merge 一大包
```

較典型作法：

```text
main
↓
完成 bug fix
↓
驗證

再 cherry-pick
↓
release/1.5
```

也就是 Fix on trunk first，這樣 main 不會漏掉修正。

TrunkBasedDevelopment.com 把「只在 release branch 修，再往 trunk 回灌」列為錯誤模式。

# 13. 你實際工作只要記這 6 題

收到 Ticket 時問：

```text
① 我能不能把它切到一天內可以 merge？

② 這個 PR 現在 merge，main 還能正常工作嗎？

③ 未完成功能能不能用 Feature Flag 隱藏？

④ 大改造能不能用 abstraction 讓新舊實作共存？

⑤ CI 能不能快速告訴我這次改動有沒有破壞系統？

⑥ 這個 branch 明天還會存在嗎？
```

如果第 ⑥ 題的答案是 Yes，就該檢查自己是不是切得太大。

---

# 14. TBD 跟 GitFlow 最核心的差別

不用背一堆 branch 名稱，看整合的順序就好。

### GitFlow 類思維

```text
先隔離
↓
做完整
↓
最後整合
```

### Trunk-Based 思維

```text
先切小
↓
持續整合
↓
任何時候都保持可工作
```

TBD 改變的其實是你拆分工作的方式，Git 操作反而變化不大。

# 15. 能力地圖

```text
完全不懂
↓
知道 main / short-lived branch
↓
知道「不要長期分叉」
↓
會建立短期 branch + PR
↓
會每天整合
↓
會維持 CI Green
↓
會把大需求切 Small Batch
↓
會用 Feature Flag
↓
會用 Branch by Abstraction
↓
知道 Release Branch 什麼時候合理
↓
能處理大型 migration / hotfix / 多版本
↓
能設計團隊的 TBD 工作流程
```

初階、中階、資深的分水嶺：

```text
初階
「我知道 branch 最好不要開太久」

          ↓

中階
「我能把工作切到每天都能 merge」

          ↓

資深
「即使功能要做兩星期，
我仍然可以設計成每天安全地整合 main。」
```

DORA 的研究給了幾個檢查值：每天至少整合一次、branch 非常短命、active branches 盡量少、不要靠 code freeze 解決整合問題。

接下來值得學兩件事：`Small Batch` 怎麼切，以及 `Feature Flag / Branch by Abstraction`
怎麼讓未完成的工作也能安全進 main。

## 參考資料

上面的內容主要來自這 7 個來源

### 核心必讀：先看這 4 個

**1. Trunk Based Development 官方首頁**

這是整個主題的入口。先用它確認「什麼才算 TBD」。

重點看：

- Trunk / Main 的角色
- Direct to trunk
- Short-lived feature branch
- Release branch 為什麼仍然可以存在

[Trunk Based Development 官方首頁](https://trunkbaseddevelopment.com/)

---

**2. Short-Lived Feature Branches（最建議仔細讀）**

這頁跟日常開發最直接相關，回答了前面談過的這些問題：

```text
branch 可以存在多久？
一個 Story 可以拆幾個 PR？
PR 等 review 算不算 branch 存活時間？
merge 前要不要同步 main？
rebase / merge 怎麼看？
```

官方的界線：短期 branch 通常只維持一兩天，完成後 merge 回 trunk 並刪除；一張 Story 也不等於一個 PR。

[Short-Lived Feature Branches](https://trunkbaseddevelopment.com/short-lived-feature-branches/)

---

**3. DORA：Trunk-Based Development**

TBD 官網難免自己說自己好，想看業界研究就讀這篇。

DORA 是 Google Cloud 的軟體交付研究體系，對 TBD 給了這些具體標準：

```text
每天至少整合一次
branch 最好不到一天
active branches 很少
CI 要快
main 壞掉要立刻修或 revert
```

它也把 TBD 跟軟體交付效能連起來看，不只講 Git branching。

[DORA：Trunk-Based Development](https://dora.dev/capabilities/trunk-based-development/)

除了 TBD 官方網站，我認為這是參考價值最高的一篇。

---

**4. You're Doing It Wrong：判斷自己有沒有真的在做 TBD**

這篇直接列出常見的錯誤做法：

```text
❌ 有 trunk 這個 branch ≠ TBD

❌ feature branch 活很多天
❌ 多人在同一個 feature branch 開發
❌ release branch 修完再往 main 回灌
❌ 接近 release 就 code freeze
❌ branch 一直留著不刪
```

之後在公司看到某套 Git Flow，可以拿這篇對照。

[You're Doing It Wrong](https://trunkbaseddevelopment.com/youre-doing-it-wrong/)

### 遇到特殊情況再讀這 3 個

**5. Feature Flags**

當你遇到：

```text
功能需要做 5 天
但 branch 又不應該放 5 天
```

就讀這篇。做法是：

```text
程式先 merge main
+
Feature Flag 關閉
+
持續完成
+
最後開啟
```

官方也提醒：Feature Flag 放著不清理，本身會變成技術債。

[Feature Flags](https://trunkbaseddevelopment.com/feature-flags/)

---

**6. Branch by Abstraction**

已經有實務經驗的工程師很值得讀這篇。

用在：

```text
大型 Refactor
框架替換
Library Migration
Database / API 改造
舊系統逐步替換
```

做法是讓新舊實作在 trunk 上並存，不開一個 branch 做兩星期：

```text
建立 abstraction
↓
舊實作繼續工作
↓
加入新實作
↓
逐步切換
↓
刪掉舊實作
```

官方用「預計要五天才能完成的改動」示範怎麼留在 trunk 上完成。

[Branch by Abstraction](https://trunkbaseddevelopment.com/branch-by-abstraction/)

這頁另有繁體中文版：

[Branch by Abstraction 繁體中文](https://tw.trunkbaseddevelopment.com/branch-by-abstraction/)

---

**7. Branch for Release**

想知道 Release Branch 在 TBD 裡能不能存在，就看這篇。

核心觀念：

```text
開發工作 → trunk

Release Branch
= 某個版本的 release / stabilization 線
```

bug fix 原則上先進 trunk，再視需要 cherry-pick 到 release branch；release branch 不當主要開發來源。

[Branch for Release](https://trunkbaseddevelopment.com/branch-for-release/)

---

### 沒時間的話，只讀這 3 個

照這個順序：

```text
① Short-Lived Feature Branches
        ↓
理解「每天到底怎麼工作」
```
