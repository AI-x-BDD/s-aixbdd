# CH2：從使用技能到設計團隊工作流程

## 延伸練習：後台清單分頁

假設 PM 希望既有後台清單新增分頁，並趕在近期交付。

### 先讓大家能討論交付範圍

先確認使用者遇到的是載入太慢、資料太多難找，還是需要逐頁瀏覽。再檢查後端是否已支援分頁，以及篩選、排序是否會影響結果。

若後端尚未支援，就把依賴與風險說清楚，讓 PM 能討論範圍與順序。Sales 關心客戶何時能用，QA 關心怎麼驗收，RD 關心契約與既有結構；一份可討論的方案要能回答這些問題。

### 把這次發現留下來

修改前先找專案已有的分頁頁面，確認哪些做法值得沿用。完成後，記錄實際遇到的失誤與判準，例如篩選變更時如何處理目前頁碼、查無資料時顯示什麼。

只有經確認、會再次用到的內容，才放進 Skill。若每次都需要相同的變更說明，可以提供樣板；若只是這個頁面的特殊行為，就留在該功能的規格中。

### 用結果決定要不要繼續投資

下一個清單頁沿用流程時，觀察是否減少人工補充與審查退回，驗收時是否更容易發現漏接的行為。記錄實際發生的返工，才有依據判斷這套工具是否值得擴充。

## 幾個可以直接帶回工作的應用

| 工作情境 | 可以採用的做法 | 要看的效果 |
| --- | --- | --- |
| 同類功能反覆開發，例如後台分頁、表單與 API 串接 | 把共同流程與常見失誤整理成 Skill，保留各功能自己的規格。 | 是否少漏步驟、少返工。 |
| Code Review 一再提出相同意見 | 將已取得共識的判準配上正反例，讓產出前就有依據。 | 是否減少相同原因的退回。 |
| 提案與技術文件每次結構不同 | 提供骨架與完成範例，先穩定審查需要的資訊位置。 | 審查者是否能快速找到決策所需資訊。 |
| 每次理解專案都要重讀大量檔案 | 先利用可靠工具取得有限範圍的結構摘要，再選擇性讀取原始資料。 | 是否縮短查找時間，且仍能追查來源與確認細節。 |
| AI 產出反覆不符合預期 | 留下失敗案例，追查相關 Skill 的交接與判準，再修改並重跑。 | 同類問題是否在新任務中改善。 |
| 新同事接手團隊工作 | 讓流程、範例與實際專案一起接受審查，補上使用者看不懂的部分。 | 接手者是否能說明原因，並獨立完成一次任務。 |

## 怎麼確認自己已經學會

- [ ] 給我一份陌生的 Skill，我能解釋主流程、資源載入時機，以及每個部位的責任。
- [ ] 給我一個不滿意的產出，我能描述預期差異，並以執行紀錄或檔案內容支持根因判斷。
- [ ] 換新對話後，Skill 仍能運作；必要資訊已寫入檔案或由流程取得。
- [ ] 我能實際檢查產物：畫面能操作、文件可閱讀、圖能呈現需要的資訊，腳本結果可核對。
- [ ] 改善工具後，我有重跑原失敗情境，也確認一個原本可成功的情境仍能完成。
- [ ] 面對 PM、QA、Sales 或 RD 的限制，我能提出可採用的交付方式，說清楚需要誰提供什麼資訊。
