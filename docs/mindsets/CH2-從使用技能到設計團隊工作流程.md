# CH2：從使用技能到設計團隊工作流程

走過第二章後，應該能把一次 AI 協作中的問題說清楚，找出流程哪裡失效，並把改善方式留下來，讓下一次工作也用得到。

這份筆記依 `wsa-course` 的章節 2 導讀與單元 1–11 整理能力目標。工作情境與自評題是延伸應用；它們代表接下來要能做到的事，不代表看完課程就已經通過驗收。

## 各階段應該練出的能力

以下依學習目的分組，方便對照每個階段要留下什麼能力。

| 階段與對應單元 | 應該具備的能力 | 能拿來確認能力的證據 |
| --- | --- | --- |
| 嘗試一次生成完整 Skill，實際使用它（1–2） | 能把 AI 生成的流程當成待驗證的假設；分辨「有產出檔案」「測試通過」「使用者真的能完成操作」各自證明了什麼。 | 挑一條主要操作，從畫面、API 到結果走完；能指出尚未串接或未被測試涵蓋的部分。 |
| 放回 Sales、PM、QA、RD 的合作現場（3） | 能理解不同角色的交付壓力，把技術限制翻成範圍、時程與品質的取捨；找出工具可以介入的交接點。 | 面對臨時插單，能提出需補充的資訊、受影響的功能及可討論的交付範圍。 |
| 拆解既有 Skill，建立模組化觀念（4–5） | 能分辨流程、判準與補充提示，找出重複規則、模糊動作及不清楚的依賴；判斷何時需要拆分。 | 收到一項修改需求時，能說明應改哪個部位、由哪裡載入，以及為何不用在其他地方重寫同一條規則。 |
| 寫出可執行的 SOP（6） | 能把腦中的做事方式轉成明確動作，交代何時讀資料、做判斷、產出成果與交給下一步。 | 換一個新對話，只提供 Skill 與任務，AI 仍能照流程產出可供審查的結果。 |
| 寫出規則，接回需要它的步驟（7–8） | 能把「我覺得不好」改寫成可判斷的標準；用同一情境的正反例說明差異，並檢查規則是否真的會被使用。 | 對一份不合格產出，能指出違反哪條判準、如何修正；修正後的例子仍符合其他規則。 |
| 用樣板穩定交付格式（9） | 能區分內容品質與文件結構，設計可填寫的骨架及完成範例，讓審查者容易找到所需資訊。 | 換一個需求，仍能產出相同結構的提案；內容依需求改變，必要欄位保留。 |
| 用腳本處理重複工作（10） | 能辨識適合確定性處理的部分，定義腳本輸入、輸出與失敗情況；利用結構化結果縮小後續閱讀範圍。 | 腳本輸出可核對，遇到不支援的輸入會明確回報；AI 能根據結果決定下一步要讀什麼。 |
| 編排工具，從根因改善整組 Skill（11） | 能由預期與現況的落差往回追，檢查上下游的流程、規則與樣板；決定局部修改或重新整理，並重跑任務驗證。 | 能把「失敗現象 → 根因證據 → 修改部位 → 實跑結果」連起來，也能說明哪些舊內容應刪除。 |

## 工作上最有用的幾個判斷

### AI 做得越多，越需要知道怎麼驗收

第二章前段的實驗提醒了一件很實際的事：程式與測試都有產出，使用者操作仍可能走不通。如果只讀 AI 的完成報告，很容易把局部完成當成整體交付。

工作上要能自己定義「完成」。例如後台新增分頁，至少得確認切換頁碼後真的送出新查詢、資料跟著更新、總筆數與頁碼一致；只在畫面放上分頁按鈕，還不能交付。

測試也有範圍。資料轉換的單元測試通過，可以支持轉換邏輯正確；畫面是否送出正確參數、後端是否依參數回傳資料，還需要對應的驗證。應該說得出目前證據涵蓋到哪裡。

### 能改得動，才有辦法因應公司的限制

拿到別人的 Skill，第一件有價值的事是看懂它如何做決定。公司可能已有固定的需求文件、共用元件、審查流程和測試環境，導入時得找到可以接上的位置。

我會先選一個反覆發生、範圍小的問題，例如「後台清單每次都漏傳分頁參數」。先改善這個環節並觀察效果。若只是一次性修改，清楚的任務說明可能就足夠，未必值得建立完整的 Skill 工具組。

當同類任務開始重複，才逐步沉澱出可重用的流程與判準。每次擴充，都要能解釋新增內容解決了什麼問題。

### 把個人偏好寫成別人能判斷的標準

「提案要清楚」「程式要好維護」很難直接拿來驗收。需要往下說到具體差異：審查者要看什麼、缺少什麼會無法決策、哪種寫法符合專案現況。

例如「分頁要符合既有做法」，可以進一步釐清成：沿用專案既有的分頁元件、使用 API 約定的參數名稱、依總筆數計算可用頁碼。這些判準仍須由團隊確認，AI 提出的通用慣例只能作為討論起點。

正反例最好使用同一個情境。若壞例是「切換頁碼只改畫面上的數字」，好例就應展示同一次操作如何觸發查詢並更新資料。兩個互不相關的例子，很難看出到底改善了哪件事。

### 資訊放對地方，之後才容易修改

| 部位 | 要回答的問題 | 以後台分頁為例 |
| --- | --- | --- |
| SOP | 這次工作依什麼順序完成？ | 先確認 API 與既有頁面做法，再修改、驗證。 |
| Rule | 做到什麼程度才算符合要求？ | 分頁參數遵守 API 契約；頁碼、總筆數與資料顯示一致。 |
| Template | 交付文件需要什麼結構？ | 變更說明固定包含影響頁面、行為差異與驗證結果。 |
| Script | 哪些操作可以交給程式重複執行？ | 依事先定義的規則列出相關呼叫位置，供後續檢查。 |

同一條判準要有明確的維護來源。若 API 參數約定同時寫在 SOP、規則檔和多份提示裡，日後變更就容易只改到其中一處。

拆成檔案後，還得檢查使用時機：哪一步需要讀它？讀完要做什麼？如果沒有接回實際動作，多一份規則檔也無法改善執行結果。資源應在需要時載入，避免每次任務都先讀進全部細節。

這裡也要分清工具組的責任：`skill-form-*` 把關部位內容，`skill-derive-*` 負責從步驟抽出資源並接回流程，`skill-engineering` 則協調整體改動。這種分工可以借用到其他工具設計：讓共用的品質標準集中維護，減少每個入口各寫一套。

### 優化前，先找出失敗發生在哪裡

假設 AI 修改後的頁面沒有重新查詢資料，直覺上可以補一句「一定要重新查詢」。但得先確認：是需求沒說清楚、事件沒有串接、既有共用元件被誤用，還是驗收根本沒檢查這條操作？原因不同，應修改的位置也不同。

如果流程一直漏掉查詢契約檢查，就應調整流程；如果流程有做，但判準不清楚，就補足規則與範例。若下游一直誤解上游產物，還需要檢查兩者交接的內容。

有些舊步驟與重複說明會讓問題更難看清楚，這時應刪除或重寫。改動幅度應由根因決定，驗證則回到原本失敗的任務，確認預期行為真的出現。

## 放進一次實際工作的方式

以下是延伸的假設情境，尚未在本文中實作驗證：PM 希望既有後台清單新增分頁，並趕在近期交付。

### 先讓大家能討論交付範圍

先確認使用者遇到的是載入太慢、資料太多難找，還是需要逐頁瀏覽。再檢查後端是否已支援分頁，以及篩選、排序是否會影響結果。

若後端尚未支援，就把依賴與風險說清楚，讓 PM 能討論範圍與順序。Sales 關心客戶何時能用，QA 關心怎麼驗收，RD 關心契約與既有結構；一份可討論的方案要能回答這些問題。

### 把這次發現留下來

修改前先找專案已有的分頁頁面，確認哪些做法值得沿用。完成後，記錄實際遇到的失誤與判準，例如篩選變更時如何處理目前頁碼、查無資料時顯示什麼。

只有經確認、會再次用到的內容，才放進 Skill。若每次都需要相同的變更說明，可以提供樣板；若只是這個頁面的特殊行為，就留在該功能的規格中。

### 用結果決定要不要繼續投資

下一個清單頁沿用流程時，觀察是否減少人工補充與審查退回，驗收時是否更容易發現漏接的行為。記錄實際發生的返工，才有依據判斷這套工具是否值得擴充。

Skill 的檔案數與 AI 產出的程式碼行數，無法直接回答這個問題。

## 幾個可以直接帶回工作的應用

| 工作情境 | 可以採用的做法 | 要看的效果 |
| --- | --- | --- |
| 同類功能反覆開發，例如後台分頁、表單與 API 串接 | 把共同流程與常見失誤整理成 Skill，保留各功能自己的規格。 | 是否少漏步驟、少返工。 |
| Code Review 一再提出相同意見 | 將已取得共識的判準配上正反例，讓產出前就有依據。 | 是否減少相同原因的退回。 |
| 提案與技術文件每次結構不同 | 提供骨架與完成範例，先穩定審查需要的資訊位置。 | 審查者是否能快速找到決策所需資訊。 |
| 每次理解專案都要重讀大量檔案 | 先利用可靠工具取得有限範圍的結構摘要，再選擇性讀取原始資料。 | 是否縮短查找時間，且仍能追查來源與確認細節。 |
| AI 產出反覆不符合預期 | 留下失敗案例，追查相關 Skill 的交接與判準，再修改並重跑。 | 同類問題是否在新任務中改善。 |
| 新同事接手團隊工作 | 讓流程、範例與實際專案一起接受審查，補上使用者看不懂的部分。 | 接手者是否能說明原因，並獨立完成一次任務。 |

## 怎麼確認自己已經學會

下面保留為未勾選的驗收清單。每一項都應拿實際任務來回答。

- [ ] 給我一份陌生的 Skill，我能解釋主流程、資源載入時機，以及每個部位的責任。
- [ ] 給我一個不滿意的產出，我能描述預期差異，並以執行紀錄或檔案內容支持根因判斷。
- [ ] 我能選擇保留簡單步驟、補規則、加樣板、抽腳本或拆 Skill，並說明取捨。
- [ ] 我能寫出同一情境的正反例，讓另一個人指出兩者的品質差異。
- [ ] 換新對話後，Skill 仍能運作；必要資訊已寫入檔案或由流程取得。
- [ ] 我能實際檢查產物：畫面能操作、文件可閱讀、圖能呈現需要的資訊，腳本結果可核對。
- [ ] 改善工具後，我有重跑原失敗情境，也確認一個原本可成功的情境仍能完成。
- [ ] 面對 PM、QA、Sales 或 RD 的限制，我能提出可採用的交付方式，說清楚需要誰提供什麼資訊。

第二章練到的是把流程與工具變得可理解、可修改的基礎。完整的 SDD、TDD、BDD，仍需後續章節與實作驗證；這裡出現的類別圖、Java Web Framework 和解析腳本，主要用來練習與驗收 Skill 的演進，也不能直接當成已精通那些技術的證明。
