# 雙鑽石原則

雙鑽石要防的是兩件事：太早認定問題、太早愛上某個解法。

核心節奏：

```text
問題看起來是 A
      ↓
Discover：先展開，不急著相信 A
      ↓
Define：根據證據，決定真正要解什麼
      ↓
Develop：不要只想一個解法，展開多個方案
      ↓
Deliver：用測試與證據收斂，留下有效方案
```

Design Council 官方把它稱為 Double Diamond，定位是設計與創新流程的視覺模型／方法論，不是一套嚴格的 Specification。官方另外還有四個 Design Principles：以人為本、視覺且包容地溝通、協作共創、持續迭代。

---

# 0. 資料來源

資料分三層。

**第一層：Design Council 官方**

主要依據：

[Design Council：Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/)

這是目前官方擴充版 Double Diamond 的主要說明。官方說：

- Double Diamond 是 Framework for Innovation 的核心。
- 四階段為 Discover → Define → Develop → Deliver。
- 兩個鑽石代表「發散 → 收斂」發生兩次。
- 流程不是線性的。
- 可以因為新的學習重新回到前面的階段。

第二份：

[Design Council：The Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/)

官方說它是描述設計過程的簡單模型，不是告訴你每一步該怎麼做的操作手冊。

第三份：

[Design Council：History of the Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/history-of-the-double-diamond/)

這份解釋 Double Diamond 原本想解決什麼問題、四階段怎麼形成，以及今天有哪些實際用途。

**第二層：Design Council 實務 Toolkit**

官方 Toolkit 把它寫得更接近實務：

> Discover 找洞察 → Define 明確問題 → Develop 建立與測試多個方案 → Deliver 找到可工作的方案並準備推出。

Toolkit 也指出，最大的錯誤之一是略過第一個鑽石，結果把錯的問題解得非常漂亮。

**第三層：業界實務補充**

Nielsen Norman Group（NN/g）認為 Discovery 除了了解使用者，還要處理：

```text
使用者需要什麼？
商業上值得做嗎？
技術上做得到嗎？
```

也就是常見的三個面向：

```text
Desirable   使用者想要
Viable      商業可行
Feasible    技術可行
```

下文會區分這幾種說法：

- 官方定義
- 官方建議
- 業界慣例
- 團隊規則
- 實務判斷

# 1. 核心目的

## 它解決什麼？

它主要解決兩種錯誤：

```text
錯誤 1
需求一來
↓
直接開始做
↓
最後才發現問題根本不是這個
```

以及：

```text
錯誤 2
已經確定問題
↓
第一個想到的方案直接實作
↓
做到一半才發現有更簡單的方案
```

所以兩個鑽石分別處理：

```text
第一鑽石
「我們到底應該解什麼問題？」

第二鑽石
「這個問題到底應該怎麼解？」
```

Design Council 的歷史資料用一組對照說明兩個鑽石：

```text
第一鑽石
Design the right thing
找對事情

第二鑽石
Design the thing right
把事情做好
```

---

## 為什麼需要？

因為實際工作收到的「需求」，常常已經偷偷包含了解法。

例如 PM 說：

> 「會員列表加一個 Excel 匯出按鈕。」

新人容易理解成：

```text
需求 = 做 Excel 按鈕
```

資深一點會先問：

```text
為什麼需要匯出？
↓
誰需要？
↓
拿去做什麼？
↓
多久做一次？
↓
真正問題是資料無法整理？
還是報表功能不足？
還是財務系統需要資料？
```

最後可能發現：

```text
真正問題：
會計每月底要統計會員方案。

解法 A：Excel
解法 B：直接提供月報
解法 C：自動寄報表
解法 D：Accounting API
```

釐清「會計每月底要統計會員方案」是第一鑽石的工作；列出 A～D 四個解法是第二鑽石的工作。

---

# 2. 關鍵字

要記的只有這幾個。

## Divergent Thinking

發散思考。

白話：

> 先不要急著選答案，把可能性打開。

例如 Discover：

```text
為什麼轉換率低？

可能是：
註冊流程
價格
頁面速度
登入問題
信任問題
付款問題
文案問題
```

不是看到第一個原因就開始改。

---

## Convergent Thinking

收斂思考。

白話：

> 看完證據後，把不重要的排掉，決定現在真正要處理什麼。

---

## Problem Space

問題空間。

就是：

> 我們現在到底在研究什麼問題？

第一個鑽石主要處理這裡。

---

## Solution Space

解決方案空間。

就是：

> 已經知道問題後，有哪些解法？

第二個鑽石主要處理這裡。

---

## Discover

Discover 的工作是先挑戰目前對問題的假設。

官方說法：

> 理解問題，而不是直接假設自己已經知道問題。

---

## Define

Define 的工作是決定現在到底要解哪一個問題，整理研究資料只是過程。

正式產物通常會變成：

```text
Problem Statement
Design Brief
Opportunity
Success Criteria
```

Design Council 官方歷史資料也指出，Define 最後會形成一個清楚定義挑戰的 design brief。

---

## Develop

工程師很容易把 Develop 誤會成「開始開發」。在 Double Diamond 裡，Develop 指的是發展多種可能方案，可能包含：

- Sketch
- Prototype
- 技術 Spike
- Architecture option
- Flow
- UI
- Concept
- 小型 PoC

官方的描述：

> 開發、測試、改善多個潛在解法。

---

## Deliver

Deliver 也不等於 `git push → deploy production`。它是把候選方案進一步驗證、改善，找到真的可以工作的方案，再交付。

官方說明包含小規模測試、淘汰不能工作的方案，以及持續改善。

---

# 3. 方法論

實務上的 Mental Model 可以縮成四個問題：

```text
1. 我們真的知道問題嗎？
        ↓
2. 哪個問題最值得處理？
        ↓
3. 只有這一種解法嗎？
        ↓
4. 有什麼證據證明它有效？
```

記住這四題，比背 Discover → Define → Develop → Deliver 管用。

---

## 資深工作者的思考順序

### 第一題：現在的不確定性在哪？

先不要問「現在在哪一階段？」，先問「現在還有什麼東西不知道？」

例如：

```text
不知道使用者為什麼離開
→ Discover

知道原因，但不知道哪些最重要
→ Define

知道問題，但不知道怎麼解
→ Develop

已經有方案，但不知道效果
→ Deliver / Test
```

---

# 4. 執行步驟

以下是建議在實際工作使用的版本。

---

## Step 0：收到需求

例如：

> 「搜尋頁要新增進階篩選。」

第一件事不要開 Jira 開始切 Component。

先寫：

```text
已知：
使用者要求更多篩選。

未知：
為什麼？
哪些人？
現在遇到什麼困難？
多常發生？
目前怎麼繞過？
成功應該長什麼樣？
```

---

## 第一個鑽石：找對問題

### Step 1：Discover

目標：

> 把「我們以為的問題」拆掉。

看四類資料：

```text
使用者
↓
行為資料
↓
商業需求
↓
技術限制
```

#### 使用者

業界常見：

- 訪談
- 觀察
- Support ticket
- Customer feedback
- Sales feedback

#### 行為

例如：

- Analytics
- Funnel
- Error log
- Search log
- Session replay

#### Business

例如：

- Revenue
- Conversion
- Customer retention
- 人工作業成本
- 法規

#### Technology

例如：

- API 限制
- Performance
- Legacy system
- Security
- 資料品質

NN/g 也把 Discovery 定義成探索使用者、商業與技術未知數的階段。

---

### Discover 何時算夠？

不看訪談了幾個人，而是問：

```text
我們現在最大的未知，
是否已經小到足以做決策？
```

#### 實務判斷

如果繼續研究：

```text
不太可能改變決策
```

就可以開始收斂。

這叫 diminishing returns：再花時間，得到的新資訊已經很少。

這是實務判斷，官方沒有這條規定。

---

### Step 2：Define

現在開始收斂。

把大量資料轉成：

```text
我們到底要解什麼？
```

可以使用：

```text
Evidence
↓
Pattern
↓
Insight
↓
Problem
↓
Priority
```

例如：

Discover 發現：

```text
70% Support ticket
都不是抱怨搜尋條件少。

真正問題是：
搜尋結果太多，
而且使用者不知道資料差在哪裡。
```

於是原本：

> 新增 20 個搜尋條件

可能重新定義成：

> 幫助客服快速找到最可能符合條件的會員。

---

### Define 的產物

實務上至少回答五件事：

```text
誰？
↓
遇到什麼問題？
↓
為什麼重要？
↓
什麼叫成功？
↓
有哪些限制？
```

例如：

```text
客服人員

在尋找會員時，
經常得到大量相似搜尋結果。

因此平均需要 45 秒找到正確會員。

目標：
降到 15 秒。

限制：
不能增加會員個資曝光。
```

這比一句「新增 Advanced Search」好很多：有對象、有數字目標，也寫清楚限制。

---

## 第二個鑽石：找對解法

### Step 3：Develop

現在才開始大量想解法。

原則：

```text
先增加選項
不要第一個方案直接做
```

例如：

問題：

> 客服找會員太慢。

方案：

```text
A 精準篩選
B 搜尋排名
C 顯示更多識別資訊
D 最近查詢
E autocomplete
F fuzzy search
```

然後做便宜的驗證。

例如：

```text
Wireframe
Prototype
SQL query
技術 Spike
Mock API
Fake Door
小規模 PoC
```

---

### 選方案的原則

不要問「哪個方案最漂亮？」，要問：

```text
哪個方案可以最便宜地驗證最大的風險？
```

---

### Step 4：Deliver

現在收斂。

例如只剩：

```text
A 搜尋排名
B 精準篩選
```

測試：

```text
使用者能不能找到人？
速度改善多少？
錯誤率多少？
效能如何？
開發成本？
維護成本？
```

最後選擇方案。

---

### Deliver 之後不是結束

官方說明 Double Diamond 不是線性的，產品也沒有真正「永遠完成」的狀態；部署後得到新的 Feedback，可能重新進入前面的探索與改善。

所以：

```text
Deliver
↓
Production
↓
Measure
↓
Learn
↓
必要時重新 Discover / Define / Develop
```

---

# 5. 規則

Double Diamond 不是 RFC 或 ISO 那種規格，所以不存在「你沒有做五次訪談，所以違反 Double Diamond」這種說法。

---

## 官方模型

核心結構是：

```text
Discover
↓
Define
↓
Develop
↓
Deliver
```

加上：

```text
Diverge → Converge
Diverge → Converge
```

---

## 官方原則

Framework for Innovation 另外提出四個核心原則：

1. Put people first
2. Communicate visually and inclusively
3. Collaborate and co-create
4. Iterate, iterate, iterate

白話就是：

```text
從人開始
↓
讓大家看懂
↓
不要一個人閉門做
↓
不斷測試修改
```

---

## 官方說明：不是線性流程

所以這種理解是錯的：

```text
Discover ✅
Define ✅
Develop ✅
Deliver ✅

永遠不能回頭
```

各階段可以來回：

```text
Discover
  ↕
Define
  ↕
Develop
  ↕
Deliver
```

---

## 業界慣例

通常會替每次收斂設定一個 Decision Gate：

```text
Discover → Define
有足夠證據了嗎？

Define → Develop
問題清楚嗎？

Develop → Deliver
方案有證據支持嗎？

Deliver → Launch
風險可接受嗎？
```

這不是 Design Council 的強制規則，但很實用。

---

# 6. 判斷方式

## Decision Tree

```text
收到需求
│
├─ 問題和解法都非常明確？
│
│   ├─ 是
│   │   ↓
│   │  直接做 / 縮短 Double Diamond
│   │
│   └─ 否
│       ↓
│
├─ 不知道真正問題？
│   │
│   └─ Discover
│
├─ 有很多問題，不知道做哪個？
│   │
│   └─ Define
│
├─ 問題知道，但不知道怎麼解？
│   │
│   └─ Develop
│
└─ 已有解法，但不知道是否有效？
    │
    └─ Deliver / Test
```

---

## 更簡單的 Checklist

每次只問四題：

### 1

```text
我現在講的是問題，
還是其實已經是解法？
```

例如：

> 「需要加 Tab。」

這是解法，真正問題還不知道。

---

### 2

```text
這個問題是證據，
還是某個人猜的？
```

例如：

> 「老闆覺得大家不會用。」

這是 Hypothesis，不是 Fact。

---

### 3

```text
我們是不是只考慮一個方案？
```

如果是，第二個鑽石可能根本沒有展開。

---

### 4

```text
我們拿什麼證明這個方案成功？
```

如果答案是：

> 大家覺得不錯。

代表 Deliver 還沒有真的完成。

---

# 7. 適用條件

Double Diamond 特別適合：

### 問題不明確

例如：

> 使用者留存降低。

---

### 利害關係人很多

例如：

```text
使用者
客服
PM
工程
營運
財務
法務
```

官方 Framework 也強調 collaboration、co-creation 與 stakeholder engagement。

---

### 解法成本高

例如：

```text
重寫系統
新產品
支付流程
大型 UX 改版
會員系統
新商業模式
```

因為做錯代價大。

---

### 需求本身很可能只是解法

例如：

> 「新增 AI Chatbot。」

這種適合先回第一個鑽石：

```text
到底什麼問題需要 chatbot？
```

---

# 8. 例外與邊界

## 不需要完整 Double Diamond

例如：

```text
Button padding 12px 寫成 8px
```

已知：

```text
問題 ✅
原因 ✅
解法 ✅
驗證方式 ✅
```

直接修。

不要：

```text
Discover workshop
User interview
Journey map
Brainstorm
Prototype
```

這叫 process theatre：為了看起來有流程而跑流程。

---

## 緊急事故

例如：

```text
Production login 全掛
```

這時：

```text
Stop bleeding
↓
修復
↓
恢復服務
```

不是先開 Workshop。

事後再：

```text
Incident review
↓
Discover root cause
↓
Develop preventive solution
```

---

## 法規要求

例如：

> 「法律規定這個欄位必須存在。」

問題可能已經非常確定，第一鑽石可以很短；第二鑽石仍可能有價值：

```text
UI 怎麼放？
怎麼減少摩擦？
怎麼保存？
怎麼驗證？
```

---

## 已經非常成熟的問題

例如：

> 「把既有 `/users` API 的 timeout 從 5 秒改成 10 秒。」

如果原因、影響與驗證都已經知道，就不用跑完整流程。

NN/g 也有類似觀點：問題成熟、團隊已累積大量領域知識時，有經驗的團隊會把設計流程壓縮，而不是完全拿掉。

---

# 9. 常見錯誤

## 錯誤 1：把需求當問題

```text
PM：
做 Excel export。

工程師：
OK。
```

錯。

正確：

```text
為什麼需要 Export？
```

---

## 錯誤 2：Discover 變成無止境研究

一直：

```text
訪談
研究
Workshop
調查
分析
```

但永遠不決策。

研究的目的是降低足以影響決策的不確定性，不是越多越好。

---

## 錯誤 3：Define 只是整理便利貼

Workshop 很容易變成：

```text
100 張 Post-it
↓
拍照
↓
結束
```

沒有回答「所以我們到底要解什麼？」，Define 就沒有完成。

---

## 錯誤 4：Develop 只有一個方案

```text
問題
↓
設計師畫一版
↓
工程師開發
```

看起來有流程，實際上沒有第二個鑽石。

---

## 錯誤 5：Prototype 做太完整

Prototype 的目的是用最便宜的方式回答一個還不知道的問題，不需要看起來像正式產品。

Design Council 也建議使用最簡單能測試想法的原型，而不是一開始就製作複雜產品。

---

## 錯誤 6：把四階段當 Waterfall

```text
Discover 完全結束
↓
永遠不能回 Discover
```

官方直接否定這種理解。

---

# 10. 實戰案例

## Case 1：簡單案例

### 情況

使用者說：

> 搜尋不好用。

### Discover

查詢：

```text
搜尋 log
客服 ticket
使用者操作
```

發現問題不在搜尋演算法，而是很多人不知道會員編號在哪裡。

### Define

真正問題：

```text
使用者不知道可搜尋哪些資訊。
```

### Develop

想到：

```text
A placeholder
B examples
C autocomplete
D 搜尋提示
```

### Deliver

快速 Prototype 測試，結果 Autocomplete 效果最好。

---

## Case 2：一般產品工作

### 情況

PM：

> 註冊流程新增 Google Login。

### Discover

研究：

```text
目前 abandonment 在哪裡？
```

結果大部分使用者卡在 Email verification 信件太晚收到。

### Define

真正的問題是：

```text
Email verification friction 太高。
```

登入方式太少不是主因。

### Develop

方案：

```text
A Google Login
B 改寄信流程
C resend
D magic link
E verification 延後
```

### Deliver

先改善寄信 + resend，成本可能遠低於導入 OAuth。

PM 提的 Google Login 其實是一個 Solution，真正的 Problem 是驗證信太慢。

---

## Case 3：最容易判斷錯

### 情況

老闆：

> 系統太慢，要換 Redis。

### 錯誤做法

```text
Redis → 開工
```

### Discover

先量：

```text
Frontend
Network
Backend
DB
3rd-party API
```

結果真正瓶頸是：

```text
SQL N+1 query
```

### Define

問題：

```text
DB query 次數爆炸。
```

### Develop

方案：

```text
A eager loading
B batch query
C cache
D schema/index
```

### Deliver

最後可能：

```text
根本不需要 Redis。
```

## Case 4：邊界案例

### 情況

Production API 有 SQL Injection 漏洞。

### 要不要跑完整 Double Diamond？

不要。

第一件事：

```text

↓

↓
Deploy
↓
Verify
```

之後再進行：

```text
為什麼 Code Review 沒抓到？
為什麼測試沒抓到？
為什麼架構允許？
```

這時才重新進入 Problem Discovery。

## 與 Design Thinking 的關係

兩者不互斥，比較準確的關係是：


# 12. 日常用的 Mental Model

不用每天畫兩顆鑽石，碰到需求時問這四題：

```text
① Problem
我們真的知道問題嗎？

② Evidence
這是證據還是假設？

③ Alternatives
我們是不是只想到一個解法？

④ Validation
什麼證據會讓我們相信它有效？
```

# 參考連結

推薦 5 個：前 3 個講 Double Diamond 本體，後 2 個補上實際工作需要的方法。不需要再看 Medium、一般 UX Blog、顧問公司 SEO 文或 Double Diamond 懶人包。

### 1. Design Council：Framework for Innovation

優先級：最高，必讀。

[Design Council：Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/)

這是上面內容最主要的依據，回答了：

- Discover / Define / Develop / Deliver 是什麼
- 為什麼是「發散 → 收斂」兩次
- 為什麼流程不是線性的
- 為什麼可以回到前面的階段
- 四個官方 Design Principles 是什麼

如果只能留一個連結，就留這個。

---

### 2. Design Council：The Double Diamond

優先級：最高，必讀。

[Design Council：The Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/)

第一篇講完整 Framework 怎麼運作，這篇直接回答「Double Diamond 本身是什麼」。

官方在這篇說明：

> Double Diamond 是用來描述設計流程的模型，不是一份逐步操作說明書。

所以下面這種打勾式 SOP 是誤解：

```text
Discover 做完打勾
Define 做完打勾
Develop 做完打勾
Deliver 做完打勾
```

---

### 3. Design Council：History of the Double Diamond

優先級：高。

[Design Council：History of the Double Diamond](https://www.designcouncil.org.uk/resources/the-double-diamond/history-of-the-double-diamond/)

我很推薦這篇。只看 Framework 很容易「知道怎麼畫」，卻不知道當初為什麼要做這個模型。

這篇說明 Double Diamond 是把設計工作中原本就存在的節奏整理成一個容易溝通的模型，不是 Design Council 憑空發明的流程：

```text
探索
↓
收斂
↓
再探索
↓
再收斂
```

讀完也比較好理解 Problem Space → Solution Space。

---

### 4. Nielsen Norman Group：Discovery: Definition

優先級：非常高，實務補強。

[NN/g：Discovery: Definition](https://www.nngroup.com/articles/discovery-phase/)

看懂官方 Double Diamond 後，下一篇我會選這篇。

Design Council 說 Discover 要理解真正的問題，但實際工作馬上會遇到：「怎麼知道自己真的理解問題了？」

NN/g 把 Discovery 講得更接近產品團隊：

- Problem Space 是什麼
- 怎麼研究問題
- 怎麼區分假設與證據
- Discovery 最後應該得到什麼
- 為什麼不是直接開始想 Solution

它補強了前面講的：

```text
需求 ≠ 問題

Feature ≠ Problem

Stakeholder 說的話
≠ 已經驗證的 Fact
```

---

### 5. IDEO：Design Thinking Process

優先級：高，補 Mental Model。

[IDEO：Design Thinking Process](https://designthinking.ideo.com/process)

這篇不用當成另一套七步驟來學，重點是一個核心：

> Creating choices → Making choices

白話就是：

```text
先把可能性打開
        ↓
再選擇

Diverge
↓
Converge
```

IDEO 也說這不是線性流程。對照著看，會更清楚 Double Diamond 的核心是兩次發散 → 收斂：

```text
發散 → 收斂
發散 → 收斂
```
