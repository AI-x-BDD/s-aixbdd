# Jev 接入驗證結果

日期：2026-10-16。

2026-10-17 處置：已撤回本次新增的樣板語意檢查與 Skill 分流，回復已提交的任務分流版本；保留本報告與原始實測數據。下列結果描述撤回前的實驗版本，不是目前程式的成績。

目前兩項輔助可運作，但這輪測試沒有顯示比原流程更有效率。建議維持實驗性質，不將它們視為已證實的效率改善；優先重新評估樣板檢查，再決定是否擴大使用。這次不修改正式題目、門檻或總開關。

## 實際執行

- 12 次真實 Jev API 請求，回應模型為 `jev-1.13.0`，無 API 失敗。
- 16 次獨立的真實 Codex CLI 呼叫，比較有無 Jev 提示的主模型決策。CLI 為 `0.163.0`，執行環境設定為 `gpt-6.1-sol`／`medium`，兩組使用相同設定。
- 原有路由、新增輔助與安裝保護測試全數通過，共 14 組測試函式，涵蓋總開關、敏感資料攔截、失敗回退、重複檢查與安裝衝突。
- 已快取樣板的 `PostToolUse` 本機處理，各量測 50 次：開啟平均約 23 毫秒，關閉約 0.006 毫秒，均不呼叫 API。

所有案例依專案現有規則建立，答案在呼叫 API 前固定，沒有要求使用者另外提供答案。這是以專案規則正反例製作的控制案例，沒有使用私人對話或宣稱它們是已發生的真實工作紀錄。

## 1. 樣板語意檢查

依據 `.agents/skills/skill-form-template/rules/樣板組-格式規範.md` 的 Rule 1、Rule 3 與正反例，建立 6 組樣板、共 12 項判斷。

| 案例 | 預期 | 目前正式門檻下的提示 |
| --- | --- | --- |
| T1：明確命名與一致的類別填位 | 兩項符合 | 兩項皆未提示疑點 |
| T2：類別圖樣板只命名為 `template.mmd` | 命名違規、填位符合 | 兩項都交回主代理 |
| T3：同一 `NAME` 同時代表類別與方法 | 填位違規 | 命名未提示疑點，填位交回主代理 |
| T4：來源類別重複出現卻改用 `sourceClass` | 填位違規 | 命名未提示疑點，填位交回主代理 |
| T5：來源與目標為不同項目，但範例都是 Order | 兩項符合 | 兩項皆未提示疑點 |
| T6：類別與方法採不同填位符號 | 兩項符合 | 兩項皆未提示疑點 |

3 個刻意放入的違規都沒有達到正式門檻，沒有產生「疑似違規」提示。其餘輸出有 8 項高信心符合、4 項回到主代理，沒有高信心誤報或錯判通過。

模型原始最高機率選項也不是全部正確：T3 的填位違規被選為 consistent，confidence 為 0.62。門檻阻止了這次錯判變成符合提示；直接降低門檻無法保證改善。

**判斷：回退保護有效，但本輪沒有證明樣板輔助能增加抓錯能力。它仍把三個違規都留給主代理處理。**

## 4. Skill 分流

使用專案實際的 15 個 Skill 候選，依各 description 的相鄰 Skill 分流條件建立 6 個任務。

| 案例 | 預期直接入口 | Jev 提示 |
| --- | --- | --- |
| S1：只改 description | skill-form-description | 符合 |
| S2：只改既有骨架與範例 | skill-form-template | 未推薦，機率為 0.89，低於 0.9 門檻 |
| S3：抽取樣板並更新 SOP 載入 | skill-derive-template | 符合 |
| S4：只改既有 RuleFile 正反例 | skill-form-rule | 符合 |
| S5：純文字轉大寫 | 無 | 符合 |
| S6：缺少上下文的「好，繼續」 | 無 | 符合 |

以此入口定義核對，6 個任務中 5 個符合，1 個漏推薦，沒有額外推薦。需要 Skill 的 4 個任務中，3 個有正確推薦。這不是對所有工作或長期準確率的估計。

**判斷：能提供適當候選，但本輪主模型原本就能選對，尚未證明額外提示有益。**

## 主模型決策的開／關對照

選 S3、S5、T3、T5 四種任務，各重複兩次，交錯執行順序。原流程與輔助組都有同一份完整規則／候選資料；輔助組另外收到依本輪 Jev 回應與正式門檻整理的簡短提示。預期答案不傳給模型。

| 指標 | 原流程 | 加入 Jev 提示 |
| --- | --- | --- |
| 決策正確 | 8／8 | 8／8 |
| 主模型平均時間 | 5.87 秒 | 6.02 秒 |
| 加計已量得的 Jev API 時間 | 5.87 秒 | 6.24 秒 |
| 主模型輸入 token 合計 | 208,010 | 206,256 |
| 其中 cached input token | 49,792 | 26,624 |
| 主模型輸出 token 合計 | 255 | 269 |

沒有正確性提升。本次平均總耗時增加約 0.36 秒。呼叫次數少、CLI 啟動與快取有波動，不能據此推估所有實際任務的速度。

12 次 Jev API 評測另外使用 34,758 個 input token、2,433 個 output token。這是整套評測的實際用量，不是每個工作任務的用量。主模型總輸入略少但快取命中也較少，加上額外 Jev 用量，不能把它解讀為成本節省；未以不同服務的 token 直接換算金額。

## 驗證界線

這是主模型決策層的受控重播，使用真實模型、真實 API 與實測用量；不是 mock，也不是完整 Skill 施工的端到端驗收。提示採評測程式中的簡短版本，由 CLI developer instructions 提供；沒有宣稱實際 Codex Hook 信任與 UI 呈現已通過。

全新 session、相同候選與規則、唯讀環境，不執行 Skill 施工或工具操作，避免正式工作目錄受到影響。總開關保持原狀。CLI 呼叫期間強制停用自動 Jev 路由，避免測試提示再次送進 Hook、混入第三項任務派工的效果。Jev 提示來自先前 12 次 API 回應，重播時沒有重抽樣，因此未測量模型跨次穩定性。

現有證據足以說「目前沒有測出新增效益」，不足以說「任何任務都不會有幫助」。若未來要投入優化，應先改善已觀察到的漏判／棄答，再增加未參與調整的驗收案例。
