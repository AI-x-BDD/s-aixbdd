## 2. `/double-diamond`：分析 Step 3

### 輸入

```text
/double-diamond <docs/需求清單.md 的 Step 3 全文>
```

需求是除了 `,` 之外，也允許用 `\n` 當分隔符，可以混用：

```text
add("1\n2,3") -> 6
add("1\n2\n3") -> 6
```

### Agent 的判斷

Agent 先讀了 `docs/過程/2.md`，發現 Step 2 是「先分析，收到指令才實作」，所以這次也只做分析。

這是明確的功能規格，問題、解法和驗證方式都已知，可以壓縮雙鑽石流程。

最大的不確定性有兩個：

- 現有設計會不會擋住這個需求：已確認不會，只要改 `split` 的條件。
- 修改後會不會破壞 Step 1、Step 2：用既有的 5 個測試驗證。

商業價值標為「待驗證，練習專案不適用」，沒有當成已知事實。

### 比較方案

| 方案                                     | Agent 的判斷                                                  |
| ---------------------------------------- | ------------------------------------------------------------- |
| A. `split(",")` 改成 `split("[,\n]")`    | 只改一行，最直接，建議採用                                    |
| B. 先 `replace("\n", ",")` 再 `split` | 也是一行，但 Step 5 加入自訂分隔符時要再串一次 replace        |
| C. 抽出 `parse()` 或 `Tokenizer`         | 現在只有兩種分隔符，算過度設計，等 Step 5 或 Step 8 需要再抽 |

最便宜的驗證：先寫兩個新測試，確認它們失敗（紅燈），套用方案 A 後跑全部測試。

### 範圍外的觀察

Agent 另外記下兩個現象，但這次不處理：

- `split()` 會丟掉結尾的空字串，所以 `add("1,2,")` 現在會直接回傳 3。這是 Step 4 的範圍，到時候要用 `split(regex, -1)` 或另外檢查。
- `"1,\n2"` 會切出空字串，然後丟出 `NumberFormatException`。這屬於 Step 7 的錯誤處理。

這一步只完成分析，沒有修改程式。

## 3. 「do it」：實作

### 輸入

Agent 這次沒有建立分支，直接在 `main` 的工作目錄修改。

### 紅燈

先新增兩個測試：

```java
@Test
void newlineAndCommaCanBeMixedAsSeparators() {
    assertEquals(6, calculator.add("1\n2,3"));
}

@Test
void newlineAloneCanSeparateNumbers() {
    assertEquals(6, calculator.add("1\n2\n3"));
}
```

執行 `mvn test`：


### 綠燈

只改一行：

```java
String[] parts = numbers.split("[,\n]");
```

`[,\n]` 是 regex 的字元集合，`,` 或 `\n` 都算分隔符。迴圈加總的部分沒有動。

再次執行 `mvn test`：

```text

```

### 修改的檔案

| 檔案                                                 | 修改                                           |
| ---------------------------------------------------- | ---------------------------------------------- |
| `src/main/java/calculator/StringCalculator.java`     | `split(",")` 改成 `split("[,\n]")`             |
| `src/test/java/calculator/StringCalculatorTest.java` | 新增混用與只用換行兩個測試，保留原有 5 個測試 |

## 4. `/conventional-commits`：建立 commit

### 輸入

```text
/conventional-commits
```

只輸入 Skill 名稱，沒有附加說明。

### 和 Step 2 的差異

Step 2 的 Agent 把 `$conventional-commits it` 解讀成「只寫 message」，停在產生 message。這次的 Agent 把它解讀成「建立 commit」，直接執行了。兩次都是 Agent 對指令範圍的解讀，Skill 本身沒有規定一定要哪一種。

Agent 先確認 Step 2 的分支命名是 `step-2-*`，因為目前在 `main`，就先開短期分支再 commit：

```sh
git switch -c step-3-newline-delimiter
```

只 stage 程式與測試兩個檔案，建立：

```text
4aa289f feat(calculator): accept newline as a number separator

Split input on both "," and "\n" so callers can mix the two
separators, e.g. add("1\n2,3") returns 6.

Custom delimiters and trailing-separator validation are left for
later steps.
```

判斷理由：

- 新增使用者可以用的能力，用 `feat`。
- 沿用既有的 `calculator` scope。
- body 寫明這次刻意不做的範圍。
- 實作與測試屬於同一個 TDD 循環，放在同一個 commit。

## 這次學到的

- **Skill 指令的範圍要講清楚**：只輸入 `/conventional-commits`，Step 2 的 Agent 停在 message，這次的 Agent 直接 commit。想要哪一種，最好在指令後面寫明，例如「只給 message」或「commit」。
- **分支什麼時候開**：這次實作是在 `main` 的工作目錄做的，commit 時才開分支。結果一樣，但如果中途被打斷，未完成的修改會留在 `main` 上。想照 TBD 走，可以在實作前就開分支。
- **CI 的觸發條件會影響收尾方式**：`ci.yml` 不會在 push feature branch 時觸發，所以方案 A 的 CI 一定是 merge 之後才跑。想讓 CI 擋在 merge 前，就要開 PR。
- **範圍外的發現先記下來**：`add("1,2,")` 回傳 3 的問題留到 Step 4 處理，這次沒有順手修。
