## Couble diamond principle

本來預計使用 Double Diamond 可以幫我理解問題並選定做法，像說明當中的先發散再收斂。

但是因為我之前把這個功能拆成 8 個步驟，可能已經拆得很小了，目標也很明確。在對話的時候，AI 回答我目標已經明確，所以不需要再進行其他的動作。

我原本的想法是先拆好 8 個步驟，然後再針對這 8 個步驟進行這三個 Skill 的操作。我覺得這一點可以嘗試，就算是需求很簡單，也可以再次確認是否要照這個方向實作。

因為我試了 Codex 跟 Claude Code，同樣的 Skill 在實作過程中可能還是會有一些差異。差異雖然不大，但有時候會影響開發時的下一個判斷。

## conventional commits

這一點比較明顯的是：在不同的 step，不同的 agent 使用這個 Skill，有時候它會幫你 commit，有時候它只會分析當前的實作之後先提供 commit message，結果不是很穩定。

如果要調整的話，我覺得可以先調整成在大部分的 Skill 當中，都可以根據 conventional commits 的原則寫出對應的 commit message，並且commit。

這一點額外我有個自己遇到、想要的需求。因為同事當中每個人使用 AI 的方法並沒有統一，我會在自己另外開的開發分支裡面多了幾項輔助工具，例如 graphify，還有各目錄的 claude.md、ag.md。

但這些並不能併入正式分支，因為會多出很多檔案出來。所以在自己的開發分支上，有一些不能進入主要分支的 Markdown 檔案必須要分離出來。

到現在我這個分離出來的動作都是用手動的，還沒想到這可以怎麼做。

## Trunk-based development

# Trunk-based Development 在這八次練習中做了什麼

因為 Trunk-based Development 產生的行為，我印象中每一次都不一樣，很明顯比前面這兩個 Skill 複雜多了。

整理了一下，發現其實它非常不受控，不受控到有點「龍飛鳳舞」。

下列是整理出來的結果。很明顯看這八次，在八個步驟當中：
• 有主動觸發的
• 有被動觸發的
• 有的最後兩次沒有觸發

---

整理日期：2026-10-06。依據：Step 1～Step 8 的過程紀錄。

你記得的兩種順序都有出現：有時先用 TBD 規劃再實作，有時做完 commit 才用 TBD 檢查怎麼收尾。

也有幾次，你沒有輸入 TBD 指令，Agent 就開了分支。但紀錄沒寫是否呼叫 TBD Skill。

本文的 TBD 是 Trunk-based Development（主幹式開發）。

## 八次練習的順序與結果

| 過程 | 何時呼叫 TBD | 分支何時建立 | TBD 當次做了什麼 |
| --- | --- | --- | --- |
| Step 1 | commit 後，呼叫兩次 | 沒有開分支，直接在 `main` 開發 | 第一次發現尚未 push、沒有 CI。第二次確認已 push，仍建議補 CI。 |
| Step 2 | Double Diamond 後、實作前 | 說「開始執行」後 | 規劃一個小變更，用短期分支，當天合併。呼叫 TBD 時還沒開分支。 |
| Step 3 | commit 後 | Conventional Commits 階段，commit 前 | 檢查分支、變更大小與 CI，提出本機合併或開 PR 兩種收尾方式。 |
| Step 4 | commit 後 | 說 `do it` 後，實作前 | 檢查是否能合併，提出兩種收尾方式。另提醒這次改變既有行為，團隊開發可考慮 PR。 |
| Step 5 | Double Diamond 後、實作前 | 呼叫 TBD 時 | 先開分支，並規劃兩個 commit：先重構，再新增功能。 |
| Step 6 | 沒有獨立呼叫 | 說 `do it` 後，實作前 | 沒有獨立做 TBD 規劃。Agent 仍開了分支，最後依「收尾」指令完成整合。 |
| Step 7 | Conventional Commits 草稿後 | 沒有開分支 | 檢查時變更已提交在 `main`。建議修正 commit 標題、確認遠端後 push。沒有執行這些建議。 |
| Step 8 | Conventional Commits 草稿後 | 沒有開分支 | 檢查已提交的狀態，說明事後補開分支不會改變先前的開發過程。 |

Step 7、8 的 Conventional Commits 回覆都只有草稿。後續檢查才發現變更已提交。紀錄沒有寫誰執行了 commit。

## commit 後呼叫 TBD，接下來多了哪些事

Step 3、4 最接近你記得的順序：

```
Double Diamond → do it → Conventional Commits → TBD → 選擇收尾方式
```

當時程式已經寫完，也已經 commit，但還留在功能分支上。TBD 接著檢查：

1. 這次變更夠不夠小。
2. 分支有沒有跟上 `main`。
3. 本機測試是否通過，遠端 CI 是否執行。
4. 要直接合併後 push，還是先開 PR。

Agent 提出兩種選擇：

| 選擇 | 操作順序 | CI 何時執行 |
| --- | --- | --- |
| A：本機合併 | 合併回 `main`，再 push | push 後 |
| B：開 PR | 開 PR，檢查通過後再合併 | 合併前 |

你在 Step 3 回覆「a, do it」，在 Step 4 回覆「a」。Agent 才執行合併、測試、push、刪分支，並確認 CI 通過。

所以，那兩次呼叫 TBD 之後，主要增加的是整合檢查與收尾選擇。程式沒有因此多出新功能。

## 沒有輸入 TBD，為什麼也會開分支

以下三次都有這個情況。

### Step 3：要求 Conventional Commits 時才開分支

Agent 在 `main` 上完成實作。你接著輸入 `/conventional-commits`。

Agent 參考 Step 2 的分支命名，建立 `step-3-newline-delimiter`，然後 commit。你是在這之後才輸入 `/trunk-based-development`。

這次開分支是 Agent 處理 commit 時一併做的。

### Step 4：Double Diamond 已經說好先開分支

Agent 在分析結果中寫明「先開分支再實作」。你回覆 `do it`，Agent 就建立 `step-4-trailing-delimiter`，再開始實作。

這次是執行前一輪提出的做法，也補上了 Step 3 分支開太晚的問題。

### Step 6：跳過 TBD 指令，直接說 do it

Double Diamond 分析結束後，Agent 建議你輸入：

```
$trunk-based-development 依建議
```

你直接回覆 `do it`。Agent 使用 TDD Skill，建立 `step-6-negative-numbers`，然後實作。

後來你追問流程是否完成，Agent 承認沒有獨立做 TBD 規劃。

這三次都有開分支。至於 Agent 有沒有在背後呼叫 TBD Skill，過程紀錄沒有寫，無法確認。

目前的 Double Diamond Skill 也沒有規定「下一步必須呼叫 TBD」。它只要求提出具體的下一步。

## do it 沒有每次都開分支

Step 4、6 在 `do it` 後開了分支，但 Step 7、8 沒有。

Step 8 你追問原因，Agent 回覆：

> 是，沒有特別理由。是我沒有延續既有的短期分支流程，並非基於功能複雜度或風險評估後做出的決定。
> 

因此，先前幾次的成功操作，沒有讓「實作前開分支」變成每次都會執行的固定流程。

## 後來一句「收尾」包含了什麼

Step 5、6 已經有前面的操作慣例。你說「收尾」，Agent 就完成以下工作：

1. 合併回 `main`。
2. 執行本機測試。
3. push 到遠端。
4. 確認 CI 通過。
5. 刪除本機功能分支。

實際刪分支的時機略有不同：Step 5 在等待 CI 結果前刪除，Step 6 在 CI 通過後刪除。

Step 8 你說「需要收尾嗎？要就做，不需要跟我講一下」。Agent 查到本機與遠端 `main` 相同，工作目錄乾淨，也沒有功能分支可刪。因此只回報不需要額外操作。那次沒有查詢遠端 CI 結果。

## 當時整理出的五步流程

Step 4 討論後，Step 5 採用了下面的順序。Step 6 的紀錄也再次列出這套流程：

| 步驟 | 指令 | 要完成的事 |
| --- | --- | --- |
| 1 | `$double-diamond <需求>` | 比較方案，決定這次做什麼。 |
| 2 | `$trunk-based-development 依建議` | 決定怎麼拆、怎麼合併，建立短期分支。 |
| 3 | `do it` | 實作與測試。 |
| 4 | `$conventional-commits commit` | 建立 commit。加上 `commit`，避免只得到草稿。 |
| 5 | `收尾` | 合併、push、確認 CI、刪分支。 |

Step 5 的兩個 commit 就是在第 2 步規劃的：先抽出 `tokenize()`，確認原有測試通過，再加入自訂分隔符。這次 TBD 同時決定了工作拆分與分支安排。
