# 測試輸入與判準

日期：2026-10-17。測試題與判準在讀取修改前回答之前建立。S1–S8 均為新編情境，非複製 Skill 範例；屬既有用途回歸。S9 是靜態與記錄核對，不列為模型實跑。原始需求是重構短提示詞，沒有使用者回報的行為失敗輸入。

## 動態情境

共同預先回覆：無；目標 Skill 沒有使用者核准閘門。資訊不足時保留待驗證並提供下一步，不編造使用者回覆。模型只取得 JSON 輸入，未提供本文件判準。

### S1

輸入：

```text
主管說：「儀表板要加 AI 助理，大家一定比較愛用。」目前只有這句話，沒有訪談、使用量或流失資料。請用 double-diamond 分析下一步。
```

判準：將 AI 助理識別為解法、主管說法為假設；未知不捏造；先蒐證不列三個產品方案。

### S2

輸入：

```text
倉庫揀貨員找儲位平均花 80 秒。觀察 12 次作業並核對 log，瓶頸是儲位代碼容易看錯，非網路延遲。目標降到 35 秒、錯拿率不增加、不得新增硬體；可改標籤或介面，尚未選方案。請分析並比較方案與最便宜的驗證。
```

判準：Problem Statement 的五欄對應輸入；至少三個不同方向、不新增硬體，便宜驗證測可讀性／任務時間及錯拿風險；不宣稱已有實測結果。

### S3

輸入：

```text
活動頁的日期文字顏色套錯 design token，原因已確認；將 color-danger 改成 color-muted，設計稿與截圖比較可驗證，無其他影響。請判斷是否需要完整雙鑽石及下一步。
```

判準：不跑完整雙鑽石／訪談；建議直接換 token 並截圖比對。只給一個確定修正不算失敗。

### S4

輸入：

```text
production 訂單 API 在新版本上線後大量 500，值班已確認是設定鍵更名，回滾方案與驗證用 smoke test 已備妥。請用雙鑽石建議處理順序；只給建議，不實際執行。
```

判準：先止血（可回滾）與修復驗證，事後回顧；不要求事故處理前先研究或三方案；無實際執行。

### S5

輸入：

```text
公司法遵已確認新版規定要求申請頁顯示保存期限，文字與生效日已核准，不需要重新判斷要不要遵守；但放置位置尚未決定，希望不增加放棄率。請分析要探索什麼、如何驗證。
```

判準：法遵已確認的義務當限制；探索呈現位置與放棄率，提出方案與低成本測試，不能宣稱新增的法律結論。

### S6

輸入：

```text
我們已做「把帳單提醒改成預設推播」prototype，目標讓逾期率由 12% 降至 8%，目前只有設計師覺得不錯，尚無使用者測試或實際結果。請判斷目前階段及下一步，能直接說成功嗎？
```

判準：偏 Deliver／Test（可指出需補其他階段證據）；不宣稱已達 8%；對 prototype 提出任務與成效測試。

### S7

輸入：

```text
研究倉庫交接遺漏已有作業觀察、訪談與紀錄交叉核對，三輪新資料均未改變問題優先順序，主要風險轉為新交接表是否能用；同事卻說官方規定至少訪談 20 人，現在只有 11 人不能前進。請判斷是否繼續研究，以及你的判斷屬於官方原則或實務判斷。
```

判準：無官方固定 20 人門檻；依不確定性可收斂至新表驗證，標明屬實務判斷。

### S8

輸入：

```text
請說明 Double Diamond 的兩次發散收斂、四個 Design Principles，以及它與 Design Thinking、Agile 的關係。Develop 是開始寫程式、Deliver 就是 deploy 嗎？流程可以回頭嗎？
```

判準：四階段及兩次發散收斂、四原則、可返回、Develop 非直接寫 code、Deliver 非只部署、Design Thinking／Agile 關係及來源區分。

## S9：靜態與記錄核對

逐項檢查 E8–E12：原規則追溯、frontmatter、SOP、RuleFile 正反例、條件載入／清單／消費／CHECK、兩側實體同步、audit、原始輸入與回答、版本雜湊與差異、前後比較與影片素材。動態載入須查實跑紀錄，靜態通過不能替代。

## 隔離與限制

兩輪均使用 fork_turns=none 新子代理，模型與 reasoning 繼承父代理不覆寫；同輪八題依序共用上下文，非逐題獨立對話。只給受測 package 副本、固定輸入與輸出指示，未給根因、方案或判準。不宣稱盲測可代表整體準確率；服務端精確部署與隨機性參數未知。題目僅分析，不建立產品、法律判斷或部署。設定與 package 雜湊見執行設定.json。
