# Rule 1 - 先整理已知未知，再針對問題蒐證

- 收到需求時，必須先列出已知與未知，不得直接按指定解法切 component。
- Discover 的目標是拆掉「我們以為的問題」；應依本次未知檢視下列資料。

| 類別 | 資料 |
| ---- | ---- |
| 使用者 | 訪談、觀察、support ticket、customer／sales feedback |
| 行為 | analytics、funnel、error log、search log、session replay |
| Business | revenue、conversion、retention、人工作業成本、法規 |
| Technology | API 限制、performance、legacy system、security、資料品質 |

- NN/g 的三面向可以當檢查：Desirable（使用者想要）、Viable（商業可行）、Feasible（技術可行）。

## Good Example

先保留未知，再選能回答問題的資料。

- 情境：PM 要求新增批次通知，沒有說明誰需要、頻率與目前困難。
- 已知：PM 指定批次通知。
- 未知：為什麼、哪些人、多常發生、目前怎麼繞過、成功長什麼樣。
- 下一步：觀察目前通知作業、查 support ticket 與失敗 log，核對人工作業成本及 API 限制。

## Bad Example

相同情境沒有蒐證，直接把指定解法切成工程工作。

- 情境：PM 要求新增批次通知，未提供其他資料。
- 下一步：直接建立前端按鈕、通知 API、排程三張 ticket。

# Rule 2 - Define 必須形成可決策的 Problem Statement

- Define 必須把資料轉成決策：Evidence → Pattern → Insight → Problem → Priority。
- Problem Statement 必須至少回答下列五件事；證據不足的欄位必須標「待驗證」。

| 欄位 | 內容 |
| ---- | ---- |
| 誰 | 對象 |
| 遇到什麼問題 | 具體情境 |
| 為什麼重要 | 影響、數據 |
| 什麼叫成功 | 可量測的目標 |
| 限制 | 不能違反的條件 |

- 沒有回答「所以到底要解什麼」，不得把 Define 視為完成，不管整理了多少便利貼。

## Good Example

原有範例同時提供對象、問題、數字目標與限制。

```text
誰：客服人員。
遇到什麼問題：尋找會員時經常得到大量相似結果。
為什麼重要：平均 45 秒才找到正確會員。
什麼叫成功：降到 15 秒。
限制：不能增加個資曝光。
```

## Bad Example

相同需求只有指定解法，沒有定義真正問題；缺少資料也未標待驗證。

```text
Problem Statement：新增 Advanced Search。
Define 已完成，因為已整理 100 張 Post-it。
```

# Rule 3 - 方案探索必須比較不同方向並以便宜原型驗證風險

- 問題明確且需要探索解法時，必須列出至少三個方向不同的方案，不得第一個方案直接做。
- 問題未定義時，必須先不列候選解法；已知修正與緊急事故依任務分流判斷直接處理時，不得為湊方案數而強加多方案。
- 選方案時，必須判斷「哪個方案可以最便宜地驗證最大的風險」，而不是只問「哪個最漂亮」。
- 可以使用 sketch、wireframe、prototype、SQL query、技術 spike、mock API、fake door、小規模 PoC 等方式驗證。
- Prototype 只要能回答一個還不知道的問題，不需要像正式產品；應使用最簡單能測試想法的原型。

## Good Example

相同問題有不同方向，先用簡單原型回答最大風險；例外不硬湊選項。

- 情境：已確認排班人員常漏看換班申請，尚不知道什麼方式有效。
- 方案：A 改申請清單排序、B 在既有行事曆顯示待辦、C 調整交班確認流程。
- 驗證：先用紙本任務測試比較漏看率與完成時間，不先建完整排班產品。
- 例外情境：已確認連結打錯字、正確 URL 與連結測試皆已知，直接修正及驗證。

## Bad Example

相同情境只偏愛第一個解法；確定的小修正反而被迫多方案。

- 情境：已確認排班人員漏看換班申請，尚不知道什麼方式有效。
- 做法：只畫一版漂亮通知中心，直接投入完整開發，沒有比較或驗證。
- 例外情境：連結打錯字也先列三種重建導覽方案，才允許修正 URL。

# Rule 4 - Deliver 必須依測試證據收斂並持續量測

- 對剩下的候選方案，必須以使用者能否完成任務、改善多少、錯誤率、效能、開發成本及維護成本等適用證據測試，淘汰不能工作的方案，改善後選定。
- 上線後應持續 Production → Measure → Learn，必要時重新 Discover／Define／Develop。

## Good Example

成效取決於測試，失敗可淘汰，上線後仍追蹤。

- 情境：有兩種換班待辦原型。
- 做法：請排班人員執行相同任務，記錄完成率、漏看率、時間及維護成本，淘汰無效版本並改善另一版。
- 上線後：持續量測漏看率；新資料顯示漏看源於交班時機時，回頭重新探索問題。

## Bad Example

相同情境只看團隊感覺，上線即視為結束。

- 情境：有兩種換班待辦原型。
- 做法：主管喜歡其中一版就宣布有效，沒有任務測試。
- 上線後：只記錄 deploy 成功，不追蹤漏看率。

# Rule 5 - Decision Gate 是決策問題，不是官方強制程序

- 使用 Decision Gate 時，必須標明它是業界慣例，非官方強制。
- 可以以下列問題檢視是否具備進一步決策的依據。

| 轉換 | 決策問題 |
| ---- | ---- |
| Discover → Define | 有足夠證據了嗎？ |
| Define → Develop | 問題清楚嗎？ |
| Develop → Deliver | 方案有證據支持嗎？ |
| Deliver → Launch | 風險可接受嗎？ |

## Good Example

把閘門當成業界常用的決策檢視，不是硬性簽核。

- 情境：團隊詢問能否從問題定義走向方案比較。
- 回答：可以用「問題清楚嗎？」檢視對象、問題及限制；這是 Decision Gate 的業界慣例，不是 Design Council 強制簽核。

## Bad Example

相同情境把慣例說成官方強制，並另加簽核制度。

- 情境：團隊詢問能否進入方案比較。
- 回答：官方強制每個階段由主管簽名，未簽名不得往前。

# Rule 6 - 輸出必須符合本次用途

- 分析一個需求時，必須用下列欄位呈現；Problem Statement 的內容依本檔 Rule 2，候選方案的適用性與內容依本檔 Rule 3，不另設相反要求。

```text
需求原文：<...>
判斷：這是問題／已經是解法
目前最大的不確定性：<...> → 所在階段：<Discover／Define／Develop／Deliver／不需完整流程>
Problem Statement：<依 Rule 2 填寫>
候選方案：<依 Rule 3 的適用性填寫>
最便宜的驗證：<用什麼方式驗證哪個最大風險>
下一步：<具體行動>
```

- 下一步必須是具體行動。
- 方法說明或方法比較時，應依使用者的問題回答；不得無故套用產品需求分析格式。

## Good Example

同一個已知小修正依適用範圍交付，候選方案不強湊數量。

```text
需求原文：說明頁的連結 URL 少一個字元，正確地址及測試已確認。
判斷：問題、原因、解法與驗證已知。
目前最大的不確定性：無需探索的重大未知 → 不需完整流程。
Problem Statement：誰：說明頁使用者；問題：連結錯誤；重要性：無法到達目的頁；成功：連結測試通過；限制：只修 URL。
候選方案：直接採已確認修正，不需展開多方案。
最便宜的驗證：執行既有連結測試。
下一步：修正 URL 並驗證目的頁可達。
```

## Bad Example

相同情境雖有欄位，下一步卻無法執行。

```text
需求原文：說明頁連結 URL 少一個字元，正確地址及測試已確認。
判斷：要處理。
下一步：做得更好。
```
