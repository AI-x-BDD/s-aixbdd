## 原本問題與發現方式

使用 [指定短提示詞](提示詞.txt) 呼叫 Skill Engineering，目標為 double-diamond；不是縮短 Skill Engineering 本身。先保存原版、訂八題及判準，再執行基線、查結構與來源；根因及工程藍圖分別取得使用者「OK，執行」與「確認」後施工。

R1：160 行主檔混合模型說明、分流、規則、例外及格式，沒有正式 SOP 或獨立 RuleFile；結構診斷 JSON 有 SOP001。R2：已知小修正／事故可以壓縮流程，但通用輸出格式另寫至少三方案，適用範圍不夠清楚。這是文字與結構問題；基線 S3／S4 已正確處理例外，不能寫成「之前一定強迫三方案」。

主檔負責辨識任務、載入適用清單、分析、產出及檢查；兩個 Phase 是代理工作流程，沒有把非線性的雙鑽石模型改成固定兩階段。

| 部位 | 責任 |
| ---- | ---- |
| 雙鑽石判準（3 條） | 四階段與兩次發散收斂、來源與四原則、Design Thinking／Agile 關係 |
| 任務分流（3 條） | 不確定性與日常四問、小修正／事故／法規例外、研究何時收斂 |
| 需求分析（6 條） | 資料、五欄問題定義、方案、驗證、建議性 Decision Gate 與適用輸出 |

多方案要求留在需要探索解法的情境；已知修正、事故與未定義問題的處理更明確。七欄格式限需求分析，方法說明依用途回覆。READ 有條件與清單名稱，後續 THINK／WRITE 消費清單，CHECK 檢查適用規則已載入及使用，缺漏就返回補讀。

主檔縮短不等於整體內容變少：整包因規則正反例而增加，沒有速度、成本或總 token 節省證據。完整內容見 [前快照](最佳化前技能/SKILL.md)、[後快照](最佳化後技能/SKILL.md)、[package diff](技能前後差異.diff)、[統計](結構統計.json)。

## 實際施工分工

Skill Engineering 負責根因、驗收、藍圖、編排及回歸；skill-form-sop 先建立胖 SOP（W1），skill-derive-rule 搭配 skill-form-rule 依序抽出需求分析（W2）、任務分流（W3）、共通判準（W4），最後 skill-form-sop 收尾至已核准全文（W5）。沒有為湊部位建立 template 或 script，也沒有改 description。

primitive 由主代理載入執行，不等於另開五個代理。隔離代理只用於 Skill Engineering 指定的行為驗收。每一步原文與責任見 [施工紀錄](施工紀錄.md) 及 `施工中間版本/`；37 項既有約束對照見 [結構與追溯驗收](結構與追溯驗收.md)。
