# Rule 1 - workflow 審查維度與常見誤判

- 審查 branch／PR／團隊 workflow 時，必須依已載入的「TBD 判準檢查清單」判斷規則來源與分級，並逐項檢查下列現況。
  - 有沒有 `develop`、`team-a`、`release-next` 這類長期共同開發分支？
  - 每人每天至少整合 main 一次嗎？
  - branch 壽命（含 review 等待）多長？active branches 多少？
  - CI 多快回饋？main 紅了是否立即修或 revert？
  - 有沒有靠 code freeze 解決整合問題？
  - Feature Flag 有沒有清理？
- 涉及變更、分支或 PR 的審查，必須同時使用已載入的「變更規劃檢查清單」判斷適用項目；其中 Rule 4 的六題自檢不得以本 Rule 的六個 workflow 問題取代。
- 審查者必須區分已知現況、未知資訊及不適用項目；不得只因 branch 從 main 建立就認定為 TBD。

## Good Example

逐項審查現況，並以原常見錯誤對照判準，不把分支起點當成唯一證據。

- 情境：所有 branch 從 main 建立，但 feature 活兩三週，PR 很小卻等 review 三天。
- 判斷：前者是長期分開開發；後者必須把等待算入壽命。審查也逐項使用規劃 Rule 4 的六題，而非只查天數。
- 其他對照例：一張 Story 可以拆成 refactor、API、UI、cleanup 多個 PR；API 已改、前端未跟上的 PR 會破壞 main，需按規劃清單判斷相容遷移。
- 多人在同一個 feature branch 開發、branch 一直不刪、接近 release 就 code freeze，都是官方 You're Doing It Wrong 列出的模式。

## Bad Example

相同現況只看 branch 起點，沒有檢查長期開發與 review 等待。

- 情境：所有 branch 從 main 建立，但 feature 活兩三週，PR 很小卻等 review 三天。
- 判斷：「都從 main 開 branch，所以是 TBD；PR 小就不需要再檢查六題。」

# Rule 2 - 導入前提與風險

- 導入評估必須檢查自動 build、自動 test、快速 CI、小批次開發能力、快速 code review。
- 說明風險時必須保留來源區分：DORA 指出經驗不足、缺 gated checks、沒有「broken trunk 優先修復」紀律的團隊，實行 TBD 反而可能增加錯誤與返工。
- 遇到缺少前提的團隊，必須先指出缺的前提，不得直接建議全面導入。缺這些時，TBD 容易變成「大家一直 merge main，main 一直壞」。

## Good Example

先辨識缺口，再討論導入。

- 情境：團隊缺 gated checks，也沒有 broken trunk 優先修復紀律。
- 回覆：先指出自動驗證與修復紀律的缺口，再評估如何補足導入前提。

## Bad Example

相同前提不足卻直接要求全面切換。

- 情境：團隊缺 gated checks，也沒有 broken trunk 優先修復紀律。
- 回覆：「立即移除所有分支流程，大家直接持續 merge main 就會改善。」

# Rule 3 - 適用場合與 GitFlow 比較

- 評估適用性時，可以依下列既有場合判斷：SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統、頻繁發布、多人共同維護的 codebase。需求一直變、多人同時改、需要頻繁 release 三者同時成立時價值最高。
- 比較 TBD 與 GitFlow 時，必須保留下列整合方式的差別。
  - GitFlow 類：先隔離 → 做完整 → 最後整合。
  - TBD：先切小 → 持續整合 → 任何時候都保持可工作。
- 必須說明 TBD 主要改變拆分工作的方式，Git 操作本身變化不大。
- 比較或導入建議涉及具體整合驗證、技巧或版本維護時，必須使用已載入的「變更規劃檢查清單」中適用的判準，不得以更換分支名稱代替工作拆分。

## Good Example

比較整合順序與工作拆分，再連同前提評估適用性。

- 情境：多人維護、頻繁改需求並發布的 Web App 想採用 TBD。
- 回覆：這類場合適用；相較隔離後完成再整合，需先切小、持續整合並維持 main 可工作，仍需檢查 Rule 2 的導入前提。

## Bad Example

同一場合只改命名，沒有比較整合方式。

- 情境：多人維護、頻繁改需求並發布的 Web App 想採用 TBD。
- 回覆：「把 develop 改名 main 就完成導入。」
