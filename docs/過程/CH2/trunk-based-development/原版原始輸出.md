### 完整回答

## S3

### 輸入

Axios 換 Fetch wrapper 需一週，不能中斷現有功能。請安排每天可 merge 的步驟。

### 完整回答

這是大型重構，採 Branch by Abstraction，讓 Axios 與 Fetch 在過渡期共存；不要建立一個活一週的 `refactor/http-client` branch。每天從最新 main 開短期 branch，完成後跑 build、lint、unit test，以及必要的整合測試，review 與 CI green 後立即 merge。

PR 1（第 1 天）：建立 HTTP abstraction 與契約測試　— 使用技巧：Branch by Abstraction

先定義 wrapper 的介面、錯誤與取消／timeout 等必要行為，但保留原有呼叫結果。此步驟不改變實際 transport，merge 後既有功能照舊使用 Axios。

PR 2（第 2 天）：讓 Axios 接到 abstraction　— 使用技巧：Branch by Abstraction

把原本直接使用 Axios 的路徑接到 wrapper，補上 adapter 測試。預設行為仍是 Axios，確保 main 可工作。

PR 3（第 3 天）：加入 Fetch implementation　— 使用技巧：Branch by Abstraction

完成 Fetch adapter 與同一組契約測試。先不切換既有呼叫，或以受控設定讓預設仍為 Axios，因此新實作可以先部署而不影響使用者。

PR 4（第 4 天）：分批把 callers 切到 abstraction／Fetch　— 使用技巧：Branch by Abstraction

依模組或 endpoint 分成數個小 PR，每次只切一批 callers，逐批跑整合測試。必要時用設定或 Feature Flag 控制切換，讓回退仍可用。

PR 5（第 5 天）：完成切換並移除 Axios　— 使用技巧：Branch by Abstraction

確認所有 callers 都經過 wrapper、監控與測試穩定後，移除 Axios adapter、相依套件與暫時設定，再補清理測試。若剩餘工作仍大，就再拆成可每日 merge 的 PR。

每個 PR merge 後 main 為什麼仍可工作：先建立抽象，再讓舊 Axios 實作接上；Fetch 先以新實作存在，逐步切換且保留回退路徑。每一步都保留一個可工作的實作，沒有把「新 API 已改、所有 callers 尚未跟上」的狀態放進 main。

預估 branch 壽命（含等 review）：每個小 PR 目標在當天完成，含 review 不超過一天；整體一週是連續的每日整合，不是單一長期 branch。

## S4

### 輸入

後端 API 與前端 consumer 由不同人改，不能同時完成，整體需三天。如何分批整合？

### 完整回答

採新舊並存與向後相容的順序，先讓後端能同時支援舊 consumer 與新 consumer，再讓前端切換，最後才清理舊路徑。不要先把既有 API 改成前端尚未支援的 breaking change。

PR 1（第 1 天）：後端加入新 API／新欄位，保留舊 API 契約　— 使用技巧：新舊並存

後端先提供新契約，舊 response／endpoint 仍可用；加入兩套契約與回歸測試。若需要路由或版本控制，讓新舊路徑能同時存在。merge 後舊前端仍可正常工作。

PR 2（第 2 天）：前端加入新 consumer，先以受控設定或相容 adapter 切換　— 使用技巧：新舊並存／Feature Flag

前端以新 API 契約完成 consumer，通過 mock／integration test；若新行為尚未要對使用者開放，先保持 flag 關閉。後端仍保留舊契約，因此兩位開發者不必在同一時間完成，main 仍能服務舊流程。

PR 3（第 3 天）：完成切換、驗證後移除舊路徑　— 使用技巧：新舊並存

確認所有 consumer 已遷移、監控與整合測試通過後，才把新路徑設為預設；再用另一個小 PR 刪除舊 API／adapter。若舊 consumer 還存在，就延後清理，不把相容性一次拿掉。

每個 PR merge 後 main 為什麼仍可工作：後端先維持舊契約，前端接入新契約時仍有舊路徑與回退方式；跨人、跨層的工作透過相容介面解耦，不需要等待三天後一次整合。

預估 branch 壽命（含等 review）：每個 PR 以數小時到一天內完成，含 review 與 CI；三天是分批整合的總時程。每次 merge 前從最新 main 同步，merge 後刪除短期 branch。

每個 PR merge 後 main 為什麼仍可工作：flag 預設關閉，未完成的 UI、API、驗證與追蹤不會改變使用者目前的路徑；每一天仍可 build、test、review、merge。週五的開旗是發布時機，不把五天的工作留在單一長期 branch。

預估 branch 壽命（含等 review）：每個每日 PR 以數小時到一天內完成，review 等待也算在內；週一到週四是連續 merge，不是 branch 存活四天。若 review 排隊會超過一天，應先處理 review 流程。

## S6

### 輸入

production 是 1.5，main 是 1.6，兩邊都有同一個 bug。如何修與發佈 1.5？

### 完整回答

採 fix on trunk first：先在 `main` 修正並驗證，再把同一個修正 cherry-pick 到 `release/1.5`。不要只在 `release/1.5` 修完再把一大包變更回灌 main。

PR 1：在 main 修正 bug 並加入回歸測試　— 使用技巧：無（fix on trunk first）

從最新 `main` 開短期 branch，例如 `fix/bug-on-trunk`，加入修正與測試。跑 build、lint、unit test 及必要的 integration test；review 與 CI green 後 merge 到 main。確認 main 的 1.6 也保留這個修正。

PR 2：把 main 的修正 cherry-pick 到 `release/1.5` 並發布　— 使用技巧：Release Branch

從已 merge、已驗證的 main 修正取得 commit，cherry-pick 到 `release/1.5`。在 release branch 重新跑該版本的 CI、回歸測試與發布檢查，必要時依 1.5 的差異調整等價修正，然後產出 1.5 的 release／部署。`release/1.5` 只處理該版本穩定、bug fix 與發布，不加入 1.6 新功能。

每個 PR merge 後 main 為什麼仍可工作：修正先進 main 並有回歸測試，main 不會漏掉 production 的 bug；release branch 只承接已驗證的修正，1.5 的發布不會把未完成的 1.6 工作帶進去。

預估 branch 壽命（含等 review）：main 上的修正 branch 應在數小時到一天內完成，含 review 與 CI；release branch 可依版本生命週期存在，但它不是拿來承載新功能的長期開發 branch。

## S7

### 輸入

我們 PR 都很小，但 review 常等三天。只要 branch 不超過兩天就是符合 TBD 的硬性標準嗎？

### 完整回答

不是。官方把短期 branch 通常描述為約 1～2 天，但這不是「不超過兩天」的硬性通過標準；DORA 更嚴格地以少於一天為目標。branch 壽命要包含實作、等待 review 與 CI 的時間，所以 PR 雖然很小，若等 review 三天，實際上仍是三天的 branch。

TBD 的核心要看整體行為：沒有長期開發分支、至少每天整合 main、main 維持可工作。三天 review 排隊會削弱頻繁整合的效果，也被 TBD／DORA 視為常見阻礙。應縮短 review 等待，例如建立快速 reviewer 輪值、讓自動 build／test 先給出快速回饋、分配 review 負載，並持續確認小 PR 是否能在同日或隔日完成。不能只用「branch 名義上沒有超過兩天」來掩蓋等待時間。

## S8

### 輸入

團隊採 merge commit、同步 main 用 merge、允許直接 push、有時一位 reviewer。這些是否違反 TBD？

### 完整回答

這些 Git 選項本身都不是 TBD 的核心規則，因此不能單獨判定違反：

- 使用 merge commit：TBD 沒規定一定要 squash、merge commit 或 rebase merge。
- 同步 main 用 merge：TBD 沒規定同步時一定要 merge 或 rebase。
- 允許直接 push：是否禁止 direct push 是團隊規則；只要 build／test、review 與 main 可工作的治理仍成立，就不是 TBD 本身的硬性違反。若 direct push 繞過必要檢查而讓 main 變紅，就違反了「main 保持可工作」的核心要求。
- 有時一位 reviewer：TBD 沒規定 reviewer 人數；review 流程由團隊決定，但不能因審查不足而讓 main 不可工作或讓 branch 長期等待。

仍要另外檢查真正的 TBD 條件：有沒有長期共同開發分支、是否至少每天整合 main、branch 是否含 review 等待而過久、CI 是否快速且會在 merge 前驗證、main 紅了是否立即修或 revert。merge 方式、同步方式、命名、reviewer 人數都屬團隊自行決定，不能說成 TBD 的要求。

## S9

### 輸入

我們 main CI 紅了晚上再修，develop 持續兩週才整合，release 前 code freeze。請審查並提出優先處理。

### 完整回答

這個 workflow 有三個明確問題，且都與 TBD 的核心或常見錯誤相衝突。

第一優先：立即恢復 main 綠燈。找到造成 CI 失敗的變更，現在就修好；如果不能快速修，就立即 revert，讓 main 回到可工作的狀態。CI 紅著時先不要繼續把新功能疊上去，也不要等到晚上才處理。修正後重新跑 build、lint、unit test 與必要的 integration test。

第二優先：停止把 `develop` 當成兩週的共同開發分支。把工作拆成能在數小時到一天內完成的短期 branch，至少每天整合最新 `main`，PR 經 review 與 CI green 後就 merge 並刪除 branch。`develop` 兩週才整合代表長期分支與延後整合，核心上不符合 TBD。

第三優先：移除以 code freeze 解決整合問題的做法。用小批次、Feature Flag、Branch by Abstraction、新舊並存與自動測試保持 main 可工作；如果需要穩定某個已發布版本，才在接近發布時切 `release` branch，讓它只做該版本的穩定、bug fix 與發布，不承載新功能。

同時要追蹤 CI 回饋速度、active branch 數量、branch 壽命（含 review 等待）與 main 修復時間。這樣才能確認改成每日整合後是真的縮短整合風險，而不是把紅燈與工作量延後。

## S10

### 輸入

我們沒有自動 build/test，review 常耗幾天，新手為主。想明天全面從 GitFlow 換 TBD。你如何建議並解釋兩者差別？

### 完整回答

不建議明天全面切換。你們目前缺少 TBD 的重要導入前提：自動 build、 自動 test、快速 CI、有效的 gated checks、快速 code review，以及 main 紅了要立即修或 revert 的紀律。新手為主且 review 已經耗時幾天時，直接要求大家每天 merge，容易變成大家一直 merge main、main 一直壞，增加錯誤與返工。

建議先分階段處理：

1. 先建立每個 commit／PR 都會觸發的自動 build 與測試，並在 merge 前設 gated check；讓 CI 在幾分鐘內回饋能否合併。
2. 訂出 broken trunk 規則：main 紅了先修或立即 revert，暫停把新功能繼續疊上去；安排 reviewer 輪值或明確的快速 review 時限，並讓新手有範例與 pairing 支援。
3. 選一個小範圍團隊或服務做 TBD 試點，把工作切成小 PR、短期 branch，至少每天同步並整合 main；用 Feature Flag 或新舊並存保護尚未完成的功能。
4. 觀察 branch 壽命、review 等待、CI 回饋、main 紅燈時間與回復時間。前提穩定、試點可持續後，再逐步擴大，而不是明天一次全面更換。

兩者的工作方式差異如下：

| 面向 | 典型 GitFlow | TBD |
| --- | --- | --- |
| 整合方式 | 先在 develop／feature 等分支隔離，完成較大功能後再整合 | 先切小變更，持續回到單一 trunk（通常是 `main`） |
| 分支 | 常有長期 `develop`、release 或較長壽命的 feature branch | 不建立長期開發分支；branch 很短命，通常約 1～2 天，DORA 以少於一天為目標 |
| main 狀態 | 整合可能集中在較晚階段，風險較集中 | main 任何時候都保持可工作、可發布 |
| 未完成功能 | 容易留在分支等待完整功能 | 用小批次、Feature Flag、Branch by Abstraction 或新舊並存，讓程式先整合但不提早曝光 |
| 發布 | 常搭配 release branch 在發布階段集中處理 | 持續整合與發布；需要維護已發布版本時才晚切 release branch |

TBD 主要改變拆分與整合工作的方式，Git 操作本身不一定完全不同。即使保留部分 GitFlow 流程，也應先解決自動驗證、快速 review 與 broken trunk 紀律，再逐步減少長期分支；在這些前提未具備前，不應宣稱已完成 TBD 導入。
