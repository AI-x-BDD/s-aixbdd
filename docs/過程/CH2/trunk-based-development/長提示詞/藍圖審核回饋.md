# 藍圖審核回饋與修訂記錄

## 審核結果

根因報告已由 `/root` 審核通過，確認 E1–E8、R1/R2 只描述結構落差，不宣稱已有行為錯誤；因此可進入工程藍圖設計。初版藍圖保存在 [工程藍圖-初版.md](./工程藍圖-初版.md)，本檔記錄後續審核意見與修訂方向。

## 本次回饋

1. E3 原本以「本次需要 TBD 判斷」載入唯一 RuleFile；該條件對使用此 Skill 的情境幾乎永遠成立，沒有呈現按主題選擇的理由。若保留單檔，必須證明一般小修也需要全部規則。
2. W2 原本只有七個 Rule 標題，沒有完整規則說明、正反例或可逐項核對原規則的施工內容，無法審核不改行為與單一溯源；需補上完整工作項、較高順位載體不適用理由及約束分配。
3. To-Be 的模式判斷只有需求規劃與 workflow；需核對既有 TBD/GitFlow 比較用途仍可由流程明確處理。

## 實際修訂

- 不保留「TBD 判斷時載入全部規則」的單一 RuleFile；改以需求拆分、流程審查、策略選擇、核心規則與來源分級的實際判斷主題分成五個 RuleFile。
- 在 SOP 中先判斷模式與分支，再逐一按條件載入相關檔案；一般小修只取核心／拆分，只有遇到未曝光功能、遷移、相容性、release/hotfix 或 workflow／GitFlow 審查時才取策略或流程檔。
- W2 改為列出五個 RuleFile 的完整規則正文、每條 Good/Bad example、原有內容映射、Rule/SOP/Template/Script 的約束分配，以及選擇 RuleFile 而非較高順位載體的理由。
- SOP 增加明確的 `TBD 與 GitFlow 比較` 模式與輸出檢查；流程審查 RuleFile 保留長期 develop、長 feature branch、code freeze、CI／main 可工作、release branch 與 GitFlow 比較的處理。
- 這次只修訂紀錄中的藍圖；尚未修改 `.agents/skills/trunk-based-development/`、同步的 `.claude/skills/trunk-based-development/` 或任何受測 package。
