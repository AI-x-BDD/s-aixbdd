# 主幹式開發（Trunk-Based Development）

# SOP

## Phase 1 -- 釐清情境與套用判斷規則

1. `READ` 使用者需求，以及使用者提供的 branch、PR、CI、release 與工作目錄現況。
2. `THINK` 判定本次是需求拆分規劃或既有 workflow 審查，列出要回答的變更、整合、來源分級與限制，並判斷是否需要完整案例。
3. `READ` 本次需要 TBD 判斷時，讀取 `rules/主幹式開發判斷-格式規範.md` 的所有 Rule，建立「TBD 判斷檢查清單」；需要完整情境拆法時，再讀取 `references/cases.md`，建立「TBD 案例參考」。
4. `THINK` 依已載入的「TBD 判斷檢查清單」與（若建立）「TBD 案例參考」分析小批次、branch、main、CI、技巧與 workflow；對每項結論保留輸入中的事實與未知限制。
5. `CHECK` 逐項確認分析覆蓋本次適用的「TBD 判斷檢查清單」與已知限制；缺少的事實標為未知，不用未提供資訊補成結論。

完成條件：已判定情境類型，必要規則與案例資源已載入並命名，分析已覆蓋適用檢查項且未知限制已標明。

## Phase 2 -- 產出與交付檢查

1. `WRITE` 依已載入的「TBD 判斷檢查清單」產生結果；需求規劃使用下列格式，workflow 審查則列出不符合項、證據、修正順序與限制。

   ```text
   PR 1：<變更>  — 使用技巧：<無／Feature Flag／Abstraction／新舊並存>
   PR 2：...
   每個 PR merge 後 main 為什麼仍可工作：<說明>
   預估 branch 壽命（含等 review）：<時間>
   ```

2. `CHECK` 逐條驗證「TBD 判斷檢查清單」，確認結果欄位完整、來源分級與未知限制已保留；未通過時修正後重新檢查。

完成條件：規劃或審查結果已交付，且交付前 `CHECK` 的適用項目全部通過。
```

To-Be 的主檔只保留 frontmatter、標題與 SOP；原本的持續性判斷規則改由單一主題 RuleFile 承載，既有案例資源維持原檔並由條件式 `READ` 取得。

### 工作項內容

#### W1：胖 SOP

- 依 `skill-form-sop` 的固定結構建立唯一 `# SOP`。
- Phase 1 暫時保留待抽取的持續性判斷內容於分析步驟；不得在此階段先載入尚未建立的 RuleFile。
- Phase 2 保留原有規劃輸出 code block；不把固定欄位拆成樣板組。
- W1 完成條件：`SKILL.md` 有連續 Phase、受控動詞步驟與完成條件，且 RuleFile 尚未被提名或讀取。

#### W2：判斷 RuleFile 與載入步驟

- 依已確認的工程藍圖把同一「TBD 判斷」主題集中在一個 RuleFile；不依案例、來源或單條規則硬拆檔案。
- RuleFile 依序建立 7 條 Rule：來源與標準分級、核心規則與主幹可工作、小批次與短期分支、技巧選擇與步驟、workflow 審查與導入前提、團隊自行決定項、常見錯誤與 GitFlow 比較。
- 每條 Rule 必須包含可檢查的條列、`## Good Example`、`## Bad Example`，正反例針對同一個判斷重點；不要把固定輸出格式或 Phase 順序重述到 RuleFile。
- SOP 的 `READ` 只在本次需要 TBD 判斷時提名 RuleFile 並建立「TBD 判斷檢查清單」；後續 `THINK`、`WRITE`、`CHECK` 使用該名稱。
- W2 完成條件：RuleFile 與載入步驟符合本藍圖，且原本 inline 判斷內容已有唯一追溯位置。

#### W3：SOP 收尾

- 依 To-Be SOP 刪除已移到 RuleFile 的主檔參考內容，避免同一約束在 SOP 與 RuleFile 重複。
- 保留 frontmatter、標題、規劃輸出格式與必要流程；案例資源仍是既有 `references/cases.md`，只在條件式 `READ` 取得。
- W3 完成條件：主檔與第 2 節 To-Be SOP 逐字一致，沒有未建立部位的路徑或重複判斷細節。
