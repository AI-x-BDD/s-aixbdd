明天先做一個可觀測的 pilot：

1. 保護 main，先建立自動 build/test 與 required checks；CI 失敗時停止新合併，立即修復或 revert。
2. 選一個低風險變更，從最新 main 開短期 branch，切成小 PR；完成 review、CI green 後合併，合併後刪除 branch。
3. 設定 review 輪值、回應時間與 branch age 度量，讓 review 等待也計入 branch 壽命；這些是團隊治理，不是把某個天數冒充 TBD 硬規則。
4. 觀察一段時間的 main failure、CI 回饋、review 等待、每日整合頻率與返工，再逐步把其他團隊或服務納入。develop 不必在明天一次刪除；可以先停止新增長期工作，將已完成的小批次逐步移回 main。

GitFlow 與 TBD 的差異：

| 面向 | GitFlow 類 workflow | TBD |
| --- | --- | --- |
| 整合節奏 | feature/develop/release 等分支先隔離，完成一段工作後再整合 | 圍繞 main 切小批次，頻繁整合 |

來源分級：TBD 官方核心是小批次、短期隔離與持續整合並保持 main 可工作；DORA 提供較嚴格的快速整合與快速回饋建議，並提醒缺少自動檢查與 broken trunk 紀律的團隊先補前提；review SLA、branch protection、merge commit/squash、pilot 範圍與 rollout 是團隊決策。題目未提供 repo 規模、部署頻率、CI 平台與 branch protection，不能據此承諾明天全面切換安全。
