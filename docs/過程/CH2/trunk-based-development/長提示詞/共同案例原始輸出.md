回答：

三天不能放在一條 feature branch 等最後一次合併。先切成可獨立整合的小批次，並在第一個會造成使用者可見變化的 PR 加上預設關閉的 Feature Flag；Deploy 與 Release 分開，flag 開啟前可部署但使用者看不到。

PR 3：接上基本搜尋流程，保留既有頁面與行為 — 使用技巧：Feature Flag

PR 4：加入分頁，包含需要的 client／UI 測試 — 使用技巧：Feature Flag

PR 5：加入權限判斷與未授權測試；服務端權限仍須真正檢查，不能只靠前端隱藏 — 使用技巧：Feature Flag

每個 PR 都從最新 main 開自己的短期 branch，完成可驗證的變更後跑必要的 build、lint、unit 或 integration test，經 review 與 CI green 才 merge，再刪除 branch。若任一 PR 超過一天，應再按 client、UI、測試或權限邊界切小。

每個 PR merge 後 main 為什麼仍可工作：API client 本身不改既有搜尋行為；輸入框、搜尋、分頁與權限都在預設關閉的 flag 後，既有畫面仍是安全路徑；每次合併都保留相容的既有行為並通過相應驗證。因此三天的完整功能不必在 main 上以半成品曝光。

預估 branch 壽命（含等 review）：每個 PR 目標為半天至一天內完成 merge，review 與 CI 等待時間計入壽命；整體 feature 仍可花三天，不能把三天算成一條 branch 的壽命。

完成驗證後才開啟 flag；穩定後安排移除 flag。flag 名稱、開啟方式與清理時間目前未知，不能自行指定。

### S3

原始輸入：

> Axios 換 Fetch wrapper 需一週，不能中斷現有功能。請安排每天可 merge 的步驟。

本題首次載入：無。

本題後仍未讀：R5、R6。

- 已知是約一週的大型 HTTP client 遷移，現有功能不得中斷。
- caller 數量、Axios 目前使用面、Fetch 相容性、fallback、flag、CI 與 review 時間未知。
- 下面用「每天」表示可合併的步驟，不代表實際已執行或每步一定只需一天。

回答：

這是大型重構，不能用一條活一週的 refactor branch。使用 Branch by Abstraction，先讓舊實作保持可用，再逐步加入與切換新實作。

PR 1：建立 HTTP abstraction 與 contract／既有行為測試，先不改 caller — 使用技巧：Abstraction

PR 2：讓 Axios 接上 abstraction，維持 Axios 為現有安全實作 — 使用技巧：Abstraction

PR 3：加入 Fetch wrapper implementation，通過同一組 contract tests，暫不切換所有 caller — 使用技巧：Abstraction

PR 4：按 caller 或小群組逐批切換到 abstraction 的 Fetch implementation；每批完成就 merge — 使用技巧：Abstraction

PR 5：確認所有 caller、錯誤處理與必要 integration test 都通過後，移除 Axios 舊實作 — 使用技巧：Abstraction

安排上可為 Day 1 建 abstraction、Day 2 接 Axios、Day 3 加 Fetch、Day 4 開始逐批切 caller、Day 5 以後完成剩餘 caller 並清理。若某天的 caller 批次不能在一天內完成，就再切成更小批次；不把剩餘工作留在一條 branch。

每個 PR merge 後 main 為什麼仍可工作：在 Fetch 通過驗證並完成 caller 切換前，Axios 仍透過 abstraction 提供既有行為；新舊 implementation 暫時共存，caller 與介面不會處在不匹配的中間狀態。每一步都應經 build、測試、review、CI green 後 merge，merge 前同步最新 main，merge 後刪除短期 branch。

預估 branch 壽命（含等 review）：每個 abstraction、implementation 或 caller 批次以一天內完成 merge 為目標；整體遷移約一週。若實際 review／CI 使 branch 逾期，題目未提供資料，應量測後再調整批次。

### S7

原始輸入：

> 我們 PR 都很小，但 review 常等三天。只要 branch 不超過兩天就是符合 TBD 的硬性標準嗎？

本題首次載入：R5、R6。

本題後仍未讀：無（受測 Skill 目錄中的資源均已讀）。

限制與未知：

回答：

不是。branch 不超過兩天不是 TBD 的普遍硬性標準；TBD 的核心是圍繞可工作的 main 做小批次、頻繁整合。branch 壽命必須包含等待 review、CI 與合併的時間。若同一 branch 實際等 review 三天，它就不可能同時是兩天內完成，除非題目所說的 review 等待不是在該 branch 上。

來源分級：

- TBD 官方常見的短期 branch 約 1–2 天，這是實務參考，不是所有團隊情境都一律違反的硬限制。
- DORA 的較嚴格建議是少於 1 天，屬於目標／能力建議，不應冒充 TBD 官方硬規則。
- review SLA、reviewer 輪值、人數、branch 命名與平台政策屬團隊規則；題目沒有提供。

目前可確認的 workflow 問題是 review queue 常等三天，這會拉長 branch 壽命並延後整合。應先量測 branch 建立到 merge 的實際時間，再處理 review 瓶頸：安排明確 reviewer、輪值或 pairing，縮小仍過大的 PR，並讓自動 CI 快速回報。任何 branch 在 merge 前仍須同步最新 main、通過驗證，merge 後刪除。

這些資料不足以判定整體 workflow 已符合或不符合 TBD，因為整合頻率、main 狀態與 CI 證據仍未知。

回答：

逐項判斷如下：

- merge commit：屬團隊選項，不是 TBD 核心違規。TBD 關注的是小批次、頻繁整合與 main 可工作，不指定必須 squash、rebase 或 merge commit。
- 同步 main 用 merge：也是 Git 操作選項，本身不違規；前提是 branch 持續同步、合併前使用最新 main，且不把同步用的 merge 當成完成產品整合。
- 允許直接 push：TBD 沒有把「禁止 direct push」列為單獨核心規則，但若 direct push 能繞過 review／CI，造成 main 紅或不可工作的程式直接進 main，就違反 main 必須可工作與驗證閘門的核心要求。需要查設定才可下結論。
- 有時一位 reviewer：reviewer 人數是團隊治理選項，不是 TBD 官方硬規定。一位 reviewer 是否足夠要依變更風險、測試與團隊政策判斷，不能只因人數就宣稱違反 TBD。

優先補上的團隊控制是保護 main、要求自動 build／test 與必要 CI gate，並明確規定 main 紅時立即修復或 revert；接著量測 review 與 branch 壽命、整合頻率，再決定 reviewer 輪值或人數。不要為了 TBD 口號任意改成另一種 Git merge 命令。

目前能判定的是上述做法本身多屬團隊選項；是否形成 TBD 違規，取決於它們是否讓 branch 長期存在、整合不頻繁、跳過驗證或使 main 紅。這些證據尚未提供。

### S10

原始輸入：

> 我們沒有自動 build/test，review 常耗幾天，新手為主。想明天全面從 GitFlow 換 TBD。你如何建議並解釋兩者差別？

本題首次載入：無。

本題開始前已載入：R0、R1、R2、R3、R4、R5、R6。

本題後仍未讀：無。

限制與未知：

- 已知沒有自動 build／test、review 常耗幾天、團隊以新手為主，並且希望明天全面切換。
- 未知目前 branch 結構、release 頻率、CI 平台、程式庫規模、人力與可以先試行的低風險範圍。
- 沒有實際改 branch policy、建立 CI 或執行遷移。

回答：

不建議明天全面切換。TBD 的導入前提尚未具備：沒有自動 build／test 就無法快速知道 main 是否仍可工作；review 已慢幾天，會讓短期 branch 變長；新手團隊還需要 broken trunk 的修復紀律、驗證閘門與小批次拆分訓練。流程審查規則也指出，缺少 gated checks、快速 CI 與 main 紅時先修的紀律時，直接全面導入可能增加錯誤與返工。這是 DORA 的導入風險建議，不是把 DORA 門檻冒充成 TBD 官方硬規定。

建議分階段：

1. 先補導入前提：建立自動 build、unit test 與必要 integration test，讓 PR 有 required checks；保護 main，定義 main 紅時立即修復或 revert 的責任與流程。
2. 先選一個低風險區域試行：把工作切成可驗證的小 PR，短期 branch 從最新 main 開始，review 與 CI green 後 merge，merge 後刪除。安排 reviewer 輪值、pairing 或教學，縮短幾天的 review queue。
3. 對不能一次完成的功能使用適當策略：未完成但不能曝光用預設關閉的 Feature Flag；大型重構用 Branch by Abstraction；跨邊界遷移先讓新舊介面並存。每次 merge 都保留可工作的舊路徑。
4. 觀察 pilot 的 main green 率、branch 從建立到 merge 的實際壽命、review 等待、CI 回饋與整合頻率，再按區域逐步停用長期 develop。不要用一次 code freeze 來掩蓋整合問題。
5. 全面採用前確認團隊能持續維持小批次、快速 review、自動驗證與 broken trunk 優先修復；若有已發布版本，release branch 只做該版本維護與 bug fix。

TBD 與 GitFlow 的差別：

| 比較面向 | TBD | GitFlow 類 workflow |
| --- | --- | --- |
| 整合節奏 | 把工作切成小批次，頻繁回到單一 main，任何時候維持 main 可工作 | 先在 feature／develop／release 等分支隔離並做完整，較晚一次整合較大批次 |
| branch 用途 | 主要是短期 topic branch；未完成能力靠 flag、abstraction 或新舊並存留在 main | 常見長期 develop、release 與較長 feature branch，分支本身承載隔離中的完整工作 |
| main 條件 | 每次 merge 都要能 build、test、運作或符合題目定義的可發布狀態 | 通常把完成後的整合交給 develop／release，再讓穩定內容進入主要發布線；整合批次較大 |
| 未完成功能 | 可部署但以 flag 關閉，或用相容層保留舊實作 | 常見做法是留在隔離 branch，直到功能完整才整合 |
| Git 命令 | 可使用 merge、rebase、PR 等一般 Git 操作；重點是批次與頻率 | 也可使用相同 Git 操作；差異是分支生命週期、整合位置與時機，不是命令名稱 |

官方 TBD 規則可把短期 branch 約 1–2 天當作參考；DORA 少於 1 天是較嚴格目標，兩者都不應在沒有量測時寫成明天必達的硬標準。reviewer 人數、branch 命名、是否 squash、是否允許 direct push 等仍是團隊政策。當前最重要的決策不是明天宣布換名，而是先讓 main 有自動驗證與可執行的修復流程，再以小範圍 pilot 證明整合能力。
