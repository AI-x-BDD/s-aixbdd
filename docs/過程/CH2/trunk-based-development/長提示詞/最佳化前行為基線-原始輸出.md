## S1

### 實際輸入

```text
產品要新增「帳單匯出」功能，包含 API、下載頁面、權限檢查、操作追蹤與測試，預估四個工作天；產品要求週五才對使用者開放。請規劃如何拆成可獨立整合的 PR，判斷是否需要特殊技巧，並依 Skill 的固定格式說明每個 PR merge 後 main 為什麼仍可工作、branch 預估活多久。
```

### 回答

這是四個工作天的跨層功能，應拆成多個可獨立合併的 PR。因為程式會先部署、週五才讓使用者使用，採用 `Feature Flag`，例如 `billingExport`，預設關閉。Feature Flag 是 TBD 官方列出的技巧；Deploy 不等於 Release，穩定後要刪除 flag。flag 名稱、權限模型與事件名稱是團隊自行決定，不是 TBD 規定。

PR 1：建立帳單匯出資料契約、API client 介面與 server-side `billingExport=false` 閘門，補契約測試 — 使用技巧：Feature Flag

PR 2：加入匯出 API 與權限檢查，補授權成功、拒絕與 flag 關閉時的測試 — 使用技巧：Feature Flag

PR 3：加入下載頁面、路由與 client-side 閘門，補頁面與路由測試 — 使用技巧：Feature Flag

PR 4：在匯出流程加入操作追蹤事件，補事件內容與不重複送出的測試 — 使用技巧：Feature Flag

PR 5：加入跨 API、權限、下載與追蹤的整合測試，以及開關開啟前的 release check — 使用技巧：Feature Flag

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 只增加契約、client 介面與預設關閉的開關；既有帳單流程不改變，匯出入口不可用。
- PR 2 的新 endpoint 先經過 server-side flag 與權限檢查；flag 關閉時既有 API 不受影響，測試驗證新路徑的安全邊界。
- PR 3 的新頁面與路由受 client-side flag 控制；既有下載頁面與導航仍走原流程。
- PR 4 只有在匯出路徑可用時才送追蹤事件；既有使用者不會進入這條路徑，也不會因追蹤程式改變原流程。
- PR 5 只增加驗證與整合測試，不改變 production 預設行為；CI 綠且 review 完成後，週五才把 flag 打開。

預估 branch 壽命（含等 review）：PR 1 約半天至 1 天；PR 2 約 1 天；PR 3 約 1 天；PR 4 約半天至 1 天；PR 5 約 1 天。每個 branch 做完即 merge 並刪除，避免把四天工作放在一條 branch。TBD 官方對短期 branch 通常約 1～2 天；DORA 以少於 1 天為目標，因此 review 等待也必須算入壽命。

## S2

### 實際輸入

```text
現有產品所有呼叫都直接依賴舊的 REST client，團隊想在一週內換成新的 GraphQL client，但不能讓 main 進入「部分呼叫已換、部分呼叫已壞」的狀態。請用 trunk-based-development 規劃每日可 merge 的步驟，指出應使用的技巧，以及每一步的可工作理由。
```

### 回答

這是跨一週的大型 client 遷移，應使用 TBD 官方列出的 `Branch by Abstraction`。先建立穩定的抽象介面，讓 REST 與 GraphQL 暫時共存，再逐步切換，最後移除 REST。實際呼叫可按 domain 或一小組 call sites 拆成多個 PR；每個 PR 都要有相容性測試，並在合併前同步最新 main。若以 per-operation flag 選擇 REST 或 GraphQL，flag 是團隊實作選擇，不是 TBD 強制規則。

PR 1：建立涵蓋現有呼叫語意的 client abstraction，加入 characterization／contract tests；所有 production caller 暫時維持原 REST client — 使用技巧：Branch by Abstraction

PR 2：把舊 REST client 接到 abstraction，讓既有 caller 經由 abstraction 仍使用 REST；補 parity 測試 — 使用技巧：Branch by Abstraction

PR 3：加入 GraphQL implementation，通過同一組 abstraction contract tests；預設仍選 REST — 使用技巧：Branch by Abstraction

PR 4～PR n：按實際 domain 或 call-site 小組逐批把 caller 改接 abstraction；每批先以 REST 作安全預設，再以相同測試驗證 GraphQL，必要時用 per-operation 選擇器逐批開啟 — 使用技巧：Branch by Abstraction

PR n+1：所有批次都通過 parity、integration 與必要的 production 指標檢查後，將 GraphQL 設為各批次的預設實作 — 使用技巧：Branch by Abstraction

PR n+2：確認沒有 caller 依賴 REST 後，移除 REST implementation 與臨時選擇器，保留 abstraction 與 GraphQL contract tests — 使用技巧：Branch by Abstraction

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 沒有改變 production 呼叫；抽象介面由現有 REST 行為的測試定義，main 仍使用 REST。
- PR 2 只改變呼叫路徑，不改變 REST 的實作語意；若有相容性差異，contract tests 會在 merge 前阻擋。
- PR 3 只是加入未被選用的 GraphQL implementation；REST 仍是預設，新增程式不會影響現有呼叫。
- PR 4～PR n 每次只移動一小組 caller，且保留 REST fallback／安全預設；已遷移與未遷移呼叫都能透過同一 abstraction 工作，不會形成 API 已改而 caller 尚未跟上的壞狀態。
- PR n+1 只有在每批驗證完成後才改預設選擇；失敗可停在尚未開啟的批次，不影響已工作的路徑。
- PR n+2 是最後清理；只有所有 caller 已由 GraphQL contract tests 覆蓋並確認不再需要 REST 時才刪除舊實作。

預估 branch 壽命（含等 review）：PR 1、PR 2、PR 3 各約半天至 1 天；PR 4～PR n 每個小組各約半天至 1 天；PR n+1 與 PR n+2 各約半天至 1 天。每天至少合併一個可工作的 PR，branch 不應存活整週。TBD 官方通常接受 1～2 天的短期 branch；DORA 以少於 1 天及每天至少整合一次為目標。

## S3

### 實際輸入

```text
團隊有長期存在的 develop 分支；某個 feature branch 已活 9 天，CI 目前失敗。生產環境仍在 2026.10，main 已開始 2026.11 的開發；現在發現一個只影響 2026.10 的 bug。請審查這個 workflow 是否符合 TBD，列出應先處理的問題與修正順序，並說明 bug 應在哪裡修以及如何帶回發布分支。
```

### 回答

這個 workflow 不符合 TBD。已知問題與修正順序如下：

1. 先停止把 CI 失敗的 branch 合進 main，確認失敗發生在哪裡並恢復可工作的 trunk。若題目中的 CI 失敗指 main，這直接違反 TBD 核心規則 3「main 保持可工作」；應立即修復或 revert，不能等到晚上。若只指 9 天的 feature branch，該 branch 仍不可合併，必須先修到 CI green，並確認 main 本身保持 green。
2. 停止在長期 `develop` 分支上累積新的共同開發。長期開發分支違反 TBD 核心規則 1「沒有長期開發分支」；把其中尚未完成的工作切成可工作的短 PR，逐一回到 main，完成過渡後退役 `develop`。
3. 把已活 9 天的 feature branch 拆小。9 天超出 TBD 官方對短期 branch 通常約 1～2 天的建議，也超出 DORA 以少於 1 天為目標的建議；應按可獨立合併的變更拆成多個 PR，每次 merge 前同步 main，review 與 CI 等待也算在 branch 壽命內。這是明確的短期 branch 問題；題目沒有提供它是否每天整合 main 的證據，所以不能額外斷言核心規則 2 已被違反，應補查每日整合紀錄。
4. 為仍在 production 的 2026.10 維護發布分支 `release/2026.10`（若尚未存在，從目前 2026.10 的發布點建立）。這條分支只處理該版本的穩定、bug fix 與發布，不承載 main 的 2026.11 新功能。
5. 2026.10 的 bug 先修在 main，補測試並讓 main 的 CI 變綠；驗證後把同一個修正 cherry-pick 到 `release/2026.10`，再跑該發布分支的驗證與發布流程。不要只在 release branch 修完再把一大包變更回灌 main，避免 main 漏掉修正。這符合 TBD 官方的 `fix on trunk first` 與 release branch 做法。
6. 修正合併後刪除短期 feature branch，持續以小批次整合，不能靠 code freeze 解決整合問題。

違反與來源區分：

- TBD 核心規則 1：長期存在的 `develop` 是長期開發分支。
- TBD 核心規則 3：若失敗的是 main，main 已非可工作狀態；若失敗的只是 feature branch，則它尚未具備合併條件。
- TBD 官方強烈建議：feature branch 活 9 天，且等 review 的時間也要計入；官方短期 branch 通常約 1～2 天。
- DORA 建議：至少每天整合 main、branch 以少於 1 天為目標，broken trunk 立即修復或 revert，CI 應快速回饋。
- TBD 官方 release branch 規則：維護 2026.10 的 release branch；bug 先修 main、驗證後 cherry-pick 到 release branch，release branch 不承載 2026.11 新功能。
- branch 命名、是否允許 direct push、採 squash 或 merge commit，以及退役 `develop` 的具體時點，都是團隊自行決定，不能說成 TBD 強制要求。

預估 branch 壽命（含等 review）：後續每個修正或拆出的 PR 約半天至 1 天，最多以 TBD 官方約 1～2 天為上限；DORA 目標是少於 1 天。`release/2026.10` 是發布維護分支，不是拿來承載新功能的長期開發分支。
