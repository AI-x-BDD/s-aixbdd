## 2. 模式、主題界線與按需載入

### 2.1 模式判斷

SOP 的 Phase 1 第 2 步先將需求標記為一個或多個模式，並另外標記判斷主題。模式不是由「使用 TBD Skill」這個 domain 名稱決定，而是由使用者要交付的判斷決定：

| 模式／標記 | 可觀察觸發 | 必要主題 |
| --- | --- | --- |
| 需求拆分規劃 | 要規劃 PR、branch、merge、main 可工作理由或 branch 壽命 | 核心規則、需求拆分 |
| workflow 審查 | 要審查現有 develop、feature branch、CI、code review、code freeze 或導入前提 | 核心規則、流程審查 |
| TBD 與 GitFlow 比較 | 明確要求比較兩種 workflow 或說明整合方式差異 | 核心規則、流程審查 |
| 來源分級 | 要標出 TBD 官方、DORA、團隊自行決定，或輸出需要 branch 壽命的來源依據 | 來源分級 |
| 特殊策略 | 功能暫不能曝光、跨多日大型重構、API／相容性遷移、已發布版本 hotfix／release | 策略選擇 |
| 完整案例參考 | 使用者要求完整情境拆法，或明確要求參考既有案例 | references/cases.md |

### 2.2 RuleFile 選擇矩陣

每個選中的 RuleFile 都讀取該檔的全部 Rule，建立獨立且有名字的檢查清單；未選中的檔案不讀取、不把其中判斷寫進回答。

| 需求分支 | READ 的 RuleFile／資源 | 不載入的內容 |
| --- | --- | --- |
| 普通小修，且不要求來源比較 | 核心規則、需求拆分 | 策略選擇、流程審查、來源分級、案例資源 |
| 普通小修，但要求標明官方／DORA／團隊 | 核心規則、需求拆分、來源分級 | 策略選擇、流程審查、案例資源 |
| S1 的未曝光功能規劃 | 核心規則、需求拆分、策略選擇；輸出需要來源標籤時再加來源分級 | 流程審查，除非使用者另要求審查現有 workflow |
| S2 的大型 client 遷移 | 核心規則、需求拆分、策略選擇；輸出需要來源標籤時再加來源分級 | 流程審查，除非使用者另要求審查現有 workflow |
| S3 的 workflow／release 審查 | 核心規則、流程審查、策略選擇、來源分級；若要把 9 天分支拆成 PR，再加需求拆分 | 不因審查而載入完整案例，除非另要求 |
| 明確的 TBD 與 GitFlow 比較 | 核心規則、流程審查；輸出需要來源標籤時再加來源分級 | 需求拆分、策略選擇，除非比較同時涉及特殊策略 |

因此，若輸入只是「修正一個不需延期曝光、不跨層、不涉及 release 的按鈕錯字，請規劃可合併的 PR」，選擇核心規則與需求拆分即可；策略選擇、流程審查、來源分級與案例檔都有明確理由被跳過。這個分支直接證明不需要讓普通小修讀完所有 TBD 規則。

~~~~markdown
# 主幹式開發（Trunk-Based Development）

# SOP

## Phase 1 -- 釐清情境與按主題載入判斷規則

1. `READ` 使用者需求，以及使用者提供的 branch、PR、CI、release 與工作目錄現況。
2. `THINK` 將本次任務標記為需求拆分規劃、workflow 審查、TBD 與 GitFlow 比較中的一個或多個模式，並判斷是否需要執行 Decision Tree、送出前檢查、來源分級、特殊策略與完整案例；列出各模式需要的實際判斷主題與未知限制。
3. `READ` 依第 2 步的主題分支，讀取所選 RuleFile 的全部 Rule，並分別建立具名清單：需要判斷 trunk／main 是否可工作、需求／審查涉及核心整合，或需要執行送出前檢查時，讀取 rules/主幹式開發核心規則-格式規範.md，建立「TBD 核心規則檢查清單」；需要規劃 PR、branch 壽命、同步、驗證或刪除時，讀取 rules/主幹式開發需求拆分-格式規範.md，建立「TBD 需求拆分檢查清單」；需要標示官方／DORA／團隊來源或門檻時，讀取 rules/主幹式開發來源分級-格式規範.md，建立「TBD 來源分級檢查清單」；需要判斷完成時間、能否再切小或選擇特殊策略時，讀取 rules/主幹式開發策略選擇-格式規範.md，建立「TBD 策略選擇檢查清單」；審查 workflow 或比較 TBD 與 GitFlow 時，讀取 rules/主幹式開發流程審查-格式規範.md，建立「TBD 流程審查檢查清單」；只有需要完整情境拆法時，才讀取 references/cases.md 並建立「TBD 案例參考」。未選中的檔案不載入。
4. `THINK` 只使用與模式相符的「TBD 核心規則檢查清單」、「TBD 需求拆分檢查清單」、「TBD 來源分級檢查清單」、「TBD 策略選擇檢查清單」、「TBD 流程審查檢查清單」與（若已建立）「TBD 案例參考」；需求規劃列出小批次、技巧、main 可工作理由與 branch 壽命，若本次需要 Decision Tree，先判斷幾小時／一天內能否完成，再判斷能否切得更小，只有不能切小時才依不能曝光、大型重構、相容性遷移或已發布版本選擇技巧；若本次需要送出前檢查，逐項使用「TBD 核心規則檢查清單」中的「送出前檢查」；workflow 審查列出證據、違反項、導入前提與修正順序，TBD 與 GitFlow 比較明確比較隔離後一次整合與小批次持續整合，並對每項結論保留輸入事實、來源層級與未知限制。
5. `CHECK` 逐項確認已選的「TBD 核心規則檢查清單」、「TBD 需求拆分檢查清單」、「TBD 來源分級檢查清單」、「TBD 策略選擇檢查清單」、「TBD 流程審查檢查清單」與（若已建立）「TBD 案例參考」，並核對已選清單中的 Decision Tree 與「送出前檢查」項目，以及已知限制；缺少的事實標為未知，不用未提供資訊補成結論。

完成條件：模式與主題分支已判定，只有必要的 RuleFile／案例資源已載入並命名，分析已覆蓋已選檢查項且未知限制已標明。
~~~~

## 3. RuleFile 設計與完整施工內容

RuleFile 依實際執行分支分為五個主題。每個檔案至少承載兩條相互關聯的判斷，不按案例或單條規則硬拆；每條 Rule 都有正反例，可以獨立檢查同一個判斷差異。

### 3.1 核心規則

路徑：rules/主幹式開發核心規則-格式規範.md

#### # Rule 1 - 圍繞單一 trunk 頻繁整合

規則說明：

- 所有人圍繞 main 工作，不建立長期共同開發分支。
- 工作拆成可持續整合的小批次，未完成的部分用相容、抽象或關閉開關留在 main；active branches 盡量少，不靠 code freeze 解決整合問題，merge 後刪除 branch。
- DORA 的「至少每天整合一次」是較嚴格建議；它要與 TBD 官方核心方向及團隊實際證據分開標示。

## Good Example

把一週 REST 到 GraphQL 遷移切成 abstraction、舊實作接入、新實作、caller 分批切換等 PR；每天將可工作的 PR 合回 main，沒有長期 develop 或一週後一次合併的 refactor branch。

## Bad Example

所有人把工作放在長期 develop 或一條活一週的 refactor/graphql branch，等完整功能做完才合併；即使每次都是從 main 開 branch，也沒有持續整合。

#### # Rule 2 - main 必須保持可工作

規則說明：

- 每個合併都要使 main 仍可 build、test、運作或依題目定義保持可發布。
- main 紅時先查明失敗，立即修復或 revert；不能為了維持小 PR 而把已知不可工作的程式合進 main，也不能靠 code freeze 延後處理。
- 若只有 feature branch 紅，該 branch 尚未具備合併條件；不能把它與 main 紅混為同一事實。

**送出前檢查**

1. 能不能切到一天內可以 merge？
2. 這個 PR 現在 merge，main 還能正常工作嗎？
3. 未完成功能能不能用 Feature Flag 隱藏？
4. 大改造能不能用 abstraction 讓新舊實作共存？
5. CI 能不能快速告訴我這次改動有沒有破壞系統？
6. 這個 branch 明天還會存在嗎？是的話，檢查是不是切得太大。

## Good Example

CI 發現 main 紅了，團隊先停止新功能、修復失敗或 revert 造成破壞的變更；若只有 feature branch 紅，先修到 green 並確認 main 狀態，再合併。

## Bad Example

明知 main 紅了仍繼續合併新 PR，或說「晚上再看」；也不能把破壞既有 API 的半成品直接合進 main，只因 PR 很小。

### 3.2 來源分級

路徑：rules/主幹式開發來源分級-格式規範.md

#### # Rule 1 - 明確標示來源層級

規則說明：

- TBD 官方是 TrunkBasedDevelopment.com 的規則與技巧。
- DORA 是 Google DORA 的研究與較嚴格建議。
- TBD 未規定、由團隊自行決定的命名、平台、reviewer、merge 方式等，要標為團隊規則。
- 一個結論若混合多個來源，拆開寫出各自來源，不用單一標籤掩蓋差異。

## Good Example

寫「官方短期 branch 通常約 1–2 天；DORA 以少於 1 天為目標；branch 命名由團隊決定」，並把三者分成三層。

## Bad Example

寫「TBD 規定 branch 少於一天、必須 squash、每個 PR 兩位 reviewer」，把 DORA 與團隊選項冒充 TBD 硬規則。

#### # Rule 2 - branch 壽命要包含 review 並保留兩套門檻

規則說明：

- 官方常見短期 branch 約 1–2 天；DORA 以少於 1 天為目標，兩者不是同一條硬性標準。
- branch 壽命包含等待 review、CI 與合併所耗時間。
- 若題目未提供等待時間或每日整合證據，標記未知，不能假造實際壽命。

## Good Example

把「實作半天、等待 review 兩天」計為約兩天半，並分別標示官方約 1–2 天與 DORA 少於 1 天的參考，指出需要縮短 review。

## Bad Example

只計工程師動手的半天，說 branch 符合官方；或把「兩天」寫成不論情境都必須遵守的 TBD 硬限制。

#### # Rule 3 - 團隊選項不得冒充 TBD 要求

規則說明：

- squash、merge commit、rebase、branch 命名、reviewer 人數、GitHub/GitLab 與 direct push 權限屬團隊治理。
- 回答可以提出團隊選項，但要標示為決策或待決定事項。
- workflow 審查要把「沒有證據」與「違反 TBD」分開。

## Good Example

寫「可由團隊決定 squash 或 merge commit；目前未提供 direct push 政策」，不把它當成 TBD 違規。

## Bad Example

因為團隊使用 merge commit 就宣稱不符合 TBD，或把禁止 direct push 說成 TBD 官方核心規則。

### 3.3 需求拆分

路徑：rules/主幹式開發需求拆分-格式規範.md

#### # Rule 1 - Story 先切成可獨立整合的小批次

規則說明：

- 一張 Story/Ticket 不等於一個 branch 或一個 PR。
- 依可驗證、可回復、可工作的邊界拆出 refactor、契約、API、UI、權限、追蹤與測試等小變更。
- 每個 PR 都要說明與既有行為的關係及 merge 後 main 為何仍可工作。

## Good Example

四天的帳單匯出拆成契約、API/權限、頁面、追蹤與整合測試五個 PR，每個可獨立合併，功能以預設關閉的 flag 控制。

## Bad Example

建立一條 billing-export branch，四天後一次合併 API、UI、權限、追蹤與測試；理由只有「Story 尚未完成所以不能 merge」。

#### # Rule 2 - branch 短命、同步 main、review 與刪除

規則說明：

- 每個小批次使用短期 branch，目標是完成即 merge，不承載整個 feature。
- 工作期間同步 main，merge 前確認最新 main；等待 review 的時間也計入 branch 壽命。
- merge 後刪除 branch；不能用多人共用 branch 或 code freeze 代替持續整合。

## Good Example

每個 PR 於半天至一天完成，包含 review 等待；merge 前同步 main，merge 後刪除 branch，下一批再從最新 main 開始。

## Bad Example

PR 很小但等 review 三天仍說 branch 只有半天，或多人長期共用 team-a branch，接近 release 才 code freeze。

#### # Rule 3 - 以驗證閘門保護每次 merge

規則說明：

- 依變更需要執行 build、lint、unit test 與必要的 integration test。
- 對應的流程是 PR → review → CI green → merge；DORA 的較嚴格建議是每個 commit 都觸發 build 與自動測試，並在幾分鐘內得到回饋。
- 驗證不足時不能為了小批次形式把不可工作的程式合進 main。

## Good Example

新增 GraphQL implementation 先通過既有 abstraction contract tests；CI green 且 review 完成後才 merge，REST 仍是安全預設。

## Bad Example

只因 PR 只有幾行就跳過測試，或在 CI 紅時把半成品合進 main 再靠 code freeze 等待修復。

### 3.4 策略選擇

路徑：rules/主幹式開發策略選擇-格式規範.md

#### # Rule 1 - 功能尚不能曝光時用 Feature Flag

規則說明：

- 程式可以每天 merge，使用者曝光由預設關閉的 Feature Flag 控制。
- 明確區分 Deploy 與 Release；功能穩定、開啟後要安排清理 flag，官方警告不清理的 flag 會變成技術債。
- flag 名稱、權限模型與 rollout 方式是團隊決定，除非題目另有規範。

## Good Example

帳單匯出 API、頁面與追蹤每天合入 main，server/client flag 預設 false，週五完成驗證才開啟，之後刪除 flag。

## Bad Example

因為週五才能曝光就把全部程式藏在長期 branch，或留下已開啟多年、沒有清理計畫的 flag。

**Decision Tree**

~~~text
我要做一個變更
│
├─ 幾小時／一天內可完成？
│   └─ Yes → short-lived branch → CI + Review → merge main
│
└─ No → 能不能切更小？
    ├─ Yes → 切小 → 多個 PR，每個回到上一步判斷
    └─ No → 為什麼？
        ├─ 功能還不能曝光     → Feature Flag
        ├─ 大型程式重構       → Branch by Abstraction
        ├─ 舊系統／相容性遷移 → 新舊並存（Strangler）
        └─ 維護已發布版本     → Release Branch
~~~

#### # Rule 2 - 大型重構用 Branch by Abstraction

規則說明：

- 依序建立 abstraction、接上舊實作、加入新實作、逐步切換 callers、最後移除舊實作。
- 每一個步驟都要能合併 main；舊實作或安全預設在切換完成前保留。
- 不把整週工作放在一條重構 branch 後一次合併。

## Good Example

REST 與 GraphQL 共用 abstraction，先由 REST 實作與 contract tests 保持現有行為，再按 caller 小組逐批切換，全部通過後才移除 REST。

## Bad Example

在一條活七天的 refactor/graphql branch 裡同時改所有 caller，最後一次替換 REST；中間 main 會出現 caller 與 API 不匹配。

#### # Rule 3 - 相容性變更採新舊並存

規則說明：

- 跨 API、consumer 或框架邊界時，先讓舊介面與新介面同時可用，再遷移 consumer，最後移除舊介面。
- 以向後相容、抽象層或明確 fallback 保持每次 merge 的工作狀態。
- Branch by Abstraction 是大型實作遷移的具體模式；新舊並存是更一般的相容性判斷，兩者可同時適用但不混為一個步驟。

## Good Example

舊 API 與新 API 暫時並存，consumer 分批改用新 API，確認沒有 caller 依賴舊 API 後才移除舊 API。

## Bad Example

先刪舊 API、再要求所有前端一次改完，讓 main 處於 API 已變更而 consumer 尚未跟上的中間狀態。

#### # Rule 4 - 已發布版本使用晚切的 Release Branch

規則說明：

- Release branch 只承載該版本穩定、bug fix 與發布，不承載 main 的新功能。
- 已發布版本 bug 先在 main 修復、補測試並驗證，再把同一修正 cherry-pick 到對應 release branch。
- 不能只在 release branch 修完再把一大包變更回灌 main；release branch 的具體命名與發布政策由團隊決定。

## Good Example

2026.10 仍在 production 時，在 main 修 bug 並讓 CI green，接著 cherry-pick 到 release/2026.10；main 繼續開發 2026.11，release branch 只做 2026.10 維護。

## Bad Example

只在 release/2026.10 修 bug，等發布後把整條分支回灌 main，或在 release branch 開發 2026.11 新功能。

### 3.5 流程審查

路徑：rules/主幹式開發流程審查-格式規範.md

#### # Rule 1 - 先收集 workflow 證據與導入前提

規則說明：

- 審查至少檢查長期共同分支（如 develop、team-a、release-next）、每人整合 main 的頻率、branch 壽命含 review、active branches、CI 回饋速度、main 紅時處置、code freeze 與 Feature Flag 清理。
- 導入前提包括自動 build、自動 test、快速 CI、小批次能力與快速 code review；active branches 應盡量少。
- DORA 指出，經驗不足、缺少 gated checks、沒有「broken trunk 優先修復」紀律的團隊，實行 TBD 可能增加錯誤與返工；遇到這種團隊要先指出缺少的前提，不直接建議全面導入。
- 適合情境包括 SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統與頻繁發布、多人共同維護的 codebase；當需求一直變、多人同時改、需要頻繁 release 三者同時成立時，TBD 的價值最高。
- 證據不足時列為未知；不因某一個枝節符合就宣稱整體是 TBD。

## Good Example

列出 develop 長期存在、feature branch 9 天、CI 失敗位置待確認、active branches 與 review 時間待補，並先檢查 build/test/CI/review 導入前提。

## Bad Example

只因所有 branch 都從 main 建立，就直接宣稱 workflow 是 TBD；沒有查 branch 壽命、CI 速度、code freeze 或 flag 清理。

#### # Rule 2 - 按核心違規與阻礙排序修正

規則說明：

- main 紅時先修復或 revert，再處理長期共同分支、長 branch、缺少閘門與整合頻率。
- 把 TBD 核心規則、官方強烈建議、DORA 建議與團隊決策分開列出；缺少導入前提時，先補前提，不直接建議全面導入。
- 整合頻率、branch 壽命與 main 可工作判斷引用核心規則或需求拆分 Rule，不在本檔重複另一份規則正文。

## Good Example

先恢復 main green；若紅的是 feature branch，先修 branch 並確認 main 狀態，再拆解 9 天 branch；接著補 gated checks 與快速 review，最後才調整團隊選項。

## Bad Example

讓紅色 main 繼續堆新功能，或只靠 code freeze 解決合併問題；把 DORA 的速度目標直接當成 TBD 官方硬性規定。

#### # Rule 3 - 明確比較 TBD、GitFlow 與常見假 TBD

規則說明：

- GitFlow 類 workflow 先隔離、做完整、最後整合；TBD 先切小、持續整合、任何時候保持 main 可工作。
- TBD 主要改變拆分與整合的節奏，Git 操作本身不必被描述成完全不同的命令集合。
- 「都從 main 開 branch」「PR 很小但 review 等三天」「一張 Story 一個 PR」「多人共用 branch」「靠 code freeze」都是需要具體查證的常見假 TBD 或阻礙，不可用單一口號判定。

## Good Example

在比較輸出中，分別說明 GitFlow 的長隔離與晚整合、TBD 的小批次與持續整合，再指出兩者可使用相近 Git 命令；若 workflow 另有多人共用 branch，列為具體違規證據。

## Bad Example

把「使用 branch」本身說成 GitFlow、把所有從 main 開 branch 的團隊都說成 TBD，或宣稱 TBD 必須改用某一套 Git 命令。

### 6.3 W1 的完整施工內容：先產生胖 SOP

W1 由 skill-form-sop 執行，先把待抽取的全部判斷約束實寫在一個可唯一定位的 SOP 步驟內。W1 不讀取、不提名任何尚未建立的 RuleFile；它只讀使用者輸入與既有的 references/cases.md。W1 的輸出必須可以單獨執行，並保留所有待抽取語意，不能只留「之後抽取」的來源標記。

W1 施工後的 SKILL.md（frontmatter 與標題沿用原文）必須具備下列完整內容：

~~~~markdown
# SOP

## Phase 1 -- 釐清情境與套用既有判斷

1. `READ` 使用者需求，以及使用者提供的 branch、PR、CI、release 與工作目錄現況。
2. `THINK` 判定本次是需求拆分規劃、workflow 審查、TBD 與 GitFlow 比較中的一個或多個模式；另外標記是否需要 Decision Tree、送出前檢查、來源分級、特殊策略與完整案例，保留未提供的事實。
3. `READ` 若使用者要求完整情境拆法或明確要求參考既有案例，讀取既有 references/cases.md，建立「TBD 案例參考」；沒有這個條件時不讀取。
4. `THINK` 依輸入事實與第 2 步的模式，直接套用下列尚未抽取的完整判斷約束；本步驟是所有待抽取約束的唯一位置。
   - 來源分級：將結論分成 TBD 官方、DORA 較嚴格建議與團隊自行決定；官方短期 branch 通常約 1–2 天，DORA 以少於 1 天為目標，等待 review、CI 與合併也計入 branch 壽命；不要把團隊的 squash、merge commit、rebase、branch 命名、reviewer、平台或 direct push 政策說成 TBD 要求。
   - 核心規則：所有人圍繞單一 main，不建立長期共同開發分支，持續把小變更整合回 main；DORA 建議至少每天整合一次。每次 merge 後 main 要能 build、test、運作或發布；main 紅時先查明並立即修復或 revert，不繼續堆新功能，也不靠 code freeze 延後；若只有 feature branch 紅，先修到 green 再合併。送出前逐項檢查：能不能切到一天內可以 merge？這個 PR 現在 merge，main 還能正常工作嗎？未完成功能能不能用 Feature Flag 隱藏？大改造能不能用 abstraction 讓新舊實作共存？CI 能不能快速告訴我這次改動有沒有破壞系統？這個 branch 明天還會存在嗎？是的話，檢查是不是切得太大。
   - 需求拆分：Story/Ticket 不等於一個 branch 或 PR；依可驗證、可回復、可工作的邊界拆成小批次。每個小批次使用短期 branch，工作期間同步 main，merge 前確認最新 main，review 等待算入 branch 壽命，merge 後刪 branch。依變更需要執行 build、lint、unit test 與 integration test，順序是 PR → review → CI green → merge；DORA 建議每個 commit 都觸發 build 與自動測試，幾分鐘內回饋。
   - 策略選擇：先判斷幾小時／一天內能否完成；Yes 就用 short-lived branch、CI + Review 後 merge main；No 就先判斷能否切更小，Yes 就切小成多個 PR 並回到上一步，只有不能切小時才問原因。功能不能曝光用預設關閉的 Feature Flag（Deploy 不等於 Release，穩定後清理 flag；官方警告不清理的 flag 會變成技術債）；大型重構用 Branch by Abstraction，依序建立 abstraction、接舊實作、加新實作、逐步切換 caller、移除舊實作；舊系統／相容性遷移讓新舊介面並存、遷移 consumer、最後刪舊介面；已發布版本用晚切的 Release Branch，只做該版本穩定、bug fix、發布，bug 先修 main 並驗證，再 cherry-pick 到 release branch。
   - workflow／GitFlow 審查：檢查 develop、team-a、release-next 等長期共同分支、每人整合 main 的頻率、branch 壽命、active branches 是否過多、CI 回饋速度、main 紅時處置、code freeze、Feature Flag 清理，以及自動 build、auto test、快速 CI、小批次能力、快速 code review 等導入前提。經驗不足、缺 gated checks、沒有 broken trunk 優先修復紀律時，先指出缺口，不直接建議全面導入；適合 SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統與頻繁發布、多人共同維護的 codebase，需求變化、多人改動、頻繁 release 三者同時成立時價值最高。比較 GitFlow 的先隔離、做完整、最後整合與 TBD 的先切小、持續整合、main 隨時可工作；Git 操作本身不必被說成完全不同。
   - 常見錯誤與交付：不能因為都從 main 開 branch 就宣稱是 TBD；一張 Story 不必只有一個 branch／PR；不能為了 PR 小而 merge 不工作的程式；小 PR 等 review 三天仍是長壽命，DORA 將重量級、非同步、耗時 review 視為阻礙；多人共用 branch、branch 不刪、接近 release 才 code freeze 都要列為問題。需求規劃必須列 PR、技巧、每個 PR merge 後 main 可工作的理由與含 review 的 branch 壽命；workflow 審查必須列不符合項、證據、導入前提與修正順序；TBD／GitFlow 比較必須列整合節奏、分支用途與 main 可工作條件。
5. `CHECK` 逐項檢查第 4 步的來源分級、核心規則、送出前六項檢查、需求拆分、Decision Tree 與策略、workflow／GitFlow、常見錯誤與交付欄位；缺少事實標為未知，不用未提供資訊補結論。

完成條件：已判定模式，必要時取得「TBD 案例參考」，第 4 步的全部適用判斷與未知限制已完成檢查。
~~~~
