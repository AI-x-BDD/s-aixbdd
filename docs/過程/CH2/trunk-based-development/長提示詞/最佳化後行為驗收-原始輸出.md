## S1

### 實際輸入

```text
產品要新增「帳單匯出」功能，包含 API、下載頁面、權限檢查、操作追蹤與測試，預估四個工作天；產品要求週五才對使用者開放。請規劃如何拆成可獨立整合的 PR，判斷是否需要特殊技巧，並依 Skill 的固定格式說明每個 PR merge 後 main 為什麼仍可工作、branch 預估活多久。
```

### 回答

模式是需求拆分規劃；適用「TBD 核心規則檢查清單」、「TBD 需求拆分檢查清單」、「TBD 策略選擇檢查清單」、「TBD 來源分級檢查清單」與「TBD 案例參考」。需要 Feature Flag，因為程式要在週五前部署，但功能要延後曝光；Deploy 與 Release 分開處理。

PR 1：加入帳單匯出契約、資料模型與預設關閉的功能開關 — 使用技巧：Feature Flag

PR 2：加入匯出 API 與權限檢查，接上既有資料流程 — 使用技巧：Feature Flag

PR 3：加入下載頁面與 client 呼叫；開關關閉時不顯示入口 — 使用技巧：Feature Flag

PR 4：加入帳單匯出操作追蹤，僅在功能開啟且權限通過的匯出流程送出事件 — 使用技巧：Feature Flag

PR 5：加入 API、權限、頁面、追蹤的整合與回歸測試，驗證開關關閉與開啟兩種狀態 — 使用技巧：Feature Flag

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 只增加相容的契約、設定與測試，既有使用流程沒有改變。
- PR 2 的新 endpoint 受預設關閉的開關與權限檢查保護；既有 API 與既有頁面不受影響。
- PR 3 的入口在開關關閉時不曝光；即使程式已部署，使用者仍走原本可工作的頁面。
- PR 4 只在受保護的匯出流程送出追蹤；其他操作不依賴此功能。
- PR 5 是驗證與回歸測試，功能仍維持關閉直到驗證完成。

每支 PR 都從最新 main 開短期 branch，完成 review、必要的 build/lint/unit/integration test 且 CI green 後合併，合併後刪除 branch。週五通過驗證後才開啟 flag；功能穩定後安排移除 flag。開關名稱、權限模型與 rollout 方式是團隊決策，題目沒有提供。

預估 branch 壽命（含等 review）：每支約半天至一天，目標在同一工作日完成；題目沒有提供 review 與 CI SLA，因此實際含 review 壽命未知。TBD 官方常見短期 branch 約 1–2 天；DORA 的少於 1 天是較嚴格目標，不是 TBD 官方硬性門檻。

## S2

### 實際輸入

```text
現有產品所有呼叫都直接依賴舊的 REST client，團隊想在一週內換成新的 GraphQL client，但不能讓 main 進入「部分呼叫已換、部分呼叫已壞」的狀態。請用 trunk-based-development 規劃每日可 merge 的步驟，指出應使用的技巧，以及每一步的可工作理由。
```

### 回答

模式是需求拆分規劃，且是大型相容性遷移；適用「TBD 核心規則檢查清單」、「TBD 需求拆分檢查清單」、「TBD 策略選擇檢查清單」、「TBD 來源分級檢查清單」與已載入的「TBD 案例參考」。使用 Branch by Abstraction，並讓舊 REST 與新 GraphQL 新舊並存；GraphQL 在所有 caller 驗證完成前維持安全預設，必要時以 Feature Flag 控制 runtime rollout。Feature Flag 的名稱與 rollout 方式由團隊決定。

PR 1（Day 1）：建立 HTTP/client abstraction 與共同 contract tests — 使用技巧：Branch by Abstraction、新舊並存

PR 2（Day 2）：讓既有 REST client 實作 abstraction，先保留所有 caller 的既有直接行為 — 使用技巧：Branch by Abstraction、新舊並存

PR 3（Day 3）：加入 GraphQL implementation，通過同一組 contract tests；REST 仍是預設實作 — 使用技巧：Branch by Abstraction、新舊並存、（需要 runtime 漸進發布時）Feature Flag

PR 4（Day 4）：將第一個低風險 caller 小批次改接 abstraction — 使用技巧：Branch by Abstraction、新舊並存

PR 5（Day 4–5）：將下一個 caller 小批次改接 abstraction；其餘 caller 依相同邊界各自拆成短期 PR，不把所有 caller 合在一支 branch — 使用技巧：Branch by Abstraction、新舊並存

PR 6（Day 5）：所有 caller 都通過 contract、integration 與必要的行為驗證後，移除 caller 對舊 REST client 的直接依賴 — 使用技巧：Branch by Abstraction、新舊並存

PR 7（完成驗證後）：移除不再被使用的舊 REST implementation；若仍有未遷移 caller，延後此 PR — 使用技巧：Branch by Abstraction

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 是新增 abstraction 與測試，不改既有 caller；main 可照舊 build、test、運作。
- PR 2 讓 REST 走 abstraction，但行為與預設路徑不變；既有 caller 不會遇到缺少實作的介面。
- PR 3 只增加經過 contract 驗證的 GraphQL 實作，REST 仍保留且是安全預設；GraphQL 尚未通過驗證時不切換 caller。
- PR 4 與 PR 5 每次只切換一個已界定的小批次 caller；未切換的 caller 繼續使用 REST，已切換的 caller 也有 REST fallback 或安全預設。
- PR 6 只有在所有 caller 已改接並通過驗證後才移除直接依賴；不會形成 caller 與 client 不匹配的中間狀態。
- PR 7 只有在確認沒有 caller 依賴舊 implementation、CI green 且必要整合測試通過後才刪除舊實作；否則保留新舊並存。

每日流程是：從最新 main 開短期 branch，完成一個可驗證的小批次，執行對應 build/lint/unit/contract/integration test，經 review 與 CI green 後 merge；merge 前重新同步 main，merge 後刪除 branch。不能把一週工作放在單一 `refactor/graphql` branch 後一次替換。

預估 branch 壽命（含等 review）：每個 abstraction、adapter、implementation 或 caller 小批次約半天至一天，含 review/CI/merge；實際 review 時間未提供，因此實際壽命未知。TBD 官方常見短期 branch 約 1–2 天；DORA 的每日整合與少於 1 天是較嚴格建議，不把它們寫成官方硬限制。

## S3

### 實際輸入

```text
團隊有長期存在的 develop 分支；某個 feature branch 已活 9 天，CI 目前失敗。生產環境仍在 2026.10，main 已開始 2026.11 的開發；現在發現一個只影響 2026.10 的 bug。請審查這個 workflow 是否符合 TBD，列出應先處理的問題與修正順序，並說明 bug 應在哪裡修以及如何帶回發布分支。
```

### 回答

模式是 workflow 審查，並涉及已發布版本的 hotfix；適用「TBD 核心規則檢查清單」、「TBD 需求拆分檢查清單」、「TBD 策略選擇檢查清單」、「TBD 流程審查檢查清單」、「TBD 來源分級檢查清單」與已載入的「TBD 案例參考」。目前不能宣稱整體 workflow 符合 TBD；已有具體違規，另有多項證據不足。

已知證據與判斷：

- 長期存在的 `develop` 是長期共同開發分支，違反 TBD 圍繞單一 main/trunk 持續整合的核心方向。
- 活 9 天的 feature branch 違反短命 branch 與小批次持續整合的核心方向；9 天已包含題目未拆出的 review 等待時間，細項仍未知。
- 「CI 目前失敗」需要先確認失敗的是 main 還是 feature branch。若是 main，main 不可工作，違反 main 必須保持可工作的核心規則；若只有 feature branch 失敗，該 branch 尚不具備合併條件，但不能把它當成 main 已紅的事實。
- 未提供每人整合 main 的頻率、active branch 數量、review 等待時間、CI 回饋速度、是否 code freeze、是否有 gated build/test，以及 feature flag 清理狀態；這些列為未知，不能用枝節證據宣稱整體已是 TBD。

修正順序：

1. 先確認 CI 失敗的目標與根因。若 main 是紅的，立即停止新變更合併，修復或 revert 造成破壞的變更，直到 main build/test/必要驗證恢復 green。若只有 9 天 feature branch 是紅的，先修該 branch，並另外確認 main 狀態；不能把 feature branch 的失敗帶進 main。
2. main green 後，在 main 修正 2026.10 bug，補回歸測試並通過 review、CI 與必要驗證。這是 fix on trunk first；不要只在發布分支修完再把一大包變更回灌 main。
3. 將同一個已驗證的 bug 修正 cherry-pick 到對應的 `release/2026.10`（若團隊既有發布分支名稱不同，使用其既有命名），重新確認該發布分支的 CI 與發布驗證。`release/2026.10` 只承載 2026.10 的穩定、bug fix 與發布，不加入 2026.11 新功能。
4. 停止把 `develop` 當作共同整合分支，將仍需保留的工作拆成從最新 main 開出的短期 branch/PR；先保留可工作的中間狀態，逐批 merge，merge 後刪除 branch，不用 code freeze 解決整合問題。
5. 把 9 天 feature branch 拆成可驗證、可回復的小批次。每個 PR merge 前同步最新 main，完成 review、必要 build/lint/unit/integration test 與 CI green；若目前 branch 內容無法安全拆分，先保留可回復的切分邊界，再逐支合併。
6. 補齊導入前提與證據：自動 build/test 與 gated checks、足夠快速的 CI、快速 code review、小批次能力、broken-trunk 優先修復紀律，並量測整合頻率、branch 含 review 的壽命與 active branches。未具備這些前提前，不直接宣稱已完成 TBD 導入。

來源區分：TBD 官方核心要求單一 trunk、main 保持可工作、短期 branch 與在已發布版本情境以 trunk 修正後帶回 release branch；DORA 的每日整合、branch 少於一天與快速 CI 是較嚴格建議，不能冒充 TBD 官方硬限制；`develop` 是否退役、發布分支的實際命名、reviewer、merge/cherry-pick 的團隊流程屬團隊決策。
