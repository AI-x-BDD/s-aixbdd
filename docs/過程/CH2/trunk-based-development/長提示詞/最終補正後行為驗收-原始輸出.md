### 實際回答

特殊技巧：使用預設關閉的 Feature Flag。四個工作天的功能拆成小批次後每天合入 main；週五才開放是 Deploy 與 Release 的時間差，不能用長期 feature branch 等待曝光。題目沒有大型重構或相容性遷移，策略選擇只需要 Feature Flag。

PR 1：建立帳單匯出契約、相容的 API 入口與預設關閉的 Feature Flag — 使用技巧：Feature Flag
PR 2：實作匯出 API、權限檢查與後端單元測試；flag 關閉時不提供匯出流程 — 使用技巧：Feature Flag
PR 3：加入下載頁面與 client 端 flag／route guard；flag 關閉時頁面不可見 — 使用技巧：Feature Flag
PR 4：加入操作追蹤／稽核事件與測試，只有啟用匯出流程時才觸發 — 使用技巧：Feature Flag
PR 5：加入整合測試與失敗回復檢查；測試環境可明確開啟 flag，正式環境仍關閉 — 使用技巧：Feature Flag
PR 6：週五完成驗證後只提交開啟 flag 的設定變更；功能穩定後安排移除 flag — 使用技巧：Feature Flag

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 只增加向後相容的契約、入口與關閉中的開關，既有帳單流程不變。
- PR 2 的新 API 與權限檢查在 flag 關閉時不改變既有使用者路徑；單元測試通過後才合入。
- PR 3 的頁面與路由受同一個關閉中的 flag 保護，既有頁面不會進入未完成的匯出流程。
- PR 4 只在匯出流程啟用時寫入追蹤資料，既有操作不受影響，相關測試隨 PR 驗證。
- PR 5 在測試環境開 flag 驗證跨元件流程，正式環境仍可維持安全的關閉狀態；CI green 後才合入。
- PR 6 只有在前述程式已通過驗證後開放功能；若發現問題可關閉 flag，main 仍保留可工作的既有流程。

預估 branch 壽命（含等 review）：每個 PR 以半天至一天完成並等待 review，merge 前同步最新 main，merge 後刪除 branch；題目未提供實際 review 等待時間，所以實際壽命未知。官方常見短期 branch 約 1–2 天，DORA 以少於 1 天為目標，兩者都是來源分開標示的參考，不是本題可確認的實際值。

來源與未知限制：四個工作天與週五開放是題目事實；小批次、main 每次合入仍可工作與 Feature Flag 是 TBD 官方規則；少於一天與快速回饋是 DORA 較嚴格建議；flag 名稱、rollout、reviewer 與設定 PR 的形式是團隊決定。review 時間、CI 速度、既有 flag 能力與部署流程未知。

### 實際輸入

共同指示：

### 實際回答

特殊技巧：使用 Branch by Abstraction，並在遷移期間採新舊並存。先讓 REST 實作留在安全預設，再加入 GraphQL、逐批切換 callers，最後才移除 REST。若需要逐批啟用或快速回復，可由團隊決定加入 client selector／Feature Flag；題目本身只要求 main 可工作，不能把它當成已知必要條件。

PR 1（第 1 天）：建立共用 client abstraction 與 contract tests，不改既有 caller — 使用技巧：Branch by Abstraction／新舊並存
PR 2（第 2 天）：讓舊 REST client 實作 abstraction，保留相容 adapter；既有直接呼叫仍以 REST 為預設 — 使用技巧：Branch by Abstraction／新舊並存
PR 3（第 3 天）：把第一批 callers 移到 abstraction，但仍使用 REST 實作；剩餘 callers 維持原路徑 — 使用技巧：Branch by Abstraction／新舊並存
PR 4（第 4 天）：加入 GraphQL implementation 與同一套 contract tests，client selector 預設仍選 REST — 使用技巧：Branch by Abstraction／新舊並存
PR 5（第 5 天）：按 caller 群組分成小 PR，逐批由 selector 切到 GraphQL，保留 REST fallback — 使用技巧：Branch by Abstraction／新舊並存
PR 6（第 6 天）：把剩餘 callers 逐批切到 GraphQL，確認沒有直接依賴 REST 的 caller — 使用技巧：Branch by Abstraction／新舊並存
PR 7（第 7 天或驗證完成後）：在 caller 搜尋、contract／integration test 與 CI 都確認 green 後移除 REST adapter 與舊 client — 使用技巧：Branch by Abstraction

每個 PR merge 後 main 為什麼仍可工作：

- PR 1 沒有改 callers，既有 REST 路徑照常運作；contract tests 先定義新舊實作必須滿足的行為。
- PR 2 讓 REST 接上 abstraction，既有呼叫仍走 REST，行為與安全預設不變。
- PR 3 只移動已驗證的 caller 群組，這些 callers 仍由 REST 支援，尚未移動的 callers 仍走舊路徑。
- PR 4 只新增 GraphQL 實作，通過相同 contract tests；selector 預設 REST，所以 GraphQL 尚未穩定時不會改變 main 的既有路徑。
- PR 5 與 PR 6 每次只切換已驗證的 caller 群組；GraphQL 失敗時可回到 REST，未切換的呼叫仍可工作，不會形成「已換但壞掉」的中間狀態。
- PR 7 只有在所有 callers 已不再依賴 REST 且 CI、integration test 都 green 後才移除舊實作，合入後 main 由 GraphQL abstraction 提供完整路徑。

預估 branch 壽命（含等 review）：每個日批次以半天至一天完成並等待 review；每次從最新 main 開 branch，merge 後刪除。題目未提供 review 與 CI 時間，實際壽命未知；官方短期 branch 約 1–2 天，DORA 以少於 1 天為目標，這些是分開的參考門檻，不是題目已證實的數值。

來源與未知限制：所有 callers 直接依賴 REST、要在一週內遷移且 main 不可壞是題目事實；abstraction、舊實作先保留、新實作、caller 分批切換、最後移除是 TBD 官方的 Branch by Abstraction／新舊並存規則；每日整合、少於一天與快速 CI 是 DORA 較嚴格建議；selector、fallback、caller 分組與切換順序是團隊決策。caller 數量、schema 相容性、CI 速度、review 等待及 GraphQL 的實際完成度未知。

本題：

團隊有長期存在的 develop 分支；某個 feature branch 已活 9 天，CI 目前失敗。生產環境仍在 2026.10，main 已開始 2026.11 的開發；現在發現一個只影響 2026.10 的 bug。請審查這個 workflow 是否符合 TBD，列出應先處理的問題與修正順序，並說明 bug 應在哪裡修以及如何帶回發布分支。

### 實際回答

審查結論：依已知證據，這個 workflow 不符合 TBD 的核心方向。長期存在的 `develop` 是長期共同整合分支；9 天的 feature branch 顯示工作沒有拆成短期、可持續整合的小批次；CI 失敗時不能進行未經判斷的 merge。CI 失敗的 ref 尚未提供，因此不能直接把它說成 main 已紅，也不能因為它可能只是 feature branch 就當作沒有問題。

已知不符合項與證據：

- `develop` 長期存在：與所有人圍繞單一 main、避免長期共同開發分支的 TBD 官方核心規則衝突。它的長期存在本身是輸入事實；目前是否仍承載整合工作、有哪些 commit 尚未移出則未知。
- feature branch 活 9 天：與短命 branch、Story 拆成可獨立合入的小批次的方向不符，至少是 branch 過大或整合延遲的強烈證據。官方常見短期 branch 約 1–2 天；DORA 以少於 1 天為目標，這兩個來源都不是「9 天即違反」的單一硬性數字，但本題已知 9 天應先處理。
- CI 目前失敗：main 紅時必須先修復或 revert，不能繼續堆新變更；若只有 feature branch 紅，則該 branch 尚未具備合併條件，應先修好並另外確認 main 狀態。失敗對象、失敗原因與回饋速度未知。

導入與修正前提：需要自動 build、unit／必要的 integration test、PR review、CI green 的 gated check、足夠快速的 CI 回饋，以及 main 紅時優先修復的團隊紀律。這些前提目前沒有完整證據，不能只因存在 branch 或 PR 就宣稱整體已是 TBD。

修正順序：

1. 先確認 CI 失敗的 ref 與原因。若是 main，暫停非必要合併，立即修復或 revert 造成破壞的變更並恢復 green；若是 feature 或 develop，先修該 branch，並獨立確認 main 是否 green，不能把兩者混為同一件事。
2. 在 main 狀態確認後，停止把長期 `develop` 當共同整合入口。盤點其中的工作，從最新 main 將可工作的部分拆成短期 PR；各 PR 經 review、CI green 後合入並刪除 branch，完成遷移後依團隊政策退役 `develop`。
3. 將 9 天 feature branch 拆成可驗證、可回復、可獨立合入的小批次；每批先同步最新 main，修到 branch green，再依 PR → review → CI green → merge 順序進入 main。等待 review 也算 branch 壽命；不要用 code freeze 把整條 branch 留到最後一次整合。
4. 補齊 gated checks、快速回饋與 broken trunk 的處置規則，並記錄每日整合與 review 時間。DORA 的每日整合與少於一天是較嚴格建議，應和 TBD 官方核心規則分開追蹤，不冒充硬性官方門檻。

2026.10 bug 的修法：

1. 在目前的 main 上建立最小 bug-fix PR，補回歸測試，經 review 與 CI green 後合入。即使 bug 只影響 2026.10，也先讓 main 擁有同一個修正，避免 2026.11 漏掉已知修復。
2. 找到或依團隊發布政策建立對應的 `release/2026.10`；題目沒有證實該 branch 已存在，命名與建立方式屬團隊規則。把 main 上已驗證的同一修正 cherry-pick 到 `release/2026.10`，再在該 release branch 驗證並發布。
3. `release/2026.10` 只承載 2026.10 的穩定、bug fix 與發布；main 繼續 2026.11 開發。不要只在 release branch 修完後，把整條發布分支一次回灌 main。

來源與未知限制：長期 `develop`、9 天 feature、CI 失敗、production 2026.10 與 main 的 2026.11 是題目事實；單一 trunk、main 保持可工作、小批次與已發布版本先修 main 再 cherry-pick 到 release branch 是 TBD 官方規則；每日整合、少於一天、快速 CI 與 broken trunk 優先是 DORA 較嚴格建議；branch 命名、merge 方式、reviewer、release branch 建立與發布政策是團隊決策。CI 失敗 ref／原因、整合頻率、active branch 數量、review 等待、CI 速度、code freeze、flag 清理與 `release/2026.10` 是否存在未知。
