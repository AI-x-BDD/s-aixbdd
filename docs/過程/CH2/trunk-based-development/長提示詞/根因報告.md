# 根因報告：trunk-based-development－判斷規則模組化

- 紀錄目錄：`docs/過程/CH2/trunk-based-development/長提示詞/`
- 問題證據：`蒐證與前置診斷.md`、`前置結構診斷-原始輸出.json`、`.agents/skills/trunk-based-development/SKILL.md`、`.agents/skills/trunk-based-development/references/cases.md`、CH1 的 TBD 使用紀錄
- 模式：優化既有 Skill
- 狀態：待 `/root` 審核；尚未修改目標 Skill

## 1. 使用者回報的問題

使用者要求最佳化既有 `trunk-based-development`，保留原本用途與正確規則，將適合抽出的判斷規則模組化為按需載入的 RuleFile。驗收必須能直接檢查規則與正反例、`READ` 載入條件、具名清單、載入後如何使用，以及 `CHECK`；不得為了增加檔案數硬拆。使用者另要求修改前後用相同設定與判準在乾淨隔離環境實跑，保存輸入、原始輸出、前後差異與限制。

目前沒有足以判定既有語意規則錯誤的獨立執行結果；本報告把已查核的落差定性為結構缺口，將待外層安排的乾淨行為實跑列為待補證據。

## 2. 驗收條件

| 編號 | 驗收條件 | 來源 | 適用範圍 | 驗收情境 |
| ---- | -------- | ---- | -------- | -------- |
| E1 | 目標 `SKILL.md` 有唯一的 `# SOP`，以連續編號的 Phase、受控動詞步驟與可檢查的 Phase 完成條件描述從接收需求到交付判斷的流程 | 本次 | 通用 | S4，以及 S1–S3 的流程輸出 |

| E3 | SOP 只在任務涉及相應判斷主題時，以 `READ` 明列需載入的 RuleFile／案例資源，建立有名字的檢查清單；檔案路徑不以無條件背景閱讀取代 | 本次 | 通用 | S4，以及 S1–S3 |

| E5 | 回答仍區分 TBD 官方、DORA 與團隊規則，保留官方約 1–2 天與 DORA 不到一天的差異，不把團隊選項說成 TBD 硬性要求 | 既有 | 通用 | S1、S3 |

## 4. 演練表

以下依本次驗收預期的最小執行順序演練現有 Skill；「一致」只表示現有內容已表達該產出，不表示已有可執行 SOP。

| 步驟 | 應載入 | 實際載入 | 應產出 | 實際產出 | 判定 |
| ---- | ------ | -------- | ------ | -------- | ---- |
| P1-1 `READ` | 使用者需求與目標 Skill | 觀察：讀得到 frontmatter 與主檔；沒有 `# SOP` 入口 | 確定本次是需求規劃或 workflow 審查，並保留輸入限制 | 觀察：只有 description，沒有受控步驟或模式判定 | 偏離 |
| P1-2 `THINK` | 本次任務的輸入、目的與適用分支 | 觀察：主檔散落規劃流程、Decision Tree 與審查清單 | 確定要走的判斷路徑與必要資訊 | 觀察：文字可供模型臨場選取，但沒有 SOP 步驟、停止條件或完成條件 | 無證據 |
| P1-3 `READ` | 只在需要時載入判斷 RuleFile／案例資源，並建立具名檢查清單 | 觀察：沒有 `rules/`；`references/cases.md` 只由主檔連結，沒有 `READ` 載入條件或名稱 | 具名的規則／案例檢查清單 | 觀察：無具名清單 | 偏離 |
| P1-4 `THINK` | 已載入檢查清單 | 無載入結果可供引用 | 依檢查清單判斷小批次、技巧與來源分級 | 觀察：有 Decision Tree 與技巧條列，但無法證明使用了某個載入結果 | 無證據 |
| P1-5 `WRITE` | 判斷結果的固定輸出格式 | 觀察：主檔第 40–47 行提供 `PR 1`、技巧、main 可工作理由與 branch 壽命格式 | 產出可追蹤的規劃／審查結果 | 觀察：固定格式文字存在，但沒有流程要求每次使用 | 一致 |
| P1-6 `CHECK` | 逐條驗證已載入規則、來源分級、情境判斷與輸出格式 | 觀察：主檔第 107–114 行有送出前檢查清單，但無 `CHECK` 步驟或檢查結果格式 | 可查核的交付前驗證結果 | 觀察：沒有受控 `CHECK` 或完成條件 | 偏離 |

第一個偏離點：P1-1，`SKILL.md` 沒有 `# SOP`，因此沒有可執行的入口、步驟順序與完成條件。P1-3 與 P1-6 是在該缺口下進一步暴露的模組載入與驗證落差。

## 5. 根因

| 編號 | 位置 | 缺陷類型 | 說明與證據 | 反事實檢驗 |
| ---- | ---- | -------- | ---------- | ---------- |
| R1 | `trunk-based-development`／`SKILL.md` 第 6–114 行；整份檔案缺少 `# SOP` | 流程缺陷 | 觀察 O1、O2 顯示主檔只有參考內容，沒有 `READ`、`THINK`、`WRITE`、`CHECK` 的有序流程、停止分支與完成條件；因此 E1、E3、E4 沒有可執行載體 | 推論：若只補上可執行 SOP，仍須另有 RuleFile 才能滿足 E2；但 SOP 可使模式判定、條件載入、具名清單使用與交付檢查成為可追蹤步驟。R1 是必要但單獨不足的根因 |
| R2 | `trunk-based-development`／`SKILL.md` 第 18–114 行；`trunk-based-development/references/cases.md` 第 1–117 行 | 缺失 | 觀察 O3、O4 顯示持續適用且需要判斷的規則都留在主檔，現有案例檔也沒有 RuleFile 的固定 Rule／正反例結構；因此 E2 缺少可按需載入與獨立檢查的規則載體 | 推論：若只建立帶正反例的主題 RuleFile，仍沒有 SOP 來決定何時 `READ`、如何命名清單、如何使用與 `CHECK`；但補足 RuleFile 可使 E2 成立。R2 是必要但單獨不足的根因 |

兩個根因共同解釋 E1–E4 的結構落差；目前沒有證據支持把 E5–E8 的既有語意判定本身列為根因。

## 6. 被排除的假設

| 假設 | 缺陷類型 | 排除依據 |
| ---- | -------- | -------- |
| H1：落差只是模型臨場能力或輸入不足 | 非 Skill 問題 | 觀察 O1、O2 由檔案與結構診斷直接核對到缺少 `# SOP`；不依賴模型如何回答，因此不能以模型問題解釋此結構落差 |
| H2：`references/cases.md` 已經可以代替 RuleFile | 載體過弱 | 觀察 O4 顯示它沒有 `# Rule N`、`Good Example`、`Bad Example` 固定結構，也沒有載入條件與具名檢查清單，無法直接滿足 E2–E4 |
| H3：只要保留主檔的「送出前檢查」就已經有 `CHECK` 流程 | 不可檢查 | 觀察 O3 與演練 P1-6 顯示那是編號清單文字，不是受控 `CHECK` 步驟，也沒有指出檢查結果如何回到流程完成條件 |
| H4：應為每個案例各建立一個檔案，檔案數越多越完整 | 流程缺陷 | 觀察 O4 顯示案例已集中於同一份資源，且本次需求明確要求不為湊檔案數硬拆；現有證據不支持把案例數量當成模組化品質 |
| H5：目標 Skill 的問題需要同步修改其呼叫者 | 交接缺陷 | 前置 `audit_skill.py --graph` 的 `callers` 對 `trunk-based-development` 為空；未查到直接或間接委派者 |

## 7. 影響範圍

結構診斷的呼叫圖顯示沒有其他 Skill 委派 `trunk-based-development`，因此直接與間接呼叫者為「無」。影響集中在本 Skill 的觸發後流程、規則載入、判斷檢查與輸出一致性；CH1 既有紀錄顯示使用者仍能取得部分正確判斷，但執行順序與是否規劃分支會依臨場上下文變動（觀察 O5、O6）。
