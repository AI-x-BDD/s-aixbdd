# 共同測試輸入與判準

在重構開始前固定；判準由原版 Skill 主檔與 references/cases.md 推導，只用於行為保持驗證，不代表已核對外部官方資料。每版以相同順序測試，判準對執行代理隱藏，由主代理事後評分。各版是新代理，同一版內案例共享上下文。

## S1：小型修錯

輸入：按鈕顏色錯誤，修正加測試約 30 分鐘。請規劃 PR、分支與整合方式。

判準：短期 branch、小變更、測試／review／CI／merge，無須特殊技巧；說明 main 可工作與 branch 壽命。

## S2：三天功能

輸入：會員搜尋需三天，包含 API client、輸入框、基本搜尋、分頁與權限。功能完成前不能曝光。請拆 PR 與安排整合。

判準：拆成可獨立整合的小 PR，非三天長分支；未完成內容可用 flag；main 每步可工作；branch 壽命含 review。

## S3：HTTP 遷移

輸入：Axios 換 Fetch wrapper 需一週，不能中斷現有功能。請安排每天可 merge 的步驟。

判準：Branch by Abstraction：抽象、舊實作接入、新實作、漸進切換、清理；每步 main 可工作。

## S4：API 相容遷移

輸入：後端 API 與前端 consumer 由不同人改，不能同時完成，整體需三天。如何分批整合？

判準：新舊 API 並存、consumer 遷移後移除舊 API；不讓 main 出現 consumer 失配。

## S5：一週功能

輸入：新的操作介面週五才開放，週一 UI、週二 API、週三驗證、週四追蹤。如何每天整合且避免提早曝光？

判準：Feature Flag 關閉仍每天整合，部署與開放區分，上線穩定後清旗標。

## S6：舊版 hotfix

輸入：production 是 1.5，main 是 1.6，兩邊都有同一個 bug。如何修與發佈 1.5？

判準：main 先修及驗證，再 cherry-pick release/1.5；release 僅穩定／bugfix／發布，不開發新功能。

## S7：review 與規則來源

輸入：我們 PR 都很小，但 review 常等三天。只要 branch 不超過兩天就是符合 TBD 的硬性標準嗎？

判準：branch 壽命含 review；三天為問題；官方通常 1–2 天，DORA <1 天，不當兩天硬標準。

## S8：團隊選擇

輸入：團隊採 merge commit、同步 main 用 merge、允許直接 push、有時一位 reviewer。這些是否違反 TBD？

判準：這些屬團隊決策，不能據此斷言違反 TBD；仍檢視短命分支、頻繁整合、main 健康。

## S9：workflow 審查

輸入：我們 main CI 紅了晚上再修，develop 持續兩週才整合，release 前 code freeze。請審查並提出優先處理。

判準：指出長期開發分支、整合不頻繁、broken trunk 應立即修或 revert、freeze 問題。

## S10：導入前提及 GitFlow

輸入：我們沒有自動 build/test，review 常耗幾天，新手為主。想明天全面從 GitFlow 換 TBD。你如何建議並解釋兩者差別？

判準：先補自動化、快速 CI、小批次、快速 review 與 broken trunk 紀律，不直接全面導入；GitFlow 先隔離完成再整合，TBD 切小持續整合。
