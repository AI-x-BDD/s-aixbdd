# 原有規則保持清單

依基準版本的 SKILL.md 與 references/cases.md 整理。此為外層驗收清單，不提供施工代理；用來核對語意搬移是否完整，不新增既有行為。

- C1：核心目的為單一 trunk、沒有長期開發分支、持續小批次整合，main 可工作且可發布。
- C2：區分 TBD 官方、DORA 與團隊規則；官方短期 branch 通常 1–2 天、DORA <1 天，兩天非硬標準。
- C3：至少每日整合；broken trunk 優先，立即修復或 revert。
- C4：短命 branch、少量 active branches、不靠 code freeze 解決整合、merge 後刪 branch。
- C5：squash／merge commit／rebase merge、同步方式、命名、reviewer 人數、平台、direct push 屬團隊決策。
- C6：規劃先拆獨立小變更；Story／Ticket 不等於單一 branch 或 PR。
- C7：每個小變更短期 branch，工作期間同步 main，merge 前保持最新。
- C8：CI 的 build、lint、unit test、必要 integration test，PR／review／green／merge；DORA 每 commit build 與測試且幾分鐘回饋。
- C9：規劃輸出含每個 PR 的變更與技巧、每步 main 可工作理由、branch 壽命且包含等 review。
- C10：一天內可完成則短期 branch；否則先嘗試切小，再按曝光、重構、相容遷移、已發布版本選技巧。
- C11：Feature Flag 允許未完成功能每日整合，部署不等於發布，穩定後清旗標。
- C12：Branch by Abstraction：建立抽象、舊實作接入、新實作、逐步切換、刪舊，每步 merge。
- C13：新舊 API 並存、consumer 遷移、再刪舊 API，避免 main 不相容的中間態。
- C14：Release branch 晚切，只負責穩定、bugfix 與發布，不承載新功能。
- C15：Bug 先 main 修及驗證再 cherry-pick release；只修 release 再回灌為原版列出的錯誤模式。
- C16：長 feature branch 不能只因從 main 分出就稱為 TBD；兩三週、多人成天共用 feature branch 不合原版要求。
- C17：branch 壽命必須包含 review 等待，PR 小但 review 等三天仍是整合阻礙。
- C18：workflow 審查檢查長期共同分支、每日整合、壽命與 active branches、CI／broken trunk、freeze、旗標清理。
- C19：導入前提：自動 build／test、快速 CI、小批次、快速 review、broken trunk 紀律；不足時先指出缺口，不直接全面導入。
- C20：適用情境與頻繁發布／多人維護／需求變化的價值敘述保留，不擴大或縮減用途。
- C21：GitFlow 先隔離完成再整合；TBD 先切小、持續整合、main 可工作，主要改變工作拆分。
- C22：交付前檢查一天內整合、main 健康、flag、abstraction、CI、隔日 branch 是否切太大。
- C23：六個原案例保留可追溯內容：小 bug、三天會員搜尋、Axios → Fetch、Vuex → Pinia、一週功能、舊版 hotfix。
- C24：frontmatter 用途與觸發範圍保留；引用外部來源與既有來源區分保留。
