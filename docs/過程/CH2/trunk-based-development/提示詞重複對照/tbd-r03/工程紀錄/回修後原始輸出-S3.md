規則來源與判斷：

- **TBD 官方（TrunkBasedDevelopment.com）**
  - 以單一 `main` 作整合主線，不建立長期 `develop` 開發線。
  - 小批次、短期 branch、持續整合，`main` 隨時保持可工作。
  - 官方通常將短期 branch 置於約 1～2 天；「兩天是國際硬性標準」是錯誤說法。
- **DORA**
  - 至少每天整合，最好一天多次。
  - 每個 commit 觸發 build 與自動測試，幾分鐘內回饋。
  - broken trunk 應立即修復或 revert。
  - 以 branch 少於一天為目標，但這是目標，不是硬性門檻。
- **團隊自行決定**
  - `squash`、同步時使用 `rebase` 或 `merge`、reviewer 人數、是否禁止 direct push、branch 命名與平台，均不是 TBD 必要規則。

目前問題：

1. `develop` 每週五才合併 `main`，是長期開發線與低頻整合，屬於 GitFlow 類做法，不符合 TBD 的單一 trunk 與頻繁整合。
2. PR 實作兩小時但 review 等三天，branch 壽命必須把等待 review 算入，實際至少約三天；沉重且非同步的 review 是導入 TBD 的阻礙。
3. `main` CI 紅了仍先做新功能，違反 broken trunk 優先修復原則，應立即修復或 revert。
4. 沒有自動測試，缺少安全持續整合的基本前提，不能只靠改 branch 規則就明天全面導入。
5. 兩位 reviewer、禁止 direct push、強制 squash/rebase 可以是團隊治理選擇，但不能宣稱是 TBD 規定。
6. Feature Flag 的使用與用後清理狀態尚未提供，必須列為待確認項目，不能自行推定。

導入前提：

- 先建立每個 commit 的自動 build、測試與 gated checks，並把 CI 回饋縮短到幾分鐘。
- 建立 `main` 紅燈立即修復或 revert 的團隊紀律。
- 把 review 流程縮短到能支援每日整合。
- 培養把需求拆成可獨立合併的小變更的能力；不能日內完成時，依原因採用 Feature Flag、Branch by Abstraction、新舊並存或 Release Branch。
- 先以小範圍試點，確認團隊經驗、小批次開發與自動化檢查都足夠，再逐步擴大，不宜明天直接全面切換。

TBD 與 GitFlow 的差異：

- GitFlow 類做法先用 `develop`、feature 或 release branch 隔離工作，功能完成後再整批整合。
- TBD 先把工作切小，持續整合到單一 `main`，並要求整合後任何時候都可工作。
- 兩者可以使用相同的 Git 操作；是否 `squash` 或 `rebase` 不是區分 TBD 與 GitFlow 的依據。TBD 主要改變工作拆分與整合頻率。

2.7 修正與整合：

1. 若尚不存在，從 2.7 發布 tag 建立 `release/2.7`。
2. 從目前的 `main` 開短期 branch，先修正 bug、補自動測試，送 PR 合入 `main`。
3. `main` 驗證通過後，將相同修正 `cherry-pick` 到 `release/2.7`，執行 CI 與回歸測試，再發布 2.7.1。
4. `release/2.7` 只處理 2.7 的穩定、bug fix 與發布，不承載 2.8 新功能；不要只在 release branch 修完再把一大包修改回灌 `main`。

```text
PR 1：在 main 修正 2.7 bug 並補測試
      — 使用技巧：無（短期 branch）

PR 2：將已驗證修正 cherry-pick 到 release/2.7
      — 使用技巧：Release Branch

每個 PR merge 後 main 為什麼仍可工作：
PR 1 先讓 main 擁有已驗證的修正；PR 2 只維護已發布的 2.7，不能破壞 main。

預估 branch 壽命（含等 review）：
每個修正 PR 目標在一天內完成；目前 review 排三天會使實際壽命至少約三天，應先改善 review 流程。
```
