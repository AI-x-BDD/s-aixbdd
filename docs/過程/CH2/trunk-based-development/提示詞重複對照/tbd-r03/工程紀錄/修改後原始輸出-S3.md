目前流程不能直接全面導入 TBD，因為缺少自動測試、快速 CI、gated checks、快速 review，以及 broken trunk 優先修復的紀律。

### 規則來源與判斷

| 項目 | 規則來源 | 判斷 |
|---|---|---|
| `develop` 共同開發線、每週才合 `main` | TBD 官方核心方向 | 長期開發線且延後整合，較接近 GitFlow，不符合單一 `main` trunk 與頻繁整合 |
| 每天至少整合一次 | DORA 建議 | 應以每天至少一次為基準，一天多次更好 |
| PR 寫兩小時、review 等三天 | TBD 官方／DORA | branch 壽命必須包含等待 review；實際至少三天，重量級 review 是 TBD 的阻礙 |
| CI 紅了仍先做新功能 | TBD／DORA | 應立即修復 `main` 或 revert，不能晚上再處理 |
| 沒有自動測試 | 導入前提 | 未具備安全導入條件，直接全面切換會增加錯誤與返工風險 |
| squash、rebase、merge commit | 團隊自行決定 | TBD 沒有規定一定要 squash 或 rebase |
| 同步 `main` 用 merge 或 rebase | 團隊自行決定 | 不是 TBD 必要條件 |
| 兩位 reviewer | 團隊自行決定 | 可以是團隊政策，但不是 TBD 規則 |
| 禁止 direct push | 團隊自行決定 | 可搭配 protected `main` 與 gated checks，但不是 TBD 必要條件 |
| branch 兩天 | TBD 官方／DORA | 官方通常約 1～2 天；DORA 以不到一天為目標。兩天不是硬性的國際標準 |

導入前應先建立自動 build、每個 commit 觸發的自動測試、幾分鐘內回饋的 CI、gated checks、`main` 紅燈立即修復或 revert 的流程，並把工作拆成一天內可獨立合併的小批次。review 也要縮短，否則即使 PR 實作只需兩小時，整體仍是三天的長分支。建議先以低風險範圍試行，再逐步擴大。

TBD 與 GitFlow 的差異在工作拆分與整合方式：

- GitFlow 類流程先隔離工作，完成完整功能後才整合，通常使用長期 `develop`、feature 或 release branch。
- TBD 先把需求切成可獨立工作的變更，持續整合到單一 `main`，並讓 `main` 隨時可工作、可發布；未完成但不能曝光的功能用 Feature Flag，大型重構用 Branch by Abstraction，相容性遷移則讓新舊版本並存。
- squash、rebase 或 merge commit 不是兩者的主要區分；主要差異是隔離多久及多久整合一次。
