共同原則：每個 PR 都從 `main` 開短期 branch，merge 前同步 `main`，通過 build、lint、unit test、必要的 integration test 與 review；`main` 變紅就立即修復或 revert。以下 branch 壽命均包含 review，目標為一天內；官方通常約 1～2 天，DORA 以少於一天為目標。

### A. SMTP 遷移到郵件服務 SDK

採用 **Branch by Abstraction**，讓 SMTP 與 SDK 在 `main` 暫時共存。

| PR | 內容與技巧 | 整合安全性 | branch 壽命 |
|---|---|---|---|
| PR 1 | 建立 `MailSender` abstraction 與 contract tests。 | 呼叫端尚未改變，既有 SMTP 行為不變。 | 半天～1 天 |
| PR 2 | 建立 SMTP adapter，讓既有寄信功能改由 abstraction 呼叫，預設仍使用 SMTP。 | 所有既有寄信功能維持原路徑，可用既有測試驗證。 | 半天～1 天 |
| PR 3 | 加入郵件服務 SDK adapter、sandbox/integration tests；設定預設仍為 SMTP。 | SDK 尚未進入正式寄信路徑，不影響每日寄信。 | 半天～1 天 |
| PR 4 | 將一組低風險寄信功能切換到 SDK，保留 per-flow 設定與 SMTP fallback。 | 可逐組驗證，發生問題時切回 SMTP。 | 半天～1 天 |
| PR 5 | 依功能群分批將其餘寄信功能切換到 SDK。 | 每批獨立 merge、測試與觀察，其他功能仍可使用既有路徑。 | 每批半天～1 天 |
| PR 6 | SDK 成為預設，保留短期回退設定並加入寄送成功率、錯誤與重試監控。 | 先確認正式流量穩定，再移除舊實作；不把 SMTP 移除與切換綁成無法回退的大 PR。 | 半天～1 天 |

每個 PR merge 後 `main` 都仍可透過 abstraction 使用 SMTP，滿足既有寄信功能每天正常的要求。確認 SDK 穩定後，再另開短期 PR 移除 SMTP adapter 與回退設定。

### B. 點數兌換頁，活動前不能曝光

採用 **Feature Flag**。程式可以每天 merge 與部署，但 flag 預設關閉，直到活動前才開啟。

| PR | 內容與技巧 | 整合安全性 | branch 壽命 |
|---|---|---|---|
| PR 1 | 加入頁面 shell、route 與 `pointsRedemption` flag，預設 `false`。 | flag 關閉時頁面不可見，既有頁面與流程不受影響。 | 半天～1 天 |
| PR 2 | 加入兌換 API client 與基本資料流，所有入口受 flag 控制。 | 功能程式可進入 `main`，但使用者仍無法觸發。 | 半天～1 天 |
| PR 3 | 加入表單驗證、錯誤/loading 狀態、權限檢查與測試。 | flag 關閉時不執行；開啟前可在 staging 驗證完整流程。 | 半天～1 天 |
| PR 4 | 加入 tracking、監控、灰度開啟與回退設定。 | 正式環境仍保持關閉，可先完成部署與觀測準備。 | 半天～1 天 |
| PR 5 | 活動前以設定開啟 flag；活動後另開短期 PR 移除 flag 與過時程式碼。 | Deploy 與 Release 分開，活動前不曝光；flag 啟用可快速回關。 | 各半天～1 天 |

四天開發期間每日把可工作的增量 merge 回 `main`，不要維持一條四天未整合的 feature branch。

### C. 庫存 API 回傳格式變更，兩個舊版 consumer 分批遷移

採用 **新舊並存（Strangler）**，先提供新格式，再逐一遷移 consumer，最後才刪除舊格式。

| PR | 內容與技巧 | 整合安全性 | branch 壽命 |
|---|---|---|---|
| PR 1 | 定義新 response schema、DTO/serializer 與 contract tests。 | 只增加新契約，舊 API 行為完全不變。 | 半天～1 天 |
| PR 2 | 提供 v2 endpoint 或 content negotiation，讓 v1、v2 同時存在，預設仍為 v1。 | 舊 consumer 不需同步修改，兩種格式各自測試。 | 半天～1 天 |
| PR 3 | 將舊版 consumer 1 切換到 v2，可用設定保留 v1 fallback。 | consumer 1 可獨立驗證與回退，consumer 2 仍使用 v1。 | 半天～1 天 |
| PR 4 | 將舊版 consumer 2 切換到 v2，同樣保留必要的回退能力。 | 兩個 consumer 分批完成，API 仍支援 v1。 | 半天～1 天 |
| PR 5 | 加入 v1 使用量監控與 deprecation，確認沒有其他 consumer 仍依賴 v1。 | 先以流量與 contract evidence 確認，再進行移除。 | 半天～1 天 |
| PR 6 | 移除 v1 endpoint、舊 serializer 與相容程式碼。 | 只有在兩個 consumer 都完成遷移且舊流量為零後才 merge。 | 半天～1 天 |

v1 與 v2 可以並存較長時間，但這是 API 相容期，不代表 branch 要長期存在；每個實作 branch 仍應短命並持續整合 `main`。
