規則來源與判定：

| 項目 | 來源與判定 |
|---|---|
| 不建立長期共同開發分支 | TBD 核心規則。`develop` 每週五才合併 `main`，屬長期分支，不符合。 |
| 頻繁整合 `main` | TBD 核心方向；DORA 建議至少每天一次、一天多次更好。每週整合一次太慢。 |
| `main` 必須可工作 | TBD 核心規則。CI 紅了仍先做新功能，違反「立即修復或 revert」原則。 |
| Branch 壽命 | 強烈建議短命。官方通常約 1～2 天；DORA 以少於一天為目標。兩天不是國際硬性標準。 |
| PR review 排三天 | Branch 壽命要包含等待 review 的時間，因此實際已活三天，違反短批次與快速 review 的目標。 |
| squash、rebase 同步 | 團隊自行決定，不是 TBD 必要規則。 |
| 兩位 reviewer、禁止 direct push | 團隊自行決定，不是 TBD 必要規則；可以作為團隊治理方式，但不能宣稱是 TBD 強制要求。 |

導入前提包括：

- 自動 build、unit test，以及必要的 integration test。
- 快速 CI 與 gated checks，最好每個 commit 都能在幾分鐘內回饋。
- 能把工作拆成小批次並每天整合。
- 足夠快速的 code review。
- `main` 壞掉時優先修復或 revert 的團隊紀律。

目前沒有自動測試，且 `main` 紅了不立即修復，這些前提都未具備。應先建立自動驗證、縮短 review 等待時間，並建立 broken trunk 優先修復的流程，再分階段導入 TBD；不能只靠宣布明天開始就安全全面切換。

TBD 與 GitFlow 的差異是：GitFlow 先用分支隔離，功能完成後才整合；TBD 先把需求切小，以短命 branch 持續整合 `main`，並讓 `main` 隨時保持可工作。TBD 主要改變工作拆分與整合節奏，Git 操作本身不一定不同。
