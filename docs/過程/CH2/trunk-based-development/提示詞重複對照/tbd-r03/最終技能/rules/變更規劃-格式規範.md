# Rule 1 - 以可獨立整合的小變更選擇策略

- 必須先切小：把需求拆成多個能獨立整合的小變更。一張 Story／Ticket 不等於一個 branch 或一個 PR。
- 幾小時／一天內可完成的小變更，可以使用短期 branch，不需要強加特殊技巧；不能時必須先判斷能否再切小，再對每個小變更判斷。
- 仍不能完成時，必須依原因選擇：功能還不能曝光用 Feature Flag；大型程式重構用 Branch by Abstraction；舊系統／相容性遷移用新舊並存（Strangler）；維護已發布版本用 Release Branch。
- 未完成的工作不得靠長期 branch 藏起來；可以靠小批次、Feature Flag、抽象層、向後相容、CI、自動測試承接。
- 預估 branch 壽命必須算入等 review 的時間。PR 很小但等 review 三天，效果跟三天 branch 一樣；DORA 把重量級、非同步、耗時的 review 流程列為 TBD 常見阻礙。
- 送出前必須檢查能否切到一天內可 merge；branch 明天仍會存在時，必須檢查是否切得太大，不得把此檢查當作 branch 壽命的硬性國際標準。

## Good Example

將可獨立完成的小修改獨立整合，沒有強加 flag 或抽象層，且估時包含 review。

- 情境：登入頁文案需半小時修正測試，review 預計二十分鐘；同張登入改版票另有 UI、API 與權限需求。
- 方案：文案獨立一個短期 PR，技巧為無，完成驗證再整合；branch 壽命含 review 預估約一小時。其餘改版另拆可獨立整合的小變更。

## Bad Example

相同文案被綁進整張大票，壽命還漏算 review。

- 情境：登入頁文案需半小時修正測試，review 預計二十分鐘；同張登入改版票另有 UI、API 與權限需求。
- 方案：所有工作放在同一 branch 兩週，改版完成才整合，文案的 branch 壽命卻只列半小時。

# Rule 2 - 控制曝光與清理 Feature Flag

- 功能還不能曝光時，可以用 Feature Flag 隱藏未完成功能：flag 關閉，最後打開（Deploy ≠ Release）。
- 功能上線後必須安排刪除 flag；官方警告不清理的 flag 會變成技術債。

## Good Example

功能的部署與開放分離，上線後有清理安排。

- 情境：新活動橫幅需要多天開發，但活動開始前不能曝光。
- 方案：在關閉 flag 下持續整合程式，驗證完成及活動開始時才開啟；功能穩定後用短期 PR 清理 flag。

## Bad Example

相同功能以長分支代替曝光控制，且沒有清理計畫。

- 情境：新活動橫幅需要多天開發，但活動開始前不能曝光。
- 方案：把工作藏在長期 branch 到活動當天才合；即使用了 flag，上線後也永久留著。

# Rule 3 - 以抽象層承接大型重構

- 大型程式重構可以使用 Branch by Abstraction，讓新舊實作暫時共存。
- 採用時必須規劃：建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作。
- 必須讓每個階段都能整合 main，不得把整段改造留在多週的不穩定 branch，最後才合。

## Good Example

同一個日誌元件替換拆成可工作的階段，舊實作持續承接尚未遷移的呼叫。

- 情境：替換日誌元件需要兩週，其他功能不能因此停擺。
- 方案：建立日誌 abstraction、接入舊元件、增加新實作、逐批切換呼叫、刪除舊實作；每個階段獨立驗證並整合。

## Bad Example

相同替換在長期不穩定分支隔離，沒有持續整合的階段。

- 情境：替換日誌元件需要兩週，其他功能不能因此停擺。
- 方案：開 `refactor/logging`，期間允許系統壞掉，兩週後全部完成才一次合回 main。

# Rule 4 - 維持遷移期間的新舊相容

- 舊系統／相容性遷移可以使用新舊並存（Strangler）。
- 改 API 時必須先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。
- 不得讓 main 處在「API 改了、前端還沒跟上」的中間狀態。

## Good Example

先讓新舊 API 共存，再遷移使用端，沒有跨層破壞的中間狀態。

- 情境：配送 API 要改回傳格式，兩個 consumer 無法同時更新。
- 方案：先加新 API 並保留舊 API，逐個遷移 consumer；確認都完成後才移除舊 API。

## Bad Example

相同遷移先刪舊格式，讓尚未更新的 consumer 失效。

- 情境：配送 API 要改回傳格式，兩個 consumer 無法同時更新。
- 方案：PR 1 刪除舊 API，PR 2 才更新第一個 consumer，第二個下週再處理。

# Rule 5 - 限定 Release Branch 與修正方向

- 維護已發布版本可以使用 Release Branch；必須很晚才切，只負責該版本的穩定、bug fix、發布，不得承載新功能開發。
- Bug 必須先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch。
- 不得只在 release branch 修再回灌 main；這是官方列出的錯誤模式。

## Good Example

先讓主線包含經驗證的修正，再維護已發布版本。

- 情境：正式版本 3.4 有 bug，main 已進入 3.5 開發。
- 方案：main 修正並驗證後，將修正 cherry-pick 到 `release/3.4` 驗證發布；該 release branch 只處理 3.4 維護。

## Bad Example

相同版本問題只先修 release，還把 release 當下一版開發線。

- 情境：正式版本 3.4 有 bug，main 已進入 3.5 開發。
- 方案：只在 `release/3.4` 修，再把一大包修改回灌 main；同時在該 branch 開發 3.5 新功能。
