# Rule 1 - 區分來源、規則強度與團隊政策

- 回答時必須區分規則來源：TBD 官方是 TrunkBasedDevelopment.com；DORA 是 Google DORA 的 DevOps 研究，標準通常比官方嚴格；團隊規則是 TBD 沒規定、由團隊自行決定的部分。
- Branch 壽命必須區分來源：官方認為短期 branch 通常 1～2 天；DORA 以不到一天為目標，不得把「2 天」說成硬性標準。
- 預估或審查 branch 壽命時，必須算入等 review 的時間，不得只計算寫 code 的時間；DORA 把重量級、非同步、耗時的 review 流程列為 TBD 常見阻礙。
- squash／merge commit／rebase merge、同步 main 用 merge 還是 rebase、branch 命名、reviewer 人數、GitHub 或 GitLab、是否禁止 direct push，必須視為團隊自行決定，不得說成 TBD 的要求。

## Good Example

一天半的 PR 壽命依來源比較，團隊選擇不冒充方法要求。

- 寫 code 半天、等 review 一天，branch 壽命為一天半；符合官方通常 1～2 天的描述，但未達 DORA 不到一天的目標。
- 團隊可以選 squash；這不決定該 workflow 是否為 TBD。

## Bad Example

相同 PR 漏算等待時間，並把偏好說成硬標準。

- 只算寫 code 的半天，宣稱已達 DORA 目標。
- 宣稱超過兩天必定違反硬性國際標準，或必須 squash 才是 TBD。

# Rule 2 - 核對整合健康與方法差異

- 必須維持核心規則：所有人圍繞單一 trunk（main）工作，沒有長期開發分支，頻繁整合 main，main 任何時候都保持可工作、可發布。
- DORA 的整合頻率必須表達為至少每天一次；可以一天多次。
- CI 紅了必須先修 main，不得繼續開發新功能；DORA 建議立即修或立即 revert，不是「晚上再看」。
- DORA 建議每個 commit 都觸發 build 與自動測試、回饋在幾分鐘內，回答時必須保留此來源與建議強度。
- 應維持非常短命的 branch、少量 active branches，不靠 code freeze 解決整合問題；這些屬強烈建議，不得改成額外的硬性數字門檻。
- 審查 workflow 時，必須核對有沒有 develop、team-a、release-next 這類長期共同開發分支，以及每人的整合頻率、branch 壽命、active branches、CI 回饋、紅 main 處理與 code freeze。
- 不得因為「都從 main 開 branch」就判成 TBD；feature branch 活 2～3 週仍不是 TBD。多人長期共同使用同一個 feature branch，屬既有的常見錯誤模式。
- 比較方法時，必須保留區別：GitFlow 類是先隔離 → 做完整 → 最後整合；TBD 是先切小 → 持續整合 → 任何時候都保持可工作。TBD 主要改變拆分工作的方式，Git 操作本身變化不大。

## Good Example

團隊持續整合可工作的變更，方法比較聚焦拆分與整合時機。

- 開發者每天把小變更整合回 main，CI 幾分鐘回饋，紅燈先立即修或 revert。
- 審查時核對 branch 壽命與 active branches，不只看分支從哪裡開出來。
- 比較 GitFlow 時說明隔離完整功能後整合，TBD 則小批次持續整合。

## Bad Example

相同團隊以名稱與 merge 按鈕替代整合健康判斷。

- 多人在從 main 開出的三週 feature branch 開發，就宣稱已符合 TBD。
- CI 紅燈留到週末再看，發布前靠 code freeze 收斂差異。
- 宣稱只要更換 merge 按鈕，GitFlow 就自動變成 TBD。

# Rule 3 - 評估導入前提與適用情境

- 評估導入時，必須核對自動 build、自動 test、快速 CI、小批次開發能力、快速 code review。
- 團隊缺少這些前提時，必須先指出缺的前提，不得直接建議全面導入。DORA 指出經驗不足、缺 gated checks、沒有「broken trunk 優先修復」紀律，可能使錯誤與返工增加；回答時必須保留此限制。
- 可以依既有適用情境評估：SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統、頻繁發布、多人共同維護的 codebase。
- 需求一直變、多人同時改、需要頻繁 release 三者同時成立時，可以指出 TBD 的價值最高；不得把這些情境改成使用 TBD 的硬性資格限制。

## Good Example

頻繁發布的內部系統先處理能力缺口，再改善整合。

- 團隊有頻繁需求變動與多人協作，但自動測試與 review 回饋不足。
- 先指出需補自動測試與快速 review；再以小批次與快速 CI 支援整合。

## Bad Example

相同能力不足的團隊被直接承諾全面導入的效果。

- 團隊尚無足夠自動測試，也沒有優先修復 main 的紀律。
- 仍直接要求全面導入，保證只要每天 merge 就能降低錯誤與返工。
