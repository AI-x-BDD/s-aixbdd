# Rule 1 - 切小變更並選擇整合策略

- 必須把需求拆成能獨立整合的小變更；一張 Story／Ticket 不等於一個 branch 或一個 PR。
- 幾小時／一天內可完成的小變更，可以直接採短期 branch，不需要特殊技巧。
- 變更無法在幾小時／一天內完成時，必須先判斷能否再切小；可以切小時，必須對每個小變更重新判斷。
- 無法再切小時，必須依不能整合的原因選擇策略：功能還不能曝光用 Feature Flag，大型程式重構用 Branch by Abstraction，舊系統／相容性遷移用新舊並存（Strangler），維護已發布版本用 Release Branch。
- 未完成的工作必須以小批次、Feature Flag、抽象層、向後相容、CI 與自動測試支援整合，不得靠長期開發分支藏起來。
- 分支預計隔天仍存在時，應檢查是否切得太大。

## Good Example

同一張聯絡人搜尋 Story 可以拆成多個能獨立整合的 PR；小變更不硬加技巧。

- 聯絡人搜尋拆成 API client、搜尋輸入框、基本查詢、分頁等小 PR，各自可整合。
- 另有一個十分鐘可完成的小文案修改，使用短期 branch，使用技巧為無。

## Bad Example

同一需求被綁成長期分支，小修改又被加上無必要的技巧。

- 聯絡人搜尋因為只有一張 Story，強制放在同一個兩週 branch，全部做完才 merge。
- 十分鐘文案修改也要求先建立 abstraction。

# Rule 2 - 未曝光功能使用 Feature Flag 並清理

- Feature Flag 必須讓程式持續整合而功能暫不曝光：flag 關閉，最後才打開（Deploy ≠ Release）。
- 功能上線後必須刪除 flag；不清理的 flag 會變成技術債。
- 審查團隊 workflow 時，必須核對 Feature Flag 有沒有清理；沒有提供現況時，不得自行判定此項已符合。

## Good Example

新設定頁未公開時仍能整合，且清理安排可核對。

- 新設定頁以關閉的 flag 進入 main，持續完成小變更，公開時再開啟。
- 頁面上線後刪除 flag；workflow 審查亦核對此項清理。

## Bad Example

相同設定頁以長期分支隔離，或只開啟而不清理 flag。

- 讓設定頁 branch 放一週，公開時才整包 merge。
- 改用 flag 後，上線仍永久保留 flag，workflow 審查也跳過清理項目。

# Rule 3 - 大型重構使用 Branch by Abstraction

- 多日大型重構應採用 Branch by Abstraction：建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作。
- 每一步必須可以 merge main，不得讓使用舊實作的模組因遷移中間狀態失去可工作能力。

## Good Example

儲存層遷移的中間狀態仍能服務既有模組。

- 先建立儲存 abstraction 並接舊實作，再加入新實作。
- 逐模組切換並整合，全部遷移後移除舊實作。

## Bad Example

相同儲存層遷移必須等全部模組改完才可工作。

- 先刪除舊儲存實作，再逐一修改模組。
- 中間數天 main 無法工作，只能讓整個重構留在長期 branch。

# Rule 4 - 相容性遷移先並存再移除

- 改 API 時必須先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。
- 不得讓 main 處在「API 改了、前端還沒跟上」的中間狀態。

## Good Example

通知 API 的新舊 consumer 在遷移期間都能工作。

- 新增通知 API 時保留舊 API，consumer 逐步改用新 API。
- 所有 consumer 遷移後才移除舊 API。

## Bad Example

相同通知 API 的更新先破壞既有 consumer。

- 第一個 PR 刪除舊通知 API。
- 下一個 PR 才更新仍呼叫舊 API 的 consumer。

# Rule 5 - Release Branch 只用於版本維護

- Release Branch 必須很晚才切，只負責該版本的穩定、bug fix、發布，不得承載新功能開發。
- Bug 必須先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch。
- 不得以只在 release branch 修再回灌 main 的模式整合修正。

## Good Example

地址編碼 bug 的修復先在 main 驗證，再移植到維護版本。

- main 修復地址編碼 bug，通過驗證後將修正 cherry-pick 到維護分支。
- 維護分支只處理該版本穩定、修補與發布。

## Bad Example

相同修復採反向整包整合，維護分支亦被用於新功能。

- 在 release 分支修地址編碼 bug，再把整條 release merge 回 main。
- 繼續在 release 分支寫下一版新功能。
