consumer 遷移順序：

1. 新比較頁直接使用新 API。
2. 低風險的內部頁面、管理工具與批次工作逐一遷移。
3. 其他仍使用舊 API 的內部或公開 consumer 逐一遷移。
4. 舊訂閱頁最後處理：若繼續保留，改用新 API；若由新頁完全取代，先確認新頁穩定與可回退，再移除舊頁 consumer。
5. 外部、行動端或無法直接控制的 consumer 必須先確認沒有流量，並完成既定的相容與通知期，才能退場。

舊 API 退場順序：

1. 列出所有實際 consumer，包含程式碼、SDK、批次工作、行動端與外部整合。
2. 所有仍存續的 consumer 完成遷移或正式停用。
3. 透過監測確認舊 API 已無請求，並保留團隊規定的觀察／通知期。
4. 以獨立 PR 移除舊 API endpoint。
5. 再移除舊 DTO、adapter、client method、契約測試、文件與監測項目。
6. 最後確認新 API 的 integration test、consumer smoke test 與部署流程仍為綠燈。
