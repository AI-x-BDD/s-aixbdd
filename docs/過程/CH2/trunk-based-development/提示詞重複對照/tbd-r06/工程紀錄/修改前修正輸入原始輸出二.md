每個 PR 都從最新 `main` 開短期 branch，完成後執行 build → lint → unit test → 必要的 integration test，再 review、merge、刪除 branch。若 `main` 變紅，立即修復或 revert。

後續 consumer 遷移順序如下：

1. 新比較頁先固定使用新 API。
2. 建立完整 consumer 清單，至少核對舊頁面、管理後台、測試工具、報表／排程工作、mobile app、SDK 與外部整合；以程式搜尋、API gateway log 和各 client owner 確認沒有遺漏。
3. 先遷移低風險且可快速回復的內部 consumer，每個 consumer 各自一個小 PR。
4. 再遷移內部排程、報表或其他自有服務；遷移期間保留舊 API。
5. 新比較頁穩定且資料一致後，將舊公開頁面切換到新 API，最好先以 Flag 或小流量 rollout 驗證。
6. 最後遷移 mobile、SDK 和外部 consumer。對有版本發布延遲的 client，持續保留舊 API，直到所有仍受支援版本完成升級。

每次 consumer 遷移都要同步更新其測試、文件與監控。舊 API 的退場順序是：

1. 停止新增任何舊 API 使用，標記 deprecated 並通知各 consumer owner。
2. 完成所有支援中的 consumer 遷移，確認程式碼、測試、文件與設定已無舊 API 依賴。
3. 以 access log／metrics 確認舊 API 在團隊約定的觀察期間沒有請求，且沒有未升級的支援版本。
4. 先用獨立 PR 停用舊 endpoint，保留可觀測的錯誤回應與 rollback 方式。
5. 驗證穩定後，再刪除舊 API 實作、schema、測試 fixture、文件與相關相容程式。
6. 新頁面穩定後刪除 Feature Flag，避免留下技術債。

預估每個 branch 壽命為數小時至一個工作天，包含 review；官方短期 branch 約 1～2 天，DORA 以不到一天為目標。四天功能應拆成上述多個 PR，而不是讓單一 branch 存活四天。
