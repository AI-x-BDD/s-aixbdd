審查團隊 Git workflow 時，逐項核對：

1. 主幹與分支

- [ ] 所有人圍繞單一 `main` trunk 工作。
- [ ] 沒有長期共同開發的 `develop`、`team-a`、`release-next` 或 shared feature branch。
- [ ] `main` 隨時可建置、測試與發布。
- [ ] 每人每天至少整合一次變更回 `main`；一天多次也可以。這是 DORA 建議，不是 TBD 的硬性數字。
- [ ] branch 足夠短命、active branches 數量少；官方通常描述為 1～2 天，DORA 以不到一天為目標。branch 壽命必須包含撰寫、等待 review 與 CI 的時間。
- [ ] 沒有依賴 code freeze 才解決整合問題。
- [ ] 不能只因 branch 是從 `main` 建立，就判定符合 TBD；若 feature branch 存活 2～3 週，仍不符合短期整合精神。

2. CI、Review 與主幹健康

- [ ] 有自動 build、automated test 與快速 CI。
- [ ] 每個 commit 都能觸發 build 與自動測試，回饋目標為幾分鐘內；這是 DORA 建議。
- [ ] CI 至少依序涵蓋 build、lint、unit test，以及必要的 integration test。
- [ ] code review 足夠快速；重量級、非同步或耗時的 review 是 TBD 常見阻礙。
- [ ] `main` 紅燈時立即修復或 revert，期間不繼續開發新功能。
- [ ] 團隊具備小批次開發與快速 review 能力；若缺少自動測試、快速 CI 或「broken trunk 優先修復」紀律，應先補足前提，不能直接宣稱已適合全面導入 TBD。

3. 變更拆分與整合策略

- [ ] 一張 Story／Ticket 不直接等於一個 branch 或 PR。
- [ ] 需求拆成可獨立整合的小變更。
- [ ] 幾小時至一天可完成的變更使用短期 branch，不需額外技巧。
- [ ] branch 預計隔天仍存在時，重新檢查是否能再拆小。
- [ ] 無法再拆小時，依原因選擇策略：
  - 未曝光功能：使用關閉的 Feature Flag，發布後刪除 flag。
  - 大型重構：依序建立 abstraction、接上舊實作、加入新實作、逐步切換、刪除舊實作。
  - API 或相容性遷移：新舊 API 並存，逐步遷移 consumer，最後刪除舊 API。
  - 已發布版本維護：晚期才切 Release Branch，只處理穩定、修補與發布。
- [ ] 每個中間狀態都能整合回 `main`，不能靠長期 branch 隱藏未完成工作。
- [ ] Release Branch 的 bug 必須先修在 `main`，驗證後再 cherry-pick 到維護分支；不能只在 release branch 修完再回灌 `main`。

4. 判定時的來源區分

- TBD 官方、DORA 建議與團隊政策要分開記錄。
- squash、merge commit、rebase merge、同步 `main` 用 merge 或 rebase、branch 命名、reviewer 人數、GitHub／GitLab，以及是否禁止 direct push，都是團隊政策，不是 TBD 必要條件。
