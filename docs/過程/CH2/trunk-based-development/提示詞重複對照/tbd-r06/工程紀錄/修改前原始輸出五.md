不符合 TBD。

- 沒有 `develop` 只代表沒有這項長期分支；每個功能 branch 活兩週，仍屬長期開發分支，違反 TBD 核心精神。應把功能拆成可在數小時至一天內完成並合併的小 PR。
- 寫程式半天、review 等三天，branch 實際壽命至少三天半；review 等待也算 branch 壽命，已不符合短期整合。
- CI 紅了直到晚上才修，違反「main 保持可工作」；應立即修復或 revert，不能繼續疊加開發。
- 自動測試不足，缺少 TBD 導入的重要前提，容易造成頻繁整合卻頻繁破壞 main。
- 強制 squash、rebase、兩位 reviewer 都是團隊流程選擇，不是 TBD 核心規則，也不能把長 branch 變成 TBD。
- 「官方規定最多兩天」不正確。官方通常描述短期 branch 約 1～2 天；DORA 以少於一天為目標，兩天不是硬性上限。

建議調整為：拆小變更、每天至少整合 main、縮短 review 回饋、建立足夠的自動 build 與測試，並對紅色 main 立即修復或 revert。未完成但不能曝光的功能使用 Feature Flag；大型重構使用 Branch by Abstraction。

- GitFlow：以分支隔離完整功能，最後集中整合。
- TBD：把工作切小，持續合併到單一 `main`，讓 main 隨時保持可工作、可發布。
