# Rule 1 - Feature Flag

- **Feature Flag**：程式每天 merge，flag 關閉，最後打開（Deploy ≠ Release）。功能上線後要刪 flag，官方警告不清理的 flag 會變成技術債。

## Good Example

關閉旗標分批整合，開放後清理。

- 新優惠橫幅先在關閉的旗標後逐步整合到 main，正式開放後移除旗標。

## Bad Example

與相同情境相比，破壞規則要求的整合方式。

- 相同優惠橫幅用一個長期 branch 藏住所有未完工作，或上線後永久留下臨時旗標。

# Rule 2 - Branch by Abstraction

- **Branch by Abstraction**：建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作。每一步都 merge main。

## Good Example

透過抽象層保持舊新實作可逐步切換。

- 影像處理先建立抽象，接上舊引擎，再加入新引擎、逐步切換，最後刪除舊引擎；每一步都進 main。

## Bad Example

與相同情境相比，破壞規則要求的整合方式。

- 相同影像引擎改造隔離一週，最後一次切換並整包整合。

# Rule 3 - 新舊並存

- **新舊並存**：改 API 時先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。不要讓 main 處在「API 改了、前端還沒跟上」的中間狀態。

## Good Example

讓既有 consumer 在遷移期間仍可工作。

- 商品編碼介面先保留舊欄位並新增新欄位，consumer 完成遷移後才刪舊介面。

## Bad Example

與相同情境相比，破壞規則要求的整合方式。

- 相同商品編碼遷移先刪舊欄位，舊 consumer 尚未更新，main 中間狀態不能工作。

# Rule 4 - Release Branch

- **Release Branch**：很晚才切，只負責該版本的穩定、bug fix、發布，不能承載新功能開發。Bug 先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch；只在 release branch 修再回灌 main 是官方列出的錯誤模式。

## Good Example

在 main 先修與驗證，再挑到版本維護分支。

- 已發布的報表版本出現計算錯誤；先在 main 修復與驗證，再 cherry-pick 到對應 release branch，該分支只做維護與發布。

## Bad Example

與相同情境相比，破壞規則要求的整合方式。

- 相同錯誤只在 release branch 修，再向 main 回灌；還在 release branch 繼續開發下一版新功能。
