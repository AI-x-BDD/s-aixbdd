PR 2：加入推薦清單 UI 並接上 API，入口仍維持關閉。 — 使用技巧：Feature Flag

PR 3：加入推薦清單追蹤事件與測試，只在同一個 flag 開啟時送出。 — 使用技巧：Feature Flag

PR 4：週四確認 CI、review 與功能驗證都通過後，只開啟 flag 讓推薦清單曝光；穩定後移除 flag。 — 使用技巧：Feature Flag

建議依序在 `main` 上整合：第一天 API、第二天 UI、第三天追蹤，第四天開啟 flag。每支 branch 都從最新 `main` 建立，merge 後刪除；前一支尚未完成時，後續工作可先準備但不可讓 `main` 依賴未整合的程式。

每個 PR merge 後 `main` 仍可工作：API 保持向後相容，既有 consumer 不必同步修改；UI 在 flag 關閉時不改變既有入口；追蹤事件在 flag 關閉時不執行；週四的 PR 只切換已部署且已驗證的功能，發現問題可立即關閉 flag。CI 應在 5 分鐘內回報；`main` 若變紅，先修復或 revert 再繼續整合。

預估 branch 壽命（含等 review）：每支 branch 的實作時間再加約 35 分鐘（CI 5 分鐘 + review 30 分鐘；若兩者並行，等待時間約取較長者）。輸入沒有提供各項實作工時，因此無法精確換算；目標是每支當日完成並 merge，不跨日。若任一支隔天仍存在，應再拆小或處理 review 等待。

六題檢查均通過：API、UI、追蹤已能分別切成小 PR；現在 merge 不會讓 `main` 失去工作狀態；未完成曝光用 Feature Flag 隱藏；沒有需要 Branch by Abstraction 的大型重構；CI 5 分鐘可快速回饋；每支 branch 以當日 merge 為目標。
