# 驗收回報

## 任務輸入

> production 3.2 有時區 bug，main 已開發3.3；review20分鐘、CI5分鐘，如何 hotfix，release branch 可否順便開新報表

## 任務類型

- hotfix 與 Release Branch 技巧諮詢。
- 3.3 新報表的變更切分與整合規劃。

## 任務判準

- 以 `main` 為單一 trunk，維持可工作，修復先回到 trunk。
- hotfix 的 branch 壽命包含實作、20 分鐘 review 與 5 分鐘 CI 等待時間。
- Release Branch 只負責既有版本的穩定、bug fix 與發布，不承載新功能。
- 官方 TBD 通常將短期 branch 視為約 1～2 天；DORA 以不到一天為目標。這些是不同來源的目標，不是硬性門檻。

## 整合計畫

PR 1：修正 production 3.2 的時區 bug，先在 `main`（3.3）完成修正與測試；使用技巧：無。

1. 從最新 `main` 開短期 hotfix branch，修正時區 bug，補上能重現 3.2 問題的測試，並確認 3.3 仍可工作。
2. 提出 PR，預留 20 分鐘 review 與 5 分鐘 CI；CI 順序為 build → lint → unit test，必要時補整合測試。
3. PR 通過後先 merge `main`，使修復成為 trunk 的已驗證變更。
4. 若尚未有 3.2 維護分支，從 production 3.2 實際發布的 tag 或 commit 建立 `release/3.2`。將已在 `main` 驗證的修復 cherry-pick 到 `release/3.2`，處理差異後重新驗證，再發布 3.2 hotfix。

PR 2：3.3 新報表，從 `main` 另開短期 branch 與 PR；使用技巧：未完成或尚未準備曝光時使用 Feature Flag。

- 新報表的每個可獨立整合的小變更分開提交與 merge。
- 若功能尚未完成，先以關閉的 Feature Flag 合併，確保 `main` 可工作；正式開放後移除 flag。
- 新報表不得放進 `release/3.2`。Release Branch 只維護 3.2 的穩定、bug fix 與發布；不能在該分支順便開發下一個新功能。

每個 PR merge 後 main 為什麼仍可工作：PR 1 在 merge 前以測試與 CI 驗證時區修正；PR 2 以小批次整合，未完成部分由關閉的 Feature Flag 隱藏。修復先進 `main`，再挑到 3.2 維護分支，避免只在 Release Branch 修復而讓 trunk 落後。

預估 branch 壽命（含等 review）：hotfix 至少包含實作／測試、20 分鐘 review、5 分鐘 CI 及 cherry-pick 後驗證，目標在同一天完成；新報表每個小 PR 也應以一天內完成為目標，若明天仍會存在就再切小。實際實作與部署時間未提供，無法再精確估算。

## 六題送出前檢查

1. 能不能切到一天內可以 merge？可以：hotfix 與新報表拆成獨立的小 PR；hotfix 的 review 加 CI 已知為 25 分鐘，另加實作與驗證時間。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？可以，前提是 hotfix 測試通過，且新報表未完成部分保持關閉。
3. 未完成功能能不能用 Feature Flag 隱藏？可以，用於 3.3 新報表，開放後清理 flag。
4. 大改造能不能用 abstraction 讓新舊實作共存？本題沒有大改造，無需使用 Branch by Abstraction。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以，已知 CI 約 5 分鐘；至少執行 build、lint、unit test，必要時補整合測試。
6. 這個 branch 明天還會存在嗎？hotfix 目標不應存在；新報表若明天仍未能 merge，應檢查並進一步切小。
