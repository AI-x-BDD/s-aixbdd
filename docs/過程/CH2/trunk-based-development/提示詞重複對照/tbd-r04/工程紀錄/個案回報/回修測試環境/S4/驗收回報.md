# S4 trunk-based-development 驗收回報

## 任務輸入

使用者輸入：

> 地址 API 的 street 欄位改為 addressLines，舊版手機 app 仍使用 street，要分批遷移，CI5分鐘、review30分鐘

本次範圍是 API 欄位相容性遷移、舊版手機 app 的分批 consumer 遷移，以及 CI 與 review 時間限制。

## Phase 1：任務類型與判準

任務類型：

- 需求規劃：把欄位變更拆成可獨立 merge 的小變更。
- 遷移技巧分析：舊版 app 尚未遷移，適用「新舊並存」。
- 未涉及既有 branch／PR／團隊 workflow 審查，也未涉及 TBD 與 GitFlow 比較。

任務判準：

1. 遷移期間舊版手機 app 仍可使用 `street`，main 每次 merge 後都可工作。
2. 先新增 `addressLines` 並保留 `street` 相容路徑，再分批遷移 consumer，最後才移除舊欄位。
3. 每個 PR 都能獨立驗證與 merge，CI 回饋目標為 5 分鐘內，review 目標為 30 分鐘內。
4. 每個 branch 的壽命包含實作、CI 與等待 review，目標在一天內完成；若超過一天則再拆小。
5. API contract、unit test 與必要的 targeted integration test 要覆蓋新舊欄位的相容行為。

共通判準的來源區分：TBD 官方通常以 short-lived branch 約 1～2 天描述；DORA 的目標更嚴格，為不到一天。本次「CI 5 分鐘」與「review 30 分鐘」是任務提供的團隊時間限制，不宣稱為 TBD 官方要求。

## Phase 2：技巧分析與整合計畫

主要技巧是「新舊並存」：API 先同時支援 `street` 與 `addressLines`，consumer 完成遷移後才刪除 `street`。不需要用長期 branch 藏住未完成工作。

`addressLines` 的資料型別、`street` 到 `addressLines` 的 mapping、請求與回應的相容規則，應在第一個 PR 的 API contract 中固定；若內部模型先改，也要由相容 mapping 保持舊 consumer 可用。

### 變更切分

1. **PR 1：API 新舊欄位並存。** 新增 `addressLines`，保留並持續接受／回應 `street`；建立 contract、unit 與必要的 integration tests，明確定義 mapping 與 deprecation 記錄。這個 PR merge 後，舊版 app 不需更新即可工作。
2. **PR 2：第一批手機 app consumer 遷移。** 新版 app 優先讀取／寫入 `addressLines`，保留對 `street` 的 fallback 或相容寫入；以獨立 PR 驗證一批使用者或一個版本，API 仍保留舊欄位。
3. **PR 3：後續 app 版本或 consumer 分批遷移。** 每批只處理可在一天內完成的範圍，依使用量或版本逐批切換；每批 merge 前確認 `addressLines` 的讀寫與 `street` fallback。
4. **PR 4：移除 `street`。** 待仍受支援的舊版 app 與其他 consumer 完成遷移，且 usage／相容性指標確認沒有仍需 `street` 的 consumer 後，獨立移除舊欄位、fallback、deprecation 與相關測試。若仍有未遷移 consumer，延後此 PR，不讓 main 進入不相容狀態。

### CI 與 review

每個 PR 的 CI 依序包含 build、lint、unit test，以及 API contract 與必要的 targeted integration test，回饋目標在 5 分鐘內；review 目標在 30 分鐘內。每個 PR 只處理一個遷移步驟，讓 reviewer 能在該時間內檢查 contract、相容性與測試。CI 紅燈時先修復或 revert main，再繼續後續遷移。

### 交付格式

PR 1：新增 `addressLines` 並保留 `street` 的 API contract、mapping 與測試 — 使用技巧：新舊並存

PR 2：第一批手機 app 改用 `addressLines`，保留 `street` fallback／相容寫入 — 使用技巧：新舊並存

PR 3：後續 app 版本或 consumer 分批遷移 — 使用技巧：新舊並存

PR 4：所有受支援 consumer 完成後移除 `street` 與相容程式碼 — 使用技巧：新舊並存

每個 PR merge 後 main 為什麼仍可工作：PR 1 以新增欄位及相容 contract 為主，保留舊版 app 依賴的 `street`；PR 2 與 PR 3 只遷移已選定的 consumer，API 仍同時支援新舊欄位；PR 4 延後到 consumer 完成且使用量確認為零後才移除舊欄位。每個 PR 都必須通過相容性測試與 5 分鐘內的 CI。

預估 branch 壽命（含等 review）：每個 PR 以當日完成為目標，包含最多 30 分鐘 review 與 5 分鐘 CI 回饋；若任一 PR 會延續到隔日，應依 consumer 批次或 API／client 工作再拆分。分支不應成為長期開發分支。

## Phase 2/3 檢查

依共通判準、整合技巧規則及 Skill 指定的原六題檢查：

1. 能不能切到一天內可以 merge？可以。API additive change、每批 consumer 遷移與 cleanup 各自獨立，仍超過一天時再縮小批次。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以。第一個 PR 保留 `street`，後續 PR 也不在所有 consumer 遷移前移除相容路徑。
3. 未完成功能能不能用 Feature Flag 隱藏？本需求不必依賴 Feature Flag；新舊並存的相容 API 已提供可工作的中間狀態。若團隊另有 staged rollout 需求，可在 consumer 批次外加 flag，但不能取代 `street` 相容路徑。
4. 大改造能不能用 abstraction 讓新舊實作共存？本需求不是大型內部實作重構；若內部模型先改，使用 API mapping／adapter 保持新舊欄位共存，並以每步 merge 的方式落地。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以。以 5 分鐘內的 build、lint、unit、contract 與必要 targeted integration test 驗證每個小 PR；API contract test 專門攔截 `street` 與 `addressLines` 的相容性破壞。
6. 這個 branch 明天還會存在嗎？目標是不會。若包含實作與 30 分鐘 review 仍會跨日，代表 PR 太大，應按 API、單一 app 批次或 cleanup 再拆。

檢查結論：整合計畫符合本次適用的共通判準與新舊並存規則，可交付。
