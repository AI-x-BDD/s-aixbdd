# 驗收回報

## 任務輸入

> 將通知寄送由 SMTP adapter 換為雲端郵件 SDK，需六天，不能中斷寄信，CI 6 分鐘、review 30 分鐘

## 任務判定

- 任務類型：需求規劃、遷移技巧分析。
- 主技巧：Branch by Abstraction。
- 搭配技巧：新舊並存、Feature Flag。
- 不使用 Release Branch；本任務不是已發布版本的維護修正。

適用判準是所有變更持續整合到單一 `main`，不建立長期開發分支，且 `main` 隨時保持可工作。每個小變更都要能獨立 merge；CI 順序為 build → lint → unit test → 必要的 integration test，CI 綠燈且完成 review 才能 merge。分支壽命包含實作、等待 review 與 CI；官方通常以 1～2 天描述 short-lived branch，DORA 則以少於一天為目標，兩者都不是「兩天內必然符合」的硬性門檻。

## 六天整合計畫

六天是整體遷移工期，不是讓同一個 feature branch 存活六天。每個 PR 都從最新 `main` 開始，merge 前再次同步 `main`；merge 後刪除短期 branch。以下每個 PR 都可獨立進入 `main`。

- PR 1：新增通知寄送 abstraction 與 contract tests，不改變現有 SMTP 呼叫行為 — 使用技巧：Abstraction。merge 後 `main` 仍使用原本 SMTP 路徑。
- PR 2：讓現有 SMTP adapter 實作 abstraction，將既有 caller 改走 abstraction，預設 provider 仍為 SMTP — 使用技巧：Abstraction／新舊並存。merge 後實際寄送方式不變，既有寄信可繼續工作。
- PR 3：加入 provider selection 設定與 Feature Flag，預設關閉雲端 provider，保留可立即切回 SMTP 的設定 — 使用技巧：Feature Flag／新舊並存。merge 後 flag 關閉時仍走 SMTP。
- PR 4：加入雲端郵件 SDK adapter，接到同一 abstraction，flag 關閉時不啟用 — 使用技巧：Abstraction／新舊並存。merge 後新程式碼存在但不影響預設 SMTP 流程。
- PR 5：補上雲端 adapter 的 contract／必要 integration tests、timeout、失敗處理與告警驗證，確認切換失敗時仍有安全回退路徑 — 使用技巧：新舊並存／Feature Flag。merge 後仍以 SMTP 為預設，且可驗證不中斷寄信的回退行為。
- PR 6：以可逆的 canary 設定讓受控比例流量使用雲端 provider，其餘流量維持 SMTP；保留 rollback 開關 — 使用技巧：Feature Flag／新舊並存。merge 後未進入 canary 的流量與 rollback 路徑仍由 SMTP 處理。
- PR 7：在 canary 指標、錯誤率與必要測試通過後，逐步把流量切到雲端 provider，仍保留可立即切回 SMTP 的開關 — 使用技巧：Feature Flag／新舊並存。merge 後若發生問題可關閉 flag，`main` 與寄信服務仍可工作。
- PR 8：雲端 provider 穩定後，移除 SMTP adapter 與臨時切換旗標，留下雲端實作及必要的永久設定 — 使用技巧：Abstraction。merge 後 `main` 只保留已驗證的雲端寄送路徑；若 PR 7 的穩定條件未達成，PR 8 不 merge，先維持 SMTP fallback。

預估 branch 壽命（含等 review 與 CI）：PR 1、2、3、6、7、8 各約半天；PR 4、5 各不超過一天。review 預留 30 分鐘，CI 預留 6 分鐘；若 review 或 CI 阻塞使分支可能跨日，先拆小或處理阻塞，不把未完成遷移留在長期 branch。六天內可完成 PR 1～7 的安全切換；PR 8 必須在切換穩定條件已具備時才合併，不能為湊工期跳過回退能力與觀測結果。

## 送出前六題檢查

1. 能不能切到一天內可以 merge？可以；已拆成八個可獨立 merge 的 PR，單支 branch 最長不超過一天。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？可以；SMTP 保持預設，雲端實作先以 abstraction、flag 與新舊並存接入。
3. 未完成功能能不能用 Feature Flag 隱藏？可以；雲端 provider 在 PR 3～7 由 flag 控制，預設關閉或受控 canary，並保留 rollback。
4. 大改造能不能用 abstraction 讓新舊實作共存？可以；先建 abstraction、接上 SMTP，再加入雲端 SDK，最後才移除舊 adapter。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以；每個 PR 執行 build、lint、unit test 與必要 integration test，CI 約 6 分鐘，只有綠燈才 merge；`main` 紅燈時立即修復或 revert。
6. 這個 branch 明天還會存在嗎？目標是不會；branch 壽命包含 30 分鐘 review 與 6 分鐘 CI，控制在半天至一天，merge 後立即刪除。PR 8 是新的短期 cleanup branch，不與前面 PR 共用長期 branch。

## 互動確認閘門

無。此 Skill 的 SOP 沒有要求在 Phase 之間停下向使用者確認，本次直接完成內部判定、技巧分析、六題檢查與交付。PR merge 的 review／CI 條件，以及 canary 指標通過後才逐步切換，都是執行條件，不是本次互動確認閘門。
