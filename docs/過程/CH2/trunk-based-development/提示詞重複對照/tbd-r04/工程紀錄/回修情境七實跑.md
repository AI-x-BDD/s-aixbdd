## 實際最終回覆

不建議現在直接全面改成 TBD。

這個企業內部 Web 系統符合 TBD 的適用情境：需求常變、多人維護、需要頻繁發布。但目前沒有自動 build、沒有自動測試，review 平均四天，導入前提不足；直接要求大家頻繁 merge，容易變成 main 持續損壞與返工。

建議先分階段整備，再在小範圍導入：

```text
PR 1：建立 CI 自動 build 與既有 lint 檢查，讓每次變更有快速的基本回饋 — 使用技巧：無
PR 2：補上關鍵流程的自動 unit／smoke test，將 build 與測試設為 gated checks — 使用技巧：無
PR 3：把工作切成小批次，設定 reviewer 責任與快速 review 目標，縮短目前四天等待 — 使用技巧：無
PR 4：選一個團隊或服務試行 TBD：短期 branch、每天至少整合 main 一次、CI 綠才 merge、main 紅時立即修復或 revert — 使用技巧：無
```

每個 PR 都應能獨立合併；既有行為不因 PR 1、PR 2 的工具與測試建置而改變，PR 4 則只在 build、lint、unit test，以及必要的 integration test 通過後合併，因此 main 維持可工作。CI 順序為 build → lint → unit test → 必要的 integration test。DORA 的目標是每個 commit 都觸發 build 與自動測試，幾分鐘內得到回饋。

目前 review 平均四天，branch 壽命至少會包含這段等待，因此現況不符合短期整合目標。導入後以 DORA 的不到一天為目標；TBD 官方常見的 short-lived branch 約一至兩天，這是不同來源的建議範圍，不是硬性門檻。若仍常等四天，應先改善 review 流程，不應宣稱已完成 TBD。

未完成的功能每天合併時使用關閉的 Feature Flag，正式開放後移除 flag；大型重構依序使用 Branch by Abstraction，讓舊、新實作共存後逐步切換；API 遷移先保留新舊介面，consumer 完成遷移後再刪舊介面。Release Branch 只在接近發布時建立，僅處理該版本穩定與 bug fix；bug 先在 main 修復、驗證，再挑到 release branch。這些技巧是否採用，取決於實際變更，不能用來掩蓋長期 branch。

導入前必須確認的六項檢查如下：

1. 現況無法穩定在一天內 merge，四天 review 是主要阻礙；改善後才以不到一天為目標。
2. 現況沒有足夠自動驗證，不能保證每次 merge 後 main 正常；先建立 gated checks 與 broken trunk 立即修復或 revert 的紀律。
3. 未完成功能可用 Feature Flag 隱藏，開啟後清理 flag。
4. 大型改造可用 abstraction 讓新舊實作共存，再逐步切換。
5. 現況不能由 CI 快速告知破壞；PR 1、PR 2 必須先補齊 build、lint、unit test 及必要 integration test。
6. 目前 review 等待四天，branch 很可能隔天仍存在；若改善後仍如此，變更切分或 review 流程仍過大。

因此結論是「適用 TBD，但現在不具備直接全面導入條件」；先補自動驗證與 review 回饋，再以小範圍試行並逐步擴大。
