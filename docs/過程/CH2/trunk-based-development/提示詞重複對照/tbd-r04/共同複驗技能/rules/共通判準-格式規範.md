# Rule 1 - 來源與 branch 壽命

- 回答時區分規則來源：

- **TBD 官方**：TrunkBasedDevelopment.com。
- **DORA**：Google DORA 的 DevOps 研究，標準通常比官方嚴格。
- **團隊規則**：TBD 沒規定、由團隊自行決定的部分。

- Branch 壽命兩邊標準不同：官方認為短期 branch 通常 1～2 天；DORA 以不到一天為目標。不要把「2 天」說成硬性標準。

## Good Example

分開陳述來源與目標，沒有把常見時間範圍說成硬門檻。

- 官方 short-lived branch 通常約 1～2 天；DORA 的目標更嚴格，為不到一天。
- 對某個歷時約一天半的 PR，依整合情況及 review 等待分析，不只用兩天一刀切。

## Bad Example

相同 PR 的判斷把不同來源合成硬標準。

- 宣稱 TBD 官方與 DORA 都強制兩天內 merge，未超過兩天就一定符合 TBD。

# Rule 2 - 核心目的與規則

- 核心目的：不要讓大家的程式碼分開太久。所有人圍繞單一 trunk（`main`）工作，不建立長期開發分支，持續把小變更整合回 main，main 任何時候都保持可工作、可發布。

- **核心規則**（違反就不算 TBD）：

- 沒有長期開發分支。

- 頻繁整合 main。DORA：至少每天一次，一天多次更好。

- main 保持可工作。CI 紅了先修 main，不繼續開發新功能；DORA 建議立即修或立即 revert，不是「晚上再看」。

- 未完成的工作不靠 branch 藏起來，靠小批次、Feature Flag、抽象層、向後相容、CI、自動測試。

## Good Example

小變更持續回到 main，出問題先恢復可工作狀態。

- 團隊每天整合數次，不保留長期開發分支。
- main 的自動測試失敗時，先立即修復或 revert，再繼續新功能。

## Bad Example

相同團隊讓工作長期分叉，並延後修復 main。

- 功能分支維持數週才整合。
- main 已紅燈，仍先開發新功能，之後有空才修。

# Rule 3 - 建議、團隊選項及常見誤判

- **強烈建議**：branch 非常短命；active branches 盡量少；不靠 code freeze 解決整合問題。

- **團隊自行決定**（不要說成 TBD 的要求）：squash／merge commit／rebase merge、同步 main 用 merge 還是 rebase、branch 命名、reviewer 人數、GitHub 或 GitLab、是否禁止 direct push。

- **「我們都從 main 開 branch，所以是 TBD」**：feature branch 活 2～3 週就不是 TBD。

- **PR 很小但等 review 3 天**：效果跟三天 branch 一樣。branch 壽命要算入等 review 的時間。DORA 把重量級、非同步、耗時的 review 流程列為 TBD 常見阻礙。

- **多人在同一個 feature branch 開發**、**接近 release 就 code freeze**：都是官方 You're Doing It Wrong 列出的模式。

## Good Example

不把團隊選項冒充核心要求，且計入等待時間。

- 某團隊選擇 merge commit，工作花兩小時、等待 review 一個工作天。
- 說明 merge commit 是團隊決定，branch 壽命包含整段等待；評估 review 是否阻礙短期整合。

## Bad Example

相同情境誤判團隊選項並漏算 review。

- 宣稱只有 rebase merge 才算 TBD。
- 只計算寫碼兩小時，就判定 branch 很短命，忽略一個工作天的等待。
