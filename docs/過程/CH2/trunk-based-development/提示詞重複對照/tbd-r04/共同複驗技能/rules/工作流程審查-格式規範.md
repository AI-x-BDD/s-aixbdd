# Rule 1 - 審查項目

- 檢查是否真的在做 TBD，依「任務判準」解讀下列問項。
- 有沒有 `develop`、`team-a`、`release-next` 這類長期共同開發分支？
- 每人每天至少整合 main 一次嗎？
- branch 壽命（含 review 等待）多長？active branches 多少？
- CI 多快回饋？main 紅了是否立即修或 revert？
- 有沒有靠 code freeze 解決整合問題？
- Feature Flag 有沒有清理？

## Good Example

逐項檢查共同整合方式，沒有因為分支名稱就直接判定。

- 團隊各自使用短期工作分支，持續回到共同 main。
- 審查同時核對整合頻率、review 等待、CI、紅燈處理、freeze 與 flag 清理。
- 另一團隊以 team-a 作長期共同開發線；審查指出此整合方式的問題。

## Bad Example

相同團隊的審查只看分支從哪裡切，忽略問項。

- 因為 team-a 最初從 main 切出，就判定這條長期共同開發線符合 TBD。
- 沒有檢查整合頻率、review、CI、freeze 或 flag。

# Rule 2 - 導入前提

- 導入前提：自動 build、自動 test、快速 CI、小批次開發能力、快速 code review。缺這些時，TBD 容易變成「大家一直 merge main，main 一直壞」。DORA 指出經驗不足、缺 gated checks、沒有「broken trunk 優先修復」紀律的團隊，實行 TBD 反而可能增加錯誤與返工。遇到這種團隊，先指出缺的前提，不要直接建議全面導入。

## Good Example

先指出缺少的前提，沒有直接要求全面導入。

- 某團隊只有手動測試，也沒有 gated checks。
- 建議先建立自動 build、test 及快速回饋，並建立 broken trunk 優先修復的紀律，再評估導入。

## Bad Example

相同團隊缺乏驗證前提，卻直接全面改分支策略。

- 只要求所有人每天 merge main。
- 沒有處理缺少自動測試與 broken trunk 修復紀律的風險。

# Rule 3 - 適用情境

- 適合：SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統、頻繁發布、多人共同維護的 codebase。需求一直變、多人同時改、需要頻繁 release 三者同時成立時價值最高。

## Good Example

依維護與發布情境判斷價值。

- 一個企業內部系統需求持續變動，由多人維護且需頻繁發布。
- 指出這組條件下 TBD 的價值，並另依導入前提評估準備程度。

## Bad Example

相同系統的適用判斷忽略工作情境。

- 只因程式碼放在 GitHub 就判定適合 TBD。
- 沒有考慮需求變動、共同維護或發布頻率。
