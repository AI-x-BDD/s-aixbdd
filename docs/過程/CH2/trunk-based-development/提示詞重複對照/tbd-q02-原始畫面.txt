  S4：目前不符合 TBD。

  • 長期 develop、release-next 若承載共同開發，違反「沒有長期開發分支」的核心規則。
  • review 等待兩天必須算進 branch 壽命，已阻礙每天整合；PR 小不能抵銷等待時間。
  • CI 變紅仍繼續開發，違反 main 保持可工作的核心規則；應立即修復或 revert。

  先補足快速 review、自動 build／test、快速 CI 與 broken trunk 優先修復的紀律，再逐步將工作改成小批次整合 main。若 release-next 要保留為發布分支，必須晚切、只做穩定與修補，不能繼續承載新功能。

  尚缺每天整合頻率、active branches 數量、CI 回饋時間、code freeze 與 flag 清理情況，無法確認其餘項目。

  S5：先修 main，再 cherry-pick 到 v2.4 發布分支。

  1. 在 main 以短期修補 branch 重現問題、加入回歸測試並修正，經 review、CI 通過後 merge。
  2. 若已有 v2.4 維護分支就沿用；沒有則從實際部署的 v2.4 tag／commit 切出，不能從已含 v2.5 的 main 切出。
  3. 將已驗證的修補 commit cherry-pick 到 v2.4 分支；若有版本差異，調整後重新驗證。
  4. 執行 v2.4 的回歸與發布檢查，建立 v2.4.1 tag 並發布。
  5. 刪除已合併的短期修補 branch；v2.4 分支只在仍需維護該版本時保留，不接收 v2.5 新功能。

  修補 PR 含 review 以不到一天為目標；main 與 v2.4 必須各自驗證。Release branch 的維護期間依版本支援需求決定，不套用短期開發 branch 的壽命目標。
