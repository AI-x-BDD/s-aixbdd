## Phase 1：共通判斷

- TBD 的核心是圍繞單一 `main`，避免長期開發分支，頻繁整合小變更，並讓 `main` 任何時候都可工作、可發布。
- API 相容性遷移必須先讓舊欄位與新欄位並存，再逐一遷移 consumer，最後才移除舊欄位。不能先破壞仍在使用舊欄位的 consumer。
- 每個小變更都開短期 branch；merge 前同步 `main`，依序完成 build、lint、unit test 及必要的 integration/contract test，經 review 且 CI 綠燈後 merge，merge 後刪除 branch。
- CI 若變紅，先修復 `main` 或立即 revert，不在 broken `main` 上繼續堆新功能。
- branch 壽命需包含 review 等待時間。TBD 官方通常以 1～2 天描述短期 branch；DORA 以不到一天為目標。兩天不是硬性門檻，實際 review 時間目前未知。
- 此情境沒有大型重構或未曝光功能的資料，因此不選用 Branch by Abstraction 或 Feature Flag；「新舊並存」已直接滿足舊 consumer 不停機的限制。

## Phase 2：規劃結果

PR 1：帳單 API 同時提供新欄位與舊欄位，加入相容性與欄位契約測試，讓既有 consumer 不需停機即可繼續使用 — 使用技巧：新舊並存

PR 2：遷移 consumer A 使用新欄位；保留舊欄位供尚未遷移的 consumer 使用 — 使用技巧：新舊並存

PR 3：遷移 consumer B 使用新欄位；保留舊欄位供回滾或尚未完成的使用者使用 — 使用技巧：新舊並存

PR 4：確認兩個 consumer 都已使用新欄位並完成執行期驗證後，移除舊欄位及不再需要的相容程式與測試 — 使用技巧：無

每個 PR 都從當下的 `main` 開短期 branch，完成後先同步最新 `main`，再執行適用的 build、lint、unit test 與 API/consumer integration 或 contract test，經 review 且 CI 綠燈後 merge，隨即刪除 branch。PR 2 與 PR 3 是否可並行取決於是否碰到相同程式碼或共享部署資源；題目未提供這些專案細節，保守安排為 PR 2 完成後再做 PR 3。

每個 PR merge 後 `main` 為什麼仍可工作：PR 1 是向後相容的新增，舊欄位仍存在；PR 2 只改 consumer A，consumer B 與其他仍使用舊欄位的程式仍可讀取舊欄位；PR 3 同理且舊欄位仍保留；PR 4 延後到兩個 consumer 完成遷移並通過驗證後才移除舊欄位。因此整個遷移期間沒有要求舊 consumer 停機，也沒有把「API 已改、consumer 尚未跟上」的中間狀態 merge 到 `main`。

預估 branch 壽命（含等 review）：PR 1、PR 2、PR 3 各以一天內完成為目標，PR 4 為短期清理變更；若 review 等待使 branch 跨日，依 TBD 判準重新檢查切分與 review 阻礙。實際壽命無法從題目推定，應以團隊 review 時間校正；官方通常 1～2 天，DORA 目標不到一天。

## 送出前六題檢查

1. 能不能切到一天內可以 merge？可以。兩個 consumer 各自獨立成一天的 PR；API 相容新增與最後清理也各自保持小批次。若實作細節顯示 PR 1 或 PR 4 超過一天，應再拆成更小的相容新增、測試或清理變更。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？可以。每一步都保留舊欄位，PR 4 只在兩個 consumer 完成並驗證後執行。
3. 未完成功能能不能用 Feature Flag 隱藏？本情境不需要以 Feature Flag 處理；API 欄位以新舊並存提供相容性。若實際需求另有尚未曝光的行為開關，才依專案資料補充 flag。
4. 大改造能不能用 abstraction 讓新舊實作共存？本題不是大型實作替換，採新舊欄位並存即可；若現有 API 架構無法同時輸出兩個欄位，需在實作前確認可用的相容 adapter，題目沒有提供足夠資料指定其位置。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？計畫要求每個 PR 依序執行 build、lint、unit test 及必要的 API/consumer integration 或 contract test；實際 CI 工具與時間未提供，不能虛構其現況。
6. 這個 branch 明天還會存在嗎？若因 review 或 CI 等待而跨日，重新檢查 PR 是否過大或流程成為阻礙；跨日不是單獨的硬性違規判定。預設以短期 branch、快速 review 為目標。

## 最終產出

這是一個符合 TBD 核心的相容性遷移規劃：先以新舊欄位並存保護舊 consumer，再分別整合兩個一天的 consumer 遷移，最後在驗證完成後移除舊欄位；每個步驟均可獨立 merge，並維持 `main` 可工作與舊 consumer 不停機。沒有執行程式修改、部署或 Git mutation。
