## Phase 1：任務範圍與共通判斷

### 任務範圍

- 審查目前的團隊 Git workflow。
- 評估是否適合直接全面導入 TBD。
- 不做需求拆分，也不做 TBD 與 GitFlow 的完整比較。

### 共通判斷

- TBD 的核心是圍繞單一 `main` 工作，不建立長期開發分支，持續把小變更整合回 `main`，並讓 `main` 隨時可工作、可發布。
- 每天至少整合一次、一天多次更好，是 DORA 的建議；不是把「每天一次」當成唯一硬性門檻。
- branch 壽命要包含等待 review 的時間。TBD 官方通常以 1～2 天描述短期 branch；DORA 以少於一天為目標，兩者都不是把兩天當成硬性規則。
- CI 紅燈時應優先立即修復或 revert，不能等到晚間才處理。CI 快速、可靠且確實執行自動測試，是導入前提。
- 少量 active branches、避免 code freeze 是強烈建議；長期共同開發分支、多人在同一長期 branch 工作，以及靠 release 前 freeze 解決整合問題，都是需要改善的模式。
- Feature Flag、Branch by Abstraction、新舊並存與 Release Branch 是依變更類型選用的整合技巧，不是所有團隊都必須同時使用；branch 命名、merge 方式與 reviewer 人數則是團隊規則。

### 是否直接全面導入 TBD

結論：**不適用直接全面導入 TBD。**

目前已知的 `develop` 三週、review 等待三天、CI 40 分鐘且偶爾無測試，以及 `main` 紅燈延後到晚間才修，表示長期分叉、慢且不可靠的驗證、以及缺少 broken trunk 優先修復紀律。若現在直接要求大家更頻繁 merge `main`，很可能變成「大家一直 merge，`main` 一直壞」；這符合 workflow 審查 Rule 對缺少導入前提的風險描述。

可以把 TBD 作為改善方向，但應先補足以下前提，再以小範圍逐步導入：

1. 取消以三週為單位的共同 `develop` 開發，將可獨立整合的小變更改成短期 branch，完成即 merge `main`；每個 branch 的 review 等待也要納入壽命。
2. 修正 review 流程，使小 PR 能在合理時間內完成 review；DORA 目標是少於一天，TBD 官方常見範圍是 1～2 天，兩者都應清楚標示為建議而非硬性期限。
3. 讓每個 commit 都可靠執行 build 與自動測試，縮短 CI 回饋到幾分鐘等級，並補上目前偶爾缺少的測試步驟。
4. 建立 `main` 紅燈立即修復或 revert 的團隊紀律與責任。
5. 以小批次、Feature Flag、Branch by Abstraction 或新舊並存處理尚不能曝光、大型重構或相容性遷移；用完的 flag 要清理。發布維護若真的需要 Release Branch，應很晚才切、只處理穩定與 bug fix，修正先落在 `main` 再帶到 release branch。
6. 用持續整合與可工作的 `main` 取代依賴 release 前 code freeze；在導入前提尚未完成前，不宜把 freeze 當成已完成 TBD 的證據。

### 本次六題送出前檢查

1. **能不能切到一天內可以 merge？** 目前 review 要等三天，流程尚未做到；需先改善 review 與切分。
2. **這個 PR 現在 merge，`main` 還能正常工作嗎？** 已知 `main` 會紅且延後修復，無法確認能保持正常工作。
3. **未完成功能能不能用 Feature Flag 隱藏？** 情境未提供，無法判斷；若有未曝光功能，應評估使用並在完成後清理。
4. **大改造能不能用 abstraction 讓新舊實作共存？** 情境未提供大型重構，無法判斷；若有，應以 Branch by Abstraction 分步整合。
5. **CI 能不能快速告訴我這次改動有沒有破壞系統？** 不能。已知約 40 分鐘且偶爾無測試，未達可靠快速回饋前提。
6. **這個 branch 明天還會存在嗎？** `develop` 已知會存在三週；PR 也可能因三天 review 等待跨日。這是要求重新檢查切分、review 與整合節奏的訊號，不單獨把跨日當成硬性違規。

## 最終產出

對情境「多人共用 `develop` 三週、PR 寫一小時但等 review 三天、CI 40 分鐘且偶爾無測試、`main` 紅燈晚間才修、發布前 freeze；應直接全面導入 TBD 嗎？」的回答是：

> **不適用直接全面導入 TBD。** 已知 workflow 尚缺快速可靠 CI、自動測試、快速 review 與 broken trunk 優先修復等前提，並存在長期共同 `develop` 與 code freeze。應先補前提、縮短整合回饋，再以小變更逐步改善；目前未提供的 branch 數量、每日整合頻率、Feature Flag、測試分層與 release branch 資訊，不能自行推定。
