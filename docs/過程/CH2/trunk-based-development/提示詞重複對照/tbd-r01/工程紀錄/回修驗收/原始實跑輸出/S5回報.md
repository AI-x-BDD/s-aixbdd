# 測試回報

## 最終回答（逐字）

本題是相容性遷移，不能以「不適用」結案。已知兩個 consumer 各需一天，且舊 consumer 不可停機；未提供專案現況、review／CI 時間、API 部署方式，因此以下是依已給資料的規劃，不推定未提供的現況。

整合技巧判斷：本題使用新舊並存（Strangler）。Feature Flag 不是目前必要條件，因為主要問題是 API 相容性；Branch by Abstraction 適用於大型重構，本題未提供這類需求。

PR 1：讓帳單 API 同時提供舊欄位與新欄位，加入或更新 API contract test，保留舊欄位 — 使用技巧：新舊並存
PR 2：遷移 consumer 1 讀取新欄位，保留相容處理與測試 — 使用技巧：新舊並存
PR 3：遷移 consumer 2 讀取新欄位，保留相容處理與測試 — 使用技巧：新舊並存
PR 4：在兩個 consumer 都完成並通過驗證後，移除 API 舊欄位及相容程式 — 使用技巧：新舊並存

每個 PR 都從最新 main 開短期 branch，完成即跑 build → lint → unit test → 必要的 API／consumer integration 或 contract tests，PR → review → CI green → merge；merge 前同步 main，merge 後刪 branch。每個工作日應至少整合一次；若 CI 紅了，先修復或 revert main，再繼續新工作，不建立涵蓋整個遷移的長期 branch。

每個 PR merge 後 main 為什麼仍可工作：PR 1 merge 後舊 consumer 仍可讀取舊欄位；PR 2、PR 3 各只切換一個 consumer，另一個仍可讀取舊欄位；PR 4 只有在兩個 consumer 都已改用新欄位並通過驗證後才移除舊欄位。因此 API 先保持新舊欄位並存，main 每次 merge 都維持相容。舊 consumer 不停機的前提是 API 先保持雙欄位相容；本題未提供 consumer 部署是否需重啟，無法進一步保證部署細節。

預估 branch 壽命（含等 review）：PR 2、PR 3 各已知約 1 個工作日實作，總壽命還要加上 review 時間；PR 1、PR 4 的實作時間未提供，不能精確估計。以 TBD 官方通常 1～2 天、DORA 目標少於 1 天作為檢查基準；若因 review 或切分使 branch 跨日，重新檢查是否可再切小並持續整合。這些是來源建議，不是把 1～2 天當成硬性規則。
