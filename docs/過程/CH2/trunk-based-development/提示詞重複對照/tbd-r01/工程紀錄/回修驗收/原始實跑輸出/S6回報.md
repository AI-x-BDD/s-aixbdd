# 測試回報

## 最終回答（逐字）

預先回覆：不適用。

本次情境適用 `trunk-based-development` 的已發布版本維護規劃。已知資料只有：production 為 2.4、`main` 正在開發 2.5、2.4 有金額計算錯誤，且需要安排 hotfix 與 `release/2.4` 維護。以下不假設實際 repository 狀態。

共通判斷：

- TBD 的核心是所有人圍繞單一 trunk（`main`）工作，不建立長期開發分支，持續把小變更整合回 `main`，並維持 `main` 可工作、可發布。
- 這是已發布版本維護情境，適用 Release Branch：`release/2.4` 只負責 2.4 的穩定、bug fix 與發布，不承載 2.5 新功能。
- 依 TBD 官方的 `fix on trunk first`，先在 `main` 完成並驗證修正，再把已驗證修正 cherry-pick 到 `release/2.4`；不能只在 `release/2.4` 修完再回灌 `main`。
- DORA 建議至少每天整合一次，一天多次更好；CI 紅了要立即修復或 revert，不能繼續堆新的開發工作。這些與官方建議的來源、強度要和團隊自行決定的 branch 命名、merge 方式、review 人數分開。
- Feature Flag、Branch by Abstraction、新舊並存不是目前已知情境的必要技巧：題目沒有未曝光的新功能、大型重構或相容性 API 遷移的資訊。

規劃：

PR 1：從 `main` 開短期 `hotfix/2.4-amount-calculation`，修正金額計算錯誤並加入回歸測試；完成 build、lint、unit test，以及必要的 integration test，通過 review 與 CI 後合併 `main`。 — 使用技巧：無

PR 2：以 PR 1 在 `main` 已驗證的修正為來源，帶入 `release/2.4`（優先 cherry-pick；若版本差異造成衝突，先在該維護分支完成等價修正並重新驗證），完成 2.4 的維護與發布驗證。 — 使用技巧：Release Branch

每個 PR merge 後 `main` 為什麼仍可工作：PR 1 只包含小範圍的金額修正與回歸測試，只有在 CI 綠燈且 review 通過後才合併，2.5 的其他開發仍留在 `main`；PR 2 只把已在 `main` 驗證的修正帶到 2.4 維護線，不把新功能放進 `release/2.4`，因此兩條線各自保持可工作。

同步與整合順序：

1. 讓 `hotfix/2.4-amount-calculation` 從當下 `main` 開出，保持範圍只含這個錯誤與必要測試；合併前同步最新 `main`。
2. 先在 hotfix branch 完成測試、review 與 CI，合併回 `main`；CI 失敗時先修復或 revert，不繼續疊加新功能。
3. 若 `release/2.4` 尚不存在，應從實際 production 2.4 的正確 tag 或基線建立；若已存在，先確認它確實是 2.4 維護線，再帶入 PR 1 的已驗證修正。
4. 在 `release/2.4` 只做 2.4 的穩定、bug fix、發布驗證與必要的 release 工作；hotfix branch 合併完成後刪除短期 branch。`release/2.4` 的保留時間由團隊支援政策決定，不應拿它承載 2.5 開發。

預估 branch 壽命（含等 review）：`hotfix/2.4-amount-calculation` 以幾小時至一天內完成為目標。TBD 官方通常把短期 branch 描述為 1～2 天，DORA 以不到一天為目標；兩天不是硬性規則，等待 review 也要算入。`release/2.4` 是已發布版本的維護線，壽命取決於團隊支援政策，不套用短期 feature branch 的期限。
