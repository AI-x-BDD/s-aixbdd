# 測試回報

## 最終回答

本題可以做方法論層級的比較；輸入沒有提供現有 branch、PR、CI 或 review 流程，因此只能判斷適用性與規則邊界，不能判定團隊目前是否已符合 TBD。

| 面向 | GitFlow 類 | TBD |
| --- | --- | --- |
| 工作切法 | 先隔離開發，完成較完整的功能後再整合 | 先切成可獨立整合的小變更，完成就合回 `main` |
| 整合節奏 | 容易由長期 feature、develop 或 release 分支延後整合 | 圍繞單一 trunk（`main`）持續整合；DORA 建議至少每天一次，一天多次更好 |
| 主幹要求 | 可能在分支分叉期間延後得到整合結果 | 沒有長期開發分支，`main` 持續保持可工作、可發布；CI 紅了要優先修復或 revert |

需求常變、多人維護、每週發布，三項條件都使 TBD 的價值較高：小批次與持續整合能較早發現衝突，降低長期分支造成的整合風險。這只是依輸入做的適用性判斷，不能據此推論該團隊現有流程。若採 TBD，仍需具備或補齊自動 build、測試、快速 CI、小批次開發與快速 code review；缺少這些前提時，頻繁合併可能只會讓 `main` 持續壞掉。未完成但尚不能曝光的功能可用 Feature Flag；不能一天完成的大型重構可用 Branch by Abstraction，讓每一步仍能安全合回 `main`。

TBD 的核心判準是沒有長期開發分支、頻繁整合 `main`，以及讓 `main` 保持可工作。官方通常把短期 branch 說成約 1～2 天；DORA 以少於一天為目標，兩者都不是「超過兩天就一律違規」的硬性規定，而且 branch 壽命要包含等待 review 的時間。

`squash` 不是 TBD 規定。採用 squash merge、merge commit 或 rebase merge，以及同步 `main` 時用 merge 或 rebase，都由團隊自行決定。reviewer 人數也不是 TBD 規定；一位、兩位或其他數量屬團隊規則。這些選擇不決定是否符合 TBD，仍要看是否切小、持續整合、`main` 是否可工作，以及 review 是否拖長 branch 壽命。

### 送出前六題檢查（依已給資料）

1. 能否切成一天內可以 merge 的小變更：目前沒有需求拆分資料；應以此作為切分目標。
2. 現在 merge 後 `main` 是否仍能正常工作：沒有現有 CI 或程式狀態，無法判定。
3. 未完成功能能否用 Feature Flag 隱藏：沒有具體功能資料，無法判定；若不能立即曝光，應評估 Feature Flag。
4. 大改造能否用 abstraction 讓新舊實作共存：沒有大型重構資料，無法判定；若出現此類變更，應評估 Branch by Abstraction。
5. CI 能否快速告知改動是否破壞系統：沒有 CI 資料，無法判定；導入 TBD 前需確認自動 build、lint、unit test 及必要 integration test 的回饋速度。
6. branch 明天是否仍會存在：沒有 branch 與 review 時間資料，無法判定；若會跨日，應重新檢查是否切得太大，不能只因跨日就直接判定違規。
