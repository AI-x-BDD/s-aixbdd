# 測試回報

判斷：適用。預先回覆「不適用」不符合本情境；這是六天的郵件供應商遷移，涉及需求規劃、短期 branch／PR 拆分，以及 Branch by Abstraction、新舊並存與 Feature Flag 的整合方式。本次只做規劃。

目前已知只有：SMTP 呼叫散落、估計六天、現有寄信必須持續服務。沒有提供語言、模組邊界、呼叫點數量、新供應商 API、CI／review 流程、Feature Flag 或部署回退能力，因此以下不虛構實際檔名、分支名、指令或現況；呼叫端應依實際模組再拆成可獨立合併的 PR。

共通判斷：所有人圍繞單一 `main` 工作，不建立六天的長期開發分支；每個小變更完成即整合，`main` 隨時保持可工作、可發布。整合頻率至少每天一次，一天多次更好；CI 變紅時先修復 `main` 或立即 revert，不繼續疊加新功能。這些是 TBD 核心；squash／merge commit、branch 命名、reviewer 人數與同步 `main` 用 merge 或 rebase 則由團隊決定。官方通常以 1～2 天看待短期 branch，DORA 以不到一天為目標，兩者都要把等待 review 的時間算入，且不是「兩天」硬性門檻。

PR 1：建立郵件傳送 abstraction（例如 `MailSender`／`EmailProvider`）及現有 SMTP adapter，保留原有行為並補上介面與 adapter 測試 — 使用技巧：Branch by Abstraction

PR 2：建立集中寄信入口，將一個小的呼叫端群組接到 abstraction；預設仍使用 SMTP — 使用技巧：Branch by Abstraction／新舊並存

PR 3：依實際模組或呼叫端群組，逐一把其餘散落 SMTP 呼叫改接集中入口；每個群組各自短期 branch／PR，不能把全部呼叫端綁成一個大 PR — 使用技巧：Branch by Abstraction／新舊並存

PR 4：加入新郵件供應商 adapter、設定驗證與 provider contract／sandbox 測試；不切換既有流量，SMTP 仍是預設 — 使用技巧：Branch by Abstraction／新舊並存

PR 5：加入 provider selection 的 Feature Flag 或等效可回退設定，預設關閉新供應商；加入小範圍 allowlist／canary、成功率與錯誤監測，以及切回 SMTP 的操作方式 — 使用技巧：Feature Flag／新舊並存

PR 6：依監測結果逐步擴大新供應商流量；確認送信成功率、錯誤、延遲、重試與重複寄送風險後，再把新供應商設為預設，並保留可回退窗口 — 使用技巧：Feature Flag／新舊並存

PR 7：新供應商穩定且不再需要回退後，另開小 PR 移除舊 SMTP adapter 與已用完的 flag／設定 — 使用技巧：新舊並存

六天是上述工作流的總估計，不是單一 branch 的壽命。可用的時間框架是：第 1 天完成 PR 1；第 2 天完成 PR 2；第 3 天起依呼叫端群組合併 PR 3；第 4 天加入 PR 4；第 5 天完成 PR 5 並開始 canary；第 6 天依證據執行 PR 6。PR 7 應等穩定觀測完成後再做，不能為湊六天而提前刪掉回退路徑。

每個 PR merge 後 `main` 為什麼仍可工作：PR 1～4 都保留原 SMTP implementation 且不改變預設路徑；PR 2～3 只把呼叫端接到仍使用 SMTP 的 abstraction；PR 5～6 的新路徑由預設關閉的 flag／設定控制，異常可切回 SMTP；PR 7 只有在所有 consumer 已使用新供應商、測試與監測通過且不再需要回退時才可合併。每個 PR 都應先同步最新 `main`，再完成 build、lint、unit test，以及必要的 integration／provider contract test，通過 review 與綠燈 CI 後合併，合併後刪除 branch。

送出前六題自檢：

1. 能否切到一天內可以 merge？可以；PR 3 依呼叫端群組再細分。若任一群組仍需跨日，繼續切小。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？可以，前提是保留 SMTP 預設與相容入口；這是每個 PR 的合併條件。
3. 未完成功能能否用 Feature Flag 隱藏？可以；新供應商在 PR 5 前不承接正式流量，flag 預設關閉。
4. 大改造能否用 abstraction 讓新舊實作共存？可以；PR 1 先建立 abstraction，PR 4 再加入新 adapter。
5. CI 能否快速告訴我這次改動有沒有破壞系統？應要求 build、lint、unit 與必要的 integration／contract test；目前未提供現有 CI，因此無法確認實際指令或速度。
6. 這個 branch 明天還會存在嗎？目標是不會；若因 review 或工作量跨日，應把它視為切分或 review 流程需要重新檢查的訊號，不把跨日直接當成硬性違規。
