判斷：適用 TBD。預先回覆「不適用」不成立：需求可拆成每日整合的小變更，且月底前不能曝光可用 Feature Flag 將 Deploy 與 Release 分開。

PR 1：建立報表匯出 Feature Flag、API contract 與新增 endpoint 骨架；flag 預設關閉，不改變既有流程 — 使用技巧：Feature Flag
PR 2：完成報表匯出 API 與自動化測試，接上同一個 flag — 使用技巧：Feature Flag
PR 3：加入報表匯出權限定義、API authorization 與未授權測試；既有 API 與既有流程維持可用 — 使用技巧：Feature Flag
PR 4：加入 UI 匯出入口、下載流程與必要的 UI/API integration test，依同一個 flag 及權限控制顯示 — 使用技巧：Feature Flag

每個 PR merge 後 main 為什麼仍可工作：每個小變更各自開短期 branch，完成後經 PR review 與 CI 驗證再 merge，merge 後刪除 branch；flag 預設關閉時 UI 不顯示、新 endpoint 不對使用者開放，既有流程仍走原路徑。驗證依 build → lint → unit test → 必要的 integration test 執行；工作期間持續同步 main。月底驗證完成後才開啟 flag，功能穩定後另開清理 PR 移除 flag，避免形成技術債。

預估 branch 壽命（含等 review）：每個 PR 以半天至一天內完成並 merge 為目標；若 review 或實作超過一天，應再切小。TBD 官方通常以 1～2 天為短期 branch，DORA 以不到一天為目標；兩者都是建議，不是「兩天」硬性規則。

拆分與限制：題目只提供四天工期、UI/API/權限、月底曝光與每日部署，未提供實際技術棧、既有 CI、權限模型、Feature Flag 基礎設施或 branch 命名；以上是依已知需求提出的 PR 責任切分，不宣稱專案現況。題目未指出大型重構、舊 API 相容遷移或已發布版本維護，因此不使用 Branch by Abstraction、新舊並存或 Release Branch。
