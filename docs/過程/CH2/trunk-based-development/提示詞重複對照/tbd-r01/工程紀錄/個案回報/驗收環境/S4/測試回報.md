## Phase 1：任務範圍與共通判斷

### 任務範圍

- 需求規劃：把六天的供應商遷移切成可獨立整合的小變更。
- branch／PR／workflow 規劃：每個小變更使用短期 branch，持續同步並合併 `main`。
- 整合技巧判斷：使用 Branch by Abstraction，並在新供應商尚未準備好或需要逐步切換時使用 Feature Flag／路由設定。
- 不包含：既有 workflow 審查、GitFlow 比較、實際程式碼修改與 Git mutation。

### 共通判斷

- TBD 的核心是圍繞單一 `main` 工作，不建立長期開發分支，持續把小變更整合回 `main`，並讓 `main` 隨時可工作、可發布。
- 每個小變更都應在幾小時至一天內具備 merge 條件；若仍需跨日，應重新檢查是否能再切小。TBD 官方通常把短期 branch 描述為 1～2 天，DORA 以不到一天為目標；兩者都包含等待 review 的時間，不能只計算寫程式的時間。
- 整合頻率採 DORA 建議：至少每天一次，一天多次更好。若 CI 使 `main` 變紅，應先修復或立即 revert，再繼續其他工作。
- Branch 命名、squash 或 merge commit、rebase 或 merge 同步方式、reviewer 人數與是否禁止 direct push，都是團隊規則，題目沒有提供，不能寫成 TBD 硬性要求。

## Phase 2：拆分與整合規劃

### 拆分與阻礙

六天超過一天可完成的尺度，而且 SMTP 呼叫散落各處；若把全部呼叫點、新供應商與切換一次放在一支 branch，會形成長期 feature branch。現有寄信服務又必須持續運作，因此採 Branch by Abstraction，讓舊 SMTP 與新供應商在過渡期間共存。

實際呼叫點數量未知，不能捏造 PR 數量。每個可獨立測試且不超過一天的呼叫點或安全群組各自形成一個遷移 PR；若某群組仍需跨日，就再切成更小的 PR。`N` 代表實際盤點後的呼叫點遷移 PR 數量。

### 整合技巧檢查清單結果

- 建立 abstraction：先定義集中寄信邊界，例如 `MailSender`，搭配契約測試與測試替身；此步不改變寄信行為。
- 舊實作接上：建立既有 SMTP 的 adapter／implementation，先讓現有呼叫可經由 abstraction 執行，預設仍走 SMTP。
- 加入新實作：新郵件供應商實作相同 abstraction，並以設定或 Feature Flag 保持關閉，直到測試與切換條件具備。
- 逐步切換：按郵件類型、呼叫點或其他可回復的安全範圍逐步導向新供應商；每個切換都保留 SMTP 回退路徑並觀察成功率、錯誤與延遲。
- 刪除舊實作：所有 consumer 已遷移且新供應商穩定後，才移除散落 SMTP 呼叫、舊 adapter、用完的 flag 與相關死碼。
- Feature Flag 若尚未具備：題目沒有說明現有機制，不能假定可直接使用；團隊需在實作前選定設定／路由方式。旗標預設關閉，穩定後要清理，避免形成技術債。
- Release Branch 不適用：題目沒有已發布版本維護或 hotfix 情境。

### 案例對照

- 「Axios → Fetch wrapper」與本次相同，都是多天的實作替換：先建 abstraction，再接舊實作、加入新實作、逐步切換，最後移除舊實作。
- 「一週的功能：Feature Flag」提供部署與開放分離的做法；本次可將新供應商先部署到 `main`，以關閉的路由設定或旗標維持 SMTP，待驗證後逐步開放。

## 需求規劃結果

PR 1：建立 `MailSender` abstraction、契約測試與測試替身；既有寄信路徑不改變。 — 使用技巧：Abstraction

PR 2：建立既有 SMTP implementation／adapter，讓一個最小且可驗證的寄信路徑經由 abstraction 執行，預設仍使用 SMTP。 — 使用技巧：Abstraction／新舊並存

PR 3～PR `N+1`：每個 PR 遷移一個呼叫點或可安全驗證的呼叫點群組至 abstraction，保留尚未遷移的 SMTP 呼叫；逐 PR 補上對應測試。若單一群組無法在一天內 merge，再繼續拆分。 — 使用技巧：Abstraction／新舊並存

PR `N+2`：加入新郵件供應商 implementation、契約測試與必要的 provider integration test；以關閉的 Feature Flag 或等效路由設定保留 SMTP 為預設。 — 使用技巧：Abstraction／Feature Flag／新舊並存

PR `N+3`：針對一個可回復的郵件類型、呼叫點群組或流量範圍啟用新供應商，補上成功率、錯誤、延遲與回退驗證；未通過條件時切回 SMTP。若需要多個切換範圍，各自拆成短期 PR。 — 使用技巧：Feature Flag／新舊並存

PR `N+4`：在所有寄信路徑都已驗證且新供應商穩定後，完成預設切換；保留團隊決定的回退設定直到觀察期結束。 — 使用技巧：Feature Flag／新舊並存

PR `N+5`：移除散落的 SMTP 呼叫、舊 SMTP adapter、已用完的旗標與死碼，更新必要的測試與文件。 — 使用技巧：無（清理已完成的遷移）

每個 PR merge 後 `main` 為什麼仍可工作：PR 1 沒有行為變更；PR 2 至 PR `N+1` 仍以 SMTP 寄信，且每個 consumer 逐步接上相容的 abstraction；PR `N+2` 的新供應商預設關閉，SMTP 仍是可用路徑；PR `N+3` 至 PR `N+4` 逐步切換並保留回退；只有在全部路徑已驗證後，PR `N+5` 才刪除舊實作。因此不會把「API 已改、consumer 尚未跟上」的不可工作狀態合併到 `main`。

預估 branch 壽命（含等 review）：每個小 PR 以不到一天為 DORA 目標，官方通常標準為 1～2 天；若包含 review 仍超過此範圍，應再切小。六天是整體遷移的題目估計，不代表一支 branch 可存活六天。每支 branch 完成後同步最新 `main`，通過 CI 與 review 後合併，再刪除 branch；具體 branch 命名與 merge 形式由團隊決定。

### 六天估計的限制

可暫以「abstraction／SMTP 接線 → 呼叫點遷移 → 新 provider → 逐步切換 → 穩定後清理」安排六天，但無法依題目資料確認每天能完成的 PR 數量。實際工期會受呼叫點數量、新供應商 API 與憑證、CI 速度、review 等待時間、可觀測性與回退機制影響；這些資料取得前，六天只能視為粗估。

### CI 與合併流程

每個 PR 依序執行 build、lint、unit test，以及必要的 integration test（至少涵蓋 SMTP 相容路徑、provider implementation、路由／旗標與回退行為）；PR review 通過且 CI green 後合併。每次提交都應盡快取得自動化回饋。`main` 變紅時先修復或立即 revert，不繼續疊加新功能。

## 送出前六題自我檢查

1. 能不能切到一天內可以 merge？可以；呼叫點依可驗證的最小範圍拆成 PR，跨日就再拆。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？可以；既有 SMTP 預設與回退路徑保留，清理 PR 延後到切換完成。
3. 未完成功能能不能用 Feature Flag 隱藏？可以；新 provider 先關閉，逐步切換時再啟用。若現有專案沒有旗標，需由團隊選定等效設定／路由機制。
4. 大改造能不能用 abstraction 讓新舊實作共存？可以；本計畫先建 `MailSender`，再接 SMTP 與新 provider。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？規劃要求每個 PR 執行 build、lint、unit test 與必要 integration test；實際指令與速度尚未提供，不能假定。
6. 這個 branch 明天還會存在嗎？目標是不會；若含 review 仍跨日，重新檢查拆分，不把跨日直接當成硬性違規。
