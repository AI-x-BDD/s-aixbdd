# workflow 審查結果

結論：不適用。依現有資料，不應直接全面導入 TBD。應先補齊自動 build/test、快速且可靠的 CI、快速 code review，以及 broken main 優先修復的紀律，再以小範圍試行評估。

已知事實與判斷：

- 多人共用 `develop` 三週：這是長期共同開發分支。TBD 核心要求團隊圍繞單一 `main` 工作、沒有長期開發分支、頻繁整合，而且 `main` 始終可工作；此現況不符合核心。
- PR 實作一小時但等 review 三天：branch 壽命必須把 review 等待算入，至少三天以上。TBD 官方通常建議短期 branch 約 1～2 天，這不是硬性上限；DORA 以不到一天為目標。現況的 review 等待是導入阻礙。
- CI 40 分鐘且偶爾無測試：目前沒有足夠證據顯示具備快速、可靠的自動 build/test gate；40 分鐘也不符合幾分鐘內取得回饋的目標。不能據此宣稱已有完整測試覆蓋。
- `main` 紅燈到晚間才修：沒有遵守 broken trunk 立即修復或立即 revert 的紀律。直接導入會增加錯誤與返工風險。
- 發布前 freeze：依賴 code freeze 解決整合問題，屬 TBD 官方指出的錯誤模式，也是應避免的強烈建議。

導入前置：

1. 讓每個變更觸發自動 build/test，補上可靠的 gated checks，並將 CI 回饋縮短到幾分鐘。
2. 建立 `main` 紅燈立即修復或 revert 的規則與責任流程。
3. 縮短 review 等待，確保 branch 壽命（含 review）回到短期範圍。
4. 用小批次持續整合 `main`；未完成功能可用 Feature Flag 隱藏，功能完成後清理 flag，不再依賴長期 `develop` 或 freeze。
5. 前置條件具備後再試行；是否全面導入應依試行結果重新評估，現在不宜直接宣告全面切換。

目前未提供、因此不能推測的資訊：每日整合 `main` 的次數、active branches 數量、Feature Flag 是否有清理流程、需求變動頻率，以及實際發布頻率。

六題自我檢查：

1. 能不能切到一天內可以 merge？目前不能確認能做到；已知 review 等待三天，需先改善 review 流程與切分。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？不能保證；已知 `main` 會紅，且不是立即修復。
3. 未完成功能能不能用 Feature Flag 隱藏？資料未提供，不能假設可以。
4. 大改造能不能用 abstraction 讓新舊實作共存？資料未提供，不能假設有大改造或其可行性。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？目前不能；CI 需 40 分鐘，且偶爾沒有測試。
6. 這個 branch 明天還會存在嗎？`develop` 已經共用三週；這顯示長期共同開發分支問題，但判斷依據是長期分支違反 TBD 核心，不是把跨日單獨當成硬性門檻。
