## 任務範圍與共通判斷

本次任務範圍是比較 GitFlow 與 TBD 在指定團隊情境下的工作方式，並區分 TBD 核心、DORA 建議與團隊自行決定的 Git 規則。輸入沒有提供現有 branch、PR、CI、review 等待時間、active branch 數量或 main 是否曾經故障的資料，所以只能做適用性比較，不能判定這個團隊目前已符合哪一種 workflow，也不能虛構現況。

共通判斷如下：

- TBD 的核心是圍繞單一 trunk（`main`）工作，不建立長期開發分支，持續把小變更整合回 `main`，並讓 `main` 隨時保持可工作、可發布。
- DORA 建議至少每天整合一次，一天多次更好；CI 變紅時應優先立即修復或 revert，不能繼續堆新功能。
- 官方通常把短期 branch 說成約 1～2 天；DORA 以不到一天為目標。兩者都不是「一律兩天內」的硬性規則，而且 branch 壽命要包含等待 review 的時間。
- branch 命名、GitHub 或 GitLab、是否 direct push、同步 `main` 用 merge 或 rebase、squash／merge commit／rebase merge，以及 reviewer 人數，都屬團隊規則，不是 TBD 規定。

## 比較結果

GitFlow 類的工作方式是先隔離，再把一個較完整的功能或版本做完，最後整合；TBD 是先切成可獨立整合的小變更，持續整合，任何時候維持可工作的 `main`。Git 操作本身不是主要差異，主要差異是工作切分與整合時機。

對這個需求常變、多人維護、每週發布的內部 Web 系統，TBD 的適用價值較高：需求可拆成小 PR，每個短期 branch 做完就 merge，降低多人長時間分叉後一次整合的衝突；每週發布也能從持續可工作的 `main` 取版本。這只是根據輸入條件的適用性判斷，不代表目前專案已經採用 TBD。

建議的 TBD 工作方式是：

- 把排班需求拆成幾小時至一天內可 merge 的變更，各自使用短期 branch；merge 前同步最新 `main`，merge 後刪除 branch。
- 依序完成 build、lint、unit test，必要時加 integration test，再走 PR、review、CI green、merge。
- 尚未能開放給使用者的功能用 Feature Flag 隱藏，程式仍可每天整合；功能穩定並開放後清理 flag。Deploy 不等於 Release。
- 若日後有不能一天完成的大型重構，使用 Branch by Abstraction 讓新舊實作逐步共存；若有已發布版本需要維護，Release Branch 晚切且只做穩定、修 bug 與發布。

### Squash 與 reviewer 人數

答案是「不適用於 TBD 規定判斷」：TBD 不規定必須 squash，也不規定必須使用 merge commit 或 rebase merge；TBD 也不規定 reviewer 人數。這些由團隊依稽核、歷史紀錄、review 速度與風險自行決定。是否符合 TBD，仍要看是否小批次、頻繁整合、`main` 保持可工作，而不是看採用哪一種 merge 方式或幾位 reviewer。

在目前資料不足的情況下，不能進一步宣稱團隊採用 squash、要求幾位 reviewer，或已有快速 review；只能說這些是尚待團隊定義或查證的 workflow 規則。

## 六題送出前檢查

1. 能不能切到一天內可以 merge？可以作為目標；但具體排班需求尚未提供，應再拆成小變更，不能把整張 Story 當成一個 branch 或 PR。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？每個 PR 都必須符合；尚未完成的功能應以 Feature Flag、向後相容或抽象維持可工作，現況是否做到未知。
3. 未完成功能能不能用 Feature Flag 隱藏？可以，適用於尚不能曝光但仍要持續整合的排班功能；輸入沒有說明目前是否已有 flag。
4. 大改造能不能用 abstraction 讓新舊實作共存？若之後出現跨日的大型重構，可以；本次情境沒有提供這類重構，不能假定已有需求。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？規劃上必須有 build、lint、unit test 及必要的 integration test；輸入沒有提供現有 CI 速度或結果，不能宣稱已具備。
6. 這個 branch 明天還會存在嗎？若會，應重新檢查是否切得太大並嘗試再拆；跨日不是單獨的一律違規判定，且目前沒有實際 branch 壽命資料。

## 最終產出

對本情境的結論是：TBD 比 GitFlow 類的「先隔離、完整做完、最後整合」更適合需求常變、多人維護、每週發布的內部 Web 系統，但導入前仍須確認自動 build、測試、快速 CI、小批次開發與快速 code review 等前提。squash 與 reviewer 人數不由 TBD 規定，屬團隊自行決定；目前資料不足以判定該團隊現有 workflow 的實際狀態。
