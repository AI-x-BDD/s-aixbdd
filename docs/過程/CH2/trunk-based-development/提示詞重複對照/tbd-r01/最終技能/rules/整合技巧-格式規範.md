# Rule 1 - 未曝光功能使用 Feature Flag

- 功能尚不能曝光時，應使用 Feature Flag，程式每天 merge、flag 關閉、最後打開（Deploy ≠ Release）。
- 功能上線後，必須刪除用完的 flag；TBD 官方警告，不清理的 flag 會變成技術債。

## Good Example

部署與開放分開處理，未完成功能仍可逐步整合。

- 情境：新的下注介面需一週，週五才開放。
- 做法：main 上 `newBettingUI = false`；週一 UI、週二 API、週三 validation、週四 tracking 每天整合；週五打開，功能穩定後刪 flag。

## Bad Example

相同情境用長分支等待整個功能，沒有持續整合。

- 情境：新的下注介面需一週，週五才開放。
- 做法：讓 `feature/new-betting-ui` 放五天，全部完成才 merge。

# Rule 2 - 大型重構使用 Branch by Abstraction

- 不能一天完成的大型重構，應使用 Branch by Abstraction 讓新舊實作暫時共存，而非長期隔離開發。
- 規劃必須保留建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作的演進，每一步都 merge main。

## Good Example

先有共同邊界再逐步替換，每次整合仍能使用舊實作。

- 情境：Axios 換成 Fetch wrapper，需要一星期。
- 做法：建立 HTTP abstraction、Axios 接上、加入 Fetch implementation、逐步切換、刪 Axios；每一步完成就 merge。

## Bad Example

相同替換工作隔離到全部完成，沒有分步整合。

- 情境：Axios 換成 Fetch wrapper，需要一星期。
- 做法：在 `refactor/http-client` 工作兩星期，最後才 merge。

# Rule 3 - 相容性遷移使用新舊並存

- 舊系統／相容性遷移，應使用新舊並存（Strangler），逐步讓 consumer 遷移。
- 改 API 時，必須先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。
- 不得讓 main 處於「API 改了、前端還沒跟上」的中間狀態；不得為了 merge 小而把不能工作的程式 merge main。

## Good Example

consumer 遷移完成前保留相容介面，跨層改動中間仍可工作。

- 情境：訂單 API 改變回傳欄位，前端尚使用舊欄位。
- 做法：舊、新 API 並存，遷移前端後才刪舊 API。

## Bad Example

相同情境先破壞既有 consumer，main 中間無法工作。

- 情境：訂單 API 改變回傳欄位，前端尚使用舊欄位。
- 做法：第一個 PR 刪舊欄位並 merge，第二個 PR 才調整前端。

# Rule 4 - 已發布版本使用 Release Branch

- Release Branch 應很晚才切，只負責該版本的穩定、bug fix、發布；不得承載新功能開發。
- Bug 必須先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch。
- 不得只在 release branch 修再回灌 main；這是 TBD 官方列出的錯誤模式。

## Good Example

先確保主幹有修正，再帶到需要維護的版本。

- 情境：Production 是 1.5，main 已開始 1.6，1.5 出現 bug。
- 做法：main 修復並驗證，再 cherry-pick 至 `release/1.5`；該 branch 只維護 1.5。

## Bad Example

相同版本情境把 release 當開發來源，main 可能漏掉修復。

- 情境：Production 是 1.5，main 已開始 1.6，1.5 出現 bug。
- 做法：只在 `release/1.5` 修復，繼續做 1.6 功能，最後把一大包 merge 回 main。
