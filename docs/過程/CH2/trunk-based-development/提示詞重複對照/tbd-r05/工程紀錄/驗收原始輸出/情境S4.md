## 完整最終回答

需求拆成兩條可交錯整合的變更流；每個 PR 都以幾小時至一天內完成為目標，等待 review 的時間也算在 branch 壽命內。

寄信 provider 遷移使用 Branch by Abstraction，保留 SMTP 到 HTTP 穩定為止；用 Feature Flag 控制逐步切換。API 欄位遷移使用新舊並存，讓舊 consumer 在兩週相容期內逐一遷移。

PR 1：建立 `EmailSender` abstraction，將既有 SMTP service 接到 abstraction，行為維持不變 — 使用技巧：Abstraction

PR 2：加入 HTTP provider implementation，先由 abstraction 持有但不改預設路由 — 使用技巧：Abstraction

PR 3：加入 provider 設定／Feature Flag、錯誤監控與可回退的路由；預設仍走 SMTP — 使用技巧：Feature Flag

PR 4：先以小比例或指定流量切到 HTTP，確認成功率、延遲與重試，再逐步開到全量；HTTP 異常立即關閉 flag 回到 SMTP — 使用技巧：Feature Flag

PR 5：HTTP 穩定且觀察完成後，移除 SMTP implementation 與不再需要的 flag／相容程式碼 — 使用技巧：Abstraction

PR 6：API 同時接受／輸出 `total` 與舊欄位 `amount`，在 mapping 層統一成同一個內部值，補上 contract tests 與棄用說明 — 使用技巧：新舊並存

PR 7：逐一把舊 consumer 改用 `total`；每個 consumer 各自形成可在一天內完成的 PR，持續量測 `amount` 使用量 — 使用技巧：新舊並存

PR 8：相容期滿兩週且監控確認沒有 `amount` 使用後，移除 `amount` mapping、文件與測試，完成 API 清理 — 使用技巧：新舊並存

每個 PR merge 後 main 為什麼仍可工作：

| PR | merge 後 main 仍可工作的原因 |
| --- | --- |
| 1 | SMTP 仍是實際 provider，只新增 abstraction，既有寄信行為不變。 |
| 2 | HTTP implementation 尚未成為預設路由，SMTP 仍可服務。 |
| 3 | flag 預設關閉，並保留回退路徑；監控與設定可獨立驗證。 |
| 4 | 逐步切換且可關閉 flag 回到 SMTP；切換期間不讓舊服務中斷。寄信需沿用既有 idempotency／去重機制，避免回退造成重複寄送。 |
| 5 | 只有在 HTTP 已穩定並完成觀察後才刪 SMTP；main 不再依賴已淘汰實作。 |
| 6 | 新 consumer 可用 `total`，舊 consumer 仍可用 `amount`；若兩欄同時送入，應拒絕不一致值或明確定義 `total` 優先。 |
| 7 | 每次只遷移一個 consumer；API 仍保留 `amount` 相容入口，尚未遷移者不會被破壞。兩週是相容窗口，不是讓同一 branch 存活兩週。 |
| 8 | 先以使用量監控確認已無舊 consumer，再刪除相容層；移除後不留下仍需要 `amount` 的呼叫者。 |

整合節奏：每個工作日同步 main，merge 前先更新 branch 到最新 main。每個 commit 觸發快速 build 與自動測試，PR 依 `build → lint → unit test → 必要的 integration test` 驗證，完成 review 且 CI green 才 merge。若 main CI 紅，先立即修復或 revert，再繼續其他變更；merge 後刪除完成的 branch，避免依賴 code freeze。

預估 branch 壽命（含等 review）：每個 PR 目標半天至一天；官方通常接受短期 branch 約 1～2 天，DORA 以不到一天為目標，兩者都不是把兩天當硬性上限。若任一 PR 預估會隔夜，繼續拆小或改成可獨立 merge 的步驟。API 的兩週是新舊 API 在 main 上並存的相容期，不是長期 feature branch。

六題自檢：

1. 能不能切到一天內可以 merge？可以；provider 遷移拆成 abstraction、HTTP implementation、flag、逐步切換、清理，API 遷移拆成相容層、consumer 遷移與清理。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以；每個 PR 都保留可工作的 SMTP 或 API 舊欄位路徑，並有 flag／回退或新舊並存保護。
3. 未完成功能能不能用 Feature Flag 隱藏？可以；HTTP provider 的曝光用 flag 控制，flag 關閉時仍走 SMTP。API 則以新舊並存提供相容性。
4. 大改造能不能用 abstraction 讓新舊實作共存？可以；`EmailSender` 先接 SMTP，再加入 HTTP，逐步切換後才移除 SMTP。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以；每個 commit build／自動測試，PR 依 build、lint、unit test、必要 integration test 驗證，並要求 CI green 才 merge。
6. 這個 branch 明天還會存在嗎？目標是不會；每個 branch 含 review 控制在半天至一天。若會隔夜，檢查是否仍能再拆；兩週 API 相容期由多次 merge 維持，不以長期 branch 承載。
