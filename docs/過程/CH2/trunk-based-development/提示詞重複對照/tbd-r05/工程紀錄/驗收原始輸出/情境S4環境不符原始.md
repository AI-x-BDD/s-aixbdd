## Phase 1 執行情況

### 需求輸入

原文為：

> 把寄信供應商從 SMTP SDK 換成 HTTP provider，需要六天，舊服務不能中斷。另有 API 欄位要由 amount 改為 total，舊 consumer 兩週後才遷移。請規劃

預先回覆為：

> 無目標 Skill 閘門；若出現則回覆「確認，僅提供規劃／審查，不操作 Git」，並依 E2 判失敗

### 任務範圍

判定為「變更規劃」，涉及：

- 六天工作拆成可每日整合的小批次。
- SMTP SDK 到 HTTP provider 的大型實作切換。
- 服務不中斷所需的 Abstraction、Feature Flag 與 rollback。
- `amount` 到 `total` 的舊新 API 相容遷移。
- merge main、CI 驗證、branch 壽命與六題自檢。

未涉及既有 branch／PR／團隊 workflow 的審查、導入評估或 GitFlow 比較，因此未載入「工作流程評估-格式規範.md」。

### 分析結果

- 不建立涵蓋六天的長期 feature branch；每個可獨立整合的變更各自使用短期 branch。
- provider 切換使用 `Abstraction`：先建立 abstraction 並接上 SMTP，再加入 HTTP，最後逐步切換並在穩定後刪除舊實作。
- provider 曝光使用 `Feature Flag`：flag 關閉時每天 merge、SMTP 維持預設；部署與釋出分開，先 staging/canary，再逐步放量，失敗可切回 SMTP。
- API 使用「新舊並存」：先提供 `total` 並保留 `amount`，consumer 遷移完成後才刪除 `amount`。主幹不能出現 API 已改而舊 consumer 尚未跟上的狀態。
- 每個 merge 前先同步最新 main，驗證順序固定為 build → lint → unit test → 必要的 integration test，接著 PR → review → CI green → merge。
- 實際 CI pipeline、HTTP provider 的 idempotency 能力、consumer 使用量與 rollout 平台未由情境提供，以下將它們列為執行前需確認的條件，不當作已通過的證據。

## Phase 2 執行情況

### 完整最終回答

建議六天內以短期 branch 和小 PR 持續整合 main。SMTP 保留到 HTTP provider 穩定完成，API 的 `amount` 與 `total` 先並存，避免服務中斷或舊 consumer 失效。

```text
PR 1：建立 EmailProvider abstraction，將既有 SMTP 實作接到 abstraction，行為維持不變 — 使用技巧：Abstraction
PR 2：加入 HTTP provider adapter、contract test 與 unit test，但尚未切換既有寄信路徑 — 使用技巧：Abstraction
PR 3：加入 provider selection、timeout、retry、metrics 與 Feature Flag；flag 關閉且 SMTP 為預設 — 使用技巧：Feature Flag／Abstraction
PR 4：完成 HTTP provider 的必要 integration test、staging smoke test 與 rollback 設定 — 使用技巧：Feature Flag
PR 5：以 canary 逐步啟用 HTTP provider，觀察成功率、錯誤率、延遲與重複寄信指標；異常立即切回 SMTP — 使用技巧：Feature Flag
PR 6：將 HTTP provider 放量至全量，保留 SMTP adapter 作為短期 rollback 路徑，直到穩定觀察期結束 — 使用技巧：Feature Flag／Abstraction
PR 7：API 新增 canonical 欄位 total，同時保留 amount；request 暫時接受兩者，若同時傳入則要求值一致；response 同時提供兩者，並補上 contract test、文件與 amount 使用量指標 — 使用技巧：新舊並存
PR 8：更新已可遷移的 producer／consumer 使用 total，舊 consumer 繼續使用 amount；兩週遷移期間持續監控 amount 使用量 — 使用技巧：新舊並存
PR 9：HTTP provider 完成穩定觀察後，刪除 SMTP adapter 與 provider Feature Flag；若觀察未完成則延後此 PR — 使用技巧：Abstraction／Feature Flag
PR 10：兩週後確認舊 consumer 已遷移且沒有 amount 流量，再刪除 amount；仍有使用者時延長並存期間，不直接破壞 API — 使用技巧：新舊並存
每個 PR merge 後 main 為什麼仍可工作：PR 1 保留原 SMTP 行為；PR 2 的 HTTP 程式尚未被選用；PR 3 至 PR 6 以關閉或可回退的 flag 控制 provider，並保留 SMTP；PR 7 同時提供 amount 與 total；PR 8 只遷移已準備好的 consumer；PR 9 與 PR 10 都以穩定觀察及使用量證據為前置條件，分別在 provider 與 consumer 遷移完成後才移除舊路徑。
預估 branch 壽命（含等 review）：每支目標半天至一天，並以能獨立 merge 為界；開發和等 review 的時間都算 branch 壽命。
```

六天的工作順序可安排如下：

- Day 1：PR 1、PR 2；同時可先完成 PR 7 的 API 相容模型，但分成獨立 PR。
- Day 2：PR 3、PR 7；SMTP 仍是預設，`amount` 仍可用。
- Day 3：PR 4、PR 8 的 consumer contract 調整；先在非 production 驗證。
- Day 4：PR 5，以 staging/canary 開始 HTTP provider。
- Day 5：PR 6 的逐步放量前半段及監控檢查。
- Day 6：PR 6 完成放量；PR 8 完成可遷移 consumer 的切換。PR 9 等穩定觀察期結束後再做，PR 10 等兩週遷移期結束後再做。

工作期間每個 branch 都要定期同步 main，merge 前再次更新到最新 main。每個 commit 觸發 build 與自動測試，目標在幾分鐘內回饋；main 若 CI 變紅，先立即修復或 revert，不繼續堆新變更。merge 後刪除已完成 branch，維持 active branch 少量，避免以 code freeze 解決整合問題。squash、merge commit、rebase merge、branch 命名及 reviewer 人數屬團隊選擇，不是 TBD 核心判準。

branch 壽命的來源需分開看：TrunkBasedDevelopment.com 通常以 1～2 天的短期 branch 為例；DORA 以不到一天為目標。兩者都要把 review 等待算進壽命，本規劃以半天至一天為目標，但不把任何天數說成 TBD 的硬性上限。

六題自檢：

1. 能不能切到一天內可以 merge？可以；provider 和 API 都拆成可獨立 merge 的 PR。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以；SMTP 預設保留、HTTP 有 flag、API 先新舊並存。
3. 未完成功能能不能用 Feature Flag 隱藏？可以；HTTP provider 在 flag 關閉時不接管流量，部署不等於釋出。
4. 大改造能不能用 abstraction 讓新舊實作共存？可以；EmailProvider 讓 SMTP 與 HTTP 共存，完成切換後才刪 SMTP。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？規劃要求是可以，順序為 build、lint、unit test、必要 integration test，且每個 commit 觸發；但目前沒有實際 pipeline 資訊，不能把此題視為已驗證通過。
6. 這個 branch 明天還會存在嗎？目標是不會；每支 branch 含 review 以半天至一天完成。若 review 等待使其隔夜，等待時間仍算壽命，應切小或加速 review；這是檢查訊號，不是把隔夜直接當成硬性禁令。
