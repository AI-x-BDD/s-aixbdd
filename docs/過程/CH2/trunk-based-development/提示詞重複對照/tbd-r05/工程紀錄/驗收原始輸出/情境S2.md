## 完整最終回答

這是可在一天內完成的單一小批次，使用 short-lived branch；不需要 Feature Flag、Abstraction 或新舊並存。

PR 1：更正文案錯字，只修改需要修正的文字並補上必要的文件檢查 — 使用技巧：無

每個 PR merge 後 main 為什麼仍可工作：這是文件文字修正，不改變程式行為；PR 經 review，依序完成適用的 build → lint → unit test → 必要的 integration test，確認 CI green 後再 merge。若 CI 變紅，先修復或 revert 以維持 main 可工作。

預估 branch 壽命（含等 review）：實作約 20 分鐘；以 review 與 merge 在同一天完成、整體一天內為目標。官方通常把短期 branch 視為 1～2 天，DORA 以不到一天為目標；兩者都要把等 review 算進壽命，這些不是硬性隔夜禁令。若 review 等待使 branch 留到隔天，應檢查 review 流程或變更範圍是否過大。

執行順序：

1. 從最新的 main 開短期 branch，開始前確認目前 main；工作期間若 main 有更新就同步，merge 前再更新一次。
2. 只完成文案錯字修正，保持一個可獨立整合的小 PR；不為尚未完成的功能引入 flag，也沒有大型重構或相容遷移需要抽象層。
3. 依 build → lint → unit test → 必要的 integration test 驗證；既有快速 CI 應讓每個 commit 觸發 build 與自動測試，並以幾分鐘內回饋為目標。
4. 送 PR → review → CI green → merge main；merge 後刪除完成的 branch，讓 active branches 維持少量。

六題自檢：

1. 能不能切到一天內可以 merge？可以；20 分鐘的錯字修正可成為一個當日完成的 PR。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以；只改文件文字，且需通過 review 與 CI。
3. 未完成功能能不能用 Feature Flag 隱藏？不適用；本題沒有未完成功能或需延後曝光的行為變更。
4. 大改造能不能用 abstraction 讓新舊實作共存？不適用；本題沒有大型程式重構。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以；沿用既有快速 CI，並執行適用的 build、lint、unit test 與必要 integration test。
6. 這個 branch 明天還會存在嗎？目標是不會；若因 review 等待而存在，應檢查等待時間與範圍，而不是把隔夜本身當成硬性判定。
