## 依目標 Skill 產出的最終回覆

目前描述的做法不能視為 TBD。既有 release branch 可以保留，但必須改成「接近發布時才建立、只維護已發布版本」的分支；早早建立後持續在上面開新功能，以及只在 release branch 修 bug 再回灌 main，兩者都需要調整。

你描述的是 GitFlow 類的「先隔離、做完整、最後整合」流程；TBD 則是「先切小、持續整合、任何時候維持 main 可工作」。TBD 主要改變的是工作拆分與整合時機，Git 的 merge、squash、rebase、branch 命名及 reviewer 人數仍可由團隊自行決定，這些操作選擇本身不是 TBD 判準。

| 面向 | 目前描述的 GitFlow 類做法 | TBD 相容做法 |
| --- | --- | --- |
| 開發位置 | release branch 早早建立，並持續承載新功能 | 新功能以小批次、短命 branch 回到 main；未完成或未曝光的功能用 Feature Flag、Abstraction 或新舊並存 |
| 整合時機 | 功能或版本累積後再整合 | 每天至少整合 main 一次，越頻繁越好；main 必須保持可工作 |
| release branch 角色 | 同時做版本穩定與新功能開發，因而成為長期開發分支 | 很晚才切，只負責該版本的穩定、bug fix 與發布 |
| 舊版 bug fix | 先修 release，再回灌 main | 先在 main 修正並驗證，再 cherry-pick 到仍支援的 release branch |
| 版本維護 | 以長期分支承載多種工作 | 可以保留支援中的 release branch，但限制在已發布版本維護，版本終止支援後關閉或刪除 |

### 可以保留的部分

可以保留已發布版本的 release branch。TBD 的變更規劃本身包含「維護已發布版本 → Release Branch」這個例外，因此 TBD 不是完全禁止 release branch。可保留的條件是：

1. 不要在發布很早以前建立並長期承載開發；接近版本穩定或發布時才切。
2. release branch 只處理該版本的穩定、必要 bug fix、發布準備與發布。
3. 不在 release branch 開新功能，也不把下一版功能放在其中等待整批整合。
4. bug fix 先進 main：從 main 建立短命 branch，完成修正後依序執行 build、lint、unit test、必要的 integration test，經 PR、review、CI green 後 merge main；再把同一修正 cherry-pick 到支援中的 release branch 並驗證。
5. 明確記錄支援中的版本與終止支援時間；版本停止支援後清理 release branch，避免 active branches 無限增加。

因此，已存在的早期 release branch 可以在遷移期間暫時保留，但應立即停止在上面新增功能，將未完成工作拆成小變更回到 main；它只能逐步收斂成維護分支，不能繼續當成共同開發分支。

### 必須調整的部分

- 「release branch 早早建立並持續開新功能」違反沒有長期開發分支的 TBD 核心規則；它也不符合 Release Branch 只負責穩定、bug fix 與發布的生命週期。
- 「只在 release 修 bug，再回灌 main」方向相反。這會讓 main 暫時漏掉修正，並增加後續衝突與重複驗證；應改成 fix on trunk first，即先修 main，再 cherry-pick 到 release。
- 每個 feature 應先拆成能獨立整合的小變更，每個小變更使用短命 branch，工作期間持續同步 main，merge 前再次更新；不要等整個 feature 或整個 release 完成才整合。
- 未能曝光的半成品應在 main 上以關閉的 Feature Flag 整合，穩定後打開並刪除 flag；大型重構使用 Branch by Abstraction，每一步都回到 main；API 或相容性遷移先保留新舊並存，consumer 完成遷移後才移除舊介面。
- main 的 CI 若失敗，應立即修復或 revert，不能把紅色 main 留到稍後再處理。導入 TBD 前需要確認自動 build、automated test、gated checks、快速 CI 與快速 code review 都具備；DORA 的目標是每個 commit 觸發 build 與自動測試，幾分鐘內回饋。

### 現況證據與未知資料

情境已明確提供：

- release branch 早早建立。
- release branch 仍持續開新功能。
- bug 只先在 release branch 修，再回灌 main。

上述資料已足以判定目前流程不是 TBD。情境沒有提供以下資料，不能據此宣稱已符合：

- 每人是否每天至少整合 main 一次。
- branch 實際壽命與等 review 的時間，以及 active branch 數量。
- CI 回饋速度、是否有 gated checks、是否執行 build、lint、unit test 與必要 integration test。
- main 變紅時是否立即修復或 revert。
- 是否依賴 code freeze、Feature Flag 是否清理，以及舊版支援多久。

短命 branch 是強烈建議，不是任意自訂的硬性天數。TBD 官方通常以 1～2 天描述短期 branch；DORA 以不到一天為目標，且等待 review 的時間也要算進 branch 壽命。兩者都不能被簡化成「兩天內一定算 TBD」。

### 六題自檢

1. 能不能切到一天內可以 merge？目前情境未提供 feature 大小與 review 時間，尚不能判定；調整後應先拆成一天內可獨立 merge 的小變更。
2. 這個 PR 現在 merge，main 還能正常工作嗎？目前無 CI、測試與相容性證據，不能視為通過；每次 merge 都應保持 main 可工作。
3. 未完成功能能不能用 Feature Flag 隱藏？情境未說明；若功能尚未能曝光，應使用關閉的 Feature Flag，並在穩定後清理。
4. 大改造能不能用 abstraction 讓新舊實作共存？情境未說明是否有大型重構；若有，應採 Branch by Abstraction，逐步整合新舊實作。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？情境未提供，判定為未知；至少要有 build、lint、unit test、必要 integration test 的驗證次序，並在 review 後以 CI green 才 merge。
6. 這個 branch 明天還會存在嗎？目前 release branch 早建且持續開新功能，答案很可能是會，這表示它正被當成過大的長期開發分支；若是已發布版本的維護 branch，因支援週期而跨日可以接受，但不得因此承載新功能，且不把隔夜視為單獨的硬性違規。

調整後的版本維護流程應是：

main 上的小變更 → 同步 main → build／lint／unit test／必要 integration test → PR／review／CI green → merge main →（需要支援舊版時）cherry-pick 到晚切出的 release branch → release 驗證與發布。

## 回報結論

版本維護的「release branch」概念可以留在 TBD 裡；需要移除的是早切、混合新功能，以及 release-only 修 bug 再回灌的整合順序。把 release branch 限定為晚切的已發布版本維護線，並採用先修 main、再 cherry-pick 到 release 的 hotfix 流程，才符合 TBD 的核心規則與 Release Branch 生命週期。
