## 完整最終回答

審查結論：目前 PR 不通過，不應直接合併。

`shipmentCode` 立即改成 `trackingCode` 並移除舊欄位時，仍未遷移的舊 consumer 會被破壞，`main` 不能維持可工作狀態。這違反 TBD 的核心規則，也違反 API 相容遷移的順序：先讓新舊 API 並存，完成 consumer 遷移，再移除舊 API。

快速 CI 不足以通過審查，因為目前只驗證新 consumer；它無法告訴團隊舊 consumer 是否仍能運作。至少要加入舊 consumer 的 contract／integration 驗證，並依 `build → lint → unit test → 必要的 integration test → review → CI green → merge` 的順序完成檢查。合併前也要確認 branch 已同步最新 `main`。

建議拆成三個可獨立整合的短批次：

1. 先加入 `trackingCode`，保留 `shipmentCode` 的相容支援（依 API 方向可採雙欄位回傳、雙欄位接受後正規化或 adapter），並同時驗證新舊 consumer。
2. 舊 consumer 遷移到 `trackingCode`，在 CI 中持續驗證兩邊，完成後再合併。
3. 確認所有 consumer 已遷移並經過相容期後，另開小 PR 移除 `shipmentCode`，再次完成完整驗證。

若新欄位尚不宜對使用者曝光，可以用 Feature Flag 控制 rollout；但 flag 不能取代 API 的新舊並存，功能穩定後也要清理 flag。本案例不是大型內部實作重構，Branch by Abstraction 不屬於必要技巧。

六題自檢：

1. 能不能切到一天內可以 merge？可以，應拆成相容新增、consumer 遷移、舊欄位清理三個 PR；目前立即改名並刪欄位的單一 PR 切得不對。
2. 這個 PR 現在 merge，`main` 還能正常工作嗎？不能，舊 consumer 要到下週才遷移。
3. 未完成功能能不能用 Feature Flag 隱藏？可作為 rollout 輔助，但不能取代新舊 API 並存，因此目前不能用它合理化刪除舊欄位。
4. 大改造能不能用 abstraction 讓新舊實作共存？不適用；這是 API 相容遷移，不是大型內部實作重構。必要時應在 API 邊界保留相容轉接。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？目前不能；雖然速度快，但只驗證新 consumer，缺少舊 consumer 驗證。
6. 這個 branch 明天還會存在嗎？未知。輸入只說今天開 branch，沒有提供 review 等待與預計合併時間；若要等到下週 consumer 遷移才合併，就已經把多個變更綁在同一 branch。branch 壽命必須包含 review 等待，不能只看今天開立的時間。官方通常以 1～2 天作為短期 branch 的常見範圍，DORA 以不到一天為目標，兩者都不是可單獨取代其他檢查的硬性判準。

「一天 merge 就是 TBD」不成立。每天整合是 DORA 建議的頻率條件之一；仍要同時確認沒有長期開發分支、`main` 維持可工作，以及每次合併有足夠的自動驗證。就本 PR 而言，`main` 可工作性已失敗，因此不能因為 branch 今天開或團隊宣稱一天 merge，就判定符合 TBD。

目前可確認的 workflow 狀態如下：branch 今天開立；CI 速度被描述為快速，但驗證範圍不足；長期共同開發分支、active branch 數量、每人每天是否整合、`main` 紅燈是否立即修復或 revert、是否依賴 code freeze，以及未來 flag 是否清理，情境沒有提供證據，不能當作通過。整體 workflow 因此不能只依「一天 merge」宣稱為 TBD；本 PR 應先改為向後相容並通過舊新 consumer 的 CI，再分開完成遷移與舊欄位清理。
