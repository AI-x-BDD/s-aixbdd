## 完整最終回答

這是變更規劃，並包含 branch／PR／CI 的工作流程檢查。需求沒有提供現有 CI 實際耗時、active branch 數量或團隊目前分支流程；這些現況以下不當作已通過，先列出應採用的規劃與守門條件。

PR 1：建立帳務匯出所需的 domain／query contract 與測試骨架；新增關閉的 `account-export-v2` flag，不接既有匯出入口 — 使用技巧：Feature Flag
PR 2：完成匯出 service／format 與 unit、必要的 integration tests；flag 關閉時不改變任何既有行為 — 使用技巧：Feature Flag
PR 3：接入 API／UI 入口、權限與既有匯出 regression tests；flag 關閉時新入口不可見，既有匯出仍為可用路徑 — 使用技巧：Feature Flag
PR 4：補齊 end-to-end、錯誤處理、監控與第五天開放前的 release checklist；維持 flag 關閉並完成驗證 — 使用技巧：Feature Flag
PR 5：第五天只提交 flag 設定變更，開放新帳務匯出；既有匯出保留，必要時關閉 flag 即可回退 — 使用技巧：Feature Flag
PR 6：新功能穩定後清除 flag 條件與設定，保留既有匯出相容入口；這是開放後的清理 PR，不佔前四天的開發批次 — 使用技巧：Feature Flag

每個 PR merge 後 main 為什麼仍可工作：PR 1、PR 2 是未被呼叫或受關閉 flag 保護的新增程式；PR 3 的新入口仍受關閉 flag 控制，既有匯出不變；PR 4 只增加驗證、錯誤處理與可觀測性，仍不開放新流程；PR 5 同時保留既有匯出，並可用 flag 回退；PR 6 只在新流程穩定後移除切換條件，且需再次驗證新舊入口。每一 PR 都必須在 CI 綠燈後才 merge。

預估 branch 壽命（含等 review）：PR 1～PR 4 各以半天至一天完成並 review，PR 5 的設定變更以數小時內完成並 review，PR 6 同樣切成短批次。開發中至少每天同步 main，merge 前再更新到最新 main；merge 後刪除 branch，active branches 維持少量。官方 TBD 對短期 branch 通常以 1～2 天描述；DORA 以不到一天為目標。review 等待也算 branch 壽命，不能只計算寫程式的時間；這些是來源不同的標準，兩天不是硬性上限。

CI 與整合順序：每個 commit 觸發 build 與自動測試，回饋目標為幾分鐘內；PR 流程固定為 `build → lint → unit test → 必要的 integration test → review → CI green → merge`。PR 2 至少驗證匯出 service，PR 3、PR 4 驗證新流程與既有匯出 regression，PR 5 驗證 flag 開啟與關閉兩種狀態。main 一旦 CI 紅，立即修復或 revert，暫停新功能整合；不靠 code freeze 累積到發布前才處理。

六題自檢：

1. 能不能切到一天內可以 merge？可以；四天拆成 PR 1～PR 4，每一批以一天內完成與 review 為目標，開放日另用小型 PR 5。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以；前四個 PR 不改變預設行為，PR 5 保留既有匯出並可關閉 flag 回退。
3. 未完成功能能不能用 Feature Flag 隱藏？可以；每天 merge、flag 保持關閉，第五天才開放，穩定後清理 flag。
4. 大改造能不能用 abstraction 讓新舊實作共存？本需求未指出大型重構，判定不適用。若實作時發現是大型引擎替換，應依 `建立 abstraction → 接上舊實作 → 加入新實作 → 逐步切換 → 刪除舊實作` 分成可每日 merge 的 PR。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？規劃上可以，需具備上述順序、每 commit 自動 build／test、幾分鐘回饋與既有匯出 regression；目前沒有實際 CI 耗時資料，不能宣稱現況已達成。
6. 這個 branch 明天還會存在嗎？目標是不會；若因工作量或 review 使它跨日，應先拆小或加速 review。跨日是風險訊號，不把官方 1～2 天或 DORA 不到一天誤說成硬性隔夜禁令。

規則來源與團隊選擇：TBD 的核心是沒有長期開發分支、至少每天整合 main、main 維持可工作；branch 很短命、active branches 少、merge 後刪除與避免 code freeze 是強烈建議。branch 命名、reviewer 人數、squash／merge commit／rebase、同步 main 用 merge 或 rebase，則由團隊自行決定，不是 TBD 硬性要求。本次未取得現況資料，因此仍需確認是否存在 `develop` 等長期共同分支、實際整合頻率、CI 回饋速度、main 紅時是否立即修復或 revert、是否依賴 code freeze，以及開放後是否清理 flag。
