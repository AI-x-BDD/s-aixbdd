## 完整最終回答

PR 1：更正文案錯字 — 使用技巧：無

每個 PR merge 後 main 為什麼仍可工作：這是 20 分鐘內可完成的文字修正，不改變功能或介面。工作期間若 main 有更新先同步，merge 前再次更新 branch，依序執行 build → lint → unit test → 必要的 integration test，再走 PR → review → CI green → merge；因此合併後 main 維持可工作。

預估 branch 壽命（含等 review）：半天至一天內，包含 20 分鐘實作、快速 CI 與 review 等待。TBD 官方通常把短期 branch 描述為 1～2 天；DORA 以不到一天為目標，兩者來源與嚴格程度不同，2 天不是硬性上限。merge 後刪除 branch，避免累積 active branches，也不需要 code freeze。

六題自檢：

1. 能不能切到一天內可以 merge？可以；20 分鐘修正，加上已有的快速 CI 與 review，預計當日完成。
2. 這個 PR 現在 merge，main 還能正常工作嗎？可以；只更正文字，且必須先通過完整驗證與 CI green。
3. 未完成功能能不能用 Feature Flag 隱藏？不適用；本案沒有未完成功能，變更可獨立整合。
4. 大改造能不能用 abstraction 讓新舊實作共存？不適用；本案沒有大改造或新舊實作遷移。
5. CI 能不能快速告訴我這次改動有沒有破壞系統？可以；沿用現有快速 CI，讓每個 commit 觸發 build 與自動測試，目標在幾分鐘內回饋，並以 build → lint → unit test → 必要 integration test 驗證。
6. 這個 branch 明天還會存在嗎？預計不會；若 review 等待使 branch 延至明天，等待時間仍要算入 branch 壽命，應重新檢查變更是否切得過大並優先完成整合。

branch 命名、同步 main 使用 merge 或 rebase、merge commit／squash／rebase merge、reviewer 人數及是否禁止 direct push，屬團隊自行決定，不能當成 TBD 的硬性判準。
