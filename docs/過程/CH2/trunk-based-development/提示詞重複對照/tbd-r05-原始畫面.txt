     89 +
     90 +輸入：兩人內部 Web 工具想從 GitFlow 改 TBD，但沒有自動 test，review 每週一次。請比較兩者與導入建議。
     91 +
     92 +實際回答：
     93 +
     94 +GitFlow 以長期 `develop`、release 等分支隔離工作，適合固定版本節奏，但兩人內部工具採用它通常增加分支與整合負擔。
     95 +
     96 +TBD 以短命 branch、頻繁整合 `main`、持續可工作為核心，較適合小團隊與持續變更；但目前沒有自動 test，且 review 每週一次，缺少 TBD 的必要前提。現在直接全面切換，容易讓 `main` 經常壞掉。

     98 +建議分階段導入：
     99 +
    100 +1. 先建立最小 smoke／unit tests、自動 build 與快速 CI。
    101 +2. 將 review 改為當天或下一工作日完成。
    102 +3. 再移除長期 `develop`，採短命 branch → CI → review → `main`。
    103 +4. 未完成功能使用 Feature Flag；只有發布維護需要時才建立短期 release branch。

    105 +完成前提前，不應宣稱目前流程已是 TBD。

    111 +實際回答：
    112 +
    113 +```text
    114 +short-lived branch → 更正文案 → lint／快速 CI → PR + review → merge main → 刪除 branch
    115 +```
    116 +
    117 +程式修改約 20 分鐘，連同快速 CI 與 review 預估 branch 在一天內結束；不需要 Feature Flag、Abstraction 或 release branch。merge 後 `main` 保持可工作。

    119 +## G：來源與分級
    120 +
    121 +輸入：官方是不是規定 branch 最長兩天？DORA 跟官方差在哪？我們用 merge commit、merge 同步 main、兩位 reviewer、GitLab，會違反 TBD 嗎？
    122 +
    123 +實際回答：
    124 +
    125 +官方通常描述 short-lived branch 約 1–2 天，這是常見建議範圍，不是「超過兩天立即違規」的硬性上限。DORA 以 branch 少於一天、至少每天整合、快速 CI 與立即處理 broken trunk 為更嚴格的目標與能力指標。
    126 +
    127 +以下做法本身都不違反 TBD：
    128 +
    129 +- 使用 `merge commit`
    130 +- 用 merge 將 `main` 同步到 branch
    131 +- 指定兩位 reviewer
    132 +- 使用 GitLab
    133 +
    134 +TBD 沒有強制 squash、rebase、GitHub 或特定 reviewer 人數。判斷重點是 branch 是否短命、是否每天整合、`main` 是否持續可工作，以及 review 或 CI 是否造成長時間等待。
