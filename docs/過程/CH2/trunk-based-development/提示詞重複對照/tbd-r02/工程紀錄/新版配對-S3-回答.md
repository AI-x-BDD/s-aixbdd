### A：四天完成活動報名頁，下週曝光

使用 **Feature Flag**，將部署與曝光分開。正式環境預設關閉；頁面入口、直接網址與報名 API 都必須受控。

| PR | 變更與技巧 | merge 後仍可工作原因 | branch 壽命，含 review |
|---|---|---|---|
| A1，第 1 天 | 新增 flag 與受控頁面骨架；Feature Flag | flag 關閉，既有網站照常運作，新入口不可公開使用 | 2～4 小時 |
| A2，第 2 天 | 新增報名表單與輸入驗證；Feature Flag | 未完成流程仍被 flag 隔離，可在測試環境驗證 | 3～6 小時 |
| A3，第 3 天 | 接通報名 API 與儲存，必要結構採相容性新增；Feature Flag | 舊流程不受影響，新 API 同樣受控；開啟時已有完整報名路徑 | 4～6 小時 |
| A4，第 4 天 | 補齊成功、失敗、重複提交處理與完整流程驗證；Feature Flag | flag 關閉時無曝光，開啟時流程完整可用 | 3～6 小時 |
| A5，下週 | 到曝光日開啟 flag；Feature Flag | 使用已驗證的流程，異常時可關閉 | 若需設定 PR，1～2 小時 |
| A6，穩定後 | 移除 flag、過渡設定與不再需要的條件分支；無 | 已確定全面啟用，保留正式流程 | 2～4 小時 |

若 flag 由設定平台控制，A5 是設定操作，不必硬做成程式碼 PR。等待曝光期間不保留開發 branch。

### B：七天更換郵件供應商，目前直接呼叫甲 SDK

使用 **Branch by Abstraction**：建立抽象 → 接上甲 → 加入乙 → 逐步切換 → 刪除甲。抽象負責統一寄信契約與錯誤語意。

| PR | 變更與技巧 | merge 後仍可工作原因 | branch 壽命，含 review |
|---|---|---|---|
| B1，第 1 天 | 新增郵件抽象與甲 adapter，接通一個呼叫點；Abstraction | 實際仍使用甲，既有寄信行為維持可用 | 3～6 小時 |
| B2～Bn，第 2～3 天 | 按模組分批將直接 SDK 呼叫改接抽象；Abstraction | 每批完整接通甲；尚未遷移的模組仍可直接使用甲 | 每個 2～5 小時 |
| Bn+1，第 4 天 | 新增乙 adapter 與契約／整合驗證，預設仍選甲；Abstraction | 新實作尚未接正式流量，甲仍正常服務 | 4～6 小時 |
| Bn+2，第 5 天 | 加入供應商選擇設定，先切一小批寄信類型或租戶到乙；Abstraction | 每封信只走一個供應商，其餘仍走甲，可切回 | 3～6 小時 |
| Bn+3 起，第 6 天 | 依觀察結果分批擴大乙的使用範圍；Abstraction | 未切換批次保留甲；各批驗證投遞、錯誤與重試行為 | 每個 1～4 小時 |
| 最後一個，第 7 天 | 全部切換且驗證穩定後，移除甲 SDK、adapter 與過渡設定；Abstraction | 所有呼叫點已透過抽象使用乙，沒有甲的殘留依賴 | 2～5 小時 |

七天是目標；若乙尚未穩定，不應為了到期而刪甲。切換與回退必須避免不確定投遞結果造成重複寄信，不能直接對甲、乙各寄一次。

### C：維護已發布 4.2，main 為 4.3，兩邊都有同一 bug

採 **Release Branch** 維護 4.2，修復順序固定為 **main 優先，再 backport**。

| PR | 變更與技巧 | merge 後仍可工作原因 | branch 壽命，含 review |
|---|---|---|---|
| C1，目標 main | 重現 bug、加入回歸測試並完成最小修復；修復本身無需特殊技巧 | 4.3 的既有功能通過檢查，且 bug 已修正 | 3～6 小時 |
| C2，目標 release/4.2 | 將已驗證修復 cherry-pick 到 4.2，必要時適配差異；Release Branch | 以 4.2 的建置與測試驗證，不帶入 4.3 新功能 | 2～5 小時 |

若沒有 `release/4.2`，從實際發布的 4.2 tag／commit 建立，不能從目前 main 建立。它只承載版本穩定、bug fix 與發布。

`release/4.2` 可隨支援期間存在；這是版本維護分支。C1、C2 的工作 branch 仍須短命，不把 release branch 當作下一版共同開發線。

### 外部 consumer 分批改用新版查詢 API

使用 **新舊並存（Strangler）**，避免 API 已改、consumer 尚未跟上的中間狀態。

| PR | 變更與技巧 | merge 後仍可工作原因 | branch 壽命，含 review |
|---|---|---|---|
| Q1 | 新增新版查詢 API、契約與測試，完整保留舊版；新舊並存 | 既有 consumer 照常呼叫舊版，新版可獨立驗證 | 3～6 小時；超出則按可用查詢能力再拆 |
| Q2～Qn | 各 consumer 分批改用新版；新舊並存 | 已遷移者用新版，未遷移者仍可用舊版 | 每個 consumer／批次 2～6 小時 |
| Qn+1 | 確認所有外部 consumer 完成遷移、停用條件已滿足後，刪除舊 API；新舊並存收尾 | 已無舊版依賴，移除不會中斷使用者 | 2～4 小時 |

外部遷移可能跨週；等待期間讓兩版留在 main，不讓 branch 跨週等待。無法確認外部 consumer 已遷完，就保留舊 API。

### 共通整合要求

每個小變更重新從最新 main 開短期 branch，工作期間及 merge 前同步 main，依序完成：

**build → lint → unit test → 必要的 integration test → PR → review → CI green → merge → 刪 branch。**

C2 則以 `release/4.2` 為整合目標並驗證該版本。同步 main 到工作 branch 不等於整合回 main；開發期間應至少每天有完成的小變更回到 main。

以上壽命估計都包含 review，需事先安排快速 review。依讀取的 Skill，TBD 官方通常約 **1～2 天**，DORA 以 **不到一天**為目標，並要求至少每天整合 main；兩天不是硬性合格線。branch 隔天仍存在，就檢查切分與 review 等待。

這套安排需要自動 build／test、快速 CI、小批次與快速 review；目前未提供現況，不能視為已具備。main CI 變紅時，優先立即修復或 revert。merge 方式、同步採 merge 或 rebase、reviewer 人數屬團隊選擇；核心是持續整合、避免長期開發分支，並讓 main 持續可工作、可發布。
