# 固定測試輸入與判準

前後測逐字使用以下輸入及執行指示。判準只交給評分者，不交給受測代理。

## 共用執行指示

讀取目前 worktree 的 `.agents/skills/trunk-based-development/SKILL.md`，依該 Skill 處理下列輸入；需要時讀取它引用的資源。僅讀取這個 Skill 的檔案，不讀其他工程紀錄或其他 Skill，不修改檔案，不執行 Git 寫入操作。回覆繁體中文，先列讀取的檔案與確認閘門（沒有則寫無），接著提供完整建議。這是獨立任務。

## S1：正常小變更（回歸）

輸入：請用 trunk-based-development 規劃：通知信主旨少一個空格，修正及測試約 45 分鐘，review 當天可完成，CI 約三分鐘。只給拆分及整合建議。

判準：單一小變更；不強加 Flag／Abstraction；包含可工作依據、CI／review、含 review 的 branch 壽命。同步 main 與 merge 後刪 branch 的流程仍保留。

## S2：流程審查（回歸）

輸入：請審查這個流程算不算 TBD：三人各開兩週 feature branch，期間每天 merge main 到自己的 branch，最後才回 main；PR 只改五行但等 review 三天。團隊用 merge commit 且允許 direct push。main CI 現在紅燈，大家打算晚上再修。另一個新團隊沒有自動測試，想明天全面採用。請區分核心問題、建議、團隊選擇，並比較 GitFlow。

判準：指出單向同步不等於整合、等待計入壽命、立即修／revert、merge 方法與 direct push 非強制規則、先補前提、GitFlow 對照；官方與 DORA 壽命不混為硬界線。

## S3：技巧選擇（回歸）

輸入：請規劃三件獨立工作：(A) 四天完成活動報名頁，下週才可曝光；(B) 七天把郵件供應商從甲換成乙，目前模組直接呼叫甲 SDK；(C) 維護已發布 4.2，main 為 4.3，兩邊都存在同一 bug。另有外部 consumer 必須分批改用新版查詢 API。請列可獨立整合的 PR、技巧、每次 merge 保持可工作原因與含 review 的 branch 壽命。

判準：A Flag 關閉整合及清理；B abstraction、接舊實作、加入新實作、逐步切換、清理；C main 修正驗證後 cherry-pick release，release 不加新功能；API 新舊並存，consumer 遷移後刪舊；各步保持可工作與短 branch。

## S4：本次模組化結構檢查

輸入：本次需求全文（本次對話）；直接檢查兩側目標 Skill，使用 audit_skill.py 與人工逐條核對。

判準：主檔保留 SOP；判斷規則移至適合的 RuleFile，規則都有正反例；每個載入點有條件、READ、具名清單、後續使用及 CHECK；無孤兒資源，既有用途與正確規則可追溯保留，不以檔案數驗收。

## 隔離與限制

- 每案例各開一個 `fork_turns=none` 子代理，不提供父對話、根因或評分判準；前後測採相同工具與上述提示。
- 不覆寫模型與推理設定，繼承主代理預設。工具沒有提供精確後端模型版本、temperature、seed，故無法獨立核實；不能宣稱已完全控制模型內部設定。
- 共用檔案系統，受測為唯讀規劃／審查，無需真實產品程式、網路或 Git 寫入。這是乾淨對話隔離，並非容器隔離。
- 前後測各三個案例、各一次，不能推論穩定性或統計顯著改善。S4 是靜態結構驗收，不冒充行為實跑。
- 目標 Skill 無使用者確認閘門，預先回覆為「無」。工程本身兩個確認閘門另行記錄。
