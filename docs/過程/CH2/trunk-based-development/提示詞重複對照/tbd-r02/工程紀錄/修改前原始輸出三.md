確認閘門：無。Skill 沒有要求規劃後等待使用者確認；以下的 review、CI 綠燈與 merge 前同步 main 是工程上的整合閘門。

共通規則：每個 PR 都從最新 trunk 開出，完成後同步 main，執行 build、lint、unit test 及必要的 integration test，經 review 且 CI 綠燈後 merge，隨即刪除 branch。以下 branch 壽命都包含 review 等待時間；官方通常以 1～2 天為短期 branch，DORA 以少於一天為目標。

## A：四天完成活動報名頁，下週才曝光

技巧：Feature Flag；若需要後端，API 採向後相容的新增方式。

```text
PR A1：加入報名頁 Feature Flag、設定與 route guard
PR A2：加入頁面骨架、表單欄位與前端驗證
PR A3：加入報名 API client／endpoint、送出狀態與錯誤處理
PR A4：加入 accessibility、追蹤與端對端測試
PR A5：下週驗收後開啟 Feature Flag
PR A6：穩定後移除 Feature Flag
```

- A1：0.5～1 天。flag 預設關閉，既有路由不受影響。
- A2：0.5～1 天。頁面程式可存在 main，但 route 仍被 flag 隱藏。
- A3：0.5～1 天。API 是新增能力，不破壞既有 API；flag 關閉時不會被使用。
- A4：0.5～1 天。測試涵蓋 flag 關閉與開啟狀態，main 仍可部署。
- A5：0.25～0.5 天。只在產品驗收、監控與 CI 通過後開啟。
- A6：0.5～1 天。確認不需回退後清理 flag，避免技術債。

四天是功能開發期，不需要讓同一個 branch 存活四天；每個小 PR 都能獨立 merge，使用者直到下週才看得到功能。

## B：七天把郵件供應商甲換成乙

技巧：Branch by Abstraction，加上 Feature Flag／設定切換；保留甲作為回退路徑，避免直接在模組內混用兩套 SDK。

```text
PR B1：建立 MailSender abstraction 與 contract tests
PR B2：建立甲的 adapter，讓原模組改呼叫 abstraction
PR B3：加入乙的 adapter，甲仍是預設實作
PR B4：加入 provider selector、設定與 Feature Flag
PR B5：對內部或小批量收件人啟用乙，加入 metrics 與錯誤監控
PR B6：驗證通過後將預設 provider 切為乙，保留甲回退設定
PR B7：穩定期結束後移除甲的 adapter 與 SDK
```

每個 PR 目標為 0.5～1 天，包含 review：

- B1 沒有 runtime 行為變更。
- B2 仍使用甲，確保重構前後寄信行為一致。
- B3 新舊 adapter 共存，尚未改變預設路徑。
- B4 預設仍為甲，切換可以快速回退。
- B5 只讓限定流量走乙，甲仍可處理其他寄信。
- B6 乙已通過相同 contract、integration 與 canary 驗證，仍保留回退設定。
- B7 只有在不再需要回退時才刪除甲；刪除前確保乙是唯一且已驗證的實作。

不要用雙發送來驗證寄信，否則可能讓收件人收到重複郵件；用 adapter contract tests、測試收件人、canary 與 metrics 驗證即可。

## C：維護已發布 4.2，main 為 4.3，兩邊都有同一個 bug

技巧：Release Branch；採 fix on trunk first。

```text
PR C1：在 main 修 bug，補回歸測試
PR C2：將 C1 的修正 cherry-pick 到 release/4.2
PR C3：在 release/4.2 驗證並發布 4.2.x patch
```

- C1：0.5～1 天，包含 review。先修 main，讓 4.3 不再保留這個 bug。
- C2：0.5～1 天，包含 review。從 `release/4.2` 套用同一修正並執行 4.2 相容性測試。
- 若兩版本程式碼有差異，先完成並 merge main 的修正，再在 4.2 做等價 backport；不能只在 release branch 修。
- `release/4.2` 可以在 4.2 支援期間持續存在，但它只承載穩定、bug fix 與發布，不承載新功能；這是 TBD 允許的 release branch，不是長期 feature branch。

每次 merge 後，main 或 `release/4.2` 都有對應版本的回歸測試，因此仍可工作。

## 外部 consumer 分批改用新版查詢 API

這是額外的相容性遷移流，應獨立於 A、B、C；技巧是新舊並存（Strangler／向後相容 API）。

```text
PR Q1：新增新版查詢 API，保留舊版 API
PR Q2：加入共用實作、contract tests、使用量 telemetry 與遷移文件
PR Q3…Qn：每個 consumer 或 consumer cohort 各自遷移到新版 API
PR Qfinal：確認舊版流量為零並經過 deprecation window 後移除舊 API
```

- Q1：0.5～1 天。新版是新增介面，既有 consumer 不需同步修改。
- Q2：0.5～1 天。可觀測哪些 consumer 尚未遷移。
- Q3…Qn：每個 consumer PR 目標 0.5～1 天，獨立 review、contract/integration test；不要建立一個涵蓋所有 consumer 的長期 migration branch。
- Qfinal：0.5～1 天。只有在所有外部 consumer 已切換且確認沒有舊流量後，才移除舊 API。

每個 consumer merge 後仍可使用舊版 API；新版與舊版同時存在，這使外部團隊能分批遷移。若新版 API 與 C 的 bug 位於同一查詢模組，先把 C 的回歸修正納入共用實作，再開始 Q1；否則維持兩條獨立工作流。
