- `.agents/skills/trunk-based-development/SKILL.md`
- 必要引用資源：無；題目內容已由主 Skill 覆蓋，因此未讀 `references/cases.md`。
- 使用者確認閘門：無。
- Skill 的合併閘門：`PR → review → CI green → merge`；並確認 build、lint、unit test、必要的 integration test 通過。

判定：三人各開兩週 feature branch，每天把 `main` merge 進自己的 branch，最後才合回 `main`，不算 TBD。

核心問題：

1. 兩週 feature branch 是長期分支。官方通常建議約 1～2 天，DORA 以不到一天為目標。
2. 每天同步 `main` 到 feature branch 只是更新自己的分支，不是把小變更持續整合回 trunk。真正的整合仍延後到兩週後。
3. 五行 PR 等 review 三天，branch 壽命要包含 review 等待時間；小 PR 仍可能造成三天的整合延遲。
4. `main` CI 已紅卻等晚上再修，違反 main 必須保持可工作的核心規則。應立即修復或 revert 造成問題的變更，暫停新的功能整合。
5. merge commit 與 direct push 本身不是 TBD 的判定條件。它們屬於團隊選擇；但 direct push 若繞過 review 或 CI，會破壞保持 `main` 可工作的要求。

建議：

- 把兩週工作拆成可獨立合併的小 PR，每個 branch 目標在幾小時到一天內完成 review、CI 與 merge。
- 未完成但不能曝光的功能使用 Feature Flag；大型重構使用 Branch by Abstraction；跨 API 變更採新舊並存。
- 建立快速 review 機制，例如 reviewer 輪值與明確回應時限，避免五行 PR 排隊三天。
- `main` 設定相同的 CI 與 review 閘門；若保留 direct push，仍不可繞過這些檢查。
- CI 紅燈時優先修復或 revert，不能把修復延後到晚上。
- 新團隊沒有自動測試，不建議明天全面採用 TBD。先補自動 build、基本自動測試、快速 CI、gated checks，以及「broken trunk 優先修復」的團隊紀律，再用一個小範圍專案試行，確認穩定後擴大。

GitFlow 類流程是「先隔離、完成整個功能、最後整合」；TBD 是「切成小變更、持續整合、讓 `main` 隨時可工作」。目前這個兩週 branch、最後才合回的流程較接近 GitFlow 類，即使沒有明確建立 `develop` branch。採用哪一種屬於團隊選擇，但在頻繁發布、多人同時修改的情境，這份 Skill 建議優先採用短 branch 與持續整合。
