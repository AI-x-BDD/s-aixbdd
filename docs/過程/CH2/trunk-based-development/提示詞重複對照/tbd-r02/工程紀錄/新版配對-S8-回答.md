| 比較面向 | Trunk-Based Development（TBD） | GitFlow |
|---|---|---|
| 工作拆分 | 先把需求切成可安全整合的小變更，功能尚未全部完成也能逐步整合 | 通常先隔離功能開發，完成後再整合 |
| 整合方式 | 圍繞單一 trunk（通常是 main），頻繁把小變更整合回去 | 透過 feature、develop、release 等分支分階段整合 |
| 整合時機 | 持續整合，避免程式碼長時間分離 | 以功能完成或發布階段作為主要整合時點 |
| 主線狀態 | main 持續保持可工作、可發布；CI 失敗時優先修復 | 以不同分支承接開發、發布準備與正式版本 |

TBD 的核心是「不要讓大家的程式碼分開太久」。主要改變的是**工作拆分與整合習慣**，Git 操作本身不一定有很大差異。每天把 main 更新到 feature branch，卻兩週後才合回 main，仍不算每天整合回主幹。

規則來源也要分清楚：依此 Skill，TBD 官方（TrunkBasedDevelopment.com）的短期分支通常約 1～2 天，包含等待 review；Google DORA 的研究標準較嚴格，以分支不到一天、至少每天整合回主幹一次為目標。這些不能混稱為同一個硬性期限。

下列設定**都不能單獨判定採用哪種方法**：

| 設定 | 能否判定 | 原因 |
|---|---|---|
| Squash merge | 不能 | Squash、merge commit、rebase merge 都是團隊選擇，不決定工作隔離多久、何時整合 |
| Reviewer 人數 | 不能 | 人數是團隊政策；等待 review 的時間會影響分支壽命，但沒有固定人數才能算 TBD |
| 允許 direct push | 不能 | TBD 可以直接整合主幹，也可以採短期 branch／PR；允許或禁止 direct push 都不足以定性 |

實際判斷 TBD，應看三件事：**沒有長期開發分支、頻繁整合回 main、main 持續保持可工作**。GitFlow 則應看是否採功能隔離及分階段整合的工作方式，不能只看分支名稱或 merge 按鈕。
