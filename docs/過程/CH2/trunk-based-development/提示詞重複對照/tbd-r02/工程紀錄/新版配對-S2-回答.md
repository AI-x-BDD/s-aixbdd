**目前流程不符合 TBD。** 核心問題是程式碼分離兩週才回 main，以及 main CI 紅燈後延後修復；merge commit 和允許 direct push 本身不構成違規。

以下依 Skill 的區分：TBD 官方指 TrunkBasedDevelopment.com；DORA 是 Google DORA 的 DevOps 研究，其目標通常更嚴格；其餘 Git 政策由團隊決定。

### 核心問題

| 現況 | 判斷 |
|---|---|
| 三人各開兩週 feature branch，最後才回 main | 屬長期隔離開發，不符合沒有長期開發分支、頻繁整合主幹的核心要求。 |
| 每天 merge main 到自己的 branch | 只是同步主幹更新，沒有把自己的變更整合回共同主幹，不能算每天完成整合。DORA 要求至少每天整合回主幹一次，一天多次更好。 |
| PR 只改五行，等 review 三天 | 行數小不代表整合快。Branch 壽命包含等待 review；光等待就已三天，仍是整合瓶頸。 |
| main CI 紅燈，打算晚上再修 | 不符合 main 保持可工作、可發布的要求。應停止新功能工作，立即修復；不能迅速修好時立即 revert，恢復綠燈後再繼續。 |

### 建議

1. **先恢復 main，再調整工作拆分。** 把兩週功能切成幾小時至一天能完成、可獨立整合的變更；一張 Story／Ticket 可以對應多個 PR。每次 merge 後 main 都必須仍可工作，不能先破壞 API，再等後續 PR 補 consumer。

2. **縮短包含 review 的整體等待。** TBD 官方的短期 branch 通常約 1～2 天；DORA 以不到一天為目標，兩天不是硬性合格線。安排快速 review，避免五行 PR 卡三天；branch 隔天仍存在時，檢查拆分與等待原因。

3. **依阻礙選技巧，不用長期 branch 等全部完成。**
   - 功能尚不能曝光：用 Feature Flag 關閉曝光，持續整合；部署與開放使用分開，穩定後清除 flag。
   - 大型重構：用 Branch by Abstraction，先建立抽象並接上舊實作，再加入新實作、逐步切換、刪除舊實作。
   - API／相容性遷移：新舊並存，consumer 遷移完成後才移除舊介面。
   - 可直接完成的小修改：不必引入特殊技巧。

   本次未提供 Feature Flag 使用情況，**無法確認是否有清理**，需補查已上線且穩定的 flag。

4. **若採短期 branch／PR 路徑：** 切小 → 每個小變更開短期 branch → 工作期間及 merge 前同步 main → build、lint、unit test、必要的 integration test → PR、review、CI 綠燈後 merge → 刪 branch。這是該路徑的建議，不是所有 TBD 團隊必用的 Git 操作。另應保持少量 active branches，避免靠發布前 code freeze 集中處理整合。

### 團隊選擇

下列項目不決定是否為 TBD：

- Squash、merge commit 或 rebase merge。
- 同步 main 使用 merge 或 rebase。
- 是否允許 direct push。
- Branch 命名、reviewer 人數、GitHub 或 GitLab。

因此，團隊可以保留 merge commit 與 direct push 政策，但仍須做到頻繁整合、快速檢查及主幹故障優先修復。

### 沒有自動測試的新團隊

**不建議明天全面導入。** 已知缺少自動測試；自動 build、快速 CI、gated checks、小批次開發能力、快速 review、團隊經驗及主幹修復紀律則尚未確認。

應先補齊這些前提，再從小範圍試行。依 DORA 建議，每個 commit 都觸發 build 與自動測試，幾分鐘內取得回饋。缺少這些能力時，只要求每天 merge 可能增加錯誤與返工。

### 與 GitFlow 比較

| 面向 | GitFlow 類流程 | TBD |
|---|---|---|
| 工作方式 | 先隔離功能，做完整後再整合 | 先切成可工作的小變更，持續整合 |
| 整合時機 | 較晚集中整合，衝突與相容性問題可能延後暴露 | 頻繁回到共同 main，及早取得整合回饋 |
| 未完成功能 | 主要留在功能分支等待完成 | 透過小批次、flag、抽象層或相容性設計持續進 main |
| 主幹狀態 | 完整流程還需看團隊規則 | 持續保持可工作、可發布 |

你們目前「隔離兩週、最後回 main」的行為較接近 GitFlow 類的整合方式，但資訊不足以認定採用了完整 GitFlow。改成 TBD 的主要工作是改變**拆分與整合時機**，不只是換 branch 名稱或 merge 選項。

TBD 也可以有維護發布版本的 Release Branch：很晚才切，只做穩定、修復與發布；bug 先在 main 修復及驗證，再 cherry-pick 過去，不讓它變成持續開發新功能的另一條主線。
