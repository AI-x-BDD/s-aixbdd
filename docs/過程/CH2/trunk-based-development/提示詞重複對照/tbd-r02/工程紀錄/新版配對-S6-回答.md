**目前 PR 不應以「先移除舊 endpoint，明天才改 consumer」的方式合入 main。** TBD 要求小變更持續整合，同時保持 main 可工作、可發布。

問題有三項：

- **拆分造成不相容的中間狀態。** 兩個外部 consumer 尚未遷移，今天刪除 endpoint，main 就無法繼續支援現有 consumer。即使今天不部署，也失去可隨時發布的條件。
- **mock 單元測試綠燈不足以證明整合安全。** mock 可能保留舊契約，無法發現真實 endpoint 已移除；應補上兩個 consumer 的契約驗證及必要的 integration test。
- **已 merge 的 branch 留三星期未刪，應清理。** merge 後刪 branch 是強烈建議；但僅憑殘留三星期，不能推定程式碼三星期未整合，也不能直接判成長期開發分支。

可行拆分採用**新舊並存（Strangler）**：

| PR | 變更與技巧 | merge 後 main 為何仍可工作 |
|---|---|---|
| PR 1：今天 | 保留或恢復舊 endpoint，提供新 endpoint；加入相容性驗證。技巧：新舊並存 | 現有兩個 consumer 繼續使用舊 endpoint，新介面可獨立驗證 |
| PR 2：consumer A | 在其所屬 repo 遷移、驗證並部署 consumer A。技巧：新舊並存期間的遷移 | A 使用新介面，B 仍可使用舊介面 |
| PR 3：consumer B | 在其所屬 repo 遷移、驗證並部署 consumer B。技巧：同上 | 兩個 consumer 均可使用新介面，舊介面暫時保留 |
| PR 4：最後清理 | 確認兩個 consumer 已實際部署切換，且無舊介面依賴後，移除舊 endpoint。技巧：完成新舊並存 | 移除時已無 consumer 依賴舊契約 |

若新 endpoint 已存在，PR 1 只需撤出刪除舊 endpoint 的變更，並補足驗證。**「明天修改」或「consumer PR 已 merge」都不足以作為刪除條件，須確認實際切換完成。** 若破壞相容性的 PR 已合入，應立即恢復舊 endpoint 或 revert，不等待明天。

每個 PR 應切到幾小時內可完成，含 review 以不到一天為目標；外部遷移等待期間，讓相容程式留在 main，不讓單一 branch 一直等待。短期 branch／PR 流程為：切小 → 開 branch → 工作期間及 merge 前同步 main → build → lint → unit test → 必要的 integration test → PR／review／CI green → merge → 刪 branch。

來源與強度須區分：TBD 官方通常建議 branch 約 1～2 天；DORA 以不到一天、至少每天整合回 main 為目標，兩天不是硬性合格線。merge／rebase／squash 等方式由團隊決定。本案關鍵是**先維持相容、逐一遷移、最後移除**。
