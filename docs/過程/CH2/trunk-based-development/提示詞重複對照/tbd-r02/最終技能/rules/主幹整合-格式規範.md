# Rule 1 - 區分 TBD 目的與規則來源

- 說明 TBD 時，應以「不要讓大家的程式碼分開太久」解釋核心目的：所有人圍繞單一 trunk（main）工作，持續整合，main 保持可工作、可發布。
- 回答時必須區分規則來源：TBD 官方是 TrunkBasedDevelopment.com；DORA 是 Google DORA 的 DevOps 研究，標準通常比官方嚴格；團隊規則是 TBD 沒規定、由團隊自行決定的部分。

## Good Example

同一個說明保留共同整合的目的，且區分來源。

- 說明團隊透過單一 main 持續整合來避免長期分離，並分別標明官方、DORA 與自家團隊政策。

## Bad Example

同一說明只看名稱，或把團隊政策冒充官方定義。

- 只因 branch 叫 main 就說已經做到 TBD；把自家要求 squash、兩個 reviewer 全稱為 TBD 官方規定。

# Rule 2 - 以核心整合行為判斷 TBD

- 判斷是否符合 TBD 時，必須檢查沒有長期開發分支、頻繁整合 main、main 保持可工作這三項核心規則。
- 不得只因工作 branch 從 main 開出就判為 TBD；feature branch 活 2～3 週、develop／team-a／release-next 長期共同開發、多人共用 feature branch 都是需指出的錯誤模式。
- 必須區分把 main 同步到工作 branch 與把小變更整合回 main；DORA 要求至少每天整合 main 一次，一天多次更好。
- main CI 紅了必須先修 main，不繼續開發新功能；依 DORA 建議立即修或立即 revert，不得等到晚上再看。

## Good Example

同團隊以實際回到 main 的整合及可工作狀態判斷。

- 每人把小變更至少每天整合回 main；CI 紅了優先修復或 revert，恢復可工作後再繼續新功能。

## Bad Example

同團隊只做單向同步並延後處理壞掉的主線。

- 多人共同開發一條長 feature branch，每天把 main 更新進去，兩週後才合回，卻宣稱每天整合；main 紅了仍繼續新功能，晚上再修。

# Rule 3 - 區分短命目標與強烈建議

- Branch 應非常短命，壽命必須包含等 review 的時間；官方通常約 1～2 天，DORA 以不到一天為目標，不得把兩天說成硬性標準。
- active branches 應少；應避免靠 code freeze 解決整合問題；merge 後應刪 branch。這些屬強烈建議，必須與核心規則區分。
- 審查時應指出 PR 小但等 review 三天、branch 一直不刪、接近 release 就 code freeze 的問題；branch 明天仍存在時，應檢查是不是切得太大。

## Good Example

同一 branch 的評估計入等待，並區分目標與強度。

- 一天寫完卻等兩天 review，算三天壽命，建議縮短等待與檢查切分；分開說明官方約 1～2 天與 DORA <1 天目標。
- 同時指出 active branches 太多、靠 freeze 整合及 merge 後未刪 branch 的風險。

## Bad Example

同一 branch 漏算等待，或把建議當硬門檻。

- 一天寫完等兩天 review 仍算一天，並說只要不超過兩天就必定是 TBD；靠 code freeze 收尾，已 merge branch 留著也不檢查。

# Rule 4 - 團隊選擇不冒充 TBD 要求

- Squash／merge commit／rebase merge、同步 main 用 merge 還是 rebase、branch 命名、reviewer 人數、GitHub 或 GitLab、是否禁止 direct push，都可以由團隊決定，不得說成 TBD 的要求。
- 使用短期 branch／PR 的示範流程時，必須保留其適用範圍，不得推定所有團隊都必須採相同 Git 操作。

## Good Example

同一團隊的 Git 選擇與核心整合行為分開評估。

- 團隊採 merge commit、自訂 reviewer 人數與 direct push 政策；審查時依實際整合行為判斷，而不是只看是否 squash。

## Bad Example

同一團隊只因選了不同 Git 選項就被誤判。

- 因團隊不用 squash、沒有特定 reviewer 人數或允許 direct push，就直接說不算 TBD。

# Rule 5 - 審查導入前提與適用情境

- 導入前應具備自動 build、自動 test、快速 CI、小批次開發能力與快速 code review；DORA 建議每個 commit 都觸發 build 與自動測試，回饋在幾分鐘內。
- 缺經驗、缺 gated checks 或沒有 broken trunk 優先修復紀律時，必須先指出缺的前提，不得直接建議全面導入；DORA 指出此時可能增加錯誤與返工。
- 評估適用情境時，可以列出 SaaS、Web App、Backend API、Frontend App、Microservice、企業內部系統、頻繁發布、多人共同維護的 codebase；需求一直變、多人同時改、需要頻繁 release 三者同時成立時價值最高。

## Good Example

同團隊先補足整合安全前提，再考慮導入。

- 頻繁發布的 Web 團隊沒有自動測試，先指出需補 build／test、快速 CI、review、小批次與 broken trunk 紀律，不直接建議全面改用 TBD。

## Bad Example

同團隊只換 branch 政策就被當成準備完成。

- 沒有自動測試的 Web 團隊被建議明天全面導入，只要每人每天 merge 就會安全，忽略 CI、經驗與修復紀律。

# Rule 6 - 比較工作整合方式

- 比較時必須區分：GitFlow 類先隔離 → 做完整 → 最後整合；TBD 先切小 → 持續整合 → 任何時候都保持可工作。
- 應指出 TBD 主要改變拆分工作的方式，Git 操作本身變化不大，不得只用 branch 名稱或 merge／rebase 選擇當作方法論差異。

## Good Example

同一比較聚焦工作拆分及整合時機。

- GitFlow 類把功能隔離到完成後才整合；TBD 把需求切小、持續回 main，因此團隊需要改變工作拆分習慣。

## Bad Example

同一比較只看工具細節，沒有說明整合方式。

- 把 GitFlow 與 TBD 的差異說成 branch 叫 develop 或 main，或說一個必須 merge、另一個必須 rebase。
