# Rule 1 - 先切可獨立整合的小變更

- 必須先把需求拆成能獨立整合的小變更。一張 Story／Ticket 不等於一個 branch 或一個 PR。
- 每個小變更必須保持 main 可工作；不得為了 merge 小，把不能工作的程式 merge main，或造成「API 改了、前端還沒跟上」的中間狀態。
- 判斷時必須先看幾小時／一天內能否完成，再看能否切更小；可以時切成多個小 PR，分別重新判斷。
- 無法直接完成或再切小時，必須依原因選技巧：功能還不能曝光用 Feature Flag，大型程式重構用 Branch by Abstraction，舊系統／相容性遷移用新舊並存，維護已發布版本用 Release Branch。
- 小 bug 等可直接完成的小變更可以不使用特殊技巧；不得只因需求工期較長就讓單一 feature branch 存活到全部完成。
- 未完成的工作應靠小批次、Feature Flag、抽象層、向後相容、CI、自動測試整合，不得靠長期開發分支藏起來。

## Good Example

切成可工作的整合單位，小變更也不強加技巧。

- 三天的資料列表功能拆成 API client、列表骨架、讀取資料、分頁數個 PR；每次整合仍可工作，未能曝光的部分另依曝光技巧處理。
- 同專案的小文案修正可在一個短期 PR 完成，技巧為無。

## Bad Example

同需求把工期等同 branch 壽命，或為了切小而破壞 main。

- 三天的資料列表功能只開一個 branch，全部做完才合回；或先移除可用 API，等下一個 PR 才修 UI。
- 同專案的小文案修正也要求先引入抽象層，沒有情境上的理由。

# Rule 2 - 用 Feature Flag 分離部署與曝光

- 功能還不能曝光時，應使用 Feature Flag 關閉功能，程式每天 merge，最後打開（Deploy ≠ Release）。
- 功能上線並穩定後應刪除 flag；不得把不清理的 flag 當作沒有技術債。
- 審查團隊 workflow 時，必須檢查 Feature Flag 有沒有清理。

## Good Example

相同曝光限制透過 flag 控制，並保留清理步驟。

- 帳務頁要到公布日才能開放，開發期間 flag 關閉、小批次持續進 main；驗證後開啟，穩定後刪 flag。
- 審查這個團隊時，核對其已上線 flag 是否清理，而非只檢查 branch 壽命。

## Bad Example

同帳務頁把發布等待藏在長 branch，或讓 flag 永久累積。

- 功能到公布日才把一週的 branch 合回；或功能已穩定，仍將永不清理 flag 視為沒有問題。
- 審查這個團隊時，只因 branch 短就省略 Flag 清理檢查。

# Rule 3 - 用 Abstraction 漸進替換實作

- 大型程式重構應採 Branch by Abstraction：建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作。
- 每一步都必須可整合到 main，不得等整個替換完成才合回長期 branch。

## Good Example

新舊實作在 main 共存，替換可逐步整合。

- 更換付款 SDK 時，先建抽象並接舊 SDK，再加新 SDK、逐步切換，最後刪舊 SDK；各步分別整合。

## Bad Example

同替換隔離太久或過早刪掉可用實作。

- 更換付款 SDK 開一週 branch 最後才合回；或抽象尚未接好就先刪舊 SDK，讓 main 暫時不能付款。

# Rule 4 - 相容性遷移先並存後移除

- 改 API 或做舊系統相容性遷移時，應採新舊並存（Strangler）：先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。
- 每一步都必須保持可工作，不得讓 main 處在 API 已改、consumer 還沒跟上的中間狀態。

## Good Example

同一 API 遷移讓 consumer 有可工作的過渡路徑。

- API 欄位遷移先保留 v1 並新增 v2，各 consumer 分批遷移後才刪 v1。

## Bad Example

同一遷移先破壞舊契約，再等待 consumer 補上。

- API 欄位遷移先刪 v1，consumer 要幾天後才切到 v2，期間仍把 main 當作可工作。

# Rule 5 - Release Branch 只維護發布版本

- Release Branch 應很晚才切，只負責該版本的穩定、bug fix、發布；不得承載持續的新功能開發。
- Bug 必須先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch；不得只在 release branch 修再回灌 main。
- 判斷時必須區分維護已發布版本的 Release Branch 與長期共同開發分支，不得只因 release branch 存在就認定違反 TBD。

## Good Example

相同版本維護以 main 為修復來源，release 不承載下一版開發。

- 已發布 2.7 有共通 bug，在 main 修正及驗證，再 cherry-pick 到 release/2.7；該分支只做版本穩定、修復與發布。

## Bad Example

同一分支變成開發線，或讓 main 可能漏掉修正。

- 只在 release/2.7 修共通 bug，再把整包變更回灌 main；並在 release/2.7 繼續開發下一版功能。
