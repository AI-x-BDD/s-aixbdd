# 短提示詞共同案例評分

評分者：主代理。依 [事前固定判準](../測試輸入.md) 核對 [實際原始輸出](共同案例原始輸出.md)，執行代理未取得判準。

| 案例 | 結果 | 可核對內容 |
| --- | --- | --- |
| S1 | 通過 | 單一短期 PR、同步／review／CI／刪 branch，main 安全理由與含 review 壽命。 |
| S2 | 通過 | 四組小 PR、flag 關閉、逐步安全整合與 branch 壽命。 |
| S3 | 通過 | 抽象與舊 Axios、新 Fetch、分批 consumer、驗證後清理；每天 merge。 |
| S4 | 通過 | API 新舊並存，consumer 就緒後切換，最後才移除舊介面。 |
| S5 | 通過 | 每日整合，週五才開 flag；區分部署與 release，交代清理。 |
| S6 | 通過 | main 先修驗證，再 cherry-pick release；不帶入新功能。 |
| S7 | 通過 | 官方通常1–2天、DORA不到一天，兩天非硬標準，review等待計入。 |
| S8 | 通過 | merge方式、direct push與reviewer人數屬團隊選項，查實際整合結果。 |
| S9 | 通過 | main立即修或revert，拆除兩週develop問題，不能以freeze解決整合。 |
| S10 | 通過 | 先補build/test/CI/review前提並試點，說明GitFlow隔離與TBD持續整合。 |

本輪10/10，僅表示固定十題判準通過。驗收前後逐檔SHA-256一致。文字情境未執行產品、Git、CI或部署。

## 判準之外的輸出觀察

- S2提到「週五或完成驗證前」，題目只有三天且沒有指定週五；這是本輪額外加入的排程措辭，不能當作輸入事實。
- S6把修正branch與release branch一併建議短期存在，後接「或依團隊發布規則保留release branch」。原版沒有要求維護release branch必須與feature branch同壽命；解讀時應保留後面的團隊政策條件，不擴大成TBD硬規則。
- 這些附帶觀察不改寫預先固定的十題評分，但不因10/10就宣稱所有回答完全等價。
