## S1

### 原始輸入

按鈕顏色錯誤，修正加測試約 30 分鐘。請規劃 PR、分支與整合方式。

### 回答

這是幾小時內可完成的小變更，使用一個短期 branch 與一個 PR 即可。

```text
branch：fix/button-color
PR：修正按鈕顏色，加入對應測試
```

先從最新 `main` 開 branch，修改與測試完成後同步 `main`，送 PR，依序通過 review、build、lint、unit test（必要時再跑 integration test）後 merge `main`，merge 後刪除 branch。這個 PR 沒有未完成的跨層依賴，merge 後 `main` 應仍可工作。

branch 壽命要包含 review 等待。若 review 與 CI 能在當天完成，預估約半天至一天；題目沒有提供實際 review 等待時間，所以無法確認確切壽命。TBD 官方常見短期 branch 約 1～2 天，DORA 以不到一天為目標；兩天不是 TBD 的硬性上限。

## S3

### 原始輸入

Axios 換 Fetch wrapper 需一週，不能中斷現有功能。請安排每天可 merge 的步驟。

### 回答

這是大型程式遷移，使用 Branch by Abstraction，不建立一個活一週的 migration branch。先讓現有 Axios 實作接在抽象層後面，再逐步加入 Fetch、遷移 consumer，最後才移除舊實作；每天完成一個可工作的 PR 並 merge `main`。

```text
第 1 天／PR 1：建立 HTTP wrapper 介面與契約測試，先接既有 Axios adapter
           可 merge 理由：consumer 的呼叫路徑與行為不變，Axios 仍是預設實作。

第 2 天／PR 2：加入 Fetch adapter，通過同一組 wrapper contract tests
           可 merge 理由：新實作尚未取代預設路徑，既有功能仍走 Axios。

第 3 天／PR 3 以後：每個 consumer 各自改用 wrapper，必要時逐個切到 Fetch
           可 merge 理由：每次只改一個小 consumer，失敗時可回到仍存在的 Axios adapter。

第 4 天／PR：選定 consumer 切換 Fetch，補齊錯誤處理、timeout、header 等相容性測試
           可 merge 理由：切換仍在抽象層之後，未遷移 consumer 不受影響。

第 5 天／PR：確認所有 consumer 已遷移後移除 Axios adapter 與相依套件
           可 merge 理由：前一步已證明所有呼叫者使用 wrapper；CI 與整合測試綠後才清理。
```

每個 PR 都應在開發期間同步 `main`，經 review 與 CI 後 merge、刪 branch；每一個 branch 的壽命含 review 等待，目標是一天內。consumer 數量、實際 HTTP 行為與相容性要求未提供，所以上述天數是可調整的安排，不是已知產品排程。

## S4

### 原始輸入

後端 API 與前端 consumer 由不同人改，不能同時完成，整體需三天。如何分批整合？

### 回答

用新舊並存，先加後端的新 API 或相容版本，保留舊 API；前端 consumer 準備好前，不能把舊 API 改成只有新契約。每一批都從最新 `main` 開短期 branch，完成 review 與 CI 就 merge。

```text
PR 1（後端）：以 additive 或版本化方式加入新 API，保留舊 API 與既有回應
              技巧：新舊並存（Strangler）
              可 merge 理由：尚無 consumer 使用新 API，舊前端仍可使用舊 API。

PR 2（前端）：加入新 consumer 的相容 adapter／新契約支援，預設仍走舊 API
              技巧：新舊並存
              可 merge 理由：前端同時能處理既有路徑；新路徑未準備好時不取代舊路徑。

PR 3（整合）：在 contract、integration 與權限測試通過後，切換 consumer 到新 API
              技巧：新舊並存
              可 merge 理由：前後端都已支援，切換後仍可保留回退路徑。

PR 4（清理）：確認沒有 consumer 使用舊 API 後，再移除舊 API 與相容程式
              技巧：新舊並存
              可 merge 理由：清理是獨立且可驗證的最後變更，不把未完成的中間狀態放進 main。
```

三天是整體時程，不是單一長期 branch 的壽命；每個 PR 的 branch 都應把 review 等待算入，目標短於一天。若後端無法以 additive 或版本化方式保留舊契約，應先建立相容層，再讓前端逐步遷移；題目沒有提供這項技術事實，因此不能斷定具體 API 方案。

## S5

### 原始輸入

新的操作介面週五才開放，週一 UI、週二 API、週三驗證、週四追蹤。如何每天整合且避免提早曝光？

### 回答

以 Feature Flag 控制曝光，flag 從週一到週四保持關閉；每天仍把小變更 merge 到 `main`。UI 與 API 都要有與 flag 或權限相容的保護，不能只把入口藏起來卻讓新 API 提早對外可用。

```text
週一／PR：加入 UI shell 與新入口，default-off flag
          可 merge 理由：flag 關閉時不渲染、不改變既有操作介面。

週二／PR：加入 API 與必要的資料流程，沿用同一個關閉狀態／服務端保護
          可 merge 理由：既有 API 與舊 UI 繼續工作；新路徑在 flag 關閉時不對外開放。

週三／PR：補驗證、unit/integration 測試與內部驗證設定
          可 merge 理由：用受控的內部 flag 或 allowlist 驗證，公開 flag 仍關閉。

週四／PR：加入追蹤、錯誤監測與開放前檢查
          可 merge 理由：監測程式本身不改變公開行為，flag 仍關閉。

週五：CI 綠、review 完成且驗證結果可接受後才打開 flag；這是 release，不必把程式延到週五才 merge。
```

每個 daily branch 都應在當天完成 review、CI、merge 與刪除；若 review 等待跨日，branch 壽命應如實計入。新功能上線後清理 flag，避免留下技術債。題目沒有說明是否有服務端 flag、內部 allowlist 或監測工具；若沒有，先補上可控的保護與驗證機制，才能安全地在週三測試而不提早曝光。

## S6

### 原始輸入

production 是 1.5，main 是 1.6，兩邊都有同一個 bug。如何修與發佈 1.5？

### 回答

採用 Release Branch，但 bug 先修在 trunk，再把同一個修正 cherry-pick 到 1.5 的 release branch；不要只在 1.5 修完再回灌 `main`。

```text
1. 從最新 main 開短期 `fix/<bug>` branch，重現 bug、加入回歸測試並修正。
2. 送 PR 到 main；review、build、lint、unit/integration test 通過後先 merge main，讓 1.6 也取得修正。
3. 從代表 production 1.5 的 release branch／commit 建立或使用 `release/1.5`；把已在 main 驗證過的修正 cherry-pick 到該 release branch。
4. 在 release branch 只做 1.5 的 bug fix 與發布驗證，跑對應回歸測試，通過後發布 1.5。
5. 若 cherry-pick 發生衝突，依 1.5 的程式碼語境保留等價修正並補驗證；不要把 1.6 新功能帶入 1.5。
```

`release/1.5` 只承載該版本穩定與發布工作，不能用來放新功能。修正 branch 與 release branch 都應短期存在並在完成後刪除或依團隊發布規則保留 release branch；實際 branch 名稱與發布流程是團隊規則，未由題目提供。

## S7

### 原始輸入

我們 PR 都很小，但 review 常等三天。只要 branch 不超過兩天就是符合 TBD 的硬性標準嗎？

### 回答

不是。兩天不是 TBD 的硬性上限，而且 branch 壽命要包含 review 等待。

- TBD 官方：短期 branch 通常約 1～2 天。

- 核心規則：沒有長期開發分支、至少每天整合 `main`，並讓 `main` 保持可工作。
- 團隊規則：團隊可以另訂兩天上限，但那是團隊門檻，不是 TBD 官方硬性標準。

如果 review 常等三天，即使程式碼很小，branch 實際壽命仍可能超過兩天；這是 review 流程造成的整合阻礙。應縮小 PR、指定快速 reviewer、加快自動 CI 與 review 服務時間，並以實際從開 branch 到 merge 的時間衡量，不要只看程式碼量或開發時間。

## S8

### 原始輸入

團隊採 merge commit、同步 main 用 merge、允許直接 push、有時一位 reviewer。這些是否違反 TBD？

### 回答

這些 Git 形式本身都不是 TBD 的核心禁令。merge commit、同步 `main` 用 merge、reviewer 人數、branch 命名與是否禁止 direct push 都屬團隊自行決定；TBD 沒有要求一定要 squash、rebase 或兩位 reviewer。

真正要檢查的是結果：是否沒有長期共同開發分支、每天持續整合 `main`、`main` 維持可工作、CI 快速回饋，以及 merge 前是否有足夠的 review 與自動檢查。允許 direct push 若能繞過 review、CI 或 branch protection，就可能使 `main` 變紅；問題在流程控制與結果，不在 direct push 這個形式本身。一位 reviewer 也可以是團隊選擇，但仍要符合團隊設定的檢查要求與變更風險。

## S9

### 原始輸入

我們 main CI 紅了晚上再修，develop 持續兩週才整合，release 前 code freeze。請審查並提出優先處理。

### 回答

優先順序如下：

1. **立即處理 main CI 紅燈。** 暫停把新功能繼續合入，先修正造成失敗的變更，或立即 revert；修到 `main` 綠且可工作後才恢復整合。晚上再修不符合 broken trunk 優先處理的核心規則。
2. **停止兩週的 `develop` 長期共同開發。** 把工作切成可獨立 merge 的小 PR，改成每天至少整合 `main`；`develop` 若只是長期整合中繼分支，應逐步移除或改成短期用途。
3. **移除 code freeze 作為整合方案。** 用小批次、向後相容、新舊並存或 Feature Flag 讓變更在 release 前持續進入 `main`；freeze 不能補救長期分支造成的整合差異。

另外要量測 branch（含 review 等待）壽命、active branches 數量、CI 回饋速度與未清理的 flag。題目未提供 CI 紅燈的根因，第一步仍應由當下失敗的 build/test log 決定是修正還是 revert。

## S10

### 原始輸入

我們沒有自動 build/test，review 常耗幾天，新手為主。想明天全面從 GitFlow 換 TBD。你如何建議並解釋兩者差別？

### 回答

不建議在沒有自動 build/test、review 常等幾天且團隊缺少經驗時，明天全面切換。這些是 TBD 的導入前提缺口；若直接全面導入，可能變成大家頻繁 merge、`main` 頻繁壞掉。建議先做受控的準備與試點：

1. 先建立自動 build、unit/integration test 與能快速回饋的 CI，並讓 merge 前有 gated checks。
2. 先選一個服務或小團隊試行，規定小 PR、短期 branch、每天整合 `main`；建立 `main` 紅燈立即修或 revert 的紀律。
3. 針對新手提供切小、review 與 Feature Flag／相容性技巧的範例，縮短 review 等待並設定 reviewer 責任。
4. 試點穩定、`main` 持續可工作後，再分階段擴大；不要把「明天全面切換」當成必要條件。

差別在整合時機與工作拆分：

| 面向 | GitFlow 類 | TBD |
|---|---|---|
| 工作方式 | 先隔離，做到較完整後最後整合 | 先切小，持續整合到 `main` |
| 分支 | 常有長期 `develop`、release 等分支 | 圍繞單一 `main`，短期 branch 做完即 merge |
| 狀態 | 整合常集中在後段 | `main` 任何時候保持可工作、可發布 |
| Git 指令 | 依團隊流程使用 Git 指令 | 不要求特殊 Git 指令，主要改變拆分與整合節奏 |

TBD 不是靠 code freeze 或長期 branch 藏住未完成功能；未完成部分應用小批次、Feature Flag、abstraction 或向後相容方式持續 merge。若團隊確實目前採 GitFlow，遷移也應先以試點和可量測的 CI/review 改善開始。
