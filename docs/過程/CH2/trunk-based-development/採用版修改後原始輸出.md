### GitFlow 與 TBD

| 面向 | GitFlow | TBD |
| --- | --- | --- |
| 整合方式 | 先隔離，功能或版本完成後再集中整合 | 先切小，持續整合 main，讓 main 維持可工作 |
| 分支 | 常見 `develop`、feature、release、hotfix 等分支，部分分支可能存活較久 | 不使用長期共同開發分支；每個小變更用短期 branch 完成後合併 |
| 發布 | 可在 release branch 集中穩定與發布 | 預設 main 持續可發布；只有維護已發布版本時才使用 release branch |
| 驗證風險 | 較多風險集中在最後的整合點 | 以每日或更頻繁的整合、快速 CI 及小 PR 分散回饋 |

| Git 操作 | 流程通常較重 | merge commit、squash、rebase、branch 命名與 reviewer 人數仍由團隊決定；TBD 主要改變工作拆分與整合節奏 |

## 依目標 Skill 產出的最終回覆

目前描述的做法不能視為 TBD。既有 release branch 可以保留，但必須改成「接近發布時才建立、只維護已發布版本」的分支；早早建立後持續在上面開新功能，以及只在 release branch 修 bug 再回灌 main，兩者都需要調整。

你描述的是 GitFlow 類的「先隔離、做完整、最後整合」流程；TBD 則是「先切小、持續整合、任何時候維持 main 可工作」。TBD 主要改變的是工作拆分與整合時機，Git 的 merge、squash、rebase、branch 命名及 reviewer 人數仍可由團隊自行決定，這些操作選擇本身不是 TBD 判準。

| 面向 | 目前描述的 GitFlow 類做法 | TBD 相容做法 |
| --- | --- | --- |
| 開發位置 | release branch 早早建立，並持續承載新功能 | 新功能以小批次、短命 branch 回到 main；未完成或未曝光的功能用 Feature Flag、Abstraction 或新舊並存 |
| 整合時機 | 功能或版本累積後再整合 | 每天至少整合 main 一次，越頻繁越好；main 必須保持可工作 |
| release branch 角色 | 同時做版本穩定與新功能開發，因而成為長期開發分支 | 很晚才切，只負責該版本的穩定、bug fix 與發布 |
| 舊版 bug fix | 先修 release，再回灌 main | 先在 main 修正並驗證，再 cherry-pick 到仍支援的 release branch |
| 版本維護 | 以長期分支承載多種工作 | 可以保留支援中的 release branch，但限制在已發布版本維護，版本終止支援後關閉或刪除 |

### 可以保留的部分

可以保留已發布版本的 release branch。TBD 的變更規劃本身包含「維護已發布版本 → Release Branch」這個例外，因此 TBD 不是完全禁止 release branch。可保留的條件是：

1. 不要在發布很早以前建立並長期承載開發；接近版本穩定或發布時才切。
2. release branch 只處理該版本的穩定、必要 bug fix、發布準備與發布。
3. 不在 release branch 開新功能，也不把下一版功能放在其中等待整批整合。
4. bug fix 先進 main：從 main 建立短命 branch，完成修正後依序執行 build、lint、unit test、必要的 integration test，經 PR、review、CI green 後 merge main；再把同一修正 cherry-pick 到支援中的 release branch 並驗證。
5. 明確記錄支援中的版本與終止支援時間；版本停止支援後清理 release branch，避免 active branches 無限增加。

因此，已存在的早期 release branch 可以在遷移期間暫時保留，但應立即停止在上面新增功能，將未完成工作拆成小變更回到 main；它只能逐步收斂成維護分支，不能繼續當成共同開發分支。

### 必須調整的部分

- 「release branch 早早建立並持續開新功能」違反沒有長期開發分支的 TBD 核心規則；它也不符合 Release Branch 只負責穩定、bug fix 與發布的生命週期。
- 「只在 release 修 bug，再回灌 main」方向相反。這會讓 main 暫時漏掉修正，並增加後續衝突與重複驗證；應改成 fix on trunk first，即先修 main，再 cherry-pick 到 release。
- 每個 feature 應先拆成能獨立整合的小變更，每個小變更使用短命 branch，工作期間持續同步 main，merge 前再次更新；不要等整個 feature 或整個 release 完成才整合。
