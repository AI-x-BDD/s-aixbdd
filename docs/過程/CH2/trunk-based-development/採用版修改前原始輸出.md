# 基線實跑

## 方法與限制

- 使用不繼承本次分析脈絡的子代理，只提供工作目錄、基線 Skill 路徑與下列輸入；要求只讀、不修改、逐案獨立回答。
- 子代理回報讀取 `AGENTS.md`、目標 `SKILL.md`、`references/cases.md`，沒有其他紀錄；目標 Skill 沒有確認閘門。
- 預先回覆一律為「確認，僅提供規劃／審查，不操作 Git」。實際無閘門，未使用。
- 下列保留實際回傳內容；沒有額外執行其規劃中的 Git／CI 指令。
- 這是一次代表性基線實跑，不是所有輸入的正確性證明，也不是重構後的驗收結果。

## A：延後曝光的多日功能

輸入：帳務匯出功能需四天完成，第五天開放，既有匯出仍須可用。請按 TBD 規劃 PR，含 branch 壽命與 CI。

實際回答：

使用 `Feature Flag`，第 1–4 天持續整合，`flag=false`；第 5 天通過驗證後才開放。既有匯出路徑全程保留。

```text
PR 1：加入新匯出流程的介面、資料準備與關閉中的 Feature Flag
PR 2：加入新匯出實作與 unit tests
PR 3：接上 API／操作入口與 integration tests，仍由 flag 控制
PR 4：補回歸測試、監控與切換／回滾設定
```

每個 branch 約半天至一天，包含 review 等待；merge 前同步最新 `main`，merge 後刪除。每個 PR 執行 build、lint、unit test、必要的 integration test，並保留既有匯出的回歸測試。CI 或 `main` 紅時立即修復或 revert。第 5 天只切換 flag，不需保留長期 feature branch。

觀察：未提及上線後清理 flag；其他上述核心行為有呈現。

## B：供應商與 API 相容遷移

輸入：把寄信供應商從 SMTP SDK 換成 HTTP provider，需要六天，舊服務不能中斷。另有 API 欄位要由 amount 改為 total，舊 consumer 兩週後才遷移。請規劃。

實際回答：

供應商替換使用 `Branch by Abstraction`；API 欄位使用新舊並存，兩條工作流可分開提交。

```text
PR 1：建立 mail provider abstraction，SMTP 實作先接上且仍為預設
PR 2：加入 HTTP provider implementation，設定或 flag 預設關閉
PR 3：加入逐步切換、監控與 SMTP fallback
PR 4：穩定後切換預設 provider，確認舊 SMTP 可回退
```

每個 provider PR 都應在一天內完成並 merge，不能讓單一 migration branch 活六天。舊 SMTP 在 HTTP provider 穩定前不能移除，確保服務不中斷。

```text
API PR 1：新增 canonical 欄位 total，保留 amount 相容層與 contract tests
API PR 2：各 consumer 分別遷移到 total
API PR 3：兩週後確認 consumer 全數遷移，再移除 amount
```

相容期間，`amount` 映射到同一個內部 `total`；若兩者同時存在且值不同，應拒絕請求，避免歧義。回應可暫時同時提供兩欄位，並標記 `amount` deprecated。CI 加入新舊 consumer contract tests、provider integration tests 與 fallback 測試；每個 merge 後 `main` 都維持可工作。

觀察：有 abstraction、舊實作接入、新實作加入與逐步切換；沒有明列穩定後刪 SMTP 的最後一步。雙欄位衝突處理屬個案設計，不作為 TBD 規則加入目標 Skill。

## C：舊版本 hotfix

輸入：production 版本 2.4 需修時區計算，main 已開發 2.5，修復一天內完成。請規劃 hotfix。

實際回答：

採用 `fix on trunk first`。

```text
PR 1：從 main 修正時區計算，加入失敗案例與回歸測試
PR 2：PR 1 通過 CI 後，將修正 backport 到 release/2.4
```

PR 1 branch 應在數小時至一天內完成，包含 review。先在 `main` 驗證，避免 2.5 漏掉修正；再將同一修正 cherry-pick 或以 backport PR 合入 `release/2.4`，通過 release CI 後發布 2.4。若尚無 `release/2.4`，才從目前 production 2.4 版本建立只負責維護與發布的 release branch。不要只修 release branch 再回灌。

## D：workflow 審查

輸入：團隊從 main 開 branch，程式修改半天但 review 等三天，CI 紅了晚上修，月底 code freeze；squash 與 rebase 強制是否才算 TBD？請審查。

實際回答：

目前不算良好的 TBD 實行：

- 半天開發加三天 review，branch 壽命至少約三天半，超過 DORA 的 `< 1 day` 目標，也超過官方通常的 1–2 天範圍。
- CI 紅到晚上才修，沒有遵守 `main` 紅就立即修復或 revert。
- 月底 code freeze 是延後整合，不能解決分支累積的整合風險。

`merge commit`、用 merge 同步 `main`、兩位 reviewer、GitLab 都是團隊選擇，不是 TBD 違規；TBD 沒有強制 squash 或 rebase。真正需要改善的是 review 速度、branch 壽命與 broken trunk 處理。可拆成更小的 PR、安排當日 review，並讓 CI 紅時立即修復或 revert。

觀察：回答額外列了輸入未指定的團隊選項，但核心判斷與既有規則一致；不將額外例子當作專案事實。

## E：比較與導入

輸入：兩人內部 Web 工具想從 GitFlow 改 TBD，但沒有自動 test，review 每週一次。請比較兩者與導入建議。

實際回答：

GitFlow 以長期 `develop`、release 等分支隔離工作，適合固定版本節奏，但兩人內部工具採用它通常增加分支與整合負擔。

TBD 以短命 branch、頻繁整合 `main`、持續可工作為核心，較適合小團隊與持續變更；但目前沒有自動 test，且 review 每週一次，缺少 TBD 的必要前提。現在直接全面切換，容易讓 `main` 經常壞掉。

建議分階段導入：

1. 先建立最小 smoke／unit tests、自動 build 與快速 CI。
2. 將 review 改為當天或下一工作日完成。
3. 再移除長期 `develop`，採短命 branch → CI → review → `main`。
4. 未完成功能使用 Feature Flag；只有發布維護需要時才建立短期 release branch。

完成前提前，不應宣稱目前流程已是 TBD。

## F：小變更

輸入：更正文案錯字預計 20 分鐘，已有快速 CI 與 review。請規劃。

實際回答：

```text
short-lived branch → 更正文案 → lint／快速 CI → PR + review → merge main → 刪除 branch
```

程式修改約 20 分鐘，連同快速 CI 與 review 預估 branch 在一天內結束；不需要 Feature Flag、Abstraction 或 release branch。merge 後 `main` 保持可工作。

## G：來源與分級

輸入：官方是不是規定 branch 最長兩天？DORA 跟官方差在哪？我們用 merge commit、merge 同步 main、兩位 reviewer、GitLab，會違反 TBD 嗎？

實際回答：

官方通常描述 short-lived branch 約 1–2 天，這是常見建議範圍，不是「超過兩天立即違規」的硬性上限。DORA 以 branch 少於一天、至少每天整合、快速 CI 與立即處理 broken trunk 為更嚴格的目標與能力指標。

以下做法本身都不違反 TBD：

- 使用 `merge commit`
- 用 merge 將 `main` 同步到 branch
- 指定兩位 reviewer
- 使用 GitLab

TBD 沒有強制 squash、rebase、GitHub 或特定 reviewer 人數。判斷重點是 branch 是否短命、是否每天整合、`main` 是否持續可工作，以及 review 或 CI 是否造成長時間等待。
