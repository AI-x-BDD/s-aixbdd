# trunk-based-development 最佳化前後比較

日期：2026-10-17。狀態：短版 r05 已套用到正式 Skill，兩側同步與套用後檢查通過。實驗紀錄、正式重構、前後對照依序分類提交；未 push。

## 原本問題與本輪調整

原版把流程、TBD 判準、技巧、輸出格式及 workflow 審查混在主檔。本輪由 Skill Engineering 整理成 SOP，領域規則依情境載入，保留既有用途與正確規則。

這次直接採用已通過驗收的短版 r05，沒有重新生成另一份結果。正式兩側 Skill 與 r05 受測版本逐檔一致。

## 問題是怎麼發現的

1. 讀取原版主檔與案例，結構診斷指出沒有正式 SOP；這是結構問題，不等於回答錯誤。
2. 原版實跑七類情境：多日功能回答漏了上線後清理 Flag，供應商遷移回答漏了最後刪舊實作。原版其實已寫這兩項要求。
3. Skill Engineering 定義驗收、分析根因並提出藍圖。第一版藍圖漏了「審查用途也要載入六題自檢」，經總指揮退回修正後才施工。
4. 模組化後以隔離代理實跑；同需求的多日功能、供應商遷移回答都有列出清理步驟。

這次主要改善流程與規則組織，另有上述實際回答完整性的差異。清理要求是原版已有的規則。

證據：[根因報告](提示詞重複對照/tbd-r05/工程紀錄/根因報告.md)、[基線實跑](採用版修改前原始輸出.md)、[工程藍圖](提示詞重複對照/tbd-r05/工程紀錄/工程藍圖.md)、[藍圖修正](提示詞重複對照/tbd-r05/工程紀錄/藍圖修正紀錄.md)。

完成範圍：模組化、保留原規則與用途、按需載入、實跑驗收、同步正式 Skill，以及保存前後差異。本次沿用相同候選的既有工程驗收，另做套用後版本、結構、同步與範圍檢查。

| 樣板／腳本 | 無 | 無 |

三份規則的職責：

- `rules/TBD判準-格式規範.md`：核心、來源、branch 壽命與團隊選擇。
- `rules/變更規劃-格式規範.md`：小 PR、整合驗證、技巧生命週期、回覆格式與六題自檢；規劃與相關審查皆可使用。
- `rules/工作流程評估-格式規範.md`：workflow 查核、導入前提、適用場合與 GitFlow 比較。

主檔變短，但加入正反例後 package 總量增加。本次確認的是職責分離、明確載入與交付檢查，未量測總 token 或速度改善。

以下五項沿用 r05 基線與修改後相同需求，僅末尾句號不同。表內描述實際回答差異，不把原版所有案例都算成失敗。

| ---- | ---- | ---- | ---- |
| A／S3 | 四天開發、第五天開放匯出 | Flag 關閉時每日整合；漏上線後清理 Flag | 保留關閉整合與既有匯出，另列啟用後清理 |
