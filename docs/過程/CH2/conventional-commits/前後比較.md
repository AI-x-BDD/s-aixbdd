# conventional-commits 最佳化前後比較

日期：2026-10-17。狀態：模組化、最終驗收與比較更新完成；本文件與 package 隨本次優化 commit 一併封存，提交證據見文末。

## 原本問題與本輪補正

1. 行為錯誤：S2 將官方允許的連字號 breaking footer 誤判為不合規。
2. 靜態衝突：效能改善被放在行為有變的分支，分支內容卻寫行為相同。
3. 靜態衝突：專案規則優先與 scope 不用檔名的文字互相牴觸。
4. 施工遺漏：前一階段雖修正以上三點、整理 SOP 並通過測試，仍把大部分規則放在主檔，未完成作業要求的模組化。使用者核對作業才發現，AI 先前宣告完成不正確。

[根因分析](根因分析.md)記錄前三項；[模組化補正](模組化補正.md)記錄第 4 項與本輪設計、施工及驗收。前三項已確認的語意修正全部保留。

## 第 1 項是怎麼發現的

1. 讀取本專案原有的 `conventional-commits` Skill，發現它只列出空格版 `BREAKING CHANGE:`。
2. 對照官方 Conventional Commits 1.0.0，第 16 條明定連字號版 `BREAKING-CHANGE:` 與空格版同義，兩種都合法。這是判斷對錯的依據。
3. 由 AI 準備 S2：假設一項移除公開設定鍵的變更，提供帶連字號版標示的提交訊息文字，請原有 Skill 審查。此題沒有真的修改產品或建立 Git commit。
4. 修改前實跑一次，回應以「未列在規則中」為由，錯誤要求改成空格版。只有規則沒寫還不能證明會誤判；這份實際回答才是行為錯誤的證據。
5. 補齊規則後，用同一題再測一次，改為正確接受連字號版。

三者角色不同：**官方規格提供正確答案；本專案的 conventional-commits 是受測對象；Skill Engineering 提供蒐證、分析、修改與重測流程。** Skill Engineering 本身沒有規定空格或連字號，也不是靠重複抽測直到偶然出錯才找到問題。

這證明本輪觀察到一次誤判、修改後同題通過，不代表已證明每次執行都會得到相同結果。原始輸入與前後回答的連結見下方「同題前後結果」。

## 修改原因與完成定義

使用者已明確授權完成四件事：模組化、模組化後驗證、更新比較、正式 commit。這次不能再只靠「audit 通過」或「原五題通過」宣告模組化完成：還必須核對規則實際分檔、正反例、READ 時機、具名清單、消費與驗證關係。

## 結構差異

| 項目 | 原版 | 先前中間版 | 最終模組版 |
| ---- | ---- | ---- | ---- |
| 主檔角色 | 流程、規則、範例混合 | 正式 SOP，但規則仍在主檔 | 只保留輸入、載入、決策、交付與驗證流程 |
| 主檔行數 | 118 | 121 | 27 |
| 正式 Phase／步驟 | 0／9 | 1／11 | 2／11 |
| RuleFile／Rule | 0／0 | 0／0 | 3／11，皆有正反例 |
| 一般參考檔 | references/cases.md | 同原版 | 內容按主題遷入規則後移除，避免兩份權威來源 |
| 載入方式 | 主要規則一次全在主檔 | 仍同左 | 分析前載入分類，訊息決策前載入格式，歷史／工具情境才載入歷史規則 |
| frontmatter | 原有用途與觸發 | 保留 | 保留原文 |
| 樣板／腳本 | 無 | 無 | 無，不為模組化硬加 |

三份規則的職責：

- `rules/變更分類-格式規範.md`：規則來源、依目的選 type、分拆無關目的。
- `rules/提交訊息-格式規範.md`：標題格式、scope 與語言、body／footer、breaking 標示與 SemVer。
- `rules/歷史處理-格式規範.md`：revert、修正既有 commit、squash 與工具設定限制，按情境載入。

主檔較短只證明主檔內容移出；加上正反例後整個 package 不一定更短，不能宣稱總 token 或效率改善。規則原本核心用途完整保留，包括 dependency、CSS、Composition API、公開歷史與不擅自安裝工具。

## 驗證限制

- 各輪為不繼承主分析對話的新子代理，未覆寫模型與 reasoning 設定；服務端精確版本與隨機性參數未知，不能宣稱逐字可重現。
- 每輪題目依序共用同一代理上下文，判準可見但要求僅作事後評分；不是盲測，也不是每題獨立新對話。模組版另外要求依 SOP 按需載入，不預先全讀規則，驗證新結構的實際使用。
- S1 使用具有相同 HEAD、status、staged diff 與檔案雜湊的暫存 Git repository 複本；其餘案例只審查文字與摘要，未建立產品功能或測試 commit。
- 規範判準來自現有用途、fixture 團隊規則與 [CC 1.0.0 規格](https://www.conventionalcommits.org/en/v1.0.0/#specification)。第 1 項是一次原版誤判與同題修正，不代表每次模型都必然相同。
- 第 2、3 項是消除靜態衝突，原版相關案例已通過；不能宣稱有額外行為改善。模組化的收益是職責分離與按需載入，總成本、速度與跨模型穩定性尚未量測。
