# conventional-commits 追問釐清與影片素材

日期：2026-10-17。這是三支技能最佳化中的第一支；後兩支尚未執行。本文記錄本輪對話的釐清經過，非逐字稿。引號內為本輪對話原句，表格其餘內容為摘要。

## 為什麼追加這份紀錄

使用者閱讀更新紀錄與 AI 說明後，仍無法理解哪裡出錯、為什麼停止、到底要改什麼。經過多次追問，才釐清三項問題與修改方向。使用者要求留下這段經過，作為後續處理另外兩支技能與製作 90～120 秒影片的材料。

## 追問如何釐清問題

| 階段 | 使用者追問或決定 | AI 原先說明的問題 | 最後釐清的內容 |
| ---- | ---- | ---- | ---- |
| 1. 為何停止 | 反覆追問是否因 Skill Engineering 判 breaking change 不合理而停止 | 最初同時列測試問題與確認閘門，沒有把兩者分開，後續又只重複「流程要求」 | 找到問題的是 conventional-commits 的實測；停止是因 Skill Engineering 要求根因確認，不是 footer 讓工具故障或無法繼續 |
| 2. 到底找到什麼 | 「那你找到什麼問題？然後根因報告在哪裡？」 | 反覆談要確認，卻沒有再次直接呈現問題與報告位置 | 實測錯誤一項、文字衝突兩項；報告是本目錄「根因分析.md」 |
| 3. 第一項哪裡錯 | 「解釋第一點，第一點我完全看不懂你在講什麼。」 | 一直使用 breaking change、footer 等術語，未先解釋用途與實際差別 | breaking change 是提醒舊用法將失效；footer 指訊息末尾的標示。本次比較的是同一標示的空格與連字號寫法 |
| 4. 差異到底在哪 | 「你給我的例子，差別是差在連字號嗎？」 | 原先沒讓讀者一眼辨識字元差異 | BREAKING CHANGE 與 BREAKING-CHANGE 只差空格和連字號；官方兩種都合法，舊 Skill 卻拒絕後者 |
| 5. 確認的是什麼 | 詢問是否要讓兩種都通過，以及是否就等於完成最佳化 | AI 曾把「官方對錯是否確定」與「是否照根因修改」混在一起 | 官方對錯已確定；使用者同意兩種都通過。完成仍需修改、同題重測、記錄前後差異 |
| 6. 另兩項要不要改 | 詢問「文字矛盾」的意思，並要求依官方與 Skill Engineering 提建議 | AI 先因實測通過而建議先不改，忽略規則本身仍互相衝突 | 用直接分類取代矛盾分支；scope 改為專案明文規則優先，模組名稱只是預設建議 |
| 7. 最終授權 | 「好，1、2、3 都依照我們剛剛這樣確認的建議下去做修改。」 | 此時已經確認具體改法，無須再重複問是否同意同一方向 | 三項一起修正，追加釐清紀錄，完成驗證；沒有 commit／push 授權 |

## 三項修改，一眼看懂

### 1. 把正確寫法判成錯誤

這行是在提醒使用者：「舊設定不能用了，請改用新設定。」

```text
BREAKING CHANGE: 請改用新設定。
BREAKING-CHANGE: 請改用新設定。
```

兩種官方都允許，差別只有中間是空格還是連字號。修改前測試拒絕第二種；本次補齊規則，讓兩種都通過。小寫 `breaking change:` 仍不合規。

### 2. 效能分支前後打架

原本上層說「行為有改變才走這裡」，走進去卻說「行為相同但更快」。這讓效能改善的分類前提不一致。

改為直接依目的分類：新增能力用 feat、修錯用 fix、功能不變但改善效能用 perf、功能不變只整理結構用 refactor。其餘類型保留。

### 3. scope 不知道該聽誰的

scope 是提交訊息中標示影響區域的部分，例如 `fix(auth):` 的 auth。

原本一句說「遵守專案規則」，另一句說「不能用檔名」。如果專案規定用檔名，兩句就無法同時遵守。

改為：先遵守專案明文規則，沒有規則時沿用既有慣例，再以功能或模組名稱為預設建議。檔名能代表影響區域時也可用；官方並沒有全面禁止檔名。

## 這次不能混在一起的兩件事

- 第 1 項有修改前實測失敗輸出；第 2、3 項是靜態文字衝突，修改前模型本次仍判對。
- 所以本次收益要分別記為「修正已觀察的誤判」與「消除規則矛盾」，不能把三項都宣稱成實測錯誤已修好。

官方依據為本輪已查閱的 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/#specification)：scope 的區域要求見第 4 條；breaking footer 的大寫與同義 token 見第 12、15、16 條。perf、refactor 的語意是採用的慣例，與 feat、fix 的官方定義分開說明。

## 接下來兩支技能的說明方式

這是本次溝通經驗的整理，沒有修改 Skill Engineering 本身：

1. 先寫「原本做錯什麼」，附最短的輸入與錯誤輸出；術語先用一句話解釋。
2. 接著寫「應該怎麼判」與「準備改哪一句」，讓使用者看得出差別。
3. 明列是實測失敗、文字衝突，還是尚未驗證的推測。
4. 需要停下時，直接說明在等哪個具體決定，附報告連結；不把流程閘門說成技術障礙。
5. 已確認的改法直接執行；只有新增、尚未確認的修改範圍才另行提出。
6. 完成後列同題前後結果，再交代限制，避免只用檔案變短宣稱行為改善。

## 模組化遺漏與四點補正

使用者再用作業原文核對，才發現 AI 所稱「最佳化完成」只完成三項語意修正與 SOP 整理，並未抽出按需載入的規則。原先的完成宣告不正確。使用者指出這個遺漏很大，若未逐層確認可能會忽略。

本輪明確只處理四點：模組化改寫、模組化後重測、更新前後比較、建立 Git commit。AI 不應在本輪回報混列其他不屬於這四點的工作。

本次完成判準增加實體 package 核對：有三個主題規則檔、每條有正反例、SOP 有具名按需載入與實際消費、動態驗收符合規則，並保存 commit 證據。不能只憑 audit 零錯誤就宣稱作業完成。

先前影片段落只說明語意修正；最終介紹本支時須再展示「SKILL.md → 三個規則檔」的結構，以及 skill-engineering → skill-derive-rule → skill-form-rule／skill-form-sop 的實際分工。驗收結果以「前後比較.md」最終版本為準。
