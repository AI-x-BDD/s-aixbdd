## 目標與範圍

使用已建立的 `skill-engineering`，最佳化以下三支 Skill，留下最佳化前後的差異與驗證結果，再製作約 90～120 秒的說明影片。

| 用途 | 本專案實際 Skill 名稱 |

| 主幹式開發 | `trunk-based-development` |

建議一次最佳化一支，先從結果較容易核對的 `conventional-commits` 開始。每支保留同題的前後實測，完成後各自 commit，最後整理影片。

依使用者指定，本次提案與後續相關紀錄放在 `docs/過程/CH2/`，使用繁體中文 Markdown 檔名。

## Commit 建議

1. 修改前記下目前 commit，作為共同基準；工作目錄乾淨時，不用額外建立備份 commit。
2. 每支完成後，將該支 Skill、兩側同步內容、根因分析、工程藍圖與驗證紀錄一起提交，形成可獨立檢視的一筆變更。
3. 最後將影片講稿與三支總比較另外提交一筆 `docs`。

Commit type 依實際修改目的決定：保留行為的整理用 `refactor`；修正錯誤用 `fix`；新增能力用 `feat`。

以下僅為訊息格式示例，不代表目前已確認有這些問題：

```text
refactor(conventional-commits): 分離判斷規則與執行流程
fix(double-diamond): 修正已知問題仍要求完整探索的流程
docs(skills): 整理三支 Skill 的前後比較與影片講稿
```

## 前後差異與驗證紀錄

每支整理一份簡短的 `前後比較.md`，原始測試輸出另外保存，固定記錄以下五項。

| 項目 | 記錄內容 |
| --- | --- |
| 原本問題 | 檔案位置或實際失敗輸出 |
| 修改原因 | 根因，以及為何選擇這個改法 |
| 結構差異 | SOP、規則與樣板如何調整 |
| 同題前後結果 | 相同輸入、通過情況與輸出差異 |
| 結論 | 改善了什麼，以及哪些效果尚未證明 |

檔案變短可以證明精簡；實跑結果才用來判斷行為是否改善。少量案例只報案例結果，不宣稱整體準確率提升。若只有結構改善、行為未見差異，照實記錄。

## 約 110 秒的影片安排

| 時間 | 畫面與說明 |
| --- | --- |
| 0～10 秒 | 三支 Skill 的用途與這次最佳化目標 |

| 20～80 秒 | 每支 20 秒，展示「原本問題 → 修改 → 同題前後結果」 |
| 80～100 秒 | 三支比較表與驗證結果 |
| 100～110 秒 | 實際收益與尚未驗證的部分 |

錄影時展示整理好的差異與結果即可。實作過程保留原始證據，避免事後為了補拍重新跑完整流程。
