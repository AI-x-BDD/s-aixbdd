## 1. `/double-diamond`：實作 Step 1

### 輸入

以 `/double-diamond` 帶入 `docs/需求清單.md` 的 Step 1 需求：

```text
add("")      -> 0
add("1")     -> 1
add("1,2")   -> 3
```

要求：

- 建立 `StringCalculator` 類別與 `int add(String numbers)`
- 先寫測試再實作
- 只處理空字串、一個數字、兩個以逗號分隔的數字
- 不實作後面的需求
- 執行測試，回報修改的檔案、實作內容和測試結果

### 雙鑽石判斷

問題、解法和驗證方式（三組輸入對應的輸出）都已經明確，符合 Skill 裡「不需要完整流程」的情況，所以沒有跑 Discover／Define，直接用測試先行的方式實作。

### 過程

1. **檢查環境：** 專案原本只有文件和 Skill，沒有 Java 專案。本機有 JDK 25 和 Maven，本機 Maven repository 已有 JUnit 5.11.4 和 surefire 3.5.2。
2. **建立專案與測試：** 新增 `pom.xml`，並在 `StringCalculatorTest` 寫 3 個測試，分別對應三組需求。
3. **紅燈：** 先用只會拋出 `UnsupportedOperationException` 的 stub 執行測試。第一次用離線模式（`-o`）時缺少 `maven-compiler-plugin`，改成連線執行後得到預期的紅燈：
   `Tests run: 3, Failures: 0, Errors: 3`
4. **綠燈：** 寫最少量的實作：
   - 空字串回傳 0
   - 以逗號切開，一個數字就回傳它本身
   - 兩個數字就回傳相加結果

   結果：`Tests run: 3, Failures: 0, Errors: 0, Skipped: 0`，`BUILD SUCCESS`
5. **額外處理：** 新增 `.gitignore`，忽略 Maven 的編譯輸出 `target/`。

### 刻意不做的事

- 沒有用迴圈加總全部數字。用迴圈的話會順便支援任意數量的數字，也就是 Step 2 的需求。
- 沒有處理換行分隔、自訂分隔符號、負數等後面才會要求的功能。

### 產出檔案

| 檔案 | 說明 |
|---|---|
| `pom.xml` | Maven 設定，使用 JUnit 5.11.4 |
| `src/test/java/calculator/StringCalculatorTest.java` | 3 個測試 |
| `src/main/java/calculator/StringCalculator.java` | `add` 的實作 |
| `.gitignore` | 忽略 `target/` |

### 實作內容

```java
public int add(String numbers) {
    if (numbers.isEmpty()) {
        return 0;
    }
    String[] parts = numbers.split(",");
    if (parts.length == 1) {
        return Integer.parseInt(parts[0]);
    }
    return Integer.parseInt(parts[0]) + Integer.parseInt(parts[1]);
}
```

### 過程

1. 查看 remote、branch 和 CI 設定：

   - 沒有 `.github/workflows/`

### 結論

符合的部分：

- 沒有長期分支
- 變更切得小
- 每個 commit 之後 main 都能用
- 直接 push `main` 由團隊決定，TBD 沒有禁止

還缺的部分：

- **還沒整合到遠端：** commit 只在本機。DORA 的標準是每天至少整合一次，應該今天內 push。
- **沒有 CI：** 只靠本機跑測試。

### 後續規劃

```text

PR 3 之後：一個 Step 一個變更，照同樣方式進行
每個 PR merge 後 main 為什麼仍可工作：每一步都是先寫測試、全部通過才 commit，而且不會改掉已經通過的行為
預估 branch 壽命（含等 review）：幾小時內，直接在 main 上做就是 0
```

# Session 2：觀念整理（CI、TBD、Conventional Commits）

日期：2026-10-01

這次沒有寫程式。內容是我對 Session 1 的追問，前一天的過程經過一兩天沉澱後，我發現自己對 TBD 的理解跟原本想的不太一樣。

## 0. 這個過程紀錄檔的 commit message

用 `/conventional-commits` 替 `docs/過程/1.md` 產生 commit message：

```text
docs: 新增 String Calculator Step 1 過程紀錄
```

- 只新增文件，所以 type 用 `docs`
- 沿用專案裡 `docs` commit 不加 scope、用中文的習慣
- 只提出 message，還沒 commit

## 1. CI 是什麼？會自動合併嗎？

**我原本以為：** CI 是發 PR 之後跑測試，成功就自動合併到 `main`。

**釐清後：**

- CI（持續整合）是一種開發方式：經常把變更整合進 `main`，每次整合都由機器自動 build 和跑測試。
- 自動跑測試只負責回報結果（✅ 或 ❌），**合併還是由人決定**。「沒過不能 merge」或「通過後自動 merge」是 GitHub 的額外設定，不是 CI 本身的行為。
- CD 負責後面的自動部署或發布，這個專案目前用不到。

## 2. `mvn test` 在哪裡跑？要準備主機嗎？

- 不用。GitHub Actions 每次會在 GitHub 雲端開一台臨時的虛擬機，跑完就丟掉。
- 只要在 repo 放 `.github/workflows/<名稱>.yml`，寫清楚三件事：什麼時候觸發、安裝 JDK 21、執行 `mvn test`。
- public repo 免費。
- 這份設定檔目前**還沒寫**，所以現在 push 不會觸發任何測試。

## 3. 直接在 `main` 上開發的日常循環

```text
本機寫測試 → 實作 → 本機 mvn test 綠燈 → commit → push → CI 綠燈 → 下一個功能
                                                        ↓ 紅燈
                                              先停下來，修好或 revert，再 push
```

- push 前先在本機跑過測試。CI 是第二道保險，不應該是第一次發現紅燈的地方。
- CI 紅燈時，那個 commit 已經在 GitHub 的 `main` 上了，所以要優先處理，修不好就先 revert。
- 本機綠燈、CI 卻紅燈的常見原因：
  - 忘了 commit 某個檔案
  - 環境不同，例如本機是 JDK 25，CI 是 JDK 21
- 如果想「先看到 ✅ 再進 main」，就改成開 PR：短期 branch → PR → CI → merge → 刪 branch。TBD 兩種做法都可以。

## 4. 我的想法：TBD 裡 Unit Test 更重要

**我的想法：** TBD 小步快跑，所以 Unit Test 是不可或缺的一環。

**釐清後：** 方向正確，但更精確的說法是：**在 TBD 裡，自動化測試是前提，Unit Test 是其中最關鍵的一種。**

- Git Flow 也需要測試，但有緩衝區，例如功能做完整才合併、release 分支上的人工測試。
- TBD 每天把小變更直接整合進 `main`，中間沒有緩衝，**測試是唯一的安全網**。
- Unit Test 特別重要的原因：
  - **快：** 每次 commit 前都能跑
  - **能精確指出錯在哪：** 符合「紅燈立刻修」的要求
- 只有 Unit Test 還不夠，真實專案還需要整合測試。

## 5. 功能還沒做完就能 commit 進 `main` 嗎？

**我原本以為：** Git Flow 在自己的分支上把功能做完整，所以功能比較不容易壞。

**釐清後：**

- Git Flow 的功能不一定比較不容易壞，只是**比較晚才發現**。分支分開越久，合併時問題一次爆出來（merge hell）。
- TBD 確實會讓還沒做完的功能進 `main`，但有一條規則：

> **功能可以還沒做完，但 `main` 不能壞。**

- 讓沒做完的程式安全進 `main` 的方法：
  - 切成每一步都能運作的小片段
  - Feature Flag
  - 新舊並存（Branch by Abstraction）
- 補充：Git Flow 的 feature 分支是合併到 `develop`，不是直接進 `main`。

## 6. 為什麼我一直覺得這次的規劃「怪怪的」

**我原本的習慣：** String Calculator 本身就是一個功能，應該就是一個 commit。

**釐清後：**

- 在 TBD 裡，String Calculator 會分成 8 個 Step，每做完一個 Step 就進一次 `main`。
- 一小片能進 `main` 的條件：有測試、測試全部通過、不弄壞已經能用的功能。
- TBD Skill 把「一張 Story = 一個 branch = 一個 PR」列為常見錯誤。
- 兩種流程的差別不在 commit 次數，而在**什麼時候進 `main`**：

| | 什麼時候進 `main` |
|---|---|
| 我原本的習慣（Git Flow 類） | 整個 String Calculator 做完，才一次合併 |
| TBD | Step 1 做完就進，Step 2 做完再進，依此類推 |

## 7. TBD 的 commit 比較多、比較亂？

**我的初步心得：** TBD 會產生大量切片式的小 commit，三個人一起開發時，看起來會被打散得比較亂。

**釐清後：**

- TBD 的 commit 不一定比較多。Git Flow 在分支上也會 commit 很多次，`main` 上看起來是「一個功能一個 commit」，常常是因為合併時用了 squash。
- 真正變細的是**進 `main` 的次數**，所以多人的切片會在 `main` 上交錯出現。

## 8. 為什麼 Conventional Commits 在 TBD 裡特別有用？

一開始我回答得不夠精確，經過幾次追問才抓到核心。

**核心：** 在 TBD 裡，原本由 branch 負責的「分組」工作，改由 commit message 的 `type(scope)` 來做。

**裝箱比喻：**

- **Git Flow 像整箱寄送。** feature A 的修改都裝在同一個箱子（`feature/a` 分支）裡，箱子外有標籤（PR 標題），箱子裡每件東西有沒有標籤不太重要。
- **TBD 沒有箱子，每件東西做好就直接放上共用的架子（`main`）。** 三個人的東西混放在一起，每件都要自己貼標籤。

```text
feat(calculator): ...   ← Step 3
fix(auth): ...          ← 同事
feat(calculator): ...   ← Step 2
feat(calculator): ...   ← Step 1
```

沒有 branch 把 Step 1～3 包在一起，能把它們串起來的只有 `(calculator)` 這個標籤。

**重點在 `type(scope)` 的固定格式，不在 description 或 body 的文字描述。** 讀者有三種：

- **人：**
  - `scope` 說明影響範圍
  - `type` 說明修改的性質和風險：`feat` 是新增能力；`fix` 是修錯；`refactor` 宣稱行為不變；`docs`、`test` 風險低
- **Agent：** Session 1 寫 commit message 前，Agent 先讀 `git log`，從固定格式看出這個專案「`docs` 用中文、`feat` 用英文」的習慣。
- **工具：** semantic-release、release-please 這類工具，會依 `feat`／`fix`／`BREAKING CHANGE` 自動決定版號，產生 CHANGELOG。

**結論：** Conventional Commits 在兩種流程裡都能用。在 TBD 裡沒有箱子了，標籤就變成必要的東西。

## 9. 為什麼 TBD 的資料和影片比較少？

**我的觀察：** TBD 的資料不多，影片觀看數少，年份也偏舊，感覺不是當代顯學。

**有出處的事實：**

- Git Flow 作者 Vincent Driessen 在 2020 年替 2010 年的原文加了說明：持續交付的軟體（例如 Web App）建議改用更簡單的流程（例如 GitHub Flow），不要把 Git Flow 當教條。
- Google 的 DORA 研究把主幹式開發列為能預測高績效團隊的技術能力之一。

**判斷（非官方）：**

- TBD 不是過時了，而是**變成了默認的做法，名字反而不常被提起**。
- 很多團隊用的「短期 branch → PR → CI → 合併 → 刪 branch」（GitHub Flow），基本上就是 TBD，只是沒這樣稱呼。
- TBD 觀念簡單、不需要特別工具，能拍成教學的東西比 Git Flow 的分支圖少。

## 10. 原來我和公司一直在做 TBD

**我的日常做法：** 從 `main` 用 `checkout -b` 開分支，30 分鐘到 3 小時就合回去。公司同事也是把功能切小，一直合回主分支。

**釐清後：**

- 短期 branch 的循環**不是 Git Flow 的一部分，而是 TBD 本身的做法**（也就是 GitHub Flow）。
- TBD Skill：「TBD 主要改變拆分工作的方式，Git 操作本身變化不大。」三種流程的差別在 branch 活多久、合併到哪裡。
- 不經過 PR 也可以，要不要 review 由團隊自己決定。
- **branch 合併後要刪掉**，不要自己留著。留著的 branch 很容易被繼續拿來開發，變成長期分支。

**對照檢查：**

| 檢查項目 | 我們的情況 | 判斷 |
|---|---|---|
| 沒有長期共同分支 | 直接合回 `main`，沒有 `develop` | 符合 |
| `main` 隨時能運作 | 是 | 符合 |
| branch 壽命 | 平常 30 分鐘～3 小時 | 符合，達到 DORA「不到一天」的標準 |
| 大功能 | 偶爾開一週，但很少 | 不符合（官方 1～2 天、DORA 不到一天） |

**結論：** 我們的日常做法已經是 TBD，只是沒有把它叫作 TBD。少數一週的大功能，可以練習「先切小，切不了就用 Feature Flag」。

要從「誤打誤撞」變成刻意的 TBD，差別在三個習慣：

1. branch 只是暫時的工作區，當天整合回 `main` 就刪掉。
2. 先切小再開 branch，每一片做完就能進 `main`。
3. 進 `main` 前要是綠燈。

## 觀念轉變

| 主題 | 之前 | 之後 |
|---|---|---|
| CI | 發 PR 跑測試，通過就自動合併 | 自動驗證每次整合，合併由人決定 |
| 功能與 commit | 一個功能 = 一個 commit／一次合併 | 一個功能分成多片，每片都能運作，各自進 `main` |
| 沒做完的功能 | 要做完整才能合併 | 可以沒做完，但 `main` 不能壞 |
| Unit Test | 好的習慣 | TBD 的前提，是唯一的安全網 |
| Conventional Commits | 寫了但平常不看 | 在 TBD 裡取代 branch 負責「分組」 |
| TBD | 只聽人提過、比較冷門 | 自己和公司其實一直在做，只是不知道名字 |
