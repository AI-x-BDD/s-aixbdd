# 過程紀錄 2：String Calculator Step 2

日期：2026-10-05

這次先用三個自建 Skill 分析需求、規劃開發與建立 commit，接著追問短期分支怎麼收尾，最後合併回 `main` 並 push。

和 Step 1 不同，這次先做需求分析與 TBD 規劃，收到「開始執行」後才實作；實作是在短期 feature branch 上進行，不是直接在
`main` 上修改。

---

## 1. `$double-diamond`：分析 Step 2

### 輸入

```text
$double-diamond docs/需求清單.md:38-71
```

需求是基於現有 String Calculator，支援任意數量、以逗號分隔的數字：

```text
add("1,2,3")       -> 6
add("1,2,3,4,5")   -> 15
```

要求：

- 保留 Step 1 的所有行為。
- 先新增測試，再修改實作。
- 不限制只能處理固定數量的數字。
- 不提前實作換行、自訂分隔符或負數功能。
- 執行全部相關測試，確認舊測試沒有被破壞。

### Agent 的判斷

這是明確的功能規格，可以壓縮雙鑽石流程，直接以測試驗證，不需要完整使用者研究。

當時還沒檢查程式，最大的不確定性是現有實作是否限制數字數量，以及修改後會不會破壞舊行為。Agent 沒有把商業價值或使用者痛點當成已有證據。

### 比較方案

| 方案                 | Agent 的判斷                                   |
| -------------------- | ---------------------------------------------- |
| 分割後逐項累加       | 邏輯直接，容易檢查，優先採用                   |
| 分割後用 Stream 加總 | 寫法精簡，但要考量練習者的熟悉程度             |
| 逐字掃描並解析數字   | 可以避免分割陣列，但目前沒有需求支持這份複雜度 |

最便宜的驗證是新增三個、五個數字的測試，修改後跑全部相關測試；另外檢查實作是否逐項處理，因為有限案例不能單獨證明「任意數量」。

這一步只完成分析，尚未修改程式或執行測試。

## 3. 「開始執行」：建立短期分支並實作

### 輸入

```text
開始執行
```

### 檢查現況

Agent 檢查 `AGENTS.md`、`pom.xml`、程式、測試與 Git 狀態：

- 當時在 `main`。
- 有尚未追蹤的 `.agents/`，不是這次計算功能的修改。
- 已有 Maven 專案，使用 JUnit 5.11.4，編譯目標是 Java 21。
- 原有 3 個測試：空字串、一個數字、兩個數字。
- 現有實作只加總前兩個數字。

Agent 另外使用 `tdd` Skill，並建立分支：

```sh
 git switch -c step-2-arbitrary-numbers
```

### 紅燈

先新增三個數字的測試：

```java
@Test
void threeCommaSeparatedNumbersReturnTheirSum() {
    assertEquals(6, calculator.add("1,2,3"));
}
```

執行 `mvn test`：

```text
expected: <6> but was: <3>
Tests run: 4, Failures: 1, Errors: 0, Skipped: 0
BUILD FAILURE
```

失敗原因就是原本只加總前兩個數字。

### 綠燈

改成分割後逐項解析、累加，不再依數量分成一個或兩個數字的處理方式：

```java
public int add(String numbers) {
    if (numbers.isEmpty()) {
        return 0;
    }
    String[] parts = numbers.split(",");
    int sum = 0;
    for (String part : parts) {
        sum += Integer.parseInt(part);
    }
    return sum;
}
```

再次執行 `mvn test`，4 個測試全部通過。

接著新增五個數字的測試：

```java
@Test
void fiveCommaSeparatedNumbersReturnTheirSum() {
    assertEquals(15, calculator.add("1,2,3,4,5"));
}
```

迴圈已經支援這個案例，因此不需要再修改實作。最後執行全部測試：

```text
Tests run: 5, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

`git diff --check` 也通過。

### 修改的檔案

| 檔案                                                 | 修改                                        |
| ---------------------------------------------------- | ------------------------------------------- |
| `src/main/java/calculator/StringCalculator.java`     | 逐項解析、累加，保留空字串回傳 0            |
| `src/test/java/calculator/StringCalculatorTest.java` | 新增三個、五個數字的測試，保留原有 3 個測試 |

沒有加入後續 Step 的功能。這時完成實作與驗證，但尚未 commit 或合併。

## 4. `$conventional-commits it`：為什麼只給 message？

### 輸入

```text
$conventional-commits it
```

Agent 查看 diff、Git 狀態與既有 commit，提出：

```text
feat(calculator): support any number of comma-separated numbers
```

判斷理由：

- Step 1 沒有要求任意數量，這次是新增能力，用 `feat`。
- 沿用既有的 `calculator` scope 與英文功能描述。
- 實作與測試是同一個 logical change，不另外拆成 `test` commit。
- 原有使用方式保留，沒有 breaking change。

但 Agent 回覆「尚未執行 commit」，停在產生 message。

### 我的追問

> 為什麼你會停在尚未執行這一步？

### Agent 的說明

Agent 把 `$conventional-commits it` 解讀為「套用 Skill 撰寫 commit message」，沒有解讀為建立 commit。

它引用 Skill 第 9 點：

> 使用者要求 commit 才執行 commit；只要求寫 message 就只給 message。

先前的「開始執行」也被它解讀為 Step 2 實作授權，沒有延伸到 commit。這是 Agent 對指令範圍的解讀，不是工具或權限限制。

### 明確要求 commit

我接著輸入：

```text
commit
```

Agent 只 stage 計算功能與測試兩個檔案，建立：

```text
8a51384 feat(calculator): support any number of comma-separated numbers
```

hook 掃描顯示 `no leaks found`。當時 `.agents/` 沒有納入這個 commit。

## 7. 下一步是再用 TBD，還是直接合併？

### 我的問題

> 那我現在要執行的是 trunk-based
> development 還是怎麼做？直接合回主分支，還是怎樣？之前用 Claude 的時候，跟我預期行為不太一樣，我也有點忘記了接下來怎麼做。

### 釐清後

Agent 說明下一步就是把短期分支合回 `main`。TBD 是開發方式，不是必須再執行一次的指令。

它提供本機合併、測試、刪除分支的指令，另外列出 push 指令；如果團隊要求 PR
review，才改走 push 分支、開 PR、通過檢查後合併。

但它最後提供了「合回 main，先不要 push」的說法，讓我又追問一次。

### 為什麼不要 push？

> 為什麼不要 push 啊？不是要直接 push 嗎？

Agent 回覆：這次可以合回 `main`，測試通過後 push 到 `origin/main`，再刪除短期分支。

它承認「先不要 push」只是本機操作的選項，沒有必要當成預設限制。TBD 的正常收尾是把完成的變更整合到共享主幹；如果專案沒有要求 PR，就可以直接 push。

## 8. 「合併回 main，然後 push」：完成整合

### 輸入

```text
合併回 main，然後 push
```

### 實際操作

Agent 先確認工作目錄乾淨、目前分支，並 fetch 遠端，再依序執行：

```sh
 git fetch origin
 git switch main
 git merge --ff-only origin/main
 git merge --ff-only step-2-arbitrary-numbers
 mvn test
 git push origin main
 git branch -d step-2-arbitrary-numbers
```

### 結果

| 項目          | 結果                                                            |
| ------------- | --------------------------------------------------------------- |
| 同步遠端      | `origin/main` 沒有新的變更                                      |
| 合併方式      | Fast-forward，`42091ac` 前進到 `cbf835a`，沒有新增 merge commit |
| 合併內容      | 計算功能、測試與 Skill 連結兩個 commit                          |
| 合併後測試    | 5 個測試全部通過，`BUILD SUCCESS`                               |
| push          | 成功，`42091ac..cbf835a main -> main`                           |
| 本機短期分支  | 已刪除                                                          |
| 最後 Git 狀態 | `main...origin/main`，工作目錄乾淨                              |

這次没有建立 GitHub PR，也沒有檢查 push 後的 GitHub Actions 結果。已確認的測試結果是本機 `mvn test`。
