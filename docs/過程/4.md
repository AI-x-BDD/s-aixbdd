# 過程紀錄 4：String Calculator Step 4

日期：2026-10-05

這次跟 Step 3 一樣用 Claude Code（Opus 5.5），流程也一樣：`/double-diamond` 分析 → 實作 → `/conventional-commits` → `/trunk-based-development` 決定收尾方式 → 合併、push、確認 CI。

和 Step 3 比較：

- 短期分支在**實作前**就開好，補上 Step 3「分支開太晚」的缺口。
- 分析時除了偵測方式，還多做了一個設計決定：要丟哪一種 Exception。
- commit type 用 `feat` 還是 `fix`、要不要標 `BREAKING CHANGE`，這次都要判斷。
- 這次的改動會改變行為：原本會回傳數字的輸入，現在會丟 Exception。

---

## 1. `/double-diamond`：分析 Step 4

### 輸入

```text
/double-diamond docs/需求清單.md:110-142
```

需求是：輸入的最後一個字元是分隔符時，要回報錯誤。

```text
add("1,2,")
add("1\n2\n")
```

要求包括：要用清楚的 Exception、測試必須驗證錯誤真的發生、不要順便加入其他還沒要求的 validation。

### Agent 的判斷

這是明確的功能規格，可以壓縮流程。但跟 Step 3 不同，有兩個設計決定要先做：

1. 用什麼方式偵測結尾的分隔符
2. 要丟哪一種 Exception

已知的現況：`split()` 會丟掉結尾的空字串，所以 `add("1,2,")` 現在會直接回傳 3，不會報錯。新測試一定會先失敗，紅燈是真的。

### 比較方案：偵測方式

| 方案                                 | Agent 的判斷                                                       |
| ------------------------------------ | ------------------------------------------------------------------ |
| A. `endsWith(",") \|\| endsWith("\n")` | 最好懂，但分隔符要寫在 regex 和 `endsWith` 兩個地方，Step 5 兩邊都要改 |
| B. `split(regex, -1)` 再看最後一個元素 | 和切割共用同一個 regex，Step 5 只要改一個地方，建議採用            |
| C. 檢查所有空元素                    | 會連 `"1,,2"` 一起擋下，等於提前做 Step 7，違反要求，淘汰          |

B 要注意：只能檢查**最後一個**元素，不然就變成 C。

### 比較方案：Exception

| 方案                                  | Agent 的判斷                                              |
| ------------------------------------- | --------------------------------------------------------- |
| `IllegalArgumentException` 加上清楚的訊息 | JDK 本來就有，語意是「參數不合法」，不用新增類別，建議採用 |
| 自訂 `InvalidInputException`          | 目前只有一種錯誤，算過度設計，Step 7 再考慮               |
| 讓它自然丟出 `NumberFormatException`  | 訊息看不出原因，不算「清楚的 Exception」，淘汰            |

### 範圍外的觀察

- `"1,,2"`、`"1,\n2"` 還是會丟 `NumberFormatException`，屬於 Step 7。
- `","` 用方案 B 會切成 `["", ""]`，最後一個是空的，所以也會報錯。這剛好符合需求的字面意思，不用另外處理。

Agent 也提到這次會**先開分支再實作**。

這一步只做分析，沒有修改程式。

## 2. 「do it」：先開分支，再實作

### 輸入

```text
do it
```

### 建立分支

先同步遠端，再開分支：

```sh
git fetch origin
git merge --ff-only origin/main
git switch -c step-4-trailing-delimiter
```

### 紅燈

新增兩個測試，除了用 `assertThrows` 確認 Exception 真的發生，也檢查錯誤訊息：

```java
@Test
void trailingCommaIsRejected() {
    IllegalArgumentException exception =
            assertThrows(IllegalArgumentException.class, () -> calculator.add("1,2,"));
    assertEquals("Input must not end with a delimiter", exception.getMessage());
}

@Test
void trailingNewlineIsRejected() {
    IllegalArgumentException exception =
            assertThrows(IllegalArgumentException.class, () -> calculator.add("1\n2\n"));
    assertEquals("Input must not end with a delimiter", exception.getMessage());
}
```

檢查訊息是為了避免別的地方剛好丟出 `IllegalArgumentException`，讓測試誤判成通過。

執行 `mvn test`：

```text
Tests run: 9, Failures: 2, Errors: 0, Skipped: 0
trailingCommaIsRejected:50 Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown.
trailingNewlineIsRejected:57 Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown.
```

`nothing was thrown` 證明舊程式確實把這兩種輸入當成合法。

### 綠燈

```java
String[] parts = numbers.split("[,\n]", -1);
if (parts[parts.length - 1].isEmpty()) {
    throw new IllegalArgumentException("Input must not end with a delimiter");
}
```

- `split` 的第二個參數傳 `-1`，結尾的空字串就會保留下來。`"1,2,"` 會切成 `["1", "2", ""]`。
- 只檢查最後一個元素，中間的空值不處理。

再次執行 `mvn test`：

```text
Tests run: 9, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

`git diff --check` 也通過。

### 修改的檔案

| 檔案                                                 | 修改                                                    |
| ---------------------------------------------------- | ------------------------------------------------------- |
| `src/main/java/calculator/StringCalculator.java`     | `split` 加上 `-1`，最後一個元素是空的就丟 Exception     |
| `src/test/java/calculator/StringCalculatorTest.java` | 新增結尾逗號、結尾換行兩個測試，加入 `assertThrows` import |

## 3. `/conventional-commits`：`feat` 還是 `fix`？

### 輸入

```text
/conventional-commits
```

跟 Step 3 一樣，Agent 把它當成「建立 commit」，直接執行。

```text
47ae6fe feat(calculator): reject input that ends with a delimiter

Throw IllegalArgumentException when the last token is empty, e.g.
add("1,2,") or add("1\n2\n"). Previously split() dropped the trailing
empty token, so these inputs silently returned the sum.

Empty tokens in the middle ("1,,2") are not validated yet.
```

### 判斷理由

**為什麼用 `feat`，不用 `fix`：** `"1,2,"` 回傳 3 雖然不對，但 Step 1～3 從來沒規定過這種輸入要怎麼處理，所以不算違反規格的 bug。結尾報錯是 Step 4 新增的規則，用 `feat`。Agent 也說明，如果把它看成「修掉被吞掉的錯誤」，用 `fix` 也講得通，規範沒有硬性規定。

**為什麼沒標 `BREAKING CHANGE`：** 原本會回傳數字的輸入，現在會丟 Exception，嚴格說行為確實變了。但舊行為只是 `split()` 剛好造成的結果，不是刻意提供的功能，而且這個練習專案沒有外部呼叫者。如果是對外發布的 library，就要考慮加 `!`。

**body 寫了三件事：** 改了什麼、舊行為為什麼會吞掉錯誤、這次還沒處理的範圍。

## 4. `/trunk-based-development`：檢查狀態、決定怎麼收尾

### 輸入

```text
/trunk-based-development
```

### Agent 的檢查

```text
PR 1：結尾是分隔符的輸入改成丟 IllegalArgumentException（含 2 個測試）  — 使用技巧：無
每個 PR merge 後 main 為什麼仍可工作：合法輸入的行為不變，9 個測試本機全部通過
預估 branch 壽命（含 review）：不到一小時，當天 merge
```

| 檢查項目         | 結果                                                       |
| ---------------- | ---------------------------------------------------------- |
| 切得夠小嗎       | 1 個 commit，實作加 4 行，加上 2 個測試                    |
| 跟 main 同步了嗎 | fetch 後比 `origin/main` 落後 0、領先 1，可以 fast-forward |
| 分支什麼時候開   | 實作前                                                     |
| CI 驗證          | 還沒跑，`ci.yml` 只在 push 到 `main` 或開 PR 時觸發        |
| Active branches  | 只有這一條                                                 |

### 這次多了一個考量

這是**行為改變**。Agent 指出：在這個練習專案裡沒有別的呼叫者，風險很低；但在真實團隊裡，這類改動比較適合開 PR，讓 CI 和 reviewer 在 merge 前先看過。

收尾方式還是兩種：A 是本機 fast-forward 後 push，B 是開 PR。Agent 建議用 A，跟前面的 Step 保持一致，並提到 B 也適合拿來練習。因為 push 會更新遠端，Agent 先問過才執行。

## 這次學到的

- **分支先開，`main` 就不會沾到半成品**：這次從紅燈到 commit 都在短期分支上，`main` 一直保持乾淨。
- **偵測方式要考慮下一步**：方案 A 和 B 現在都能過測試，差在 Step 5 加自訂分隔符時要改幾個地方。選 B 是為了讓分隔符的定義只放在一個地方。
- **「只檢查最後一個」是刻意的範圍控制**：一般化成「檢查所有空元素」看起來更完整，但這樣會提前做 Step 7。
- **測試要檢查錯誤訊息**：只用 `assertThrows` 的話，別的程式碼剛好丟出同一種 Exception 也會通過。
- **`feat`／`fix`、要不要標 breaking，是判斷問題**：要看舊行為是不是「有意提供的功能」，以及有沒有外部呼叫者。規範本身不會替你決定。
- **行為改變時，收尾方式值得再想一次**：練習專案直接 push 沒問題；團隊專案遇到這類改動，比較適合開 PR，讓 CI 在 merge 前把關。
- **TBD 不是 commit 之後的收尾步驟**：作業寫的是「每次開發前，先依序啟用」三個 Skill。Step 3、Step 4 把 TBD 放在 commit 之後，所以看起來像多餘的一步。

  三個 Skill 回答的問題不同：

  | Skill      | 回答的問題                                   | 主要作用在           |
  | ---------- | -------------------------------------------- | -------------------- |
  | 雙鑽石     | 要做什麼？怎麼做才對？                       | 開發前               |
  | 慣例式提交 | 做完的變更怎麼記錄？                         | commit 時            |
  | 主幹式開發 | 變更切多小？在哪裡開發？多快整合回 `main`？ | 開發前一路到整合完成 |

  commit 只是存進自己的 branch，別人看不到、CI 也還沒跑。TBD 管的是從開 branch 到合回 `main` 這整段：開發前先決定怎麼切、需不需要 Feature Flag、branch 預計活多久；開發中保持 branch 短命、跟 `main` 同步；開發後盡快 merge、確認 CI、刪掉 branch。Step 3 的分支開太晚，就是因為 TBD 用得太晚。

  Step 5 以後改用這個順序：

  ```text
  1. /double-diamond          → 決定要做什麼、選哪個方案
  2. /trunk-based-development → 規劃怎麼切、開 branch（還沒寫程式）
  3. 實作（TDD）
  4. /conventional-commits    → commit
  5. 照第 2 步的規劃整合：merge、push、確認 CI、刪 branch
  ```
