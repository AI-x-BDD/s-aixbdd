# 過程紀錄 5：String Calculator Step 5

日期：2026-10-05

這是第一次照 Step 4 紀錄最後整理的新順序完成一個 Step：

```text
1. /double-diamond          → 決定要做什麼、選哪個方案
2. /trunk-based-development → 規劃怎麼切、開 branch（還沒寫程式）
3. do it                    → 實作（TDD）
4. /conventional-commits    → commit
5. 收尾                     → merge、push、確認 CI、刪 branch
```

和 Step 4 比較：

- TBD 在實作**前**用，規劃完就開 branch，不再是 commit 之後的收尾檢查。
- 這次有一個寫得不明確的需求，要先做決定，並把決定寫進 commit body。
- 第一次把一個 Step 拆成兩個 commit：`refactor` 和 `feat`。
- 拆 commit 時用了 `git stash --keep-index`，pop 時發生衝突。

開始前先問了「下個是 step ?」，Agent 用 `grep "^# Step"` 找出 Step 5 在 `docs/需求清單.md` 第 146–186 行。

## 1. `/double-diamond`：分析 Step 5

### 輸入

```text
/double-diamond docs/需求清單.md:146-186
```

需求是支援 `//[delimiter]\n[numbers]` 格式的自訂分隔符：

```text
add("//;\n1;2") -> 3
add("//|\n1|2|3") -> 6
```

需求允許「parsing 邏輯開始混亂時，可以做小幅重構」。

### Agent 的判斷

這是到目前為止設計風險最高的一步，有兩個技術陷阱，還有一個寫得不明確的需求：

1. **`|` 在 regex 裡是特殊字元**：現在用 `split(regex)` 切字串，`|` 直接拼進 regex 會被當成「或」。需求的第二個範例剛好會踩到。自訂分隔符要用 `Pattern.quote()`。
2. **要求 4 有兩種讀法**：「原本的逗號與換行功能仍然必須正常」可以是 (a) 沒有 `//` 開頭的輸入照舊運作，也可以是 (b) 有 `//` 開頭的輸入裡 `,`、`\n` 也能用。需求只保證 (a)，(b) 沒有任何範例。
3. **header 自己帶一個 `\n`**：要先把 `//;\n` 切掉再處理數字，不然這個 `\n` 會被當成數字之間的分隔符。

### 比較方案

| 方案                                | Agent 的判斷                                                              |
| ----------------------------------- | ------------------------------------------------------------------------- |
| A. 全部寫在 `add()` 裡              | 改動最少，但 `add()` 同時做 header 解析、切割、驗證、加總                 |
| B. 抽出 private `tokenize()`        | 需求允許的小幅重構，`add()` 恢復好讀，Step 8 也有起點，建議採用           |
| C. 先 `replace` 成 `,` 再沿用 split | 純文字取代，不會踩到 regex 陷阱；但會讓 (b) 自動通過，等於暗中替需求做決定 |
| D. 建立 `Parser` 類別               | Step 7、Step 8 才需要，現在是過度設計，淘汰                               |

需求不明確的部分：

| 選項                                     | `"//;\n1;2,3"` 的結果       | Agent 的判斷                       |
| ---------------------------------------- | --------------------------- | ---------------------------------- |
| ① 自訂分隔符**加上**原本的 `,`、`\n`     | 6                           | 兩種讀法都滿足，建議採用           |
| ② **只用**自訂分隔符                     | 丟 `NumberFormatException` | 比較嚴格，但需求沒有範例支持       |

不管選哪個，都不為混用寫測試，因為需求沒有要求；選擇會寫進 commit body。

### 範圍外的觀察

- `"//;\n"`，有 header 但沒有數字：會被當成「結尾是分隔符」，錯誤訊息不太準確，屬於 Step 7。
- `"//-\n1-2"`：`-` 會跟 Step 6 的負數衝突，到 Step 6 再處理。

這一步只做分析，沒有修改程式。

## 2. `/trunk-based-development 依建議`：規劃並開 branch

### 輸入

```text
/trunk-based-development 依建議
```

「依建議」表示接受方案 B 和選項 ①。

### 規劃結果

```text
Commit 1：refactor — 把「輸入 → 數字字串陣列」抽成 private tokenize()，行為不變
Commit 2：feat — tokenize() 支援 //[delimiter]\n header，用 Pattern.quote()，保留 `,`、`\n`
每個 commit merge 後 main 為什麼仍可工作：
  Commit 1 不改行為，9 個測試通過才 commit
  Commit 2 只在輸入以 "//" 開頭時走新路徑，全部測試通過才 commit
預估 branch 壽命（含 review）：不到一小時，當天 merge
```

**為什麼拆成兩個 commit：** 重構時測試變紅，就一定是重構的問題，不會跟新功能混在一起；之後也可以只 revert 其中一個。這是 TBD「切小」的原則，一個需求不一定只對應一個變更。

**為什麼兩個 commit 放同一個 branch，不拆成兩個 PR：** 兩個加起來只要幾分鐘，也沒有 review 要等。拆成兩次收尾只會多一次儀式，`main` 不會更安全。如果團隊 review 要等半天，就值得先單獨 merge refactor。這是團隊自己決定的事，不是 TBD 的規定。

**這次要加的測試：**

| 測試                         | 目的                                                     |
| ---------------------------- | -------------------------------------------------------- |
| `"//;\n1;2"` → 3             | 基本的自訂分隔符                                         |
| `"//\|\n1\|2\|3"` → 6         | 確認 `Pattern.quote()` 有作用                            |
| `"//;\n1;2;"` → 丟 Exception | Step 4 的結尾檢查在自訂分隔符下仍然有效，不是新規則      |

### 實際操作

先同步遠端，確認 `main` 和 `origin/main` 是 0 / 0，再開 branch：

```sh
git fetch origin
git merge --ff-only origin/main
git switch -c step-5-custom-delimiter
```

這時還沒有修改程式。

## 3. 「do it」：refactor → 紅燈 → 綠燈

### 輸入

```text
do it
```

### Refactor

```java
public int add(String numbers) {
    ...
    String[] parts = tokenize(numbers);
    ...
}

private String[] tokenize(String numbers) {
    return numbers.split("[,\n]", -1);
}
```

`mvn test`：9 個測試全部通過，行為沒變。

因為「do it」只授權實作，commit 要等 `/conventional-commits`，Agent 先把 refactor 的修改 **stage** 起來，讓 commit 時能分成兩個。

### 紅燈

新增三個測試，`mvn test`：

```text
Tests run: 12, Failures: 1, Errors: 2, Skipped: 0
trailingCustomDelimiterIsRejected:75 expected: <Input must not end with a delimiter> but was: <For input string: "//;">
customDelimiterSeparatesNumbers:63 » NumberFormat For input string: "//;"
regexSpecialCharacterCanBeCustomDelimiter:68 » NumberFormat For input string: "//|"
```

**值得注意的一點：** `trailingCustomDelimiterIsRejected` 其實有丟出 Exception，丟的是 `NumberFormatException`。它是 `IllegalArgumentException` 的子類別，所以只用 `assertThrows` 檢查型別的話會**誤判通過**。能抓到問題，是因為 Step 4 的測試也檢查了錯誤訊息。

### 故意先不加 `Pattern.quote`

```java
return numbers.substring(headerEnd + 1).split("[,\n]|" + delimiter, -1);
```

`mvn test`：

```text
Tests run: 12, Failures: 0, Errors: 1, Skipped: 0
regexSpecialCharacterCanBeCustomDelimiter:68 » IllegalArgument Input must not end with a delimiter
```

`;` 的測試過了，`|` 的失敗。regex 變成 `[,\n]||`，中間多出一個能比對空字串的選項，每個位置都被切開，最後被誤判成「結尾是分隔符」。陷阱是真的。

### 綠燈

```java
private String[] tokenize(String numbers) {
    if (numbers.startsWith("//")) {
        int headerEnd = numbers.indexOf('\n');
        String delimiter = numbers.substring(2, headerEnd);
        return numbers.substring(headerEnd + 1).split("[,\n]|" + Pattern.quote(delimiter), -1);
    }
    return numbers.split("[,\n]", -1);
}
```

- 開頭是 `//` 才算有 header，`//` 和第一個 `\n` 之間就是分隔符。用 `substring` 取一段字串，所以多字元分隔符也能用，雖然需求沒要求。
- 先切掉 header，只處理後面的數字。
- `Pattern.quote` 讓 `|` 被當成一般字元。
- Step 4 的結尾檢查還留在 `add()`，自訂分隔符的輸入也會經過。

`mvn test`：

```text
Tests run: 12, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

`git diff --check` 也通過。這時 refactor 是 staged，feat 是 unstaged。

## 4. `/conventional-commits`：拆成兩個 commit

### 輸入

```text
/conventional-commits
```

### Commit 1：單獨驗證 refactor

Agent 用 `git stash push --keep-index` 把 unstaged 的 feat 修改收起來，只留 staged 的 refactor，跑 `mvn test`（9/9 通過）才 commit：

```text
e98484a refactor(calculator): extract tokenize from add

Move the input-to-tokens split into a private tokenize method so add
only validates and sums. Prepares for custom delimiter parsing.

No behavior change.
```

這樣確認這個 commit 單獨存在時也能運作，之後要 revert 或 bisect 都安全。

### stash pop 發生衝突

commit 後執行 `git stash pop`，`StringCalculator.java` 出現衝突：

```text
UU src/main/java/calculator/StringCalculator.java
The stash entry is kept in case you need it again.
```

原因是 stash 的基準和剛建立的 refactor commit 改到同一段程式碼。處理方式：

1. 確認 refactor commit 已經建立，stash 還在，測試檔也已經還原。
2. 用 stash 裡的完整 feat 版本覆蓋衝突的檔案：

   ```sh
   git checkout stash@{0} -- src/main/java/calculator/StringCalculator.java
   git restore --staged src/
   ```

3. 確認檔案裡沒有 conflict marker，12 個測試全部通過，diff 跟原本的 feat 版本一樣。
4. 建立 Commit 2 之後才 `git stash drop`。

沒有遺失任何東西。

### Commit 2

```text
a926cbc feat(calculator): support custom delimiter header

Parse an optional "//[delimiter]\n" header and split the remaining
numbers on that delimiter, e.g. add("//;\n1;2") returns 3. The
delimiter is quoted with Pattern.quote so regex metacharacters such
as "|" are treated literally.

"," and "\n" stay valid alongside the custom delimiter. The spec only
requires inputs without a header to keep working; accepting both
was chosen because it satisfies either reading of that requirement.
```

body 的第二段記下選項 ① 的需求判斷。以後有人問「為什麼混用也能過」，可以在 git log 找到答案。沒有 header 的輸入行為完全不變，所以沒有 breaking change。

## 這次學到的

- **新順序有效**：TBD 放在實作前，branch 一開始就開好，`main` 從頭到尾沒被直接修改。規劃時也順便決定了要拆幾個 commit、加哪些測試。
- **故意讓陷阱發生一次**：先不加 `Pattern.quote` 跑一次，看到 `|` 真的失敗，才能確定那個測試在保護它該保護的東西。
- **測試檢查訊息不是多餘的**：`NumberFormatException` 是 `IllegalArgumentException` 的子類別。Step 4 只用 `assertThrows` 的話，這次的紅燈會變成假的綠燈。
- **需求不明確時，選一個能滿足兩種讀法的方案，並把理由寫下來**：選項 ① 不會違反任何一種讀法，判斷寫進 commit body，而不是只留在對話裡。
- **refactor 和 feat 拆成兩個 commit**：每個 commit 都單獨驗證過，出問題時比較好查、也比較好 revert。
- **同一個檔案上，不要用「stage refactor、接著寫 feat」**：`stash --keep-index` 在同一段程式碼上 pop 會衝突。下次比較簡單的做法是 refactor 一跑綠就先 commit，再開始寫 feat。可以輸入 `do it，refactor 完先 commit`。
