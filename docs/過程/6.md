## 1. `$double-diamond`：分析 Step 6

### 輸入

```text
$double-diamond docs/需求清單.md:190-234
```

需求：

```text
add("-1,2")    → Exception，訊息為 Negative not allowed: -1
add("-1,2,-3") → Exception，訊息為 Negative not allowed: -1,-3
```

要求先加入單一負數測試，再加入多個負數測試；必須收集全部負數，不能遇到第一個就停止。原本正常的輸入也要繼續正常。

### Agent 的判斷與方案

這是明確的功能規格，可以壓縮雙鑽石流程。現有 `add()` 直接解析、加總，會接受負數；主要要決定驗證放在哪裡，以及如何完整回報。

| 方案 | 做法 | 判斷 |
| --- | --- | --- |
| A | 在現有迴圈收集負數，遍歷完成後拋錯 | 建議採用；改動小，每個數字只解析一次 |
| B | 先建立整數集合，再驗證與加總 | 職責較分明，但增加集合與遍歷 |
| C | 抽出獨立 validator | 目前只有一條新增規則，暫無足夠理由抽類別 |

例外選用 `IllegalArgumentException`。需求只規定訊息，例外類型是這次的實作決定。

### 範圍與邊界

- 維持 `tokenize()` 的切割規則，以解析後的數值判斷負數。
- 自訂分隔符 `-` 與負號可能衝突，這次沒有另訂跳脫語法，也沒有新增對應測試。
- `-1,,2` 等複合錯誤留在 Step 7，這次沒有保證多種錯誤會一併回報。
- 規劃驗證單一負數、多個負數、換行、自訂分隔符與零，並保留既有 12 個測試。

這一步只有分析，沒有修改程式或執行測試。Agent 建議下一步輸入 `$trunk-based-development 依建議`。

### 第一輪：單一負數

先加入 `singleNegativeNumberIsRejected`，從公開方法 `add("-1,2")` 驗證例外與完整訊息。

執行 `mvn -o test` 得到預期紅燈：

```text
Expected java.lang.IllegalArgumentException to be thrown, but nothing was thrown.
Tests run: 13, Failures: 1, Errors: 0, Skipped: 0
```

最小實作是在解析後檢查 `number < 0`，遇到負數就拋出例外。再執行 `mvn -o -q test`，成功退出，13 個測試通過。

### 第二輪：多個負數

接著加入 `allNegativeNumbersAreReportedInInputOrder`，輸入 `-1,2,-3`。

執行測試得到預期紅燈：

```text
expected: <Negative not allowed: -1,-3> but was: <Negative not allowed: -1>
Tests run: 14, Failures: 1, Errors: 0, Skipped: 0
```

這證明「遇到第一個負數就拋錯」不符合需求。改用 `StringJoiner` 收集負數，迴圈結束後才檢查：

```java
int sum = 0;
StringJoiner negatives = new StringJoiner(",");
for (String part : parts) {
    int number = Integer.parseInt(part);
    if (number < 0) {
        negatives.add(Integer.toString(number));
    }
    sum += number;
}
if (negatives.length() > 0) {
    throw new IllegalArgumentException("Negative not allowed: " + negatives);
}
return sum;
```

負數在解析成整數後被辨識，依輸入順序收集。迴圈仍計算加總，但只要收集到負數，就拋出例外，不回傳結果。再次執行測試，14 個測試通過。

### 補充驗證

最後加入三個案例，現有實作已能通過，不需再改程式：

| 輸入 | 預期結果 |
| --- | --- |
| `-3\n2,-1` | `Negative not allowed: -3,-1`，確認換行與輸入順序 |
| `//|\n-1|2|-3` | `Negative not allowed: -1,-3`，確認自訂分隔符 |
| `0,2` | 回傳 `2`，確認零仍合法 |

完整執行 `mvn -o test`：

```text

BUILD SUCCESS
```

`git diff --check` 也通過。兩個核心需求各自經過紅燈到綠燈；後三個案例是補充驗證，沒有刻意改壞實作製造紅燈。

因此把完整流程補成六步：

```text
1. $double-diamond <需求範圍>       → 分析需求、比較方案
2. $trunk-based-development 依建議 → 規劃拆分與整合、建立短期分支
3. do it                          → 實作與測試
4. $conventional-commits commit    → 提交變更
5. 收尾                           → merge、push、確認 CI、刪分支
6. 整理過程紀錄，再提交、push      → 保存提示詞、決策與驗證證據
```

第 4 步加上 `commit` 是為了讓意圖明確；這次實際輸入仍是 `$conventional-commits`。
