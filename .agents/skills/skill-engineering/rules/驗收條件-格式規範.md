# Rule 1 - 驗收條件必須描述可觀察的結果

- 預期必須寫成以 `E1`、`E2` 連續編號的驗收條件。
- 每條驗收條件必須描述 Skill 產出或行為中可觀察的特徵，使驗收者不需要推測使用者意圖即可判斷是否符合。
- 驗收條件不得只使用「清楚」、「完整」或「更好」等無法獨立檢查的描述。

## Good Example

- 驗收條件指出類別圖中可直接檢查的標示方式。

情境：

- 使用者回報：類別圖看不出哪些類別是這次新增、哪些只是修改。
- E1：類別圖中每個類別都依本次變更的角色，以 annotation 標示 `<<new>>`（新增）、`<<modified>>`（修改）或 `<<existing>>`（未修改的既有類別）其中一種。

## Bad Example

- 同一個回報被寫成主觀描述，無法判斷產出是否符合。

情境：

- 使用者回報：類別圖看不出哪些類別是這次新增、哪些只是修改。
- E1：類別圖要更容易看懂。

# Rule 2 - 每條驗收條件必須標明來源

- 每條驗收條件必須標明來源：「本次」表示使用者明確提出，「既有」表示目標 Skill 原本的核心預期，「推定」表示使用者沒有提出、由執行者推定的預期。
- 優化模式必須納入既有核心預期，並從目標 Skill 的 `description`、各 Phase 的完成條件與使用者確認閘門推導。
- 只有使用者沒有說明、但 Skill 執行時必須決定的行為可以推定；每條推定的驗收條件必須寫出推定理由。
- 來源為「推定」的驗收條件必須在確認閘門逐條請使用者確認。

## Good Example

- 除了本次的標示需求，也保留提案結構與確認閘門兩項既有預期，並把執行者推定的預期標為推定。

| 編號 | 驗收條件                                                         | 來源 |
| ---- | ---------------------------------------------------------------- | ---- |
| E1   | 每個類別依變更角色標示 `<<new>>`、`<<modified>>` 或 `<<existing>>`     | 本次 |
| E2   | 提案檔依序包含「類別圖」與「設計說明與實作順序」兩個頂層 Section | 既有 |
| E3   | 使用者明確確認提案前，不修改任何程式碼                           | 既有 |
| E7   | 測試類別不出現在類別圖中                                         | 推定 |

## Bad Example

- 只列出本次需求，重新設計時確認閘門可能因為無法追溯而被刪除；推定的預期被標成本次，使用者不會被詢問。

| 編號 | 驗收條件                                                     | 來源 |
| ---- | ------------------------------------------------------------ | ---- |
| E1   | 每個類別依變更角色標示 `<<new>>`、`<<modified>>` 或 `<<existing>>` | 本次 |
| E7   | 測試類別不出現在類別圖中                                     | 本次 |

# Rule 3 - 每條驗收條件必須標明適用範圍

- 每條驗收條件必須標明「通用」或「個案」；通用表示 Skill 每次執行都應滿足，個案表示只適用本次產出。
- 無法從使用者描述判斷適用範圍時，必須在確認閘門詢問使用者。
- 個案驗收條件不得作為修改 Skill 的依據，只能作為本次產出的調整建議。

## Good Example

- 標示需求適用於每次修改既有程式碼的提案，配色只是本次偏好，不寫入 Skill。

| 編號 | 驗收條件                                   | 適用範圍 | 處理方式                 |
| ---- | ------------------------------------------ | -------- | ------------------------ |
| E1   | 每個類別都標示變更類型                     | 通用     | 作為修改 Skill 的依據    |
| E4   | 本次類別圖改用淺色主題                     | 個案     | 只調整本次產出，不改 Skill |

## Bad Example

- 本次的配色偏好被標成通用，導致 Skill 新增一條只為單次產出存在的規則。

| 編號 | 驗收條件               | 適用範圍 | 處理方式                     |
| ---- | ---------------------- | -------- | ---------------------------- |
| E4   | 本次類別圖改用淺色主題 | 通用     | 新增 Rule 要求類別圖使用淺色 |

# Rule 4 - 每條驗收條件必須對應可執行的驗收情境

- 每條通用驗收條件必須至少對應一個以 `S1`、`S2` 連續編號的驗收情境；個案驗收條件不需要驗收情境。
- 每個驗收情境必須包含輸入、Skill 遇到使用者確認閘門時的預先回覆，以及判斷通過的方式。
- 優化模式必須以本次問題的原始輸入建立至少一個情境；只驗證既有核心預期的情境必須標記為回歸情境。
- 判斷方式只能檢查對應驗收條件要求的結果，不得要求驗收條件沒有規定的特定判斷結果。
- 驗收情境的輸入不得與目標 Skill 部位中的範例相同，避免驗收只證明 Skill 能重現自己的範例。

## Good Example

- 情境包含原始輸入、預先回覆與可直接檢查的判斷方式，並有一個回歸情境。

| 編號 | 驗證 | 類型 | 輸入 | 預先回覆 | 判斷方式 |
| ---- | ---- | ---- | ---- | -------- | -------- |
| S1 | E1、E2 | 本次 | 為既有訂單系統新增退款功能，原始碼含 `OrderService` 與 `PaymentGateway` | Phase 2 回覆「確認」 | 三個類別各有一個 annotation，且 `RefundService` 為 `<<new>>` |
| S2 | E2、E3 | 回歸 | 從零建立通知模組，沒有既有類別 | Phase 2 回覆「先不要」 | 所有類別為 `<<new>>`，兩個頂層 Section 完整，且沒有修改程式碼 |

## Bad Example

- 情境沒有輸入、預先回覆與判斷方式，驗收者無法重現或判斷結果。

| 編號 | 驗證 | 類型 | 輸入 | 預先回覆 | 判斷方式 |
| ---- | ---- | ---- | ---- | -------- | -------- |
| S1 | E1 | 本次 | 跑一次看看 | 無 | 結果看起來比較好 |
