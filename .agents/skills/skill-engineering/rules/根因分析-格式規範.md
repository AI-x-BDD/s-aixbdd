# Rule 1 - 每項判斷必須標明證據類型

- 分析中的每項判斷必須標記為「觀察」或「推論」。
- 觀察必須指出可查核的來源，例如對話紀錄中的訊息、產出檔案的路徑與位置，或 Skill 檔案的 Phase、步驟與 Rule 編號。
- 推論必須指出所依據的觀察。
- 判斷根因所需的關鍵證據缺失時，必須向使用者索取，不得以推論取代。

## Good Example

- 觀察指出紀錄中的具體行為，推論明確引用該觀察。

情境：

- 觀察：對話紀錄顯示，執行 Phase 1 步驟 10 時讀取了 `templates/class-diagram-proposal.md` 與 `templates/class-diagram-proposal.example.md`。
- 推論：類別圖提案樣板組已載入，根因不是「未載入」（依據上一項觀察）。

## Bad Example

- 判斷沒有來源，也沒有區分觀察與推論。

情境：

- AI 應該沒有讀樣板，所以類別圖格式不對。

# Rule 2 - 必須逐步演練並找出第一個偏離點

- 必須依 SOP 順序逐步填寫演練表，欄位為步驟、應載入、實際載入、應產出、實際產出與判定。
- 判定必須使用「一致」、「偏離」或「無證據」。
- 根因分析必須從第一個判定為「偏離」的步驟開始，不得從最終症狀出現的位置直接指定修改位置。
- 第一個偏離點是委派其他 Skill 的步驟時，必須進入被委派 Skill 的 SOP 繼續演練，直到找到該 Skill 內的第一個偏離點。

## Good Example

- 演練表逐步比對，第一個偏離點是產生提案檔的步驟，而不是發現症狀的確認步驟；以下節錄其中三列。

| 步驟 | 應載入 | 實際載入 | 應產出 | 實際產出 | 判定 |
| ---- | ------ | -------- | ------ | -------- | ---- |
| P1-7 | 類別設計檢查清單 | 觀察：已讀取 | 區分新增、修改與既有類別的設計 | 觀察：設計說明列出新增 `RefundService`、修改 `OrderService` | 一致 |
| P1-11 | 類別圖輸出檢查清單、類別圖提案樣板組 | 觀察：已讀取 | 使用者能從圖中辨識每個類別的變更類型 | 觀察：三個類別沒有任何變更標示 | 偏離 |
| P2-1 | 無 | 無 | 展示提案檔 | 觀察：使用者表示看不出變更類型 | 一致 |

## Bad Example

- 跳過演練，直接在症狀出現的確認步驟追加修補。

情境：

- 使用者在 Phase 2 展示提案時表示看不出變更類型。
- 分析結論：在 Phase 2 新增一個步驟，展示前詢問使用者是否需要標示。

# Rule 3 - 根因必須定位到部位並歸入缺陷類型

- 根因必須指出 Skill 名稱、部位檔案與具體位置，例如 Phase 與步驟、Rule 編號或樣板中的區段。
- 根因必須歸入下表其中一種缺陷類型。
- 多個症狀共用同一根因時，必須合併為一個根因；不同根因必須以 `R1`、`R2` 連續編號。

| 缺陷類型     | 判斷方式                                                     |
| ------------ | ------------------------------------------------------------ |
| 缺失         | 預期沒有在任何部位中表達                                     |
| 未載入       | 表達預期的部位或所需的輸入存在，但偏離步驟前沒有載入，或載入時機太晚 |
| 不可檢查     | 部位已載入，但要求無法獨立檢查，`CHECK` 無法判斷違反         |
| 衝突         | 兩個部位的要求互相矛盾、同一約束存放在兩處以上，或範例與規則說明不一致 |
| 載體過弱     | 可由腳本或樣板保證的要求，只以文字交給 AI 判斷而結果不穩定   |
| 流程缺陷     | 缺少步驟或確認閘門、順序錯誤，或 Phase 切分不當              |
| 交接缺陷     | 上游 Skill 委派時沒有交出下游需要的資訊                      |
| 觸發缺陷     | 應使用的 Skill 沒有被觸發，或觸發了不適用的 Skill            |
| 非 Skill 問題 | 落差來自模型能力、執行環境、輸入不足或個案偏好              |

## Good Example

- 根因指出 Skill、RuleFile 與 Rule 編號，並歸入一種缺陷類型。

| 編號 | 位置 | 缺陷類型 |
| ---- | ---- | -------- |
| R1 | `class-diagram-planner`／`rules/類別圖輸出-格式規範.md`／Rule 2 | 缺失 |

## Bad Example

- 根因只描述症狀，沒有指出部位位置，也沒有歸類。

| 編號 | 位置 | 缺陷類型 |
| ---- | ---- | -------- |
| R1 | 類別圖品質不好 | 未分類 |

# Rule 4 - 根因必須通過反事實檢驗並排除其他假設

- 在第一個偏離點，必須列出至少兩個屬於不同缺陷類型的根因假設。
- 每個被排除的假設必須附上排除依據，依據必須是觀察，或明確引用觀察的推論。
- 保留的根因必須通過反事實演練：假設該位置已改正，從第一個偏離點重新演練可滿足所有相關的驗收條件。
- 反事實演練無法滿足驗收條件時，不得保留該根因，必須繼續追查上游步驟或其他假設。

## Good Example

- 三個假設涵蓋不同缺陷類型，排除依據都是觀察，保留的根因通過反事實演練。

| 假設 | 缺陷類型 | 結果 | 依據 |
| ---- | -------- | ---- | ---- |
| H1：類別圖輸出規則沒有要求標示變更類型 | 缺失 | 保留 | 反事實：Rule 2 要求 annotation 時，P1-11 會寫出標示，P1-12 會逐條檢查，E1 可滿足 |
| H2：設計步驟沒有區分新增與修改 | 流程缺陷 | 排除 | 觀察：P1-7 的設計說明已區分新增 `RefundService` 與修改 `OrderService` |
| H3：樣板組沒有載入 | 未載入 | 排除 | 觀察：P1-10 已讀取骨架與範例 |

## Bad Example

- 只提出一個假設，沒有證據，也沒有反事實演練。

| 假設 | 缺陷類型 | 結果 | 依據 |
| ---- | -------- | ---- | ---- |
| H1：規則不夠多 | 缺失 | 保留 | 看起來是這樣 |

# Rule 5 - 根因不在 Skill 時必須明確結論

- 根因屬於「非 Skill 問題」，或所有落差都只來自個案驗收條件時，必須提出不修改 Skill 的結論。
- 結論必須說明判斷依據，並提供不修改 Skill 也能改善本次結果的做法，例如使用者下次需要提供的輸入。
- 不得為了回應使用者的不滿而提出修改 Skill 的建議。

## Good Example

- 落差來自輸入不足，結論是不修改 Skill，並說明下次需要提供的輸入。

情境：

- 觀察：使用者沒有提供 Java 原始碼路徑，Phase 1 步驟 2 因此沒有選定入口類別。
- 結論：非 Skill 問題（輸入不足）；Skill 已在步驟 1 讀取原始碼路徑（若有），不修改 Skill。
- 建議：下次提供原始碼路徑，Skill 即可取得既有類別結構。

## Bad Example

- 同一個輸入不足的情境，為了回應不滿而新增規則，要求 AI 自行猜測原始碼位置。

情境：

- 觀察：使用者沒有提供 Java 原始碼路徑。
- 結論：新增 Rule，要求沒有路徑時搜尋整個磁碟中的 `.java` 檔案。

# Rule 6 - 根因報告只呈現診斷結果

- 根因報告不得包含修改方案、Before／After 或新規則草稿。
- 影響範圍必須依呼叫關係，列出直接或間接委派根因所在 Skill 的所有 Skill；沒有呼叫者時必須明確寫「無」。
- 待確認事項必須包含驗收條件是否正確完整、是否同意根因，以及仍缺少的證據。

## Good Example

- 報告在影響範圍後直接請使用者確認驗收條件與根因，沒有提出解法。

情境：

- 影響範圍：沒有其他 Skill 委派 `class-diagram-planner`。
- 請確認：驗收條件是否正確、完整？是否同意 R1？E7「測試類別不出現在類別圖中」是推定的預期，是否需要？

## Bad Example

- 報告在根因確認前就提出修改方案，使用者的注意力被帶到解法。

情境：

- 影響範圍：未列出。
- 建議修改：在 Rule 2 新增 annotation 條列，並更新樣板範例。
