# Rule 1 - To-Be 必須從驗收條件推導

- To-Be 的 Phase、步驟與約束必須從驗收條件推導；優化模式另依已確認的根因推導。
- To-Be 的每個 Phase 與步驟必須追溯到至少一條通用驗收條件，或屬於使用者確認、驗證等必要流程。
- 推導必須以驗收條件為起點，先列出每個 To-Be 步驟的目的與追溯，再與 As-Is 對照；不得以 As-Is 的步驟為起點逐步修補。
- 與 As-Is 對照後，追溯結果相同的既有內容必須保留原文。

## Good Example

- 先從驗收條件推導 To-Be，再對照 As-Is，只在追溯結果不同處修改。

情境：

1. 依 E1 推導：產生類別圖的步驟需要載入要求變更標示的類別圖輸出規則。
2. 依 E2 推導：提案結構由類別圖提案樣板組保證，產生與驗證步驟只需引用樣板組。
3. 對照 As-Is：P1-11 與 P1-12 在引用樣板組之外，又重寫一次兩個頂層 Section 的結構，與 E2 的存放位置重複，因此修改；其餘步驟追溯結果相同，保留原文。

## Bad Example

- 以 As-Is 為起點，在出現症狀的步驟後面追加一句修補。

情境：

1. 讀取 As-Is 的 P1-11。
2. 在 P1-11 結尾追加「並標示每個類別是新增、修改或既有」。
3. 沒有檢查其他步驟與部位是否仍能追溯到驗收條件。

# Rule 2 - 既有元素必須舉證才能保留

- 優化模式必須為 As-Is 的 frontmatter、每個 Phase、步驟、完成條件、RuleFile、Rule、樣板組與腳本，標記保留、修改、刪除、合併或改換存放位置其中一種動作。
- 標記保留或修改的元素必須寫出追溯的驗收條件、根因或必要流程，並列出該元素表達的每一條約束編號。
- 無法追溯的元素必須標記刪除；元素表達的約束，其存放位置不是該元素時，表達該約束的內容視為無法追溯，必須刪除或修改。
- 「以前就有」、「可能有用」與「沒有壞處」不得作為保留理由。
- 依本 Rule 刪除無法追溯的元素時，不受根因位置限制。
- 新建模式沒有 As-Is，工程藍圖的刪除與保留段落必須寫「無（新建模式）」。

## Good Example

- 每個元素都寫出追溯與約束編號；元素表達的約束存放在別處時，標記刪除或修改。

| 元素 | 動作 | 追溯 |
| ---- | ---- | ---- |
| P1-11 中「第一個頂層 Section 放置 Mermaid 類別圖…」的描述 | 刪除 | 描述表達 C2，C2 的存放位置是類別圖提案樣板組，不是 P1-11 |
| `rules/類別圖輸出-格式規範.md` Rule 5 | 保留 | E5；C3 |
| Phase 2 使用者確認閘門 | 保留 | E3；C10 |
| P1-7 載入類別設計檢查清單後補充的「測試類別不列入設計」 | 修改 | E7；補充表達 C4，C4 的存放位置是 `rules/類別圖輸出-格式規範.md` Rule 2，不是 P1-7，因此刪除這段補充，其餘文字保留原文 |

## Bad Example

- 保留理由無法追溯到任何驗收條件或必要流程；步驟補充只寫追溯、沒有列出約束編號，看不出它表達的約束存放在別處。

| 元素 | 動作 | 追溯 |
| ---- | ---- | ---- |
| P1-11 中重複的結構描述 | 保留 | 以前就有，刪掉可能有風險 |
| P1-7 載入類別設計檢查清單後補充的「測試類別不列入設計」 | 保留 | E7：測試類別不出現在類別圖中 |

# Rule 3 - 修改必須落在根因位置並依缺陷類型選擇方向

- 本 Rule 只適用於優化模式。
- 修正根因的修改必須落在已確認根因所在的部位與位置；不得在症狀出現的步驟新增補償性的步驟或規則。
- 修改方向必須依下表對應根因的缺陷類型。

| 缺陷類型 | 修改方向                                                   |
| -------- | ---------------------------------------------------------- |
| 缺失     | 依約束分配檢查清單選擇存放位置，新增約束                   |
| 未載入   | 修正載入步驟的位置或適用條件，不新增內容                   |
| 不可檢查 | 將原有要求改寫為可檢查的描述，不另增要求                   |
| 衝突     | 刪除或改寫其中一方，只保留一個來源                         |
| 載體過弱 | 改換到強制力較高的存放位置，並刪除原本的載體               |
| 流程缺陷 | 重組 SOP 的 Phase 與步驟                                   |
| 交接缺陷 | 修正上游 Skill 的委派內容或委派規則                        |
| 觸發缺陷 | 修正相關 Skill 的 `description`                            |

## Good Example

- R1 位於類別圖輸出規則，缺陷類型為缺失，因此在同一個 RuleFile 中補上約束。

情境：

- 根因：R1，`rules/類別圖輸出-格式規範.md` Rule 2，缺失。
- 修改：在 Rule 2 加入每個類別必須以 annotation 標示變更類型的條列，並更新該 Rule 的正反範例。

## Bad Example

- 同一個根因被修在症狀出現的確認步驟，規則本身仍然缺少約束。

情境：

- 根因：R1，`rules/類別圖輸出-格式規範.md` Rule 2，缺失。
- 修改：在 Phase 2 展示提案前新增一個 `CHECK`，詢問使用者是否需要標示類別。

# Rule 4 - 變更必須先考慮刪改再考慮新增

- 本 Rule 只適用於優化模式；新建模式的所有元素都是新增。
- 處理每個根因或設計問題時，必須依序考慮刪除、改寫、改換存放位置與新增。
- 選擇新增時，必須說明刪除、改寫與改換存放位置為何無法處理該問題。

## Good Example

- 新增前逐一說明其他方式為何不適用，並同時刪除重複內容。

情境：

1. 刪除：沒有表達 E1 的既有內容可刪，不適用。
2. 改寫：既有 Rule 沒有任何與變更標示相關的描述可改寫，不適用。
3. 改換存放位置：E1 沒有既有的存放位置，不適用。
4. 新增：在既有 Rule 2 加入一個條列；同時刪除 P1-11、P1-12 與 P2-1 中重複的結構描述。

## Bad Example

- 直接新增步驟與 RuleFile，沒有考慮既有內容能否改寫或擴充。

情境：

1. 新增 `rules/類別狀態標示-格式規範.md`。
2. 在 Phase 1 新增一個 `CHECK` 步驟檢查標示。

# Rule 5 - 淨增減必須揭露並說明

- 工程藍圖必須列出 Phase、步驟、RuleFile、Rule、樣板組與腳本在 As-Is 與 To-Be 的數量及增減。
- 任一項目淨增加時，必須說明增加的理由，以及對應的驗收條件或根因。
- 優化模式只有新增、沒有任何刪除或改寫時，必須說明為何沒有可刪除或改寫的既有內容。

## Good Example

- 列出每個項目的數量與增減；數量都沒有增加，內容的增刪另有說明。

| 項目     | As-Is | To-Be | 增減 |
| -------- | ----- | ----- | ---- |
| Phase    | 3     | 3     | 0    |
| 步驟     | 18    | 18    | 0    |
| RuleFile | 2     | 2     | 0    |
| Rule     | 9     | 9     | 0    |
| 樣板組   | 1     | 1     | 0    |
| 腳本     | 1     | 1     | 0    |

- 內容增減：Rule 2 新增一個條列（R1）；刪除三個步驟中重複的結構描述。

## Bad Example

- 只列出新增項目，沒有 As-Is 數量與理由。

情境：

- 新增 1 個 RuleFile、1 條 Rule、1 個步驟。

# Rule 6 - 修改被其他 Skill 委派的 Skill 時必須涵蓋呼叫者

- 修改的 Skill 被其他 Skill 委派時，必須依呼叫關係列出所有直接呼叫者。
- 每個直接呼叫者必須至少有一個回歸情境。
- 修改改變了被委派 Skill 的輸入、輸出或確認方式時，呼叫者的委派步驟與委派規則必須在同一份工程藍圖中一併修改。

## Good Example

- 修改 `skill-form-sop` 的載入規則時，列出所有直接呼叫者並各自安排回歸情境。

| 直接呼叫者              | 回歸情境                                   |
| ----------------------- | ------------------------------------------ |
| `skill-derive-rule`     | S3：為單一步驟展開 RuleFile 後更新載入步驟 |
| `skill-derive-template` | S4：為單一步驟抽出樣板組後更新載入步驟     |
| `skill-derive-script`   | S5：為單一步驟抽出腳本後更新委派步驟       |
| `skill-engineering`     | S6：新建 Skill 時寫入胖 SOP                |

## Bad Example

- 同一個修改只驗證 `skill-form-sop` 本身，沒有檢查委派它的 Skill。

| 直接呼叫者 | 回歸情境 |
| ---------- | -------- |
| 未列出     | 無       |
