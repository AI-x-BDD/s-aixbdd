# Rule 1 - 小批次與技巧決策

- 規劃或審查變更時，必須先考慮切小，而不是先問「要開什麼 branch」。切小：把需求拆成多個能獨立整合的小變更。一張 Story／Ticket 不等於一個 branch 或一個 PR。
- 每個小變更應開短期 branch，目標是「這個小變更做完就 merge」，不是「整個 feature 做完才 merge」。
- 必須依下列 Decision Tree 判斷變更的整合方式；規劃時產生方案，審查時核對現有方案，不要求審查另做一份計畫。

```text
我要做一個變更
│
├─ 幾小時／一天內可完成？
│   └─ Yes → short-lived branch → CI + Review → merge main
│
└─ No → 能不能切更小？
    ├─ Yes → 切小 → 多個 PR，每個回到上一步判斷
    └─ No → 為什麼？
        ├─ 功能還不能曝光     → Feature Flag
        ├─ 大型程式重構       → Branch by Abstraction
        ├─ 舊系統／相容性遷移 → 新舊並存（Strangler）
        └─ 維護已發布版本     → Release Branch
```

- 未完成的工作必須以小批次、Feature Flag、抽象層、向後相容、CI、自動測試整合，不得靠長期 branch 藏起來。

## Good Example

同一 Story 拆成可整合的小步驟。

- 情境：會員搜尋需要多天。
- 方案：API client、搜尋輸入框、基本搜尋、分頁各自形成可整合 PR；若還不能曝光，使用 Rule 3 的技巧。

## Bad Example

同一 Story 被視為只能有一個 PR。

- 情境：會員搜尋需要多天。
- 方案：UI、API、權限、分頁全部完成才 merge 一個長期 feature branch。

# Rule 2 - 同步與 CI 整合

- 規劃或審查整合方案時，必須包含工作期間同步 main，merge 前 branch 要跟 main 保持最新。同步方法依已載入的 TBD 判準中團隊規則處理。
- 必須保留 CI 驗證次序：build → lint → unit test → 必要的 integration test；PR → review → CI green → merge。
- 說明 DORA 的 CI 建議時，必須保留每個 commit 都觸發 build 與自動測試，回饋在幾分鐘內的目標。
- merge 後的 branch 清理，應依已載入的 TBD 判準中強烈建議處理。

## Good Example

小 bug 也保持同步與驗證的次序。

- 情境：按鈕顏色錯誤，30 分鐘可完成。
- 方案：short-lived branch → fix；工作期間同步 main，merge 前更新 → build／lint／unit test／必要 integration test → PR／review → CI green → merge → 刪 branch。

## Bad Example

同一小 bug 省略整合驗證。

- 情境：按鈕顏色錯誤，30 分鐘可完成。
- 方案：「改動很小，branch 不必同步最新 main，CI 紅了也先 merge。」

# Rule 3 - 四種技巧的安全生命週期

- 使用或審查 Feature Flag 時，必須保留：程式每天 merge，flag 關閉，最後打開（Deploy ≠ Release）。功能上線後要刪 flag，官方警告不清理的 flag 會變成技術債。
- 使用或審查 Branch by Abstraction 時，必須保留：建立 abstraction → 舊實作接上 → 加入新實作 → 逐步切換 → 刪舊實作。每一步都 merge main。
- 使用或審查新舊並存時，必須保留：改 API 時先讓舊 API 與新 API 並存 → consumer 遷移 → 刪舊 API。不得讓 main 處在「API 改了、前端還沒跟上」的中間狀態。
- 使用或審查 Release Branch 時，必須保留：很晚才切，只負責該版本的穩定、bug fix、發布，不得承載新功能開發。Bug 先修在 main（fix on trunk first），驗證後再 cherry-pick 到 release branch；只在 release branch 修再回灌 main 是官方列出的錯誤模式。

## Good Example

各技巧的同一情境都有完整生命週期。

| 情境 | 完整方案 |
| ---- | -------- |
| 一週下注介面，週五開放 | flag 關閉時每天 merge，週五開啟，功能穩定後清理 flag |
| Axios → Fetch 或 Vuex → Pinia | abstraction、接舊、加新、逐步切換、刪舊，各步 merge |
| API 有舊 consumer | 先保留舊新 API，consumer 遷移後才移除舊 API |
| 1.5 hotfix，main 已開發 1.6 | main 先修並驗證，再 cherry-pick 到只維護版本的 release/1.5 |

## Bad Example

相同情境缺少生命週期或破壞次序。

| 情境 | 問題方案 |
| ---- | -------- |
| 一週下注介面，週五開放 | merge 後永遠保留 flag，不清理 |
| Axios → Fetch 或 Vuex → Pinia | 新實作未接上就刪舊，等待整週後一次 merge |
| API 有舊 consumer | consumer 尚未遷移就刪舊 API |
| 1.5 hotfix，main 已開發 1.6 | 只修 release/1.5 再回灌，並在該 branch 開發 1.6 功能 |

# Rule 4 - 規劃結果與六題自檢

- 產生規劃結果時，必須用下列格式給出；只做審查或判準說明時，不要求另產生 PR 計畫。

```text
PR 1：<變更>  — 使用技巧：<無／Feature Flag／Abstraction／新舊並存>
PR 2：...
每個 PR merge 後 main 為什麼仍可工作：<說明>
預估 branch 壽命（含等 review）：<時間>
```

- 規劃與 branch／PR 審查，必須逐項使用以下六題；workflow 審查涉及變更或分支時亦適用。未涉及的項目可以判不適用；未知資料不得當作通過。這是自檢，不強制回覆採六題報告格式。
  1. 能不能切到一天內可以 merge？
  2. 這個 PR 現在 merge，main 還能正常工作嗎？
  3. 未完成功能能不能用 Feature Flag 隱藏？
  4. 大改造能不能用 abstraction 讓新舊實作共存？
  5. CI 能不能快速告訴我這次改動有沒有破壞系統？
  6. 這個 branch 明天還會存在嗎？是的話，檢查是不是切得太大。
- 六題涉及的 branch 壽命、來源與分級，必須使用已載入的 TBD 判準；不得將自檢問題提升為隔夜禁令。

## Good Example

規劃有可核對的整合資訊，單純審查也使用六題。

```text
PR 1：加入 API client — 使用技巧：無
PR 2：加入搜尋輸入框 — 使用技巧：Feature Flag
每個 PR merge 後 main 為什麼仍可工作：PR 1 不更改既有行為；PR 2 的新入口由關閉的 flag 控制。
預估 branch 壽命（含等 review）：各半天至一天。
```

- 審查相同會員搜尋 branch：逐題核對切小、main 可工作、未曝光入口、是否涉及大改造、CI 回饋、明日是否仍存在；沒有大改造時第 4 題判不適用，不只檢查天數。

## Bad Example

同一規劃缺少整合說明，審查漏掉大部分自檢。

```text
開 feature/member-search，全部做好再 merge。
```

- 審查同一 branch：「只要存活不到兩天就通過。」沒有核對 main、曝光控制、abstraction 或 CI。
