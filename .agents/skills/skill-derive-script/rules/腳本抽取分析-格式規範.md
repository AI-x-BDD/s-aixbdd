# Rule 1 - 腳本職責必須有可驗證的邊界

- 分析指定步驟時，必須列出腳本接收的輸入、產生的輸出，以及可以檢查的完成條件。
- 列入腳本職責的工作必須能由明確輸入重複執行，且完成條件必須可檢查。

## Good Example

- 輸入、輸出與完成條件都可直接檢查。

情境：

1. 指定步驟是從 `records.csv` 建立索引。
2. 腳本讀取 `records.csv`，產生 `index.json`。
3. 完成條件是索引包含 CSV 中每筆有效紀錄的識別碼。

## Bad Example

- 同一個步驟只被描述為「整理資料」，無法判斷腳本何時完成。

情境：

1. 指定步驟是從 `records.csv` 建立索引。
2. 腳本職責被寫成「整理 CSV，產生適當結果」。
3. 沒有指定輸出檔案或可檢查的完成條件。

# Rule 2 - 副作用必須限於指定步驟

- 分析指定步驟時，必須列出腳本需要的檔案寫入、覆寫、刪除及網路操作；不存在的副作用必須明確記為無。
- 腳本規劃的副作用不得超出指定步驟已授權的工作範圍。

## Good Example

- 建立索引的步驟只規劃寫入索引檔案。

情境：

1. 指定步驟允許讀取 `records.csv` 並產生 `index.json`。
2. 規劃的副作用只有建立或覆寫 `index.json`；不刪除檔案，也不存取網路。

## Bad Example

- 同一個步驟額外規劃刪除來源檔案，超出原本的工作範圍。

情境：

1. 指定步驟允許讀取 `records.csv` 並產生 `index.json`。
2. 規劃的腳本在產生索引後刪除 `records.csv`。

# Rule 3 - 流程決策必須留在 SOP

- 使用者確認、需要 AI 判斷的決策，以及 Phase 轉移必須保留在目標 SOP。
- 腳本職責必須限定為指定步驟中已明確定義的資料處理或可重複操作。

## Good Example

- 腳本產生檢查報告，後續決策仍由 SOP 執行。

情境：

1. 腳本根據 `records.csv` 產生 `report.json`。
2. SOP 讀取報告並判斷是否請使用者確認後進入下一個 Phase。

## Bad Example

- 同一個腳本自行作出原本屬於 SOP 的決策。

情境：

1. 腳本根據 `records.csv` 產生 `report.json`。
2. 腳本自行決定是否視為使用者已確認，並直接執行下一個 Phase 的工作。
