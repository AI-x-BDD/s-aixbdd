# 根因報告：class-diagram-planner－類別變更標示

- 紀錄目錄：`specs/skill-engineering/02-class-diagram-planner-類別變更標示/`
- 問題證據：本次對話上下文（使用者訊息「這張圖看不出哪些類別是這次新增的、哪些只是改一下」）；產出檔 `specs/plan/03-order-refund/class-diagram-proposal.md`

## 1. 使用者回報的問題

使用 `class-diagram-planner` 為既有訂單系統規劃退款功能後，使用者無法從類別圖分辨哪些類別是這次新增、哪些是修改既有類別、哪些只是既有的參考類別，因此難以評估變更範圍。另外，使用者希望本次類別圖改用淺色主題。

## 2. 驗收條件

| 編號 | 驗收條件 | 來源 | 適用範圍 | 驗收情境 |
| ---- | -------- | ---- | -------- | -------- |
| E1 | 類別圖中每個類別都依本次變更的角色，以 annotation 標示 `<<new>>`（新增）、`<<modified>>`（修改）或 `<<existing>>`（未修改的既有類別）其中一種 | 本次 | 通用 | S1 |
| E2 | 提案檔依序包含「類別圖」與「設計說明與實作順序」兩個頂層 Section | 既有 | 通用 | S1、S2 |
| E3 | 使用者明確確認提案前，不修改任何程式碼 | 既有 | 通用 | S2 |
| E4 | 本次類別圖改用淺色主題 | 本次 | 個案 | 不適用，只調整本次產出 |
| E5 | 類別圖、設計說明與實作順序互相對應 | 既有 | 通用 | S1、S2 |
| E6 | 使用者確認後，程式碼依已確認的類別圖與實作順序實作 | 既有 | 通用 | S1 |
| E7 | 測試類別不出現在類別圖中 | 推定 | 通用 | S1 |

## 3. 落差

| 驗收條件 | 預期 | 實際 | 證據 |
| -------- | ---- | ---- | ---- |
| E1 | `RefundService` 為 `<<new>>`，`OrderService` 為 `<<modified>>`，`PaymentGateway` 為 `<<existing>>` | 三個類別都沒有標示 | 觀察：產出檔第 3–15 行的 Mermaid 區塊 |
| E4 | 淺色主題 | 預設主題 | 觀察：產出檔沒有主題設定 |

## 5. 根因

| 編號 | 位置 | 缺陷類型 | 說明與證據 | 反事實檢驗 |
| ---- | ---- | -------- | ---------- | ---------- |
| R1 | `class-diagram-planner`／`rules/類別圖輸出-格式規範.md`／Rule 2 | 缺失 | 觀察：Rule 2 要求新增、修改與相關的既有類別都要出現在圖中，但沒有要求標示變更類型；樣板範例也沒有示範標示。推論：P1-7 已區分的資訊沒有任何部位要求寫入圖中（依據 P1-7 與 Rule 2 的觀察）。 | 假設 Rule 2 要求 annotation：P1-11 會寫出標示，P1-12 會逐條檢查，E1 可滿足；E2、E3、E5、E6 不受影響。 |
