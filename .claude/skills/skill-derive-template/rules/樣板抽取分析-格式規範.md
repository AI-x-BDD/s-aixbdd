# Rule 1 - 樣板必須對應指定步驟的檔案產出

- 分析指定步驟時，必須辨識該步驟的輸入、產出檔案、固定格式、可變內容與完成條件。
- 候選樣板必須規範指定步驟所產生檔案（包含之後才寫入檔案的草稿）的整體內容格式，且固定結構與可變內容都能追溯至該步驟。
- 若需求只約束執行行為或獨立的條列條件，必須保留為 SOP 或 RuleFile，不得為此建立樣板。

## Good Example

- 指定步驟產生 Mermaid 類別圖；樣板保留 `classDiagram` 結構，類別與方法名稱由步驟輸入填入。

情境：

1. 指定步驟：`WRITE` 產生 Mermaid 類別圖檔案。
2. 輸入：類別與方法設計。
3. 候選樣板：固定 `classDiagram` 結構，填入類別與方法名稱。

## Bad Example

- 指定步驟只要求檢查設計品質，沒有固定的產出檔案格式，卻規劃一份類別圖樣板。

情境：

1. 指定步驟：`CHECK` 類別責任是否單一。
2. 候選樣板：`templates/class-diagram.mmd`。

# Rule 2 - 一組樣板只處理一種產出格式

- 每組樣板必須對應一種產出檔案與格式，並確定骨架及範例的共同樣板名字與副檔名。
- 同一種產出格式已有適用樣板組時，必須規劃修改既有兩個檔案；格式或用途不同時，必須規劃新的樣板組。
- 指定步驟需要產生多種不同檔案時，必須為各種產出分別規劃樣板組。

## Good Example

- 既有 `class-diagram` 樣板組已用於 Mermaid 類別圖，因此新增方法欄位時規劃同步修改兩個 `.mmd` 檔案。

```text
templates/class-diagram.mmd
templates/class-diagram.example.mmd
```

## Bad Example

- 將 Mermaid 類別圖與 Markdown 設計說明混入同一組 `.mmd` 樣板，無法對應單一產出格式。

```text
templates/class-diagram.mmd：同時包含 Mermaid 圖與 Markdown 報告
templates/class-diagram.example.mmd：只包含 Mermaid 圖
```

# Rule 3 - 抽取設計必須涵蓋骨架與範例

- 提案必須指出骨架保留的固定結構、每個可替換欄位的意義，以及範例採用的具體值。
- 填位符號的寫法必須配合目標格式，並能讓執行步驟的 Agent 明確找出要替換的位置。
- 範例必須示範骨架填完後的完整檔案；若無法給出對應的範例，必須先補足樣板設計。

## Good Example

- 提案同時列出固定結構、兩個填位符號與範例值。

| 項目 | 設計 |
| --- | --- |
| 固定結構 | `classDiagram` 與類別宣告 |
| `{{CLASS_NAME}}` | 範例值 `Order` |
| `{{METHOD_NAME}}` | 範例值 `submit` |

## Bad Example

- 提案只有骨架檔名，未指定替換位置或範例內容，無法委派寫入一組完整樣板。

```text
新增 templates/class-diagram.mmd，內容之後再決定。
```

# Rule 4 - 載入位置必須位於第一個依賴步驟之前

- 必須找出第一個需要依據樣板組進行設計、寫入或檢查的 SOP 步驟。
- 規劃中的 `READ` 步驟必須與第一個依賴步驟位於同一 Phase，且兩者之間只能有其他載入參考檔的 `READ` 步驟。
- `READ` 步驟必須同時指明骨架及範例兩個相對路徑，並為讀取結果指定可供後續步驟引用的名稱。

## Good Example

- `READ` 同時讀取兩個檔案，且緊接第一個依賴樣板的 `WRITE` 步驟。

```markdown
1. `READ` 產生類別圖時，讀取 `templates/class-diagram.mmd` 與 `templates/class-diagram.example.mmd`，建立類別圖樣板組。
2. `WRITE` 依已載入的類別圖樣板組產生類別圖。
```

## Bad Example

- 只讀取骨架；執行步驟的 Agent 不會讀到範例。

```markdown
1. `READ` 產生類別圖時，讀取 `templates/class-diagram.mmd`。
2. `WRITE` 產生類別圖。
```
