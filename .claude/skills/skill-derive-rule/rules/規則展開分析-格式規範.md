# Rule 1 - 候選規則必須可追溯至指定步驟

- 分析指定步驟時，必須辨識該步驟的輸入、可觀察的輸出或行為，以及完成條件。
- 每條候選 Rule 必須對應至少一項已辨識的輸入、輸出、行為或完成條件。
- 不屬於指定步驟的要求不得加入候選 Rule。

## Good Example

- 分析只根據指定的錯誤訊息寫入步驟推導規則，且每條候選 Rule 都能對應該步驟的輸出或完成條件。

情境：

- 指定步驟：`WRITE` 根據驗證結果產生 API 錯誤訊息。
- 輸入：驗證失敗的欄位、輸入值與預期格式。
- 輸出：回傳給 API 使用者的錯誤訊息。
- 完成條件：錯誤訊息足以讓使用者定位並修正輸入。
- 候選 Rule：錯誤訊息必須指出失敗欄位。
- 候選 Rule：錯誤訊息必須描述預期格式。

## Bad Example

- 分析加入資料庫命名要求；該要求無法追溯至指定的錯誤訊息寫入步驟。

情境：

- 指定步驟：`WRITE` 根據驗證結果產生 API 錯誤訊息。
- 輸入：驗證失敗的欄位、輸入值與預期格式。
- 輸出：回傳給 API 使用者的錯誤訊息。
- 候選 Rule：資料庫 table 必須使用 snake_case。

# Rule 2 - 風險必須轉換成可觀察的限制

- 每項風險必須描述指定步驟可能產生的具體失敗情況。
- 每條候選 Rule 必須針對失敗情況指定可執行且可檢查的行為、格式或限制。
- 「清楚」、「完整」或「適當」等無法獨立檢查的期待不得直接成為候選 Rule。

## Good Example

- 風險指出可觀察的失敗訊息，候選 Rule 也提供可以直接檢查的內容要求。

情境：

- 風險：錯誤訊息只有 `Invalid input.`，使用者無法辨識失敗欄位。
- 候選 Rule：錯誤訊息必須包含失敗欄位名稱與收到的輸入值。

## Bad Example

- 風險與候選 Rule 都只使用主觀形容詞，無法判斷輸出是否符合要求。

情境：

- 風險：錯誤訊息不夠好。
- 候選 Rule：錯誤訊息必須清楚且完整。

# Rule 3 - 流程要求與執行規則必須分開

- 行動順序、Phase 轉移與使用者確認必須保留在 SOP。
- 執行指定步驟時持續適用的行為、格式或限制可以展開為候選 Rule。
- 會改變指定步驟目的或原有流程順序的要求不得列為候選 Rule；這類要求必須另行提出 SOP 修改。

## Good Example

- 錯誤訊息的內容限制展開為候選 Rule，使用者確認仍保留為 SOP 步驟。

情境：

- 候選 Rule：錯誤訊息必須指出失敗欄位與預期格式。
- SOP 步驟：`CHECK` 使用者是否確認錯誤訊息格式；未確認時停止執行。

## Bad Example

- 候選 Rule 混入使用者確認與 Phase 轉移，實際上改寫了流程。

情境：

- 候選 Rule：產生錯誤訊息前必須請使用者確認；要求修改時返回 Phase 1。

# Rule 4 - Rule 清單必須維持單一主題且最小完整

- 同一份候選 Rule 清單必須共同規範一個完整主題。
- 不屬於同一主題的候選 Rule 必須分開規劃。
- 每條候選 Rule 必須提供獨立的檢查價值；語意重複或不改變執行行為的候選 Rule 必須合併或移除。
- 已辨識且屬於該主題的每項風險必須由至少一條候選 Rule 處理。

## Good Example

- 候選 Rule 都屬於 API 錯誤訊息內容，分別處理已辨識的定位與修正風險。

情境：

- 風險：使用者無法定位失敗欄位。
- 風險：使用者不知道如何修正輸入。
- 候選 Rule：錯誤訊息必須指出失敗欄位。
- 候選 Rule：錯誤訊息必須描述預期格式或修正方式。

## Bad Example

- 清單混合錯誤訊息、資料庫命名與測試流程，且前兩條錯誤訊息 Rule 沒有獨立檢查價值。

情境：

- 候選 Rule：錯誤訊息必須清楚。
- 候選 Rule：錯誤訊息必須容易理解。
- 候選 Rule：資料庫 table 必須使用 snake_case。
- 候選 Rule：寫入程式碼後必須執行整合測試。
