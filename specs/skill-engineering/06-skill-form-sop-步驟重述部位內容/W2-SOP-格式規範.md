# Rule 1 - SOP 使用固定的標題結構

- 每個 `SKILL.md` 必須有唯一一個 `# SOP` section，描述 Skill 從接收任務到完成交付的主要流程。
- `# SOP` 必須由一個或多個 `## Phase N -- <phase title>` 組成，`N` 必須從 `1` 開始連續編號。
- 每個 Phase 必須對應一個有明確目的的工作階段，並以 `完成條件：` 開頭的段落結束。
- 每個 Phase 內的步驟必須使用從 `1` 開始連續編號的有序清單。

## Good Example

- 唯一的 `# SOP` 下有連續編號的 Phase，每個 Phase 都以完成條件結束。

```markdown
# SOP

## Phase 1 -- 理解與設計

1. `READ` 使用者需求與目標檔案。
2. `THINK` 確定需要修改的段落。

完成條件：已確定需要修改的段落。

## Phase 2 -- 寫入與驗證

1. `WRITE` 修改已確定的段落。
2. `CHECK` 修改結果符合使用者需求。

完成條件：修改已寫入並通過驗證。
```

## Bad Example

- Phase 編號跳號、標題格式不一致，且第一個 Phase 沒有完成條件。

```markdown
# SOP

## 第一步：理解

1. `READ` 使用者需求與目標檔案。

## Phase 3 - 寫入

1. `WRITE` 修改內容。
```

# Rule 2 - 步驟必須以受控動詞開頭

- 每個步驟必須以下表其中一個受控動詞開頭，並以反引號標示。
- 每個步驟必須只使用一個受控動詞，描述一個具體行為。
- 步驟需要交給 script、工具或其他 Skill 執行時，必須使用 `DELEGATE`，並指明被委派的對象。
- 委派其他 Skill 時，執行者必須載入該 Skill 並依其 SOP 執行；只有步驟明確要求時，才另開子代理執行。
- `CHECK` 步驟可以執行不改變任何狀態的讀取命令，以取得驗證所需的證據。

| 受控動詞   | 用途                               |
| ---------- | ---------------------------------- |
| `READ`     | 讀取檔案、規範、輸入或現況         |
| `THINK`    | 分析、判斷、拆解或設計             |
| `WRITE`    | 建立或修改內容，或向使用者展示內容 |
| `CHECK`    | 驗證內容是否符合規範，或檢查使用者回覆 |
| `DELEGATE` | 將工作交給 script、工具或其他 Skill |

## Good Example

- 每個步驟只有一個受控動詞，委派步驟指明執行的 Skill。

```markdown
1. `THINK` 確定錯誤訊息需要的欄位。
2. `DELEGATE` 使用 `skill-form-rule` 建立錯誤訊息的 RuleFile。
```

## Bad Example

- 第一個步驟沒有受控動詞，第二個步驟混合兩種行為，且委派步驟沒有指明對象。

```markdown
1. 想一下錯誤訊息需要什麼欄位。
2. `THINK` 確定欄位並寫入 RuleFile，交給其他工具處理。
```

# Rule 3 - 完成條件與驗證必須可檢查

- 每個 Phase 的完成條件必須描述可觀察的結果，使執行者能判斷該 Phase 是否已完成。
- 完成條件不得只寫「已完成」、「沒有問題」等無法獨立檢查的描述。
- SOP 必須在交付前包含至少一個 `CHECK` 步驟，驗證產出是否符合需求與已載入的規範。

## Good Example

- 完成條件指出可檢查的產出，交付前有逐條驗證的 `CHECK` 步驟。

```markdown
2. `CHECK` 逐條驗證完成檢查清單；未通過時修正後重新檢查。

完成條件：目標檔案已寫入，且完成檢查清單均已通過。
```

## Bad Example

- 完成條件無法判斷，且交付前沒有任何驗證步驟。

```markdown
1. `WRITE` 修改目標檔案。

完成條件：已完成。
```

# Rule 4 - SOP 只保留必要步驟與控制內容

- 每個 Phase 必須對完成任務有直接作用。
- 每個步驟必須產生後續步驟或完成條件會使用的結果。
- 步驟內文只能描述執行條件、讀取或委派的部位、要完成的決策或產物、停止或分支的位置，以及只屬於本步驟且沒有存放在任何部位的約束。
- 步驟讀取或委派的部位已規範的內容，不得在步驟內文重述。

## Good Example

### Example 1

- SOP 只保留載入規範、寫入與驗證所需的步驟。

```markdown
1. `READ` `rules/example-格式規範.md` 的所有 Rule，建立完成檢查清單。
2. `WRITE` 依已載入的完成檢查清單修改目標檔案。
3. `CHECK` 逐條驗證完成檢查清單。
```

### Example 2

- 載入錯誤訊息規則後，寫入步驟只引用檢查清單，判準只存在於 RuleFile。

```markdown
3. `READ` 產生錯誤訊息時，讀取 `rules/API-錯誤訊息-格式規範.md` 的所有 Rule，建立錯誤訊息檢查清單。
4. `WRITE` 依已載入的錯誤訊息檢查清單產生 API 錯誤訊息。
```

## Bad Example

### Example 1

- 寫入前重複整理同一份規則，沒有產生新的工作結果。

```markdown
1. `READ` `rules/example-格式規範.md` 的所有 Rule。
2. `THINK` 重新整理已讀取的所有規則。
3. `WRITE` 依規則修改目標檔案。
```

### Example 2

- 同一情境中，寫入步驟在載入規則後又重述 RuleFile 已規範的判準；日後修改判準時必須同步修改 RuleFile 與步驟。

```markdown
3. `READ` 產生錯誤訊息時，讀取 `rules/API-錯誤訊息-格式規範.md` 的所有 Rule，建立錯誤訊息檢查清單。
4. `WRITE` 依已載入的錯誤訊息檢查清單產生 API 錯誤訊息；訊息必須指出失敗欄位、收到的值與預期格式。
```

# Rule 5 - 讀取輸入必須明確

- `READ` 步驟必須明確指定要讀取的輸入。
- 只在特定條件下存在的輸入，必須在步驟中說明適用條件。
- 輸入名稱必須使用可辨識的名稱，不得使用「它」或「該檔案」等無法從同一步驟確定指涉對象的代名詞。

## Good Example

- 步驟分別指定必讀輸入，並標明只在修改情境存在的輸入。

```markdown
1. `READ` 使用者需求、目標 Skill 的 `SKILL.md`，以及修改既有 RuleFile 時的目標 RuleFile。
```

## Bad Example

- 「它」的指涉對象不明，新建 RuleFile 時也沒有可讀取的目標檔案。

```markdown
1. `READ` 使用者需求、目標 RuleFile 與擁有它的 `SKILL.md`。
```
